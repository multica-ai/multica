## docs/unofficial-api

Unofficial, reverse-engineered OpenAPI 3.1 documentation for the Multica `/api/*`
app API, built by reading the server source (handlers, middleware, router)
rather than any official spec. Baseline revision:
`ba30324e10dfc69fb0f0a6732dd3d0f0559e01fe` (tag `v0.6.0`, 2026-09-30) — see
`openapi/openapi.yaml`'s `info.description`.

This is the Stage 1 structural ticket (PPBM-2951) for parent PPBM-2950. It
defines the directory layout, merge/lint tooling, and shared components.
Domain-specific path/operation content is added by the 8 follow-up domain
tickets listed below.

### Directory layout

```
docs/unofficial-api/
  openapi/
    openapi.yaml            # info/servers/security/tags; paths+components are
                             # overwritten by the merge script (keep them {} /
                             # empty here, don't hand-edit them in this file)
    components/
      securitySchemes.yaml  # top-level keys merge into components.securitySchemes
      parameters.yaml       # top-level keys merge into components.parameters
      schemas.yaml          # top-level keys merge into components.schemas
    paths/
      issues-comments.yaml        # domain: issues/comments
      issue-resources.yaml        # domain: 이슈 보조 리소스
      agents.yaml                 # domain: agents 계열
      autopilots-chat-inbox.yaml  # domain: autopilots/chat/inbox
      workspaces.yaml             # domain: workspaces
      account.yaml                # domain: 계정 부속 리소스
      daemon.yaml                  # domain: daemon
      cloud-integrations.yaml     # domain: cloud/연동
  scripts/
    merge.mjs              # merges the above into dist/openapi.yaml
  package.json             # devDependencies for build/lint (see below)
  .spectral.yaml           # lint ruleset (extends spectral:oas)
  dist/                    # generated by `pnpm run build`; gitignored, not committed
```

### Adding a domain's operations (for the 8 follow-up tickets)

1. Edit your domain's file under `openapi/paths/<domain>.yaml`. Its top-level
   keys are path strings (e.g. `/api/issues/{issueId}`), each mapping directly
   to an OpenAPI PathItem Object — the same shape as the document's `paths`
   object, just split by file. Do **not** nest your content under a `paths:`
   key; the file's own top level *is* that content.
2. If your domain file would exceed roughly a few thousand lines, split it
   further into `openapi/paths/<domain>/*.yaml` (any nesting depth) — the
   merge script walks the whole `paths/` tree recursively and merges every
   `.yaml`/`.yml` file it finds the same way, regardless of nesting. A single
   combined document over 10k lines is not acceptable (see parent ticket); use
   this split before you get there.
3. Reference the shared components instead of repeating them:
   `$ref: '#/components/parameters/LimitParam'`,
   `$ref: '#/components/schemas/ErrorCode'`, `security: [{PersonalAccessToken: []}]`,
   etc. See `openapi/components/*.yaml` for everything already defined.
4. If your domain needs its own schemas, add
   `openapi/components/schemas/<domain>.yaml` (nested — the directory name
   `schemas` is what tells the merge script which `components.*` bucket it
   belongs to) rather than editing the shared `schemas.yaml`. The same applies
   to `parameters/`, `responses/`, etc. if ever needed.
5. Run `pnpm run lint` from this directory before committing; see "Build and
   lint" below. A duplicate path string or component key across files is a
   hard error from the merge script (not a lint warning), so conflicts are
   caught immediately.

### Build and lint

This folder is **not** a pnpm workspace member (`pnpm-workspace.yaml` only
covers `apps/*` and `packages/*`) — it is intentionally self-contained so the
unofficial docs tooling doesn't affect the product workspace's install graph.
Install and run from this directory:

```sh
cd docs/unofficial-api
pnpm install --ignore-workspace   # first time / after changing devDependencies
pnpm run build                    # writes dist/openapi.yaml
pnpm run lint                     # build, then spectral lint (fails on any error)
```

`npm install` reproducibly failed to extract packages into `node_modules` in
the environment this ticket was done in (resolved the full dependency graph
correctly but silently wrote nothing to disk, for every package tried —
not specific to one dependency); `pnpm install --ignore-workspace` worked
reliably, so that is what's documented and what CI should use. If a future
environment doesn't reproduce that npm failure, `npm install && npm run lint`
should still work from the scripts in `package.json`.

`pnpm-lock.yaml` is committed for reproducible installs; `node_modules/` and
`dist/` are covered by the repository's root `.gitignore` (bare `node_modules`
and `dist` entries) and are not committed.

### Security schemes

Five schemes are defined in `openapi/components/securitySchemes.yaml`, one
per token-prefix branch in `server/internal/middleware/auth.go` and
`server/internal/middleware/daemon_auth.go`: `PersonalAccessToken` (`mul_`),
`AgentTaskToken` (`mat_`), `CloudNodePAT` (`mcn_`), `BrowserSession` (cookie),
and `DaemonAuth` (`mdt_`, `/api/daemon/*` only). See that file's comments for
a flagged deviation from this ticket's own description of the `mcn_` scheme's
purpose — the handler source doesn't support the originating ticket's
"plugin install token" framing, documented there instead of silently guessed.
