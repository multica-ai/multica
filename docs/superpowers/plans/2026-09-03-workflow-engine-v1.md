# Workflow Engine V1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add an opt-in, server-owned ordered workflow engine that advances existing staged child issues deterministically and preserves legacy behavior when no workflow is active.

**Architecture:** Persist immutable workflow definition versions, issue-bound workflow runs, and append-only transitions. `WorkflowService` owns transactions and state-machine rules; existing handlers own HTTP, events, timeline messaging, and existing run dispatch after commit.

**Tech Stack:** Go 1.26.6, PostgreSQL 17, pgx v5, sqlc 1.31.1, Chi, existing Multica issue/status/task services.

**Spec:** `docs/superpowers/specs/2026-09-03-workflow-engine-v1-design.md`

## Global Constraints

- V1 is an ordered linear pipeline only; no DAG, gates, retries, verifier, memory, router, budget, or child-template generation.
- Issues without an active workflow run must retain the existing stage-barrier path unchanged.
- Do not change daemon/runtime protocols, task queue schema, squads, autopilots, or frontend components.
- Workflow DB writes are workspace-scoped and transactionally serialized; network I/O/event publication never occurs inside workflow transactions.
- Promote executable child work to literal built-in `todo`; final workflow completion moves the parent to literal built-in `in_review`, never `done`.
- Definition versions and transition rows are immutable after insertion.
- Structured logs and transition payloads may contain IDs, stage/status metadata, counts, and reason codes only; never prompts, issue descriptions, credentials, or arbitrary agent output.
- At plan time the latest migration is `450`; use `451_workflow_engine_v1.{up,down}.sql`. If upstream claims 451 before implementation, rebase and renumber the pair before any code commit.
- Use the existing worktree-specific database generated by `make worktree-env`; never point destructive migration tests at a remote database.
- AMD2700X has unrelated upstream Windows baseline failures in `cmd/multica` path-format/stdout-pipe tests and several full-suite timeout flakes. Targeted workflow tests must be green; final reporting must distinguish those known failures from workflow regressions.

- [ ] **Step 3: Implement strict validation**

Use `json.Decoder` with `DisallowUnknownFields`, require EOF after one object, normalize only surrounding whitespace for comparisons, and return `ErrInvalidWorkflowDefinition` wrapping the concrete reason.

```go
var ErrInvalidWorkflowDefinition = errors.New("invalid workflow definition")

func ValidateWorkflowDefinition(raw json.RawMessage) (WorkflowDefinitionSpec, error) {
    var spec WorkflowDefinitionSpec
    dec := json.NewDecoder(bytes.NewReader(raw))
    dec.DisallowUnknownFields()
    if err := dec.Decode(&spec); err != nil { return spec, fmt.Errorf("%w: %v", ErrInvalidWorkflowDefinition, err) }
    if err := dec.Decode(&struct{}{}); !errors.Is(err, io.EOF) { return spec, fmt.Errorf("%w: trailing JSON", ErrInvalidWorkflowDefinition) }
    if spec.SchemaVersion != 1 || len(spec.Stages) < 1 || len(spec.Stages) > 32 { return spec, ErrInvalidWorkflowDefinition }
    seen := map[string]struct{}{}
    for i := range spec.Stages {
        spec.Stages[i].Key = strings.TrimSpace(spec.Stages[i].Key)
        spec.Stages[i].Name = strings.TrimSpace(spec.Stages[i].Name)
        if spec.Stages[i].Key == "" || spec.Stages[i].Name == "" { return spec, ErrInvalidWorkflowDefinition }
        if _, ok := seen[spec.Stages[i].Key]; ok { return spec, ErrInvalidWorkflowDefinition }
        seen[spec.Stages[i].Key] = struct{}{}
    }
    return spec, nil
}
```

Lock order for every reconcile call: `workflow_run FOR UPDATE` -> parent issue `FOR UPDATE` -> all child issues `FOR UPDATE`. Keep this order fixed to prevent service-level deadlocks.


For each scanned stage:

```text
no child rows                 -> blocked_materialization at that stage
all child rows effective terminal -> persist stage_satisfied; increment run revision; continue scan
any non-terminal effective non-backlog -> ErrWorkflowConflict; rollback
otherwise                     -> promote all effective-backlog children to literal todo; persist stage_advanced; stop
past final declared stage     -> if parent is not already effective in_review, move it to literal in_review; run -> completed_pending_review
```

For `blocked_materialization`, inspect `current_stage` itself: no rows -> no-op blocked; all terminal -> persist `stage_satisfied` and continue scanning; all non-terminal backlog -> promote and set `running`; any active non-backlog -> conflict.
