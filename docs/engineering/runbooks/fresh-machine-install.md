# Fresh machine install

This runbook takes a clean machine to a running Multica with the company knowledge base
(WeKnora), Hermes as an agent runtime, and the daemon. `make dev-full` does the repeatable
part, including the Hermes install and both configs. The model gateway and the accounts
are manual steps, and this runbook says where each one starts and how to prove it works.

Every value below is a placeholder. Real values belong only in `.env` or `.env.worktree`,
which git ignores, and in `~/.hermes/.env`. Do not paste them into tracked files or
shared notes.

## Prerequisites

| Tool | Version | Check |
|---|---|---|
| Node.js | 22 | `node --version` |
| pnpm | 10.28.2 | `pnpm --version` |
| Go | 1.26.9 | `go version` |
| Docker Engine with the Compose plugin | any current | `docker compose version` prints a version and `docker info` succeeds |
| openssl, curl, git | any | `command -v openssl curl git` |

The legacy `docker-compose` v1 binary is not supported. Install the Compose plugin from
[docs.docker.com/compose/install](https://docs.docker.com/compose/install/).

Also needed:

- Internet access on the first start. Docker pulls the pinned WeKnora images
  (`wechatopenai/weknora-*`, `v0.9.0`), `paradedb/paradedb`, `redis:7.0-alpine`, and
  `pgvector/pgvector:pg17` for Multica's own database.
- Free loopback ports: 3000 (web), 8080 (API), 5432 (Multica Postgres), 8085 and 8090
  (WeKnora UI and API). If another stack already uses 8085 or 8090, see
  [Troubleshooting](#troubleshooting).
- Room for the knowledge containers, which idle at roughly 650 MB of RAM together, plus
  an embedding model (see [Environment variables](#environment-variables)).
- Hermes is installed by `make dev-full` when it is missing. Its endpoint values come from
  your env file (see [Hermes](#hermes)).
- `curl` and `bash` for the Hermes installer, and internet access for its git checkout.

## Clone and run `make dev-full`

```bash
git clone <your fork or the upstream repository URL> multica
cd multica
make dev-full
```

`make dev-full` runs `scripts/dev-full.sh`, in this order:

1. **Prerequisites.** It checks for node, pnpm, go, docker, openssl and curl, and that
   `docker compose` works and the Docker daemon is running.
2. **Env file.** In the main checkout it uses `.env` and creates it from `.env.example` when
   missing. In a git worktree it uses `.env.worktree`, generated by
   `scripts/init-worktree-env.sh`, which gives the worktree its own database and ports.
3. **Secrets.** It fills in the knowledge secrets that are empty: `KNOWLEDGE_SYSTEM_AES_KEY`,
   `KNOWLEDGE_JWT_SECRET`, `MULTICA_KNOWLEDGE_SECRET_KEY`, `KNOWLEDGE_DB_PASSWORD` and
   `KNOWLEDGE_REDIS_PASSWORD`. Values that are already set are never changed, and no value
   is printed.
4. **Required values.** It checks the knowledge values only you can supply (see the table
   below). If any is empty, it lists them with what each is for, and stops. Nothing is
   started.
5. **WeKnora.** It starts the five knowledge services (`knowledge-postgres`,
   `knowledge-redis`, `knowledge-docreader`, `knowledge-app`, `knowledge-ui`) and waits for
   `http://localhost:8090/health`.
6. **Hermes.** If `hermes` is not on PATH, it runs the official installer pinned to commit
   `bf0203a7` (Hermes Agent v0.22.5) with `--non-interactive`. It then writes the custom
   endpoint into `~/.hermes/config.yaml` and `~/.hermes/.env`, backing up any existing file
   first, and runs `hermes -z` to confirm a reply. If the `HERMES_*` values are empty, it
   lists them and continues: Multica still runs, but Hermes is not configured.
7. **Multica.** It runs `make dev` (migrations, API, web). Once the API and the web app
   answer, it creates the local CLI profile if it is missing, and starts the daemon if the
   profile has a login. Otherwise it prints the login steps. Then it prints a summary.

The first run usually stops at step 4 on a fresh machine. That is expected: fill in the
listed values in `.env`, then run `make dev-full` again. Re-running is safe.

Ctrl-C stops Multica. The daemon and WeKnora keep running. The summary shows the commands
that stop them.

`make dev-full` does not create the Multica account, the first workspace, or the CLI login.
Those are browser steps, described below.

## Environment variables

Set these in `.env` (main checkout) or `.env.worktree` (worktree). "Set by make dev-full"
means the script fills the value when it is empty. "Generated" means the script creates a
random value when it is empty. The `HERMES_*` values are read only by `make dev-full`.

| Variable | Needed | What it is | Example (placeholder) |

| `FRONTEND_PORT` | optional | Multica web port | `3000` |

| `KNOWLEDGE_URL` | set by make dev-full | How Multica reaches WeKnora's API. Multica runs on this machine, so use the published port. The Docker name `http://knowledge-app:8080` works only inside Docker | `http://localhost:8090` |
| `KNOWLEDGE_UI_URL` | set by make dev-full | Target of the "Open in WeKnora" link | `http://localhost:8085` |
| `KNOWLEDGE_API_PORT` | optional | Host port for the WeKnora API. Change it if 8090 is taken | `8090` |

| `KNOWLEDGE_SERVICE_EMAIL` | required | The WeKnora login that Multica signs in as. Multica creates one WeKnora workspace per Multica workspace with it | `multica-service@example.com` |

| `HERMES_MODEL` | required for Hermes | Model that endpoint serves. Written as Hermes's default model | `<model name>` |

backup list is in `SELF_HOSTING.md`, Company Knowledge Base.

The server reads `KNOWLEDGE_*` once, when the API starts. After you change one, restart
`make dev`.

## The 9router gateway

9router is a separate OpenAI-compatible model gateway. This deployment uses it as its
model endpoint in two places: Hermes sends its chat requests to it, and WeKnora uses it for
summaries, Wiki pages and reranking.

- **It is not part of this repository.** `make dev-full` does not install, configure or
  start it. Run your own gateway, or get the base URL and a key from whoever runs it.
- **What you need:** the base URL of its OpenAI-compatible API (usually ending in `/v1`), a
  key, and the name of a model it serves.
- **Where each value goes:** the URL, key and vision model for WeKnora go in the Multica env
  file (`KNOWLEDGE_LLM_BASE_URL`, `KNOWLEDGE_LLM_API_KEY`, `KNOWLEDGE_LLM_MODEL`,
  `KNOWLEDGE_VISION_MODEL`). For Hermes, the `HERMES_*` values go in the same file and
  `make dev-full` writes them to `~/.hermes/` (see [Hermes](#hermes)). The two endpoints are
  configured independently, and may be the same gateway.
- **Reachability.** WeKnora runs in Docker and makes the calls, so `localhost` in the URL
  points at the container, not your machine. For a gateway on this host, use
  `host.docker.internal` with the gateway's port. A literal `172.17.0.1` address (the Docker
  bridge on Linux) also works, because `.env.example` allow-lists it. WeKnora refuses direct
  IP addresses and private hosts unless the host is listed in `KNOWLEDGE_SSRF_WHITELIST_EXTRA`.

## Hermes

Hermes is an external agent CLI. `make dev-full` installs it when `hermes` is not on PATH,
with the official installer pinned to commit `bf0203a794a07aac3ff764972ab9087baa4e4f4e`
(Hermes Agent v0.22.5, the version this setup was verified with). By hand, the same install is:

```bash
curl -fsSL https://hermes-agent.nousresearch.com/install.sh | bash -s -- --commit bf0203a794a07aac3ff764972ab9087baa4e4f4e --non-interactive
command -v hermes && hermes --version   # the first start can take 30 to 40 seconds
```

The installer puts `hermes` in `~/.local/bin`. Open a new shell if it is not found.

### Configure the endpoint

Set the three `HERMES_*` values in the env file (see [Environment variables](#environment-variables)).
`make dev-full` then writes the custom endpoint into Hermes's own files:

`~/.hermes/config.yaml`, changed with `hermes config set`, so the other settings stay:

```yaml
model:
  provider: custom
  base_url: <HERMES_BASE_URL>
  default: <HERMES_MODEL>
  api_key: ${HERMES_CUSTOM_10_70_39_196_20128_API_KEY}   # the name depends on the host and port
```

`~/.hermes/.env`, mode 600, holds the key under the same name:

```bash
HERMES_CUSTOM_10_70_39_196_20128_API_KEY=<HERMES_API_KEY>
```

Hermes derives the name from the endpoint's host and port (`hermes_cli/config.py`,
`custom_endpoint_key_env`): `HERMES_CUSTOM_` plus the host and port in upper case, with every
other character replaced by `_`. `config.yaml` only references the variable, so the key is
never in it. An existing `config.yaml` and `.env` are copied to `*.bak-<timestamp>` first.

`make dev-full` then runs `hermes -z "Reply with the word ok."` and prints the reply. To check
it by hand:

```bash
hermes -z "Reply with the word ok."
```

The first one-shot starts Hermes's background gateway, which can take a minute on a cold
start, so `make dev-full` retries up to three times. The gateway reads `~/.hermes/.env` for
the key. The client can print `Config ref '${HERMES_CUSTOM_...}' ... is not set` before that;
the reply still comes back, and it shows the key was resolved.

Multica finds Hermes on PATH when the daemon starts. `MULTICA_HERMES_PATH` in the Multica env
file overrides the location if you need one.

## Multica daemon

The daemon runs the agents on this machine and registers the runtimes, Hermes included,
with Multica. The `make daemon` target uses the `local` profile, so the login must use the
same profile.

`make dev-full` points the local profile at this stack on every run, and starts the daemon once
the profile has a login. Until then it prints the steps. By hand:

```bash
make cli ARGS="--profile local config set server_url http://localhost:8080"   # dev-full runs these two
make cli ARGS="--profile local config set app_url http://localhost:3000"
make cli ARGS="--profile local login"             # opens the browser to sign in
make daemon                                       # starts or restarts the local profile's daemon
make cli ARGS="--profile local daemon status"     # confirms it is running
```

Run the login once, after the account and the first workspace exist, because the login
registers the workspaces it can see. `make daemon` is safe to run again. Stop it with
`make cli ARGS="--profile local daemon stop"`.

## First run in the UI

`make dev-full` registers the WeKnora service user once, from `KNOWLEDGE_SERVICE_EMAIL` and
`KNOWLEDGE_SERVICE_PASSWORD`. Multica signs in as this user to create one WeKnora workspace for
each Multica workspace. The username is `multica-service`. A run that finds the user already
there leaves it alone.

Then, in the web app at `http://localhost:3000`:

1. Create the account, then the first workspace.
2. Settings > Runtimes: Hermes shows as online once the daemon is running. If it does not,
   see [Troubleshooting](#troubleshooting).
3. Knowledge: an owner or admin selects **Enable knowledge**. Wait for the state to show
   **Ready**.
4. Knowledge > Setup > Models: select **Test models**. Each configured model shows
   Working or Failed, with the reason.
5. Office: select **Set up your company**, then **Build your company**. Choose the squads
   and the runtime, leave the company paused, and select **Build company**. The starter
   company creates six floors: Executive, Research, Product, Build, Launch and Governance.
6. Office: open **Brief**. It shows the day's brief, or "No brief today" until the
   Secretary writes one.

**The service user is a WeKnora system administrator.** WeKnora creates owner logins only
for a system administrator. `docker-compose.selfhost.yml` passes `KNOWLEDGE_SERVICE_EMAIL`
to `knowledge-app` as `WEKNORA_BOOTSTRAP_SYSTEM_ADMIN_EMAIL`. WeKnora promotes that user only
when `knowledge-app` starts, and only if the user already exists. So `make dev-full` restarts
`knowledge-app` once after it creates the service user. If you register the user by hand, restart
`knowledge-app` after you do.

## Verification checklist

Run each check. A step passes only when its "Passes when" column holds.

| # | Check | How to prove it | Passes when |
|---|---|---|---|
| 1 | Multica API | `curl -fsS http://localhost:8080/health` | exit 0 |
| 2 | Web app | open `http://localhost:3000` | sign-in page loads |
| 3 | WeKnora API | `curl -fsS http://localhost:8090/health` | exit 0. This is the route the `knowledge-app` healthcheck uses |
| 4 | WeKnora UI | open `http://localhost:8085` | WeKnora login page loads |
| 5 | Daemon | `make cli ARGS="--profile local daemon status"` | reports running |
| 6 | Hermes registered | Settings > Runtimes, or `make cli ARGS="--profile local runtime list"` | a Hermes runtime is listed as online |
| 6a | Hermes replies | `hermes -z "Reply with the word ok."` | prints a reply (`make dev-full` runs this check and prints the reply) |
| 7 | Knowledge enabled | Knowledge page, or `make cli ARGS="knowledge health"` | state **Ready**; the command returns without error |
| 8 | Upload a document | Knowledge > Library > **Add a file**, then publish the draft. CLI: `make cli ARGS="knowledge add --kb company --title 'Smoke test' --text 'Fresh machine check.'"`, then `make cli ARGS="knowledge publish <id>"` | the document shows as published in the library |
| 9 | Search | `make cli ARGS="knowledge search 'fresh machine'"` | the document appears in the results |

## Troubleshooting

**`make dev-full` lists empty values and stops.** Expected on a fresh machine. Nothing was
started. Fill in the listed variables in the env file and run `make dev-full` again.

**Enabling knowledge returns 502 "refused to create another workspace".** WeKnora refused
another tenant: a quota error (HTTP 429 from WeKnora). WeKnora caps the workspaces one user
owns, at 10 by default. The service user owns one per Multica workspace, and a deleted
workspace's tenant is held for seven days, which still counts. The default in this repo is
`KNOWLEDGE_TENANT_MAX_OWNED_PER_USER=1000`. If your env file or an existing WeKnora stack
sets a lower value, raise it and recreate the API container:

```bash
JWT_SECRET=unused docker compose --env-file .env -f docker-compose.selfhost.yml --profile knowledge up -d knowledge-app
```

A WeKnora stack started from another compose project keeps its own settings. Change them
in that project.

**Enabling knowledge returns 502 "rejected Multica's service account".** The WeKnora login in
`KNOWLEDGE_SERVICE_EMAIL` and `KNOWLEDGE_SERVICE_PASSWORD` does not exist or has a different
password. `make dev-full` prints a warning when it cannot register the user; it does not
create the user when the email is taken with another password. The API log line
`enable knowledge failed` carries the underlying error.

**Enabling knowledge returns 503 "the knowledge service is offline".** WeKnora's health route
does not answer. Check `curl -fsS http://localhost:8090/health` and the logs of
`knowledge-app`.

**A model fails with "direct IP address access is not allowed", or a private host is
refused.** WeKnora's SSRF guard. Add the host to `KNOWLEDGE_SSRF_WHITELIST_EXTRA`, as a
comma-separated list. The list replaces WeKnora's default, so keep `host.docker.internal`
and `172.17.0.1`
in it when a gateway runs on the host. Then recreate `knowledge-app` as shown above.

**`make dev-full` fails with "port is already allocated" on 8085 or 8090.** Another stack
holds the port. Change `KNOWLEDGE_API_PORT` or `KNOWLEDGE_UI_PORT`, and update
`KNOWLEDGE_URL` or `KNOWLEDGE_UI_URL` to match. `make dev-full` never stops containers it
did not start.

**`make dev-full` refuses `KNOWLEDGE_URL=http://knowledge-app:8080`.** That name resolves only
inside Docker. Use `http://localhost:8090`, or your `KNOWLEDGE_API_PORT`.

**WeKnora does not answer after six minutes.** Check the container status and logs:

```bash
JWT_SECRET=unused docker compose --env-file .env -f docker-compose.selfhost.yml --profile knowledge ps -a
JWT_SECRET=unused docker compose --env-file .env -f docker-compose.selfhost.yml --profile knowledge logs --tail 100 knowledge-app
```

`JWT_SECRET` is only there so compose can parse the file. The knowledge services do not use
it. On a worktree, use `.env.worktree` in place of `.env`.

**`knowledge-app` cannot connect to its database after you change `KNOWLEDGE_DB_PASSWORD`.**
Postgres keeps the password it was created with. Restore the old value. Changing it means
resetting the `knowledge-postgres-data` volume, which deletes WeKnora's data.

**Hermes is not registered, or the daemon log shows "version detection failed: signal:
killed".** The daemon bounds each `--version` probe at 60 seconds. Hermes is a Python CLI
and its first start can take 30 to 40 seconds of CPU, so a cold start can hit the bound.
Run `time hermes --version` once, then run `make daemon`. If it still times out, check the
Hermes install.

**Hermes replies "No LLM provider configured".** Hermes did not find the provider. Check that
`~/.hermes/config.yaml` has `model.provider: custom` and the `base_url` from `HERMES_BASE_URL`,
and that `~/.hermes/.env` defines the variable that `model.api_key` references, for example
`HERMES_CUSTOM_10_70_39_196_20128_API_KEY`. Run `make dev-full` again to rewrite both. `hermes
model` lists what Hermes sees.

**Setup > Models shows Failed for a chat or embedding model.** The endpoint is unreachable
from the WeKnora container (use `host.docker.internal`, not `localhost`), the model name
is not served by the endpoint, or the key is wrong. The failure text names the cause.

**Summaries or Wiki are missing.** The chat variables were unset when the API started. Set
`KNOWLEDGE_LLM_BASE_URL`, `KNOWLEDGE_LLM_API_KEY` and `KNOWLEDGE_LLM_MODEL`, restart
`make dev`, then run Setup > Models > **Test models**.
