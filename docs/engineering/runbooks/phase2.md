# Phase 2 runbook: the boss's machine

These steps cannot run in CI. They need Hermes, a real Telegram bot and chat, and
the machine the boss works on. Spec 2.10 and plan 9.14 are the reference. Each
step lists its expected result. No step has been run yet, so every row starts as
**not verified**. The boss signs off each one by writing the date and the observed
result in the Sign-off column, or by recording why it could not be done.

## 1. Hermes through the daemon (WS0.2)

Prerequisite: Hermes is installed, and a model provider is configured in Hermes
(`hermes model`). Only the boss can supply the provider.

| # | Step | Expected result | Sign-off |
|---|---|---|---|
| 1.1 | Start the Multica daemon on the machine. Run `multica daemon status`. | The output lists a `hermes` runtime with status online. | not verified |
| 1.2 | Start a trivial agent run on the Hermes runtime (for example, ask for a one-line reply). | The run completes; the task shows completed, and the reply is in the issue or task log. | not verified |

## 2. Daily brief generated by the Secretary

| # | Step | Expected result | Sign-off |

## 3. Telegram: link a chat, push, buttons

Prerequisite: a Telegram bot created with BotFather, its token entered in the chat
app settings, and the boss's chat with the bot started.

| # | Step | Expected result | Sign-off |
|---|---|---|---|
| 3.1 | Link the Telegram chat to the boss's account from the chat app settings. | The binding appears in the brief push panel as the boss's chat, labelled with the bot or account name. | not verified |
| 3.2 | Turn on brief push for the chat and pick it in the panel. | The preference saves; the panel shows the chat as the destination. | not verified |
| 3.3 | Generate a brief (step 2.2). | The brief reaches the Telegram chat within one minute, with an Open the brief link, and decision rows with Approve, Reject, Snooze and Revise. | not verified |
| 3.4 | Press Approve on one decision in the chat. | The bot replies that the decision is approved. The proposal shows approved in the app. | not verified |
| 3.5 | Press Revise on a decision in the chat. | A link opens the app on that decision. Nothing changes until the boss acts there. | not verified |
| 3.6 | Press Open the brief. | The Office opens on that brief. | not verified |

## 4. Catch-up with the machine asleep at 08:00

| # | Step | Expected result | Sign-off |
|---|---|---|---|
| 4.1 | Put the machine to sleep before 08:00 with the daemon stopped, and wake it after 08:00 but before 10:00. | No brief is generated while the machine sleeps. | not verified |
| 4.2 | Let the machine wake and the daemon reconnect (`multica daemon status` shows the runtime online). | The hourly catch-up job runs the daily autopilot once with source catchup, at the 10:00 pass. A brief exists for the day by 10:00 local. | not verified |
| 4.3 | Check the workspace setting that turns catch-up off, then check the brief card. | With catch-up off, no catch-up brief is made. The card still offers Generate now. | not verified |

## 5. Secretary inquiries and the feedback loop

| # | Step | Expected result | Sign-off |
|---|---|---|---|
| 5.1 | Let the Secretary ask a squad a question with `multica brief ask`. Repeat until the daily limit. | Three inquiries are accepted in the UTC day; the fourth is refused with a limit message. | not verified |

| 5.3 | Rate a brief Not useful, tag too long, and add a note. Run the Secretary again. | The Secretary runs `multica brief feedback --recent 14d --json` first, and the next brief is shorter. | not verified |
