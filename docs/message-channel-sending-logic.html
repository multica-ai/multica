Multica 多渠道消息发送逻辑调研

SHAR-153 · 调研员 · 检索日期 2026-10-19 · 结论以代码为准，附 file:line 引用

1. 摘要

  • 消息渠道发送分两条互不相交的寻址链路：任务通知（inbox）走 EventInboxNew → WeCom 智能机器人推送；智能体回复走 EventChatDone → 回到提问时绑定的 bot（channel_task_delivery 行）。
  • 多绑定（同成员同渠道类型多个 bot）下，通知由 FindNotificationBindingForMember 选「显式通知目标」或「最旧绑定」；回复始终锚定提问 bot，与通知目标无关。
  • 只有 WeCom 订阅了 EventInboxNew，会把通知推进 bot；Slack/Lark/DingTalk/Telegram 不订阅该事件，仅回写回复、不发 bot 通知（成员侧只剩应用内 inbox）。
  • SHAR-146 修复的「新 bot 静默劫持全部通知」根因：旧 FindChannelBindingForMember 用 bound_at DESC（最新胜）。其函数当前已无出站调用方，被 FindNotificationBindingForMember 取代。
调研基线提示：本文结论基于分支 task/shar-146-notification-target-bot（含 SHAR-146 改动）。SHAR-146 已于 2026-10-19 合并 origin/main（快进，HEAD d9a036fec）；本文基线即当前 main。

3. 发送策略（按类别）

3.1 任务通知（WeCom inbox → 智能机器人）

  • 寻址：wecom/outbound.go:822 调 FindNotificationBindingForMember（channel.sql:567），按 workspace_id + multica_user_id + channel_type='wecom' 过滤，ci.status='active'。仅成员收件人（recipient_type='member'，outbound.go:796），agent 不收 bot 通知。
  • 时机：notification_listeners 在事件总线同步分发（HTTP 请求内）创建 inbox item 并发布 EventInboxNew；WeCom handleInboxNew（outbound.go:786）订阅后立即尝试 bot push。
  • 失败处理 / 重试：无绑定 / 无 socket / 发送失败 → 函数返回 false，静默 no-op，成员仍从应用内 inbox 收到（outbound.go:832,884,890）。无重试；多副本下无持租约副本时仅记 warn（outbound.go:881）。
  • 去重：inbox item 已在业务层去重（actor/exclude/muted/delegated 过滤，notification_listeners.go:429-448）；每次 EventInboxNew 经 FindNotificationBindingForMember 仅命中单绑定，bot push 不重复。

3.2 智能体回复（各渠道，回写提问 bot）

  • 寻址：回复不查通知目标，而是读提问时写入的 channel_task_delivery 行（task.go:2107 CreateChannelTaskDeliveryFromSession），由 taskAddress → GetChannelTaskDelivery 解析聊天（wecom/outbound.go:502-536）。即「在谁的 bot 里问，答回谁的 bot」。
  • 时机：chat:done 事件（WeCom outbound.go:203；各渠道各自订阅）。
  • 失败处理 / 重试：WeCom 经 relay 转发到持 WS 租约的副本（outbound.go:624）；无 live 连接则 dropped/warn，不缓冲（outbound.go:649）。Slack/Lark/DingTalk/Telegram 为无状态 HTTP，任意副本可发。
  • 去重：每条回复由唯一 task_id + delivery row 锚定到单一 bot，天然不会跨 bot 重复。

4. 多绑定场景（核心）

4.1 同渠道类型绑定多个 bot（例：WeCom bot A=旧，bot B=新）

  • 通知寻址（channel.sql:588）：ORDER BY is_notification_target DESC, bound_at ASC →
    1. 若该成员对某绑定显式设了通知目标（is_notification_target=true），优先选它；
    2. 否则选 bound_at 最小者（最旧绑定 = bot A）。
  • 效果：新绑定的 bot B 不再静默继承通知流（这正是 SHAR-146 修复的劫持，根因见 migrations/573_*.up.sql:5-8）。
  • 显式目标设置：channel_binding_notification.go:135 SetWecomBindingNotificationTarget，radio 语义（事务内先 clear 再 set，:207-234），由 partial unique index（573_*.up.sql:30，(workspace_id, multica_user_id, channel_type) WHERE is_notification_target）保证每 (成员, 渠道类型) 至多一个目标。
  • 回复不受影响：仍走提问 bot 的 delivery row，与是否设通知目标无关。

4.2 跨渠道多绑定（WeCom + DingTalk + Lark + Slack）

  • 通知 bot push 仅 WeCom 订阅 EventInboxNew（全仓库唯一对外 bot 渠道订阅方 wecom/outbound.go:218；server/cmd/server/listeners.go:108 亦订阅该事件，但属应用内 WebSocket 实时广播，非渠道 bot 推送；Slack/Lark/DingTalk/Telegram 均无 bot 渠道订阅，已核实）。因此 DingTalk/Lark/Slack 成员不会收到 bot 推送通知，仅应用内 inbox。
  • 回复：各渠道在各自 bot 回答时回写各自 delivery row，互不影响、互不重复。
  • 通知目标 API 仅 WeCom 提供（channel_binding_notification.go），其余渠道无对应设置入口，也不参与 FindNotificationBindingForMember。

4.3 账号复用链路（FindReusableChannelUserBinding，Slack-only）

  • 用途：入站身份解析。Slack 用户在未绑定的 installation 发消息，但同一 (workspace, Slack team) 已绑定另一 installation → 复用该链接，免重新授权（slack/resolvers.go:266，channel.sql:591，bound_at DESC 最新胜）。
  • 与发送寻址的交互：复用只在「入站」产生/确认绑定，不改变出站通知寻址（出站用 FindNotificationBindingForMember / delivery row）。即：Slack 复用可在另一 installation 落一条绑定，但该绑定仅在「被提问」或「被设为通知目标」时才参与出站。注意 FindReusableChannelUserBinding 仅 Slack 调用（channel.sql:606 注释明确 Slack-only）。
  • 配对关系：FindChannelBindingForMember 的 bound_at DESC 与 FindReusableChannelUserBinding 一致（channel.sql:564,612），但 FindChannelBindingForMember 当前无出站调用方（被 SHAR-146 的 FindNotificationBindingForMember 取代，见 §6 风险 5）。

6. 已知问题与风险清单

#风险 / 问题代码事实影响
1 SHAR-146 未合并 main（已解决） 2026-10-19 已快进合并；线上部署已运行 b6402a06d 线上若未合并，通知仍是 FindChannelBindingForMember 的「最新 bot 胜」劫持逻辑
2 通知 bot push 仅 WeCom 支持 全仓库唯一 EventInboxNew 订阅方为 wecom/outbound.go:218 DingTalk/Lark/Slack/Telegram 成员收不到 bot 通知，仅应用内 inbox；跨渠道成员可能预期同步通知但未发生
3 WeCom 单副本约束下的丢失窗口 outbound.go:880-884 所有副本重连中时 push 被丢弃并 warn，无重试；无 Redis relay 时单副本约束生效（outbound.go:17-30） 成员仅剩应用内 inbox（降级而非丢失），但 bot 通知可能漏发
4 显式目标 installation 被撤销后静默降级 FindNotificationBindingForMember 过滤 ci.status='active'（channel.sql:587）；撤销后 ErrNoRows → 无 bot push（outbound.go:827） 用户所选目标失效时不会收到任何提示，通知仅落应用内 inbox
5 FindChannelBindingForMember 已成死代码 全仓库无出站调用方（仅 generated/channel.sql.go 定义）；其 bound_at DESC 仅与入站复用 FindReusableChannelUserBinding 配对 保留易误用；语义与通知寻址已分离，维护者需注意不要误用于出站
6 同 bound_at 并列竞态 channel.sql:588 ORDER BY ... bound_at ASC 在并列时由 DB 任意裁决 极小概率选错「最旧」绑定（仅当同毫秒绑定多条）
7 串台防护（已具备，非风险） WeCom 回复经 ChannelIngested 来源门禁（outbound.go:335）；Slack/Lark/DingTalk/Telegram 各自 outbound 同样做来源门禁（slack/outbound.go:121） web 端运行答案不会漏入渠道群聊；回复不会跨 bot 串台
8 重复风险（已规避，非风险） 每 EventInboxNew 仅一次 bot push（命中单绑定）；每回复锚定单 delivery row；relay 路径由持租约副本计数一次（outbound.go:638） 通知/回复均不会跨 bot 重复

7. 未核实 / 存疑

  • ghsnapshot / composio 是否经成员通知寻址：二者为 GitHub 快照刷新与 Composio 动作派发，均不订阅 EventInboxNew、不调用 FindNotificationBindingForMember，故不参与成员 bot 通知目标选择。但其对外消息的精确收件人模型未深入核实（ghsnapshot/refresh.go 仅按 installation+PR 刷新，composio/dispatch.go 派发动作），标注「未核实」。
  • 跨渠道「同时绑定」的通知期望：当前设计下多渠道成员在飞书/钉钉侧无 bot 通知。是否应有跨渠道聚合通知属产品决策，非本调研范围。
  • SHAR-145 根因：本调研聚焦 SHAR-146（migration 573 已述根因）。SHAR-145 的具体内容未单独核实，文中仅沿用 issue 描述。
