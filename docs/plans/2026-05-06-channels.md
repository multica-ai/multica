# Channels — multi-party chat as enriched issues

> **Status:** Backend landed (JEH-577). Frontend follow-ups: JEH-578 (sidebar), JEH-579 (channel view).
> **Parent issue:** [JEH-571](https://app.multica.io/workspace/issues/JEH-571)

## Goal

Let workspace members talk to each other and to agents in **DMs** (1:1) and **channels** (multi-party named threads). Agents become participants in the same way they are today on issues — `@`-mention to summon, post a reply via the existing comment pipeline.

## Decision

**Channels are issues with `kind IN ('channel', 'dm')`.** A new column on the existing `issue` table is the entire data-model change. Comments are the messages. Subscribers are the participants. Mentions, push, inbox, attachments, reactions — all reused from the issue plumbing.

### Why not a separate `channel`/`channel_message` table

Considered, rejected. The cost of a parallel messaging system (~1000 lines of mirror code for handlers, mention dispatch, notifications) outweighed the conceptual cost of a polymorphic `kind` column. Every future improvement to comments would have had to be done twice.

### Why not just reuse issues with empty fields

Considered, refined into the current design. Instead of stripping fields out for chat, channels populate every issue field meaningfully — title becomes the channel name, description the topic, status='todo' is "active" / 'cancelled' is "archived", subscribers are participants, project_id groups channels under projects, assignee is the channel owner.

| Issue field | Task usage | Channel/DM usage |
|---|---|---|
| `title` | "Fix login bug" | "growth-team", "DM with Sara" |
| `description` | requirements | channel topic |
| `kind` | `task` | `channel` or `dm` |
| `status` | todo→in_progress→done | active (`todo`) / archived (`cancelled`) |
| `priority` | urgency | (unused for now; reserved for star/pin) |
| `project_id` | grouping | grouping |
| `assignee` | who works on it | channel owner |
| `creator` | who filed | who started |
| `subscribers` | watchers | **participants** |
| `comments` | activity | **messages** |
| `is_private` | privacy gate | not used (subscriber gate replaces it) |

Empty for channels: `acceptance_criteria`, `due_date`, `parent_issue_id`. That's OK.

## Access model

Channels and DMs are **subscriber-gated** — your row in `issue_subscriber` is your access ticket. Workspace admins do **not** get implicit read access; a private DM stays private even from owners. This matches the privacy model `chat_session` already enforces and is the right default for chat.

The existing `canAccessIssue` and `audienceForIssue` helpers branch on `issue.Kind`. Tasks keep their project/privacy logic; channels use the subscriber check. This keeps the gate visible in the access layer rather than scattered across handlers.

## What survived intact, by reuse

- `comment` table → the messages
- `issue_subscriber` table (already polymorphic over member/agent) → participants
- `notification_listeners.go` (subscriber inbox + mention push) → unchanged; channels inherit Slack-style notification semantics: every comment hits subscribers' inbox, mentions also hit push
- `parseMentions` + agent dispatch on `@`-mention → unchanged; mentioning an agent in a channel comment enqueues an agent task on the channel issue, the agent posts back as a comment
- Attachments, reactions, threading via `comment.parent_id` → unchanged

The corollary: chat has feature parity with issue comments from day one.

## What's separate, by design

- `chat_session` (1:1 personal-assistant chat with persistent agent memory + daemon `work_dir`) is **left alone**. It's a different product — long-running personal context, not multi-party messaging. May be unified later if it earns its keep, not now.
- `/api/issues` and `/api/channels` are separate surfaces. The issue list (`ListIssues`, `ListOpenIssues`, `CountIssues`) filters `kind = 'task'` so channels never bleed into the task UI. The channel list (`ListChannelsForUser`) filters the inverse.

## API

```
POST   /api/channels                    # body: {kind, name?, description?, project_id?, member_ids[], agent_ids[]}
GET    /api/channels                    # mine (issues where I'm subscriber AND kind in channel,dm)
GET    /api/channels/{id}               # single channel; rejects non-participants with 403

# Messages, mentions, attachments, reactions go through existing endpoints:
GET    /api/issues/{id}/comments        # = list messages
POST   /api/issues/{id}/comments        # = send message (also triggers mentioned-agent dispatch)
POST   /api/issues/{id}/subscribe       # = add participant
POST   /api/issues/{id}/unsubscribe     # = remove participant
```

DM creation is **idempotent**: opening "Message Sara" twice returns the existing DM rather than creating duplicates. Backed by `GetDMByMembers` which finds the unique 2-member DM between a pair.

## Realtime

`channel:created`, `channel:updated`, `channel:deleted` event types fan out **only to participants** (not the workspace). Comment events on a channel issue use `audienceForIssue` which now returns the participant set when `issue.Kind` is `channel` or `dm`.

## Risk: agent behavior in channels

Issues that mention an agent today expect that agent to **execute and complete the issue** — set status to done, file PR, etc. In a channel, an agent should **just respond as a participant** and leave status alone.

Mitigation: not addressed in v1. Agent behavior in channels is whatever the existing dispatch produces. If agents start treating channels as tasks (changing status etc.), follow-up: tune the agent prompt to detect `kind != task` and behave conversationally. Not blocking ship.
