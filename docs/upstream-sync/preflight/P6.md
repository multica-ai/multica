# P6 — Lint rule for CEREBRO-PATCH markers

**Verdict:** PASS

**Hypothesis:** A lint rule + CI gate can enforce that diffs in upstream-zone files contain `CEREBRO-PATCH(<name>):` markers.

## What we found

- **ESLint setup:** 5 per-package flat configs (apps/web, apps/desktop, packages/ui/core/views). No root config, no shared custom rules.
- **Pre-commit infrastructure:** NONE. No `.husky/`, no `lint-staged`, no `pre-commit` field. Greenfield.
- **CI:** Single workflow `.github/workflows/ci.yml`, two jobs (frontend, backend), triggers on `pull_request` to `main`. Trivially extensible.
- **Existing scripts dir:** `scripts/` already holds bash convention (`check.sh`, `dev.sh`). Fits perfectly for `scripts/validate-cerebro-patches.sh`.

## Key insight: ESLint is the wrong tool

A lint rule alone CANNOT detect "is this file modified in this PR" — that requires git diff context. The right pattern is a **bash/node script invoked from CI**:

1. `BASE=$(git merge-base origin/main HEAD)`
2. `git diff --name-only "$BASE"...HEAD` → filter against upstream-zone globs (`packages/views/**`, `packages/core/**`, `server/**`, excluding `**/cerebro/**`).
3. For each matching file: `git diff "$BASE"...HEAD -- "$file"` → grep added lines (`^+`) for `CEREBRO-PATCH(`.
4. Check PR body / commit messages for `CEREBRO-ALLOW-NO-PATCH:` opt-out.
5. Exit non-zero with file list if any unmarked.

## Risks / gotchas

- **False positive — marker on line not introduced:** mitigated by parsing only added (`^+`) lines, not context lines.
- **CI cost:** negligible — `git diff` on this repo is sub-second.
- **Local dev vs CI:** no pre-commit infra today. Recommend CI-only at first; add husky later if signal warrants.
- **Go-side:** no separate Go vet check needed — same script handles `server/**` paths. Go vet is for compile-time concerns, not commit-content discipline.

## Phase 0 recommendations

- **Script:** `scripts/validate-cerebro-patches.sh` (~60 lines bash).
- **Glob source of truth:** `scripts/cerebro-zones.txt` (one glob per line). Plan + script + future CODEOWNERS reference the same list.
- **CI wiring:** third job in `ci.yml` with `fetch-depth: 0`, runs the script. Job-level (not step-level) so it shows as a distinct PR check.
- **ESLint scope:** nothing. Don't write a custom plugin — wrong abstraction.
