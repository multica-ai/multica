# Runtimes and repos source map

- `server/cmd/multica/cmd_runtime.go` registers `runtime list`, `usage`, `activity`, `update`, `delete`, and `migrate-agents`.
- `runtime list` reads `/api/runtimes` and prints `id`, `name`, `runtime_mode`, `provider`, `status`, and `last_seen_at`.
- `runtime update` posts to `/api/runtimes/{runtime-id}/update`; with `--wait` it polls update status. Initiation enforces runtime-owner or workspace-owner/admin access through `canEditRuntime`; status polling additionally permits that request's immutable initiator so an in-flight poll survives an admin-role change (`server/internal/handler/runtime_update.go` and `runtime.go`).
- `runtime delete` deletes `/api/runtimes/{runtime-id}`; with `--cascade`, it first reads the `runtime_has_active_agents` conflict payload and posts those ids to `/api/runtimes/{runtime-id}/unbind-agents-and-delete` (the older `/archive-agents-and-delete` path still routes to the same handler for installed clients). Both delete paths run `unbindRuntimeForDelete` in `server/internal/handler/runtime.go`: user agents are unbound (`runtime_id = NULL`, MUL-5559), their task history is detached so deleting the runtime cannot cascade it away, active tasks are cancelled, and only `kind='system'` agents are hard-deleted.
- `runtime migrate-agents` (`runRuntimeMigrateAgents`) posts `{agent_ids, expected_source_runtime_id?, dry_run}` to `/api/runtimes/{target-runtime-id}/migrate-agents`, handled by `MigrateAgentsToRuntime` in `server/internal/handler/agent_migrate.go` (MUL-5758). In one transaction it locks the involved runtime rows in id order, optionally re-derives the source runtime's active agent set, narrows it to the caller-visible subset via `visibleAgentIDSet` (`agent_access.go`, same predicate as ListAgents) and refuses with `runtime_migration_plan_changed` (409) when that subset drifted — the 409 echoes `migrationPlanAgent` (id + name) rather than `AgentResponse`, so the path carries no mcp_config / instructions, row-locks the requested agents through `ListAgentsByIDsForWorkspaceForUpdate` (workspace-scoped, `kind='user'`), re-binds them with `MigrateAgentsToRuntime` (clearing `model` / `thinking_level` / `service_tier`, or writing the request's optional uniform `model` / `thinking_level` / `service_tier` replacement, validated against the target provider via `IsKnownThinkingValue` / `IsKnownServiceTier` in `server/pkg/agent/thinking.go`; `planAgentMigration` treats agents already on the target as in-place updates, never `already_on_target` skips), and moves their unclaimed work with `RepointUnclaimedTasksToRuntime`.
- The migration request's `model` is stored without catalog validation (custom model ids are a supported input everywhere model is written — see the create/update paths in `server/internal/handler/agent.go`); only `thinking_level` / `service_tier` are checked, against the target provider's enums. The CLI flag set for `migrate-agents` (`server/cmd/multica/cmd_runtime.go`) has no `--model`; model changes from the CLI go through `multica agent update --model`.
- Both bulk endpoints report an agent the caller cannot SEE as `not_found` with no name (`planAgentMigration` / `MergeAgentsEnv` intersect with `visibleAgentIDSet`), keeping a hidden agent indistinguishable from one that does not exist; `forbidden` is reserved for agents the caller can see but not manage.
- `expected_source_runtime_id` comes from the request body, so it is locked and read through workspace-scoped queries (`LockAgentRuntimeForWorkspace`, `ListActiveAgentsByRuntimeForWorkspaceForUpdate`) against the TARGET runtime's workspace. An id that is unknown or belongs to another workspace gets the same `400 invalid expected_source_runtime_id`, so the stale-plan 409 can never disclose another workspace's agents.
- Only `queued` and `deferred` tasks are re-pointed. `dispatched` / `running` / `waiting_local_directory` rows are already owned by the old runtime's daemon, so they stay and are counted as `tasks_staying_active` by `CountAgentTasksByMigrationGroup`. That query also backs `dry_run`, which the UI confirmation dialog reads because the presence projection (`packages/core/agents/derive-presence.ts`) folds `dispatched` into "queued" and omits `deferred`.
- The move matters because `ListQueuedClaimCandidatesByRuntime` (`server/pkg/db/queries/agent.sql`) selects claim candidates by `agent_task_queue.runtime_id`, and `TaskService.ClaimTask` only accepts a row whose runtime matches the claiming runtime — so a task queued before a plain `agent update --runtime-id` rebind stays visible only to the runtime the agent left.
- After commit the handler publishes one `agent:status` per migrated agent and calls `TaskService.NotifyRuntimeMayHaveWork` (`server/internal/service/task.go`), the exported bump-then-wake primitive, so the target runtime does not sit on a stale empty-claim verdict while holding inherited work.
- `server/cmd/multica/cmd_repo.go` registers `repo checkout <url> [--ref]`.
- `repo checkout` requires `MULTICA_DAEMON_PORT`, sends `workspace_id`, `workdir`, `ref`, `agent_name`, `task_id`, and the daemon-managed optional `checkout_mode` to local daemon `/repo/checkout`, then prints the checked-out path.
- `server/internal/daemon/health.go` resolves the checkout ref: request `ref` wins; otherwise it asks `server/internal/daemon/daemon.go` for the current task's project repo default ref. It forwards the validated isolated-checkout mode into `repocache.WorktreeParams`.
- `server/internal/daemon/daemon.go` injects `MULTICA_REPO_CHECKOUT_MODE=isolated` for Linux and Windows Codex tasks. Linux keeps the isolated checkout it already had; Windows Codex now uses the same layout to cover its native sandbox, where a linked worktree's external gitdir stays read-only and `git add` / `git commit` fail from inside the checkout (multica-ai/multica#6449). That failure only bites a Windows user who opted into `windows.sandbox` — `server/internal/daemon/execenv/codex_sandbox.go` defaults both Linux and Windows Codex to `danger-full-access` — but the checkout layout is chosen per platform, not per sandbox policy, so it does not depend on a task's resolved policy. `server/internal/daemon/repocache/cache.go` implements the mode as a local clone with task-local Git metadata and the real repository as `origin`; on Windows it clones with `--no-hardlinks` so the checkout's objects are private copies rather than NTFS links that share one file and security descriptor with the cache. Other runtimes keep the linked-worktree path.
- When the bare cache is a partial clone, that isolated checkout must have `remote.origin.promisor` / `partialclonefilter` restored before its first `checkout`: `git clone --local` neither inherits them nor errors on the missing objects it leaves behind, so the checkout would otherwise succeed with an empty working tree. The linked-worktree path shares the cache's own config and needs no such repair.
- `server/cmd/server/router.go` registers daemon APIs under `/api/daemon`, including workspace repos and task claim.
- `server/internal/daemon/daemon.go` claims tasks, prepares workdirs, launches provider CLIs, and reports completion.
- `server/internal/daemon/execenv/runtime_config.go` injects task/project/repo context into agent workdirs.
