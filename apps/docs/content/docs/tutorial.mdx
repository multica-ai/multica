Multica is a platform where people and AI agents work together. This tutorial starts from an empty workspace and walks through the entire lifecycle end to end:

- creating a workspace and navigating **Work**, **Team**, **Chat**, and **Autopilot**
- connecting your computer and configuring agents (both manually and through chat)
- delivering code through issues, inspecting runs, and previewing live with **Environments**
- tuning agent instructions and pairing an **Engineer** with a read-only **Reviewer**
- handing coordination to a **Squad**, reusing methods as **Skills**, and automating recurring checks with **Autopilots**

The example project is a personal photography portfolio website — concrete enough to show every core feature working together on real work.

**Before you start:**

- A Multica account (sign up at [multica.ai](https://multica.ai))
- A computer with at least one AI coding tool installed and signed in, such as Claude Code or Codex. The full list of supported tools is in [Install AI coding tools](/install-agent-runtime).

## Create a workspace

A workspace is where a team works: issues, projects, agents, and run history all live inside one. Sign-up onboarding walks you through creating your first workspace; if you were invited to a team, signing in opens that team's workspace directly.

This tutorial starts with a fresh workspace.

<Steps>
<Step>

Click the workspace icon at the top of the left app rail and choose **Create workspace**:

![Opening the workspace switcher in the app rail to create a workspace](/images/docs/tutorial-create-workspace-menu.webp)

</Step>
<Step>

Fill in three fields:

- **Workspace name**: shown to members; you can change it later.
- **URL**: the slug in the workspace address — the `personal-site` in `multica.ai/personal-site`. This cannot be changed after creation.
- **Issue prefix**: pre-filled from the URL and editable before creation — with `SITE`, issues are numbered `SITE-1`, `SITE-2`, and so on (changeable later in settings).

![The create workspace form with name, URL, and issue prefix](/images/docs/tutorial-create-workspace-form.webp)

</Step>
<Step>

Creating it opens the new workspace. Take a moment to note the layout:

- **App rail (far left)**: your workspace switcher, **New issue** (`C`), **Search** (`⌘K`), the four main spaces (**Work**, **Team**, **Chat**, **Autopilot**), and **Settings** at the bottom.
- **Work panel (beside the rail)**: **Inbox** at the top, followed by built-in and saved **Views** and **Projects**.
- **Bottom status bar**: shows active agents on the left and **Ask Multica** quick chat (`⌘J`) on the right.

The issue list is empty for now — the next steps bring agents in to populate it.

![A newly created, empty workspace in the Work space](/images/docs/tutorial-empty-workspace.webp)

</Step>
</Steps>

## Connect your computer

Agents execute work on the computers you connect, using the AI coding tools installed there.

This tutorial uses [Multica Desktop](https://multica.ai/download): after signing in, Desktop starts the local daemon automatically, registers your computer, and detects installed AI coding tools. Switch to **Team** in the app rail, open **Runtimes** under **Resources**, and confirm your computer shows as **Online**:

![Team space showing Runtimes with this computer online](/images/docs/tutorial-runtimes-list.webp)

Click your computer to see each detected AI coding tool and its status:

![Machine detail showing Claude Code and Codex online](/images/docs/tutorial-runtime-detail.webp)

Desktop is optional: on the **Runtimes** page, click **+** in the top right, choose **Other machine or server**, and run the install commands in a terminal. The daemon runs in the background — see [Daemon and runtimes](/daemon-runtimes).

## Create your first agent

Agents are full collaborators in a workspace: they can be assigned issues, reply in threads, and talk with you in chat. Start by creating a helper agent that handles day-to-day workspace chores — later steps in this tutorial delegate setup work to it.

In the **Team** space, click **+** in the panel header (or open **All agents** and click **New agent**).

<Steps>
<Step>

**Choose a runtime**: pick an online AI coding tool on the computer you connected — this tutorial uses **Claude Code**.

</Step>
<Step>

**Configure the agent**: fill in the key fields (or click **Let AI write it** in the top right to let the Agent Builder draft them in a conversation):

- **Name**: `Multica helper`
- **Description**: `Handles workspace chores, agent setup, and status updates.`
- **Instructions**: sent on every run; spell out what the agent owns and what it should leave alone:

```text
You are the helper of this workspace.

You handle what members ask for in issues and chat: create or update
issues, adjust statuses, configure agents, squads, skills, and autopilots,
and answer questions about what is going on in the workspace.

Keep replies short. After finishing something, reply with a one-line
summary of what you did. Do not touch code or repositories. If a
request is ambiguous, ask before acting.
```

Select a model (this tutorial uses Claude Sonnet) and leave **Access** at the default (**Only me**).

![Configure step of agent creation with Multica helper filled in](/images/docs/tutorial-create-agent-form.webp)

</Step>
<Step>

Click **Create agent**. On the agent detail page, **Multica helper** is **Online · Idle** and ready to take work:

![Agent detail page showing Multica helper online](/images/docs/tutorial-agent-detail.webp)

</Step>
</Steps>

## Prepare the site repository

The site's code lives in a GitHub repository. If your computer has the [GitHub CLI](https://cli.github.com) (`gh`) installed and signed in, an agent can create and register the repository for you too.

In **Chat**, start a conversation with **Engineer** and ask it to create an empty GitHub repository named `personal-website` under your account, then register it in this workspace with `multica repo add`. Engineer creates the repo, registers it, and replies with the URL:

![Engineer confirming personal-website was created and registered](/images/docs/tutorial-chat-create-repo.webp)

Click the **Settings** gear at the bottom of the app rail and open **Code** under **Connections & extensions**. Confirm `personal-website` appears under **Repositories**, and click **Connect GitHub** to authorize the repository. Once connected:

- pull requests that reference an issue ID (such as `SITE-1`) link to the issue automatically;
- PR diff stats and CI check status appear directly in the issue sidebar;
- merging all linked PRs can automatically move the issue to **Done**.

![Settings -> Code with GitHub connected, personal-website registered, and PR auto-linking enabled](/images/docs/tutorial-repo-settings.webp)

Without the GitHub CLI, create the repository on GitHub yourself and add it via **+ Add repository** on the same page.

## The first issue: build the site

Setup is done. From here on, day-to-day work runs through **issues**: write requirements clearly, hand them to an agent, and track every run, comment, and PR on one timeline.

The site starts from shadcn's Next.js template so Engineer builds design and content on top of a clean foundation.

<Steps>
<Step>

Click **New issue** at the top of the app rail (shortcut `C`). In the default **Create with agent** mode, you do not need to write a title: pick **Engineer** under **Created by** and write your requirements directly into the prompt (you can click **Switch to Manual** at the bottom anytime):

```text
Work in the personal-website repository registered in this workspace.

Start from a template instead of scaffolding from scratch:

pnpm dlx shadcn@latest init --preset b5rR41Mtnc --template next --pointer

Run the command, commit the template as-is, then build on top of it.

The site is for a photographer. It needs:

- Introduction — who I am and what I shoot
- My work — a selection of photos
- Contact — an email link that is easy to find
- Pricing — decide where a pricing table fits and how to present it
- Use placeholder images wherever a photo belongs, and list where I
  should replace them with my own work

Design:

- Pick a style that fits a photography portfolio. It should feel
  refined and understated; express that through layout, typography,
  and spacing, and never use words like "premium" or "high-end"
  in the copy.
- Choose the fonts.

Open a pull request when it is ready.
```

Notice the three ingredients of a strong prompt: hard constraints (start from the template), concrete content requirements, and deliberate open space (layout and typography left to Engineer). State intent and boundaries; leave implementation choices to the agent.

![New issue dialog in Create with agent mode with Engineer selected](/images/docs/tutorial-new-issue-agent-mode.webp)

</Step>
<Step>

After submitting, Multica creates `SITE-1` with a generated title, assigns **Engineer**, and starts execution immediately. Status moves to **In Progress**. Everything happening on the issue lives in the right sidebar: **Properties**, **Wakeups**, **Pull requests**, **Environments**, and **Execution log**.

While Engineer works, you can watch live progress from the **Engineer is working** badge in the header or **Execution log** on the right. If you ever spot an agent heading in the wrong direction mid-run, you do not need to stop it — post a correction in the comment box with **Add to current run** to [steer it](/mentioning-agents#steer-a-running-agent) at its next step.

![SITE-1 while Engineer is working, with active status badge and Execution log](/images/docs/tutorial-issue-engineer-working.webp)

</Step>
<Step>

Hover the active run in **Execution log** and click **View transcript** to inspect every step: agent narration, **Bash** commands, **Read** and **Edit** calls, and timing. Click the **ⓘ** button in the top right to see the machine, AI coding tool, delivered skills, and working directory for this run:

![Execution log transcript showing every command and edit Engineer ran](/images/docs/tutorial-execution-log.webp)

</Step>
</Steps>

## Write feedback into the instructions

This review uncovered two recurring habits: Engineer opened a PR without the issue ID (breaking auto-linking), and spent extra run time taking repetitive self-check screenshots when you prefer reviewing live in the browser via **Environments**.

Because both apply to every future task, write them into Engineer's instructions rather than repeating them in future issues. An agent can update its own configuration through `multica agent update` — just ask it in the same chat:

![Asking Engineer in Chat to save both rules into its own instructions](/images/docs/tutorial-chat-update-instructions.webp)

Engineer updates its instructions and explicitly notes the trade-off: skipping screenshot self-checks means visual regressions now depend on your browser pass. Open **Team → All agents → Engineer** to confirm the new **Working rules** section is saved:

![Engineer's updated instructions showing the new Working rules section](/images/docs/tutorial-engineer-updated-instructions.webp)

That is the core loop for tuning an agent: whenever a habit repeats across runs, encode the fix into its instructions once.

## A third agent: Reviewer

Engineer shipped a strong first pass, but an author rarely catches every blind spot in its own output. Bring in a second perspective: a dedicated **Reviewer** agent with a fresh context and a different tool and model.

<Steps>
<Step>

Ask **Multica helper** in Chat to create **Reviewer** on **Codex** (`gpt-5.6-sol`) with read-only instructions: read the PR diff against both code conventions and the issue's requirements, post findings with file and line numbers, run read-only verification checks, and never modify code. Open **Team → All agents → Reviewer** to confirm:

![Reviewer agent detail page configured on Codex with read-only review rules](/images/docs/tutorial-reviewer-detail.webp)

</Step>
<Step>

Review needs no separate issue and no assignee change. Back in `SITE-1`, type `@Reviewer` in the comment box and ask it to review PR #1. Notice the trigger preview directly below the composer (`Reviewer · Will start when sent`), confirming who will run on send:

![Mentioning @Reviewer in SITE-1's comment box with the live trigger preview](/images/docs/tutorial-comment-mention-reviewer.webp)

</Step>
<Step>

Reviewer comes back with **Changes requested before merge** and five concrete findings in two groups — including two requirement gaps Engineer missed (pricing presented as final terms without placeholder labels, and an unverified Instagram link) alongside three code conventions, all with file paths and line numbers.

Reply in the same thread mentioning `@Engineer` to resolve all five findings. Engineer pushes the fixes to PR #1 and reports back item by item on the same timeline:

![Reviewer's structured findings followed by @Engineer picking up the fixes](/images/docs/tutorial-reviewer-findings.webp)

</Step>
<Step>

Mention `@Reviewer` again for a second pass. All five findings are verified fixed, checks pass, and Reviewer returns **Ready to merge** with two non-blocking follow-up ideas:

![Reviewer's second-pass approval comment on SITE-1](/images/docs/tutorial-reviewer-recheck.webp)

</Step>
</Steps>

One issue now hosts two specialized agents — Engineer builds and fixes, Reviewer audits — collaborating cleanly inside one thread.

The PR card flips to **Merged**, the dev environment stops cleanly, and `SITE-1` moves to **Done** (with GitHub PR merge automation configured in **Settings → Code**):

## Form a squad

The `SITE-1` loop worked smoothly, except every hand-off depended on you: mentioning Reviewer after build, mentioning Engineer after review, mentioning Reviewer again after fixes. You can hand coordination itself to a **Squad**: a named team of agents and humans led by a leader agent.

When an issue is assigned to a squad, the leader takes ownership: it reads the issue, delegates to the right member by `@`-mention, automatically wakes up whenever a member replies, routes the next step, and reports the finished deliverable back to you.

Build **Website Team** around the division of labor you already have, plus a leader:

- **Lead** (new, Claude Sonnet): coordinates scope, dispatches Engineer and Reviewer, moves status, and writes sign-off briefs — never edits code itself.
- **Engineer** (existing): builds features, addresses review findings, and merges approved PRs.
- **Reviewer** (existing): audits every PR before delivery (read-only).
- **Maya Lin (You)**: final product sign-off.

Describe this setup to **Multica helper** in Chat — including two reusable skills (`tdd` for Engineer and `delivery-brief` for Lead, covered next) and the squad's delivery workflow. Multica helper configures the leader, squad, roles, instructions, and skill bindings in a single pass:

![Multica helper configuring the Website Team squad, Lead, and skills in one pass](/images/docs/tutorial-helper-create-squad.webp)

Open **Team → Squads → Website Team** to inspect the roster, role descriptions, and delivery instructions (you can also create or edit squads directly on this page — see [Squads](/squads)):

![Website Team squad detail showing leader, members, roles, and delivery instructions](/images/docs/tutorial-squad-detail.webp)

## Skills: reusable methods

Updating Engineer's instructions earlier solved rules unique to one agent. When a working method should be shared across multiple agents — or reused from a community package — store it as a **Skill**.

A skill follows the open Agent Skills standard: a `SKILL.md` file plus optional supporting references, templates, or scripts. Attach a skill to any agent and Multica syncs it to the runtime automatically on every run. Open **Team → Skills** under **Resources** to see the two skills configured above and which agents use them:

![Team -> Skills list showing delivery-brief attached to Lead and tdd attached to Engineer](/images/docs/tutorial-skills-list.webp)

Click `tdd` to inspect its `SKILL.md` content, supporting files (`examples/test-first.md`, `references/checklist.md`), version history, and attached agents:

![Detail view of the tdd skill showing SKILL.md, supporting files, and attached agent](/images/docs/tutorial-skill-detail.webp)

The two skills shape two different parts of the workflow:

- **tdd** (attached to Engineer): write a failing test first, make it pass minimally, then refactor cleanly.
- **delivery-brief** (attached to Lead): open every sign-off report with a one-line decision, PR summary, and numbered points needing human judgment, and never merge without approval.

Click **+** in the top right of **Skills** to see all four ways to add a skill — **Create manually**, **Import from local**, **Import from URL** (GitHub, ClawHub, Skills.sh), and **Copy from runtime** (see [Skills](/skills)):

![The four ways to create or import a skill under the + menu](/images/docs/tutorial-skill-new-modal.webp)

Review third-party skill files before importing them: Multica delivers skill content directly to the AI coding tool without sandboxing.

## The second issue: hand it to the squad

Now give **Website Team** a complete feature: convert the portfolio into a reusable template with placeholder identity (`Alex Rivera`) and email (`hello@example.com`), keeping layout and typography untouched.

Press `C` to open **New issue**, stay in **Create with agent** mode, pick **Website Team** under **Created by**, and describe the request. A squad works anywhere an individual assignee does.

Multica creates `SITE-2` assigned to **Website Team**. From that moment, **Lead** drives the entire loop automatically:

1. **Lead** scopes extra constraints (consistent identity across `<title>`, Open Graph tags, and `README.md`, plus a TDD config test) and dispatches `@Engineer`.
2. **Engineer** writes the test first, implements the change, opens PR #2 (`SITE-2: Convert portfolio into reusable template`), and reports back.
3. **Lead** wakes up automatically and routes PR #2 to `@Reviewer`.
4. **Reviewer** verifies the diff and tests and responds **Ready to merge** with zero findings.

![SITE-2 showing Lead dispatching Engineer, Engineer reporting PR #2, Lead routing to Reviewer, and Reviewer approving](/images/docs/tutorial-squad-dispatch.webp)

With review passed, **Lead** moves `SITE-2` to **In Review** and delivers a concise sign-off brief (shaped by its `delivery-brief` skill), mentioning you with the PR summary, two judgment calls, and a clear promise not to merge until you approve:

![Lead's concise delivery brief on SITE-2 mentioning Maya for sign-off](/images/docs/tutorial-squad-delivery.webp)

From scoping to implementation, testing, review, and sign-off packaging, you did not have to manually connect a single hand-off.

## Automation: Autopilot

Every run so far started from you: an assignment, a mention, or a chat message. **Autopilot** adds scheduled and webhook-driven automation so recurring maintenance runs without anyone remembering to trigger it.

<Steps>
<Step>

Ask **Multica helper** in Chat to create a weekly Monday 9:00 AM Autopilot assigned to **Reviewer** in **Create issue** mode: check out `personal-website`, scan for dead code, unused exports, outdated dependencies, and type improvements, and post findings without modifying code.

Open **Autopilot** in the app rail to inspect the configured rule — Runbook, schedule (`0 9 * * 1`, timezone, next run time), execution mode (**Create issue** vs. **Run only**), and the **Issue wakeups** view for one-off follow-ups on existing issues.

Rather than waiting for Monday, click **Run now** in the top right to trigger a run immediately:

![Autopilot detail page showing the Runbook, Monday 9:00 AM schedule, and Run now button](/images/docs/tutorial-autopilot-detail.webp)

</Step>
<Step>

Multica immediately creates `SITE-3`, assigns **Reviewer**, and starts the read-only health check. Every Monday at 9:00 AM from now on, the same audit runs automatically:

![SITE-3 created automatically by the Autopilot with Reviewer running checks](/images/docs/tutorial-autopilot-issue.webp)

</Step>
</Steps>

Autopilots also support GitHub/GitLab/generic **webhooks** and can target a **Squad** as the assignee — see [Autopilots](/autopilots) and [Issue wakeups](/issue-wakeups).

## Working with other people

So far you have been the only human in the workspace. Click the **Invite member** icon in the **Team** panel header — or open **Settings → Members** — to invite teammates by email. Choose **Member**, **Admin**, or a project-scoped **Guest** (free, no seat, scoped only to shared projects):

![Settings -> Members with the Invite member dialog open showing Member, Admin, and Guest roles](/images/docs/tutorial-invite-member.webp)

Invited teammates create issues, `@`-mention shared agents, inspect Environments, and join squads right alongside you.

## Closing

As your work grows beyond a couple of issues, Multica gives you clean structure to scale this exact loop:

- **Spaces** keep day-to-day focus separate: **Work** (Inbox, saved Views, Projects), **Team** (Agents, Squads, Skills, Runtimes, Analytics), **Chat**, and **Autopilot**.
- **Projects** group related issues under shared instructions, repositories, folders, progress forecasts, and optional custom [Workflows](/workflows) that hand off between stages automatically.

Looking back at the full arc: starting from an empty workspace, you connected your computer, built four specialized agents, shipped and previewed your first PR with Environments, encoded feedback into instructions and reusable skills, handed coordination to a squad, and automated weekly audits with Autopilot. By the end, your job narrows to setting direction and signing off on results.
