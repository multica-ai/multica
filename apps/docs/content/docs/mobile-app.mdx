The Multica iOS client is not on the App Store yet. You can build a Release version from the public source repository on a Mac and install it on your own iPhone. Android builds use the same React Native client and produce a signed standalone APK.

The installed app connects to Multica Cloud by default; sign in with your existing account. Workspaces, issues, comments, and run history all live on the server, so nothing needs to be synced from web or Desktop.

## Android APK

Use JDK 17 and Android SDK 36. Configure an external release keystore, then run this command from the repository root:

```bash
pnpm -C apps/mobile android:release
```

The APK defaults to Multica Cloud and needs no Metro server. Signing, environment variants, private backend addresses and installation checks are described in the [Android build guide](https://github.com/multica-ai/multica/blob/main/apps/mobile/docs/android-release.md). Background push notifications are not included. The instructions below cover iPhone installation.

## Prerequisites

You need:

- a Mac with Xcode installed;
- an Apple ID signed in under **Xcode → Settings → Accounts**;
- an iPhone connected via USB;
- Developer Mode enabled on the iPhone under **Settings → Privacy & Security**;
- Node.js, pnpm, and Git.

If Xcode or the on-device development environment isn't set up yet, complete Expo's [iOS device environment setup](https://docs.expo.dev/get-started/set-up-your-environment/) first.

## Installing to your iPhone

<Steps>
<Step>
Clone the repository and install dependencies:

```bash
git clone https://github.com/multica-ai/multica.git
cd multica
pnpm install
```
</Step>
<Step>
Run from the repo root:

```bash
pnpm ios:mobile:device:prod:release
```

This builds a Release version with no Metro dependency and installs it on the connected iPhone. The first build downloads iOS dependencies and compiles React Native; later builds reuse Xcode's cache.
</Step>
<Step>
Open the app on the iPhone. If iOS blocks it from opening, trust the developer certificate under **Settings → General → VPN & Device Management**.
</Step>
</Steps>

## 7-day limit of free signing

Apps signed with a free Apple ID only work for 7 days. When that expires, reconnect the iPhone to your Mac and re-run the same build command to re-sign.

Builds signed with an Apple Developer Program account stay valid longer and can also be used for TestFlight and regular distribution. With either kind of signing, server-side data is never lost by reinstalling or re-signing.

## Signing failures

If Xcode reports `No matching provisioning profiles found`, the default bundle identifier may not belong to your Apple ID. Switch to a reverse-domain name you control and rebuild:

```bash
export EXPO_BUNDLE_IDENTIFIER_PROD=com.yourname.multica
pnpm ios:mobile:device:prod:release
```

The value only needs to be available in your Apple Developer team; it does not affect your Multica account or workspaces.

## Updating

The self-installed iOS build does not auto-update. Pull the latest code, update dependencies, and rebuild:

```bash
git pull --ff-only
pnpm install
pnpm ios:mobile:device:prod:release
```

## Connecting to a self-hosted instance

Open **Server settings** on the sign-in page, or **Settings → Server settings** after signing in. Enter the **API URL** (backend root) and **Web URL** (browser/link address), then save. They may share an origin or use separate hosts. The app remembers both addresses after a restart; no rebuild is needed. **Restore Cloud defaults**, followed by Save, returns to Multica Cloud.

Both addresses require HTTPS and a certificate trusted by the device. Custom ports and base paths are supported, for example API `https://multica.example.com:8443/backend` and Web `https://multica.example.com:8443/app`. A trailing `/api` in the API address is removed because request paths add it themselves; `/auth` and `/ws` use the same backend root. HTTP and certificate-verification bypasses are not supported in the distributed APK. The device must be able to reach the addresses; `localhost` refers to the phone itself.

Changing either address signs you out and clears local drafts, workspace selection and cached data. Sign in again on the selected instance. Server-side data remains on its original instance. File downloads and images obtain fresh signed URLs from that instance without exposing your session token to an external browser.
