Multica は作業の記録と調整を担い、接続されたコンピュータが実行を担います。コンピュータ上の**デーモン**（daemon）が実行を取得し、そのマシンにインストールされた AI コーディングツールを呼び出します。

## デーモンとランタイムの違い

- **デーモン**は、1 台のコンピュータで動く Multica のバックグラウンドプロセスです。サーバーへの接続、ローカルツールの検出、実行の取得、結果の報告を担当します。
- **ランタイム**は、ワークスペースが利用できる 1 つの具体的な実行環境を表します。1 台のコンピュータと、そのコンピュータ上の 1 つの AI コーディングツール（またはカスタムランタイムプロファイル）の組み合わせに対応します。

たとえば、Claude Code と Codex の両方をインストールした 1 台のコンピュータが 2 つのワークスペースに接続している場合、デーモンはワークスペースごとに Claude Code と Codex のランタイムを 1 つずつ登録します。デーモンを再起動すると既存のレコードが更新されるだけで、同じ組み合わせに対して新しいランタイムが増え続けることはありません。

## 実行場所とデータ境界

ローカルランタイムが呼び出す AI コーディングツール、それらのツール自身のログイン認証情報、ローカルのコードディレクトリは、いずれも接続されたコンピュータに残ります。Multica サーバーがローカルツールの代わりにコマンドを実行することはなく、作業ディレクトリ全体を自動でアップロードすることもありません。

チームが協働できるように、サーバーはタスク、コメント、エージェント設定、実行のコンテキスト、実行記録、エージェントが書き戻した結果を保存します。これらには、エージェントが自ら読み取って返信に含めたコードスニペットやその他のプロジェクトコンテキストが含まれることがあります。

<Callout type="warning">
「ローカル実行」は、すべてのシークレットがこのマシンにしか存在しないという意味ではありません。エージェントのカスタム環境変数と MCP 設定はサーバー側に保存され、その表示は機密値のルールによって制限されます。カスタム環境変数は実行時にランタイムへ送られます。
</Callout>

デーモンはデフォルトでバックグラウンドで動きます。よく使うコマンド:

| コマンド | 役割 |
| --- | --- |
| `multica daemon status` | デーモンと接続の状態を表示する |
| `multica daemon logs -f` | ログを追跡表示する |
| `multica daemon restart` | デーモンを再起動し、ローカルツールを再検出する |
| `multica daemon stop` | デーモンを停止する |
| `multica daemon start --foreground` | デバッグ用に現在のターミナルで実行する |

実行用の作業ディレクトリを別のディスクに置くには、`multica config set workspaces_root <path>` で現在のプロファイルにルートを保存するか、`daemon start` または `daemon restart` に `--workspaces-root <path>` を渡します。フラグは `MULTICA_WORKSPACES_ROOT` より優先され、環境変数はプロファイル設定より優先されます。ルートを変更しても既存の実行ディレクトリは移動されません。

起動時、デーモンは `PATH` 上の対応する AI コーディングツールを検出し、あなたが接続を許可されているワークスペースにランタイムを登録します。ツールをインストールまたはログインした直後の場合は、デーモンを再起動すると再検出されます。

デーモンは、組み込みで対応している AI コーディングツールを少なくとも 1 つ検出できないと起動しません。インストール方法と実行コマンド名は [AI コーディングツールのインストール](/install-agent-runtime)を参照してください。

### ログイン時の自動起動 [#autostart]

CLI で起動したデーモンは、コンピューターを再起動すると自動では戻りません。自動で起動させるには、現在のプロファイルを登録します。

```bash
multica daemon autostart enable
multica daemon autostart status
multica daemon autostart disable
```

登録されるのはそのプロファイルの `multica daemon start --foreground` で、ログイン時に OS が起動します。Windows では現在のユーザーの Run レジストリ値、macOS では `~/Library/LaunchAgents` の LaunchAgent、Linux では systemd のユーザーユニットを使い、systemd のユーザーセッションがない場合は XDG autostart のエントリを使います。名前付きプロファイルでは `--profile <name>` を付けます。プロファイルごとに個別に登録されます。

- 登録を作るのは `enable` だけです。`multica daemon start` が自分で登録することはなく、未登録のときに 1 行のヒントを出すだけです。Multica が作った登録がある場合は、その中の実行ファイルのパスを更新するので、CLI を更新・移動しても `enable` をやり直す必要はありません。
- macOS と Linux では、ログインセッションに渡るのは `enable` 実行時のシェルの `PATH` だけです。シェルで export したほかの変数（API キー、`HTTPS_PROXY` など）は引き継がれません。デーモンの設定は `multica config set` で保存し、ほかの変数はユーザー環境に置いてください。
- systemd のユーザーユニットはログイン時に起動します。ログインせずに起動時から動かすには、`enable` の出力にあるとおり `loginctl enable-linger <ユーザー名>` を実行します。
- `multica daemon stop` は動いているデーモンを止めるだけで、登録は残ります。
- 同じ場所に Multica が作っていないファイル（自分で書いた systemd ユニットなど）がある場合、`enable` も `disable` もそのファイルを変更しません。
- Desktop が起動したデーモンは Desktop が管理します。`daemon start` はそのデーモンについてヒントを出したり登録を更新したりしません。

## ディスパッチとオンライン状態

登録されたランタイムは接続を維持し続けます。新しい実行がキューに入ると、サーバーは対応するデーモンに通知します。接続が切れて通知を取りこぼさないよう、デーモン側も定期的にポーリングします。ランタイムがオンラインで空き容量があれば、実行は通常すぐに開始されます。

デーモンは 15 秒ごとにハートビートを送ります。サーバーはハートビートと接続状態を組み合わせてランタイムのオンラインを判定し、デーモンが予期せず終了した場合、遅くとも約 3 分以内にオフラインと判定されます。**ランタイム**ページでは、接続が切れてから最初の 5 分間は「最近接続が切れました」、その後は「オフライン」と表示されます。

ランタイムがオフラインのとき:

- キュー済みの実行はランタイムの復帰を待ち、ほかのコンピュータへは移りません。失敗するのは、そのランタイムが再接続猶予を超えてハートビートを停止し、**かつ**実行自身も同じ時間キューで待った場合のみです。単に処理が詰まっているだけのランタイムは滞留分を保持し続け、すでにオフラインのランタイムに割り当てられた実行にも猶予がまるまる 1 回分あります。
- 進行中の実行はすぐには失敗しません。ランタイムのハートビートの途絶が再接続猶予（`MULTICA_RUNTIME_RECONNECT_GRACE`、デフォルト 3 時間）を超えてから `runtime_offline` で失敗します。条件を満たすタスクまたはチャットの実行は自動リトライできます。
- デーモンが再起動すると、ランタイムを再登録し、前回正常に終了しなかった実行を回収します。
- 7 日を超えてオフラインで、（アーカイブ済みを含め）どのエージェントにも紐づいていないランタイムは、自動的にクリーンアップされます。

## 同時実行の上限

1 つのデーモンはデフォルトで最大 20 件の実行を同時に処理します。各エージェントはデフォルトで最大 6 件です。実効的な同時実行数は両者の小さい方になります。

上限に達すると、新しい実行はキューで待ち続けます。個々のエージェントの同時実行数はエージェント設定で、マシン全体の上限は `MULTICA_DAEMON_MAX_CONCURRENT_TASKS` で調整できます。並列実行は、マシンの性能、ツールアカウントのクォータ、同じ作業ディレクトリを同時に取り合います。

実行で使われたトークン、費用、失敗はワークスペースごとに[分析](/analytics)ページにまとまっています。1 つのランタイムのトークン使用量は `multica runtime usage <runtime-id>` でも確認できます。

## ローカルの MCP 設定 [#local-mcp]

エージェントに MCP 設定が保存されていない場合、Multica は MCP の設定を何も渡さず、ツールはそのコンピューター上の自身の設定をいつもどおり読み込みます。

エージェントに MCP 設定があると（空の設定でも）、Multica は実行ごとに専用の設定を作ってツールに渡します。たとえば Claude Code は strict モードでこの設定だけを読み込みます。マシンにすでにあるサーバーが使えなくならないよう、デーモンはランタイムのコンピューター上でツールのユーザーレベルの MCP 設定を読み、エージェントの設定と統合します。同じ名前のサーバーは、次の順で先にあるものが使われます。

1. エージェントの **MCP** タブで Multica が管理しているサーバー、またはワークスペースの MCP ライブラリから割り当てたサーバー
2. ツールのユーザーレベルの設定ファイル
3. Claude Code のみ：有効な Claude Code プラグインに含まれる MCP サーバー。プラグインは `~/.claude/settings.json` の `enabledPlugins` から決まり、各プラグインの `.mcp.json` とマニフェストで宣言された MCP ファイルを読みます。

| ツール | 読み込むユーザーレベルの設定 |
|---|---|
| Claude Code | `~/.claude.json` の `mcpServers` と、有効なプラグインの MCP サーバー |
| Codex | `$CODEX_HOME/config.toml`（既定は `~/.codex/config.toml`）の `mcp_servers` |
| Cursor Agent | `~/.cursor/mcp.json` の `mcpServers` |
| OpenCode | `$XDG_CONFIG_HOME/opencode/opencode.json`（既定は `~/.config/opencode/opencode.json`）の `mcp` |
| OpenClaw | `$CLAWDBOT_CONFIG_PATH`、または `$OPENCLAW_STATE_DIR/openclaw.json`（既定は `~/.openclaw/openclaw.json`）の `mcp.servers` |
| CodeArts | `~/.codeartsdoer/codearts_cli.json` または `codearts_cli.jsonc` の `mcp` |

CodeBuddy、Kimi CLI、Pi は起動時に自分でユーザーレベルの設定を読み込み、Multica が渡す設定と組み合わせます。デーモンが先に統合すると同じサーバーが 2 回起動するため、これらのツールでは統合しません。CodeBuddy は名前が重なった場合 Multica が渡した方を使います。表にないほかのツールは、エージェントの設定だけを受け取ります。

統合はランタイムのコンピューター上で行われ、ローカルのサーバーのコマンド、URL、ヘッダー、環境変数はアップロードされません。エージェントの **MCP** タブの「ランタイムから継承」には、サーバー名、トランスポート、取得元、有効かどうかだけが表示されます。エージェント側の同名サーバーに上書きされたものには「Multica で上書き」と表示されます。ローカルの設定ファイルを解析できない場合、デーモンは警告をログに残し、その実行はエージェントの設定だけを使います。

## クリーンアップと保持 [#cleanup]

デーモンは起動の約 30 秒後に最初のクリーンアップを行い、その後は 2 時間ごとに行います。実行中の実行が使っているディレクトリは削除されません。`multica daemon disk-usage` でワークスペースごと、実行ごとの使用量を確認できます。以下の期間はデフォルト値で、対応する `MULTICA_GC_*` 変数は[環境変数](/environment-variables#gc)にあります。

### 実行ディレクトリ

実行ごとに作業ディレクトリのルート（既定は `~/multica_workspaces`）の下にディレクトリが作られ、チェックアウトしたコード、出力、ログが入ります。同じタスクの後続の実行はこれを引き続き使います。ディレクトリ全体が削除されるのは次のときです。

| 実行の出どころ | 削除のタイミング |
|---|---|
| タスク | タスクが `done` または `closed` カテゴリのステータスに入り、24 時間更新がないとき |
| チャット | セッションのアーカイブから 24 時間後。セッションが削除されたら次のクリーンアップ。アーカイブされていない間は残ります |
| オートパイロット（実行のみ）、クイック作成 | 実行が終わった後の次のクリーンアップ |
| 持ち主が見つからない（メタデータがない、またはサーバー上に該当する記録がない） | ディレクトリが 72 時間変更されていないとき |

タスクがまだ閉じていない場合、実行完了から 12 時間後に再生成できる内容だけを削除します。対象は `node_modules`、`.next`、`.turbo` ディレクトリと、デーモンが Codex 用に用意したキャッシュで、ほかは残ります。Multica Cloud に接続したデーモンは、タスクが閉じているかどうかにかかわらず、実行完了から 14 日後にディレクトリ全体も削除します。セルフホストでは既定でこれを行いません。

プロジェクトのローカルディレクトリでの実行は、あなた自身のディレクトリで作業し、デーモンはそこに触れません。Multica がその実行用に作る記録ディレクトリ（ログなど）も残り、中の再生成できるキャッシュだけが片付けられます。

### 共有のリポジトリキャッシュ

デーモンはワークスペースのリポジトリごとにベアリポジトリのキャッシュを 1 つ持ちます。場所は作業ディレクトリのルート下の `.repos/<ワークスペース ID>/` です。このコンピューター上の同じワークスペースの実行はこれを共有し、チェックアウトのたびにキャッシュから git worktree を作り、新しいコミットだけを取得します。再クローンはしません。例外は Linux と Windows の Codex 実行で、作業ディレクトリ内に `.git` を持つ独立したクローンを受け取ります。Codex の workspace-write サンドボックスでは、作業ディレクトリ外の Git メタデータが読み取り専用になるためです。

キャッシュが削除されるのは、どのワークスペースやプロジェクトからもリポジトリが参照されず、worktree が残っておらず、30 日間どの実行もそこからチェックアウトしていない、という 3 つがそろったときだけです。必要になれば再びクローンされます。古いエージェントブランチを消したあと、デーモンは実行中の実行がないときにキャッシュに対して `git reflog expire --expire=30.days --all` と `git gc --prune=30.days` を実行します。

### セッション、メモリ、一時ディレクトリ

| データ | 場所 | 保持 |
|---|---|---|
| Codex のセッション記録（エージェントとタスクごとに 1 つ） | Codex のホーム（既定は `~/.codex`）の `multica-sessions/` | 14 日間使われないと削除。以後、そのタスクの実行は以前の Codex セッションを再開できません |
| Hermes のセッション記録 | Multica の設定ディレクトリ（既定は `~/.multica`、名前付きプロファイルは `~/.multica/profiles/<name>`）の `hermes-sessions/` | 14 日間使われないと削除 |
| Hermes のメモリ（エージェントごとに 1 つ） | 同じディレクトリの `hermes-state/` | 90 日間使われないと削除 |
| 実行ごとの専用一時ディレクトリ（`TMPDIR`） | システムの一時ディレクトリの `multica-task-*` | 実行終了時に削除。デーモンが強制終了された場合は後のクリーンアップで削除 |

### Codex のネイティブメモリとサブエージェント [#codex-memory]

デーモンが管理する Codex の実行では、Codex のネイティブメモリが既定でオフになります。このマシンや以前の実行のメモリが別のワークスペースに持ち込まれないようにするためです。設定はその実行専用の `CODEX_HOME/config.toml` にだけ書かれ（`features.memories`、`memories.generate_memories`、`memories.use_memories` をすべて `false`）、`~/.codex/config.toml` は変更されません。ネイティブメモリを残したい場合は、デーモンの環境で `MULTICA_CODEX_MEMORY=1` を設定します。

Codex のネイティブサブエージェントも既定でオフです。Multica は親スレッドが終わった時点で実行を終了とみなすため、まだ動いているサブエージェントの結果は失われます。このリスクを受け入れる場合は `MULTICA_CODEX_MULTI_AGENT=1` を設定します。

## ランタイムの共有 [#プライベートと公開]

ローカルランタイムはデフォルトで**プライベート**です。その上にエージェントを作成できるのはランタイムの所有者だけで、ワークスペースの owner・admin も例外ではありません。ランタイムは他のメンバーのコンピュータで、そこでエージェントを動かせばそのメンバーのマシンとツール認証情報を使うことになります。

ランタイムを**公開**に変更できるのは所有者だけです。ワークスペースの管理者はランタイムの名前変更や削除はできますが、共有するかどうかは所有者が決めます。公開すると、ワークスペースの他のメンバーもこのランタイムを選び、エージェントの実行をこのコンピュータにルーティングできるようになります。基盤の AI コーディングツールのログイン認証情報は共有されません。

一部のメンバーにだけ共有するには、ランタイムの詳細で**メンバー**を選び、ワークスペースのメンバーを 1 人以上選んで**保存**します。選ばれたメンバーはこのランタイムを選択し、その上でエージェントを作成できます。リストを変更できるのは所有者だけで、リストに入っていても名前変更・削除・管理の権限は得られません。

所有者が共有メンバーを外したとき、公開ランタイムを指定メンバーに絞ったとき、または再び**プライベート**にしたとき、Multica はエージェントビルダーのセッションも含め、影響を受けるエージェントとアクティブな実行を表示します。確定すると、他メンバーの該当エージェントの接続を解除し、キュー中・配信済み・実行中・ローカルディレクトリ待ち・延期中の実行を `runtime_access_revoked` としてキャンセルします。これらのエージェントに割り当てられた有効なオートパイロットも一時停止します。所有者と、引き続きアクセスできるメンバーのエージェントと実行には影響しません。対象が変わった場合は再確認が必要で、同時にチャットが更新されている場合は再試行が必要になることがあります。作業を再開するには、利用可能なランタイムにエージェントを接続し、一時停止中のオートパイロットを手動で再開してください。

キャンセル後もチャット履歴は維持され、下書き・添付ファイルの復元データはサーバーに保存されます。Web・デスクトップ版は既存の下書き復元 UI を利用しますが、モバイル版にはまだその UI がありません。開始済みで出力のない実行は、デーモンのキャンセル確認またはサーバーの猶予期間終了を待って入力の復元を判断します。接続中のデーモンは通常の確認でキャンセルを受信します。オフラインでもサーバー側のアクセスは直ちに取り消されますが、ローカルプロセスは再接続してキャンセルを受信するまで続く場合があり、即時の遠隔停止は保証できません。

## カスタムランタイムプロファイル

チームで社内 wrapper やバージョン固定の実行ファイルを使う場合、あるいは互換ツールに固定引数を追加したい場合は、**カスタムランタイムプロファイル**を作成できます。

カスタムプロファイルが新しい通信プロトコルを追加することはありません。作成時には、Multica がすでに対応しているプロトコルファミリー（ツールの連携プロトコルの種類。[AI コーディングツール対照表](/providers)を参照）を選ぶ必要があり、コマンド自体がそのプロトコルファミリーと互換でなければなりません。

### 作業ランタイム環境

デーモンがエージェントの作業を開始すると、作業コンテキストをランタイムプロセスに注入します。これらの値はデーモンが管理するため、エージェントのカスタム環境では `MULTICA_` 変数や作業用一時ディレクトリ変数を上書きできません。

次の表は、カスタムランタイムが現在利用できる変数を示しています。完全な一覧ではなく、バージョン保証された API でもありません。連携処理では**連携契約**と記載された 5 つの変数だけを使用してください。それ以外は参考情報であり、今後変更される可能性があります。

| 変数 | 作業内の値 | 安定性 |
| --- | --- | --- |
| `MULTICA_TOKEN` | 作業スコープの `mat_` API 認証情報 | **連携契約** |
| `MULTICA_TASK_ID` | 実行中の作業の ID | **連携契約** |
| `MULTICA_AGENT_ID` | 割り当てられたエージェントの ID | **連携契約** |
| `MULTICA_WORKSPACE_ID` | 作業が属するワークスペースの ID | **連携契約** |
| `MULTICA_SERVER_URL` | デーモンが選択した Multica サーバー URL | **連携契約** |
| `MULTICA_TASK_CONFIG_ROOT` | 作業専用の Multica CLI 設定ルート | 参考情報 |
| `MULTICA_TASK_WORKSPACES_ROOT` | デーモンが管理する作業用ワークスペースのルート | 参考情報 |
| `MULTICA_AGENT_NAME` | 割り当てられたエージェントの表示名 | 参考情報 |
| `MULTICA_DAEMON_PORT` | `multica repo checkout` など作業専用コマンドが使うローカルデーモンのヘルス/API ポート | 参考情報 |
| `MULTICA_TASK_SLOT` | デーモン全体の同時実行プール内のスロット。GPU などスロット番号付きリソースに使用可能 | 参考情報 |
| `MULTICA_REPO_CHECKOUT_MODE` | Linux と Windows の Codex 実行でだけ `isolated` になり、`multica repo checkout` が作業ディレクトリ内に `.git` を持つ独立したクローンを作る。ほかの実行では設定されない | 参考情報 |
| `TMPDIR` | 実行中の作業専用の一時ディレクトリ。`TMP` と `TEMP` でも提供しますが、Windows では Git Bash の共有 `/tmp` のため作業はユーザーの一時パスを継承します。Windows の Claude Code は `CLAUDE_CODE_TMPDIR` の既定値を作業の一時ディレクトリに設定 | 参考情報 |

`MULTICA_TOKEN` を使ったリクエストの作成者はサーバーが決定し、タスクへのコメントなどの書き込みは、割り当てられたエージェントと実行中の作業に帰属します。認証情報の完全な紐付け、権限、帰属、最長 24 時間の有効期間、クリーンアップについては、[エージェント実行用の一時トークン](/auth-tokens#エージェント実行用の一時トークン)を参照してください。

<Callout type="warning">
これらの値はランタイムプロセスの実際の環境に存在します。ランタイムが起動する子プロセスは、`MULTICA_TOKEN` を含むすべての値をデフォルトで継承します。子プロセスに認証情報を渡すべきでない場合は、明示的に削除してください。存在しないプロセス分離を前提にしてはいけません。逆に、独自に子プロセス環境をフィルタするツールでは、変数の明示的な許可が必要な場合があります。たとえば Codex の shell ツールは、名前に `TOKEN`、`KEY`、`SECRET` を含む変数を除外するため、デーモンは必要な作業変数を許可する管理対象の shell ポリシーを設定します。トークンはプロセス環境内だけに保持し、prompt、ログ、リポジトリファイル、永続設定には書き込まないでください。子プロセスは親の作業と同じ ID と権限を共有し、独立した新しいスコープ ID は受け取りません。
</Callout>

### プロファイルの作成

カスタムランタイムプロファイルを作成・変更・削除できるのは、ワークスペースの owner と admin だけです。

1. **ランタイム**を開き、対象のコマンドがインストール済みのコンピュータに移動します。
2. **カスタムランタイムを追加**をクリックします。
3. コマンドが実際に互換のあるプロトコルファミリーを選びます。
4. 名前、コマンド、固定引数を入力して保存します。

プロファイルはワークスペース内で共有されます。接続済みの各コンピュータが自分でこのコマンドを探し、`PATH` 上で解決できたコンピュータだけが対応するランタイムを登録します。プロファイルを作成してもコマンドはインストールされず、他のメンバーのツールログインが代行されることもありません。

ここに入力するのは実行ファイルと引数であり、shell スクリプトではありません。通常の引数、引用符、バックスラッシュによるエスケープは使えますが、パイプ、リダイレクト、`&&`、`;`、バッククォート、環境変数の展開は使えません。これらの挙動が必要な場合は wrapper script にまとめ、そのスクリプトをコマンドとして指定してください。

### 引数の並び順

コマンド欄に入力した内容は実行ファイルの直後に置かれ、Multica が追加する引数より前に並びます。

```text
<あなたのコマンド> <あなたの固定引数> <Multica のプロトコル引数> <エージェントのカスタム引数>
```

サブコマンド型の wrapper はこの順序で動きます。コマンドが `ccms start q36` なら、ツールは先に `start q36` を受け取り、Multica の `-p` などが届く前にサブコマンドを選びます。この種の wrapper はこの順序しか受け付けません。

以前は、ここに入力した引数は最後に追加されていました。フラグ形式のコマンドの多くはどちらの位置でも同じように解釈しますが、グローバルフラグとサブコマンドのフラグを区別するコマンドではフラグの位置が意味を持ちます。固定引数付きのプロファイルをすでに使っている場合は、アップグレード後に一度実行して、正常に起動することを確認してください。

ほかにも次の点に注意してください。

- **競合したときは Multica の値が優先されます。** 固定引数で Multica も設定するフラグを指定した場合、Multica の値が後ろに来て有効になります。典型的なのは、エージェントで選んだモデルがプロファイルに固定した `--model` を上書きするケースです。全員に同じモデルを固定したい場合は、エージェントのモデル欄を空にしてください。
- **プロトコルに必須のフラグは無視されます。** `-p`、`--output-format`、`--input-format`、`--permission-mode` と、ほかのプロトコルファミリーの対応するフラグは固定引数から取り除かれます。これらを上書きするとデーモンとツールの通信が切れるためです。サブコマンドとその他の位置引数は常にそのまま渡されます。

Desktop が起動したデーモンが、ターミナルでは実行できるコマンドを見つけられない場合は、現在のコンピュータに絶対パスを設定できます。

```bash
multica runtime profile set-path <profile-id> --path /absolute/path/to/command
```

パスの上書きを解除するには:

```bash
multica runtime profile unset-path <profile-id>
```

プロファイルの変更は、それ以降に取得される実行にのみ影響します。プロファイルを削除する前に、対応するランタイムにまだ紐づいているアクティブなエージェントを先に処理してください。あるコンピュータ上のランタイムインスタンスだけを削除してもプロファイルは消えず、実行中のデーモンが再登録します。

## Qoder Cloud Agents リモートランタイム

Qoder Cloud Agents は割り当てられたタスクをリモートセッションで実行します。Multica サーバーが既存のデーモンプロトコルを使うブリッジを管理するため、ユーザーがローカルデーモンを起動する必要はありません。

### 事前準備

- ワークスペース管理者の権限が必要です。Qoder 接続はワークスペースごとに 1 つです。
- Qoder で個人アクセストークン（PAT）、1 つ以上の実行環境、使用する QCA エージェントを作成します。モデル、ツール、スキルは Multica ではなく Qoder の QCA エージェントで設定します。
- セルフホスト環境では、サーバーに `MULTICA_VCS_SECRET_KEY`（base64 エンコードされた 32 バイトの鍵。再起動後も同じ値を使用）を設定してください。未設定の場合、**追加**メニューに Qoder Cloud Agents は表示されません。

### Qoder を接続する

1. **ランタイム**ページで**追加**をクリックし、**クラウドサービス**の **Qoder Cloud Agents** を選びます。
2. **リージョン**で PAT を発行したサイトを選びます：**グローバル**（qoder.com）または**中国**（qoder.com.cn）。PAT は発行元のサイトでのみ有効です。拒否された場合は、もう一方のサイトで再試行するボタンを使います。
3. **個人アクセストークン**に PAT を貼り付けます。検証されると Qoder から**実行環境**の一覧が読み込まれます。環境が 1 つだけなら自動で選択され、複数ある場合は選択します。
4. 任意：**GitHub authorization** を開き、エージェントがクローンするリポジトリごとに URL とトークンを追加します。エージェントはここで許可したリポジトリのみクローンできます。
5. 任意：**実行設定**を開き、同時実行数（デフォルト 3、最大 10）と実行タイムアウト（デフォルト 60 分、5〜240 分）を設定します。
6. **接続**をクリックします。Qoder Cloud Agents がランタイムページのクラウドの区分に表示され、数秒でオンラインになります。

### エージェントを追加する

ランタイムページで Qoder Cloud Agents を開き、**これでエージェントを作成**をクリックします。通常どおりエージェントを作成して Qoder ランタイムを選ぶこともできます。エージェントのフォームで **QCA エージェント**からリモートのエージェントを選びます。既存のエージェントは**ルーティング**タブで QCA エージェントやデフォルトのリポジトリを変更できます。複数の Multica エージェントが 1 つの接続を共有し、それぞれ別の QCA エージェントに紐づけられます。

認証情報は暗号化され、ワークスペース内で共有されます。管理者が接続を管理し、メンバーはアクセス可能な QCA エージェントを選択できます。リポジトリと開始ブランチはプロジェクトで選び、そのリポジトリのトークンは QCA のセッション作成時に送信されます。保存した PAT がブラウザーに返されることはありません。

管理者は Qoder Cloud Agents のページで接続とリポジトリを編集できます。**一時停止**すると認証情報とエージェントを残したまま新しいタスクの送信を止め、**接続を解除**すると保存済みのトークンを削除してランタイムを外し、エージェントの紐づけを解除します。

### 実行の仕組み

同時実行数の上限を超えたタスクはキューで待機します。同じタスクの後続の実行は、前回のセッションがアイドルであればその Qoder セッションを引き継ぎます。エージェントにはデフォルトのリポジトリを設定でき、タスクのプロジェクトにリポジトリがない場合に使われます。エージェントにはタスク ID を含むブランチ名と、タスク ID で始まる PR タイトルを使うよう指示するため、PR はタスクに自動で紐づきます。

初期版はタスク実行、進捗同期、キャンセル、永続化された実行記録からの復旧に対応します。チャット、ローカルディレクトリ、添付ファイル、リモート QCA Agent の新規作成は未対応です。詳細は [README](https://github.com/multica-ai/multica/blob/main/server/cmd/qoder-runtime/README.md) を参照してください。

## ランタイムがオフラインのときの確認手順

次の順に確認します。

1. `multica daemon status` を実行し、デーモンが起動していることを確認する。
2. `multica daemon logs -f` を実行し、ログイン、ネットワーク、ツール検出のエラーを確認する。
3. 同じ実行環境で `command -v <ツールコマンド>` を実行し、デーモンがコマンドを見つけられることを確認する。
4. Multica の**ランタイム**ページを開き、対象のコンピュータと対応する AI コーディングツールがオンラインと表示されているか確認する。
5. ツールのインストール直後、パスの変更直後、プロファイルの更新直後は `multica daemon restart` を実行する。

それでも解決しない場合は[トラブルシューティング](/troubleshooting)を参照してください。
