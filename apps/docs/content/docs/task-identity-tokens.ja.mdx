実行アイデンティティトークンは、エージェントが社内システム（ERP、管理画面、wiki）に**その実行をトリガーした本人**としてアクセスできるようにします。共有サービスアカウントを経由しません。

クレーム時にサーバーが、その実行の説明責任を負う人物を記した短命の JWT に署名し、デーモンがそれをエージェントプロセスに注入します。エージェントはそのトークンを社内システムに提示し、システムはその人物からのリクエストとして扱い、すでにその人物に設定済みの権限を適用します。

設定しなければ無効です。未設定のデプロイはこれまでとまったく同じ挙動になり、**アイデンティティトークン**タブも非表示のままです。

<Callout type="info">
これはセルフホスティング向けの機能です。署名されるのは**別の信頼ドメイン**の資格情報 —— Multica の外にあり、それを受け入れることを選んだシステム向けのものです。エージェントの Multica 自身の API へのアクセスは変わらず、オーナー権限の範囲に限定されます。
</Callout>

## サービスアカウントでは足りない理由

エージェントを社内システムにつなぐと、通常はサービスアカウントを発行することになり、それは同時に 2 つを壊します。

- **権限が 1 段階に潰れる。** 全員のエージェントが同じ固定の身元で動き、若手エンジニアのエージェントもサービスアカウントが到達できるものすべてに到達できてしまいます。
- **監査が匿名になる。** 社内システムに残るのは「ボットがやった」という記録だけ。誰が依頼したのかが失われますが、それこそ監査が最も必要とする一点です。

実行アイデンティティトークンはこのトレードオフを取り除きます。あなたの権限モデルは変わりません。システムはこれまで通り、これが誰かを確認し、その権限を適用し、その名前を記録します —— 受け取るのが共有ボットではなく実在の人物になるだけです。

## 仕組み

1. **人の操作またはスケジュールが実行を開始する** —— タスクの割り当て、コメント、委任、定期実行。
2. **サーバーが承認した人物を確認し**（実行の帰属情報から）、エージェントが有効化した各アイデンティティトークンについて、その人物を `sub` に、実行するエージェントを `act_*` クレームに記して JWT に署名します。
3. **デーモンがトークンを注入する** —— テンプレートで指定された変数名（例: `BOT_TOKEN_ERP`）でエージェントプロセスの環境に入れます。
4. **エージェントがあなたのシステムを呼ぶ** —— トークンを bearer 資格情報として付けて。
5. **あなたのシステムがトークンを検証する** —— 公開された公開鍵で署名を検証し、`sub` を自前のユーザーレコードにマッピングし、そのユーザーの既存の権限と監査を適用します。

1〜3 は Multica 内で行われ、4〜5 が[あなたが構築する連携](#2つの連携パス)です。Multica があなたのシステムに対して権限を得ることは一切ありません —— 誰が要求し、どのエージェントが代行しているかを検証可能な形で述べるだけです。

<Callout type="info">
正確に言えば、これは [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693) の意味での**委任によるユーザーなりすまし**です。`sub` は委任する人物、`act_sub` / `act_name` はその代理として実行するエージェントです。GitHub Actions OIDC のようなワークロード証明**ではなく**、委任が伴う信頼上の義務を前提にレビューすべきものです。
</Callout>

## 誰が身元を得るか

身元は**実行をトリガーした人**、定期実行では**スケジュールトリガーの作成者**に属します。各エージェントの委任は `originator_user_id` に同じ人物を保持する必要があります。タスクの作成者、エージェントの所有者、ルールの公開者、後からスケジュールを編集した人に置き換えることはできません。実行が取得される時点でも、その人物はワークスペースのメンバーである必要があります。

| 出所 | 署名 |
| --- | --- |
| `direct_human` | 操作したメンバーとして署名 |
| `trigger_owner` | 実際の定期実行を確認した場合のみ、スケジュールを作成したメンバーとして署名 |
| `delegation`、`comment_source` | すべての委任が許可された根の人物を保持している場合のみ |
| webhook の `trigger_owner`、`rule_owner`、`owner_fallback`、`backfill`、`unattributed` | なし |

`run_only` と `create_issue` の両モード、および根の実行が完了した後の委任先にも対応します。出所が欠落している、途中で人物が変わった、作成者を確認できない場合はトークンを発行しません。実行は継続しますが、その資格情報が必要な操作は拒否されます。

トークンは、注入できると宣言した daemon（`task-identity-tokens-v1`）に対してのみ署名されます。機能を有効化する前に daemon を更新してください —— 古い daemon 向けに発行すると、誰も受け取っていない発行だけが監査に残ります。

署名が成功するたびに、アクティビティログに `agent_task_tokens_issued` 行が書き込まれます —— 説明責任者、エージェント、task、各トークンの `jti` と有効期限。そして fail-closed です。この行が書けなければトークンは発行されません。

## 2つの連携パス

この機能には異なる 2 種類の読者がいて、それぞれリポジトリに対応するガイドがあります。

### 1. 有効化する（運用者）

ワークスペースのオーナーまたは管理者が 2 ステップで有効化します。

1. **サーバーを設定する。** `MULTICA_TASK_TOKEN_PRIVATE_KEY`（PEM 署名鍵）と `MULTICA_TASK_TOKEN_TEMPLATES`（何を、どの変数に、どのクレームで署名できるかを定義する JSON カタログ）を設定します。[環境変数](/environment-variables)を参照。片方だけの設定は起動エラー、両方未設定なら機能はオフです。
2. **エージェントごとに有効化する。** **設定 → エージェント →** 対象のエージェント **→ アイデンティティトークン** を開き、そのエージェントに必要な分だけオンにします。カタログはサーバー設定にのみ存在するため、UI は運用者が許可した範囲から選べるだけで、何を署名できるかを定義することはできません。

カタログ形式、補間変数、`allowed_domains` 許可リスト、セキュリティ境界（影響範囲、サーバー侵害が何をもたらすか、鍵ローテーション）、トラブルシューティングを含む運用者向け完全ガイドは、リポジトリの [`TASK_IDENTITY_TOKENS.md`](https://github.com/multica-ai/multica/blob/main/TASK_IDENTITY_TOKENS.md) にあります。

<Callout type="warn">
`sub` は完全な企業メールをデフォルトにし、検証済みの企業メールを前提条件としてください —— 信頼チェーン全体の根は Multica が保持するそのアドレスです。メールのローカル部分にマッピングする場合は、必ずテンプレートの `allowed_domains` と組み合わせ、自社ドメインだけが署名されるようにします。
</Callout>

### 2. トークンを検証する（受け側システムの開発者）

これらのトークンを受け取るシステムは、Multica が認証なしで公開する JWK Set で検証します。

```
GET https://<あなたの-multica-host>/.well-known/jwks.json
```

主流の JWT ライブラリはこれを直接消費できます。社内システムが API ゲートウェイ（Kong、APISIX、nginx、クラウドゲートウェイ）の背後にあるなら、検証はしばしばゼロコードです。ゲートウェイの bearer-JWT 検証を、期待する `iss` とこの URL（`jwks_uri`）に向けるだけです。

連携そのものはセキュリティ境界です —— アルゴリズム許可リストの固定、`sub` を自動プロビジョニングせずローカルユーザーにマッピング、監査証跡に人物と代行エージェントの両方を記録すること。ステップバイステップのガイド、動作する検証コード、そして実際に刺さる落とし穴は [`TASK_IDENTITY_TOKENS_AI.md`](https://github.com/multica-ai/multica/blob/main/TASK_IDENTITY_TOKENS_AI.md) にあり、あなたのレガシーコードベース内で作業する AI エージェントに渡すために書かれています。

<Callout type="warn">
検証側で明示的なアルゴリズム許可リストを固定してください。トークンが自称する `alg` を信頼する検証側は簡単に偽造されます —— `alg: none`、または公開鍵を HMAC 秘密鍵として使う `HS256`。公開 JWKS があるため、対称アルゴリズムを許可するとこの 2 つはただ同然で成立します。
</Callout>
