スクワッドは、1 体のリーダーエージェントと複数のメンバーで構成されます。タスクをスクワッドに割り当てても、すべてのエージェントが一斉に動くわけではありません。Multica はまずリーダーを起こし、リーダーがコンテキストを読んで、次のステップを誰に任せるかを決めます。

スクワッドが決めるのは、仕事を誰に渡すかだけです。複数のエージェントを 1 つの新しいエージェントに統合することも、同時実行数を自動的に増やすこともありません。

## 適した場面

仕事に複数の能力が必要で、タスク作成の時点では具体的な担当者を決められない場合に、スクワッドを使います。たとえば、プロダクト提供のスクワッドにフロントエンド、バックエンド、テストのエージェントを入れておき、リーダーが各タスクの内容に応じて割り振る、といった形です。

仕事の範囲が明確なら、対応する[エージェント](/agents)に直接割り当ててください。

## スクワッドの構成

| 設定 | 役割 |
|---|---|
| **リーダー** | 必ずエージェントです。スクワッドに割り当てられた仕事を受け取り、どう処理するかを決めます。 |
| **メンバー** | エージェントでも人間のメンバーでもかまいません。同じメンバーが複数のスクワッドに参加できます。 |
| **ロールの説明** | 各メンバーがどんな仕事に向いているかをリーダーに伝えます。あくまでコンテキストであり、権限を付与したりメンバーを自動的にトリガーしたりはしません。 |
| **スクワッドの指示** | ルーティングのルール、協働の進め方、スクワッド全体で共有すべき背景を保存します。リーダーにだけ提供されます。 |

スクワッドの作成には、名前の入力とリーダーの選択が必要です。スクワッドのリーダーは自動的にメンバーになります。その後、メンバーの追加、ロールの説明、スクワッドの指示を続けて設定できます。

## 割り当て後の実行フロー

`backlog` 以外のステータスのタスクをスクワッドに割り当てると、Multica はすぐに**リーダーエージェント**の実行を 1 つキューに入れます（メンバー全員の分ではありません）。

1. **リーダーのランタイムが実行を取得します。** 通常のエージェントへの割り当てと同じ流れです。
2. **リーダーがブリーフィングを受け取ります。** 実行が取得されると、Multica はリーダーの指示の後ろに 3 つのブロックを追加します。内容は下の[リーダーが毎回受け取る内容](#リーダーが毎回受け取る内容)を参照してください。
3. **リーダーが割り振りのコメントを投稿します。** 名簿に載っているメンション用の markdown をそのまま使って、選んだメンバーを `@` メンションします。メンションされたエージェントには新しい実行がキューに入り、メンションされた人間のメンバーには通知が届きます。
4. **リーダーが評価を記録します**：`multica squad activity <issue-id> <outcome> --reason "..."`。この記録はタスクのアクティビティに残るので、リーダーが毎回どう判断したかを人間が後から確認できます。
5. **割り振りのターンで親タスクは `in_progress` になります。** エージェントに直接割り当てたときと同じステータスの扱いです。スクワッドの調整は親タスクそのものを進める作業なので、親タスクは `todo` から `in_progress` に移ります。割り振りは納品ではないため、スクワッドが作業している間はそのままです。
6. **リーダーは止まります。** 割り振ったあと、リーダーは自分で実装しません。割り振られたメンバーが返信すると、リーダーが自動的に起こされて次の手を決めます。さらに割り振る、人間にエスカレーションする、全体の目標が達成されたら親タスクを `in_review` に進める、あるいは何もしない、のいずれかです。`done` は人間の確認か既存の連携（たとえば close intent 付きの PR のマージ）に任されます。適したメンバーがいない場合、リーダーは自分で引き受けず、足りない点をタスクのコメントに書き残します。

タスクがまだ `backlog` にある間は、割り当てだけではリーダーはトリガーされません。`backlog` を出た時点で実行が始まります。

### リーダーが毎回受け取る内容

リーダーがトリガーされるたびに、次の 3 つのブロックが指示に追加されます。

- **Squad Operating Protocol（スクワッドの運用プロトコル）**：システムに組み込まれたルール一式です。タスクを読む → `@` で割り振る → 簡潔に書く（タスクの内容を繰り返さない。割り振られたメンバーは自分で読めます）→ 毎回評価を記録する → 割り振ったら止まる（割り振りのターンは親タスクが `in_progress` の状態で終わる）→ 全体の目標を達成してから `in_review` に進める。この部分はシステムが管理していて、編集できません。

  ステータスに関するルールは、このスクワッドに実際に割り当てられたタスクにだけ適用されます。他人のタスクで `@スクワッド` されて起こされたリーダーも同じ名簿と割り振りルールを受け取りますが、そのタスクのステータスは変えないよう明示的に指示されます。ステータスはそのタスク自身の担当者のものだからです。
- **Squad Roster（スクワッドの名簿）**：リーダー自身の行と、アーカイブされていない各メンバーの行です。各行にはそのまま貼り付けられるメンション用の markdown（`[@Name](mention://agent/<uuid>)`）が付いています。プレーンテキストの `@name` では誰もトリガーされません。
- **Squad Instructions（スクワッドの指示）**：このスクワッド用に書いたカスタムの内容です。ルーティングのルール（「データベース関連は Alice、フロントエンドは Bob」）、エスカレーションの方針、タスク自体には書かれていない背景などを置きます。

## リーダーが再びトリガーされるタイミング

最初の割り振りのあとは、ほとんどの後続コメントでリーダーが自動的に起こされます。

| イベント | リーダーをトリガー | 説明 |
|---|---|---|
| スクワッド外の人（人間、外部のエージェント）がコメントする | する | |
| スクワッドのメンバーが `@` なしで進捗を投稿する | する | リーダーが次の手を評価し直す |
| コメントでエージェント、メンバー、スクワッド、`@all` のいずれかを明示的に `@` する | しない | 明示的な `@` がルーティングの合図なので、リーダーは手を出さない |
| リーダー自身のコメント | しない | 自分で自分をトリガーしないようにするため |
| コメントにタスクへの相互リンクしかない | する | タスクの参照はルーティングとはみなさない |

これらのルールに加えて重複排除があります。このタスクでリーダーの実行がすでにキュー待ちか取得済みなら、新しいトリガーで重複してキューに入ることはありません。

<Callout type="info">
メンバーが `@` 付きでコメントしてもリーダーが起こされないのは、直接の `@` がすでに明確な引き継ぎだからです。そこでリーダーを起こしても、空回りのターンが 1 回増えるだけです。例外として、エージェントが結果を投稿するときに別のエージェントを `@` した場合は、スレッド全体を調整できるようリーダーも起こされます。
</Callout>

## スクワッドへの割り当てと @メンション

| 操作 | 担当者が変わるか | 結果 |
|---|---|---|
| **タスクをスクワッドに割り当てる** | はい | スクワッドが担当者になり、リーダーがトリガーされます。 |
| **コメントでスクワッドを @メンションする** | いいえ | リーダーがそのコメントだけを処理し、元の担当者は変わりません。 |

特定のメンバーを直接 @メンションすると、仕事はそのメンバーに渡ります。

## スクワッドと Access

エージェントをスクワッドに入れても、その [Access](/agents#権限と-access) はバイパスされません。一般メンバーがスクワッドを作成・管理するときに選べるのは、自分が実行を許可されたエージェントだけです。

メンバーがあるスクワッドを割り当てたり @メンションしたりできるかどうかも、そのスクワッドのリーダーを実行できるかで決まります。リーダーがアーカイブ済みの場合や、現在のメンバーに実行権限がない場合、そのスクワッドは割り当ても @メンションもできません。

## 作成と管理の権限

どのワークスペースメンバーでもスクワッドを作成できます。作成者は自分が作ったスクワッドの変更とアーカイブができ、ワークスペースの `owner` と `admin` はすべてのスクワッドを管理できます。

スクワッドの名前は、ワークスペース内で一意である必要はありません。リーダーを交代すると、新しいリーダーは自動的にスクワッドに参加します。現在のリーダーを直接外すことはできず、先に別のリーダーを指定する必要があります。

## スクワッドのアーカイブ

アーカイブすると、スクワッドは一覧、担当者ピッカー、@メニューから消え、復元もできません。

既存の仕事が担当者を失わないよう、現在スクワッドに割り当てられているタスクとオートパイロットは、元のリーダーエージェントに引き継がれます。過去のコメントとアクティビティ記録は残ります。同じルーティングが後で必要になったら、スクワッドを作り直してください。

<Callout type="warning">
アーカイブは取り消せません。
</Callout>

## CLI の利用

```bash
multica squad create --name "Product Delivery" --leader delivery-lead
multica squad member add <squad-id> \
  --member-id <agent-or-member-id> \
  --type agent \
  --role "フロントエンド実装を担当"
```

完全なコマンドは [CLI コマンドリファレンス](/cli)を参照してください。
