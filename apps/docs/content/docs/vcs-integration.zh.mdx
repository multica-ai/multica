<Callout type="warn">
**仅适用于自部署的 Multica。** 此集成只在你自己部署 Multica 时可用，Multica 云端不提供；自部署通常是为了让 Multica 能访问你内网里的 Git 实例。服务端需要开启 `MULTICA_VCS_INTEGRATION_ENABLED=true` 并设置 `MULTICA_VCS_SECRET_KEY`，否则 **设置 → 代码** 里不会出现这一行。
</Callout>

Multica 按工作区连接自托管的 Git 代码托管：Forgejo、Gitea 或 GitLab。连接后，分支名或标题中包含任务编号（例如 `MUL-123`）、或正文中在关闭关键字后写出该编号（`Closes MUL-123`）的 Pull Request（GitLab 为 Merge Request）会自动关联到对应的[任务](/issues)，出现在任务侧栏的 **Pull requests** 中。任务的所有关联 PR 都合并后，任务改为工作区选定的状态（默认为"已完成"）。head commit 的 CI 以检查条的形式显示在卡片上。

这些代码托管与 GitHub 并行工作，一个工作区可以同时连接多个。

<Callout type="info">
与 GitHub 不同，这些代码托管没有 App 模型。每个工作区保存自己的实例地址和访问令牌，并在其仓库或组织上注册 Webhook。令牌和 Webhook 密钥均加密存储。
</Callout>

## 前置条件（服务端）

先为该部署开启此集成。它默认关闭，未开启时该板块不会出现：

```sh
MULTICA_VCS_INTEGRATION_ENABLED=true
```

官方自部署 `docker compose` 文件（`docker-compose.selfhost.yml`）已经设置了这一项。

再设置一个 base64 编码的 32 字节密钥，供服务端加密存储的凭据。未设置时，连接表单将不可用。

```sh
openssl rand -base64 32
```

```sh
MULTICA_VCS_SECRET_KEY=<base64 32 字节密钥>
```

两者都必需：开关决定是否提供该功能，密钥用于加密存储的令牌与 Webhook 密钥。连接、Webhook、轮换都要求两者同时满足。

设置 `MULTICA_PUBLIC_URL` 为服务端的公网基础地址，Multica 即可直接给出可粘贴的 Webhook 地址；否则界面只显示 Webhook 路径，需自行拼接来源地址。

## 连接工作区

<Steps>
<Step>
在代码托管中创建具备仓库读取权限的访问令牌：

- **Forgejo / Gitea**：设置 → 应用。
- **GitLab**：具备 `read_api` 权限的个人（或群组/项目）访问令牌。
</Step>
<Step>
在 Multica 中打开 **设置 → 代码**，在 **自托管 Git** 一行点击 **连接**。
</Step>
<Step>
选择**提供方**，填写实例地址（例如 `https://forgejo.example.com`）和访问令牌，点击 **连接**。Multica 会先用该令牌访问实例进行校验，再保存。
</Step>
<Step>
复制连接后显示的 **Webhook 地址** 与 **Webhook 密钥**。
</Step>
</Steps>

<Callout type="warn">
Webhook 密钥只显示一次，请在离开页面前复制。重新连接同一实例会轮换令牌与密钥。
</Callout>

### 实例使用私有 CA

如果点击 **连接** 后提示提供方的证书 "is signed by a certificate authority this server does not trust"，说明实例的 HTTPS 证书由内部 CA 签发（或是自签名证书），而 Multica 服务端不信任这个 CA。需要由服务端管理员把该 CA 加入后端的信任库：使用 Helm 时设置 `backend.extraCACerts.configMap`；使用 Docker Compose 时挂载 CA 并设置 `SSL_CERT_DIR`。具体步骤见 [Private CA certificates](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING_ADVANCED.md#private-ca-certificates-optional)。后端还会把该 CA 下发给守护进程，使守护进程的 git 也能克隆同一实例上的仓库。

Multica 不提供跳过证书校验的选项，因为连接请求会携带你的访问令牌。如果提示证书与主机名不匹配，或证书校验失败（例如已过期），需要修复证书本身，信任 CA 解决不了。

## 注册 Webhook

在仓库上注册；要覆盖所有仓库，就注册在组织或群组上。

<Tabs items={["Forgejo / Gitea", "GitLab"]}>
<Tab value="Forgejo / Gitea" id="forgejo-gitea">

设置 → Webhook → 添加 Webhook → Forgejo/Gitea：

- **目标 URL**：上一步的 Webhook 地址。
- **HTTP 方法** `POST`，**内容类型** `application/json`。
- **密钥**：Webhook 密钥（用于校验 `X-Gitea-Signature` HMAC）。
- **触发事件**：勾选 **Pull Request**，并勾选 **Commit Status** 以镜像 CI。

</Tab>
<Tab value="GitLab" id="gitlab">

设置 → Webhooks：

- **URL**：Webhook 地址。
- **Secret token**：Webhook 密钥（作为 `X-Gitlab-Token` 发送并逐字比对）。
- **触发器**：启用 **Merge request events**，并启用 **Pipeline events** 以镜像 CI。

</Tab>
</Tabs>

Multica 会用存储的密钥校验每次投递，因此没有匹配密钥的 Webhook 会被拒绝。

## 镜像的内容

- **Pull / Merge Request** —— open、closed、merged、draft 状态，以及作者、分支和（在代码托管提供时）diff 统计。
- **任务关联** —— 标题或分支中的编号会将 PR 关联到任务，正文中的编号只有紧跟关闭关键字时才会关联；正文中的普通提及不会建立任何关联。任务的所有关联 PR（包括 GitHub 与自托管平台上的）都合并后，任务会改为工作区选定的状态，遵循与 [GitHub](/github-integration) 相同的设置和规则。连接平台后，本页也会显示同一项 **PR 合并后，任务状态改为** 设置。
- **CI** —— Forgejo/Gitea 的提交状态与 GitLab 的流水线会汇总为 head commit 的通过/失败/进行中检查条。

## 智能体创建 Pull Request

智能体创建 PR 不需要在 Multica 中做任何代码托管配置。智能体在运行时中检出仓库，用运行时主机自己的 Git 凭据推送分支和创建 PR。要让智能体在某个代码托管上工作，只要守护进程所在的主机能通过它的认证（例如 SSH 部署密钥，或主机 Git 凭据助手里的令牌），再像往常一样添加仓库地址。仓库检出支持任意 Git URL，不需要按提供方单独配置。
