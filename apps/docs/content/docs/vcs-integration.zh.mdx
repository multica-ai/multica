<Callout type="warn">
**仅适用于自部署的 Multica。** 此集成只在你**自己部署 Multica** 时可用，Multica 云端不提供。这里的「自托管」指的是 **Multica 本身自部署**——通常是为了让它能访问你自己网络内的 Git 实例。需要服务端运维开启（`MULTICA_VCS_INTEGRATION_ENABLED=true`）并设置 `MULTICA_VCS_SECRET_KEY`；在此之前，设置 → 代码里不会出现该行。
</Callout>

自部署的 Multica 按工作区连接 **Forgejo**、**Gitea**、**GitLab** 或官方 **腾讯工蜂**。连接后，任何在分支名或标题中包含任务编号（例如 `MUL-123`）、或在正文的关闭关键字后写出该编号（`Closes MUL-123`）的 Pull Request（GitLab 为 Merge Request）都会**自动关联**到对应的 [任务](/issues)，出现在任务侧栏的 **Pull requests** 中；任务的所有关联 PR 都合并后，任务会改为工作区选定的状态（默认「完成」）。Forgejo/Gitea 和 GitLab 的 head commit CI 会以检查条的形式显示在卡片上。

这些代码托管与 GitHub 并行工作：一个工作区可任意组合使用。

<Callout type="info">
与 GitHub 不同，这些代码托管没有「App」模型。每个工作区保存自己的实例地址和访问令牌，并在其仓库或组织上注册 Webhook。令牌和 Webhook 密钥均加密存储。
</Callout>

## 前置条件（服务端）

先为该部署开启此集成。它默认关闭，未开启时该板块不会出现：

```sh
MULTICA_VCS_INTEGRATION_ENABLED=true
```

官方自部署 `docker compose` 文件（`docker-compose.selfhost.yml`）已为你设置好。

再设置一个 base64 编码的 32 字节密钥，供服务端加密存储的凭据。未设置时，连接表单将不可用。

```sh
openssl rand -base64 32
```

```sh
MULTICA_VCS_SECRET_KEY=<base64 32 字节密钥>
```

两者都必需：开关决定是否提供该功能，密钥用于加密存储的令牌与 Webhook 密钥。连接、Webhook、轮换都要求两者同时满足。

设置 `MULTICA_PUBLIC_URL` 为服务端的公网基础地址，Multica 即可直接给出可粘贴的 Webhook 地址；否则界面只显示 Webhook 路径，需自行拼接来源地址。

## 连接工作区

1. 在代码托管中创建具备仓库读取权限的访问令牌：
 - **Forgejo / Gitea**：设置 → 应用。
 - **GitLab**：具备 `read_api` 权限的个人（或群组/项目）访问令牌。
2. 在 Multica 中打开 **设置 → 代码**，在 **Git 代码托管** 一行点击 **连接**。
3. 选择**提供方**，填写实例地址（例如 `https://forgejo.example.com`）和访问令牌，点击 **连接**。Multica 会先用该令牌访问实例进行校验，再保存。
4. 复制连接后显示的 **Webhook 地址** 与 **Webhook 密钥**。

<Callout type="warn">
Webhook 密钥只显示一次，请在离开页面前复制。重新连接同一实例会轮换令牌与密钥。
</Callout>

### 实例使用私有 CA

如果点击 **连接** 后提示提供方的证书 "is signed by a certificate authority this server does not trust"，说明实例的 HTTPS 证书由内部 CA 签发（或是自签名证书），而 Multica 服务端不信任这个 CA。需要由服务端管理员把该 CA 加入后端的信任库：使用 Helm 时设置 `backend.extraCACerts.configMap`；使用 Docker Compose 时挂载 CA 并设置 `SSL_CERT_DIR`。具体步骤见 [Private CA certificates](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING_ADVANCED.md#private-ca-certificates-optional)。

Multica 不提供跳过证书校验的选项，因为连接请求会携带你的访问令牌。如果提示证书与主机名不匹配，或证书校验失败（例如已过期），需要修复证书本身，信任 CA 解决不了。

## 注册 Webhook

在仓库（或组织/群组，以覆盖所有仓库）：

**Forgejo / Gitea** —— 设置 → Webhook → 添加 Webhook → Forgejo/Gitea：

- **目标 URL**：上一步的 Webhook 地址。
- **HTTP 方法** `POST`，**内容类型** `application/json`。
- **密钥**：Webhook 密钥（用于校验 `X-Gitea-Signature` HMAC）。
- **触发事件**：勾选 **Pull Request**，并勾选 **Commit Status** 以镜像 CI。

**GitLab** —— 设置 → Webhooks：

- **URL**：Webhook 地址。
- **Secret token**：Webhook 密钥（作为 `X-Gitlab-Token` 发送并逐字比对）。
- **触发器**：启用 **Merge request events**，并启用 **Pipeline events** 以镜像 CI。

Multica 会用存储的密钥校验每次投递，因此没有匹配密钥的 Webhook 会被拒绝。

## 镜像的内容

- **Pull / Merge Request** —— open、closed、merged、draft 状态，以及作者、分支和（在代码托管提供时）diff 统计。
- **任务关联** —— 标题或分支中的编号会将 PR 关联到任务，正文中的编号只有紧跟关闭关键字时才会关联；正文中的普通提及不会建立任何关联。任务的所有关联 PR（包括 GitHub 与自托管平台上的）都合并后，任务会改为工作区选定的状态，遵循与 [GitHub](/github-integration) 相同的设置和规则。连接平台后，本页也会显示同一项 **PR 合并后，任务状态改为** 设置。
- **CI** —— Forgejo/Gitea 的提交状态与 GitLab 的流水线会汇总为 head commit 的通过/失败/进行中检查条。

## 智能体创建 Pull Request

创建 PR 无需在 Multica 中进行任何代码托管配置。智能体在运行时中检出仓库，并使用运行时主机自身的 Git 凭据推送分支和创建 PR。要让智能体在某个代码托管上工作，确保 daemon 主机能对其完成认证即可——例如 SSH 部署密钥，或主机 Git 凭据助手中的令牌——再像往常一样添加仓库地址。仓库检出支持任意 Git URL，因此无需提供方专属配置。

## 腾讯工蜂

在提供方中选择 **腾讯工蜂**，官方实例地址为 `https://git.code.tencent.com`。
在工蜂账号设置中创建 **Private Token**，确保账号可以访问目标仓库；Multica
通过 `/api/v3/user` 校验令牌。工蜂官方服务也可接入自部署的 Multica，
不需要自建工蜂实例。

连接后直接选择 **工蜂仓库**。Multica 会自动配置 MR Webhook，并在后台分页导入已有 MR。令牌需要有读取目标仓库和管理 Webhook 的权限；Multica 的公开地址需要能被工蜂通过 HTTPS 访问。在 **添加仓库 → 从工蜂选择** 中选择仓库，还会将克隆地址加入工作区，供智能体使用。

仓库选择器会显示同步进度和权限错误。点击 **重新同步** 可重新导入完整历史并修复 Webhook。重新生成密钥会更新已注册的 Webhook，不会重复创建。停止同步会移除已注册的 Webhook、保留已镜像的 MR；断开连接会删除该连接及其镜像数据。若令牌失效导致远程 Webhook 清理失败，连接仍会移除，并提示在工蜂中手动删除剩余 Webhook。若需手动配置，可重新生成密钥，用提供的地址和 token 启用 **Merge request** 事件。投递使用 `X-Event: Merge Request Hook` 和 `X-Token`。

创建、更新、关闭、重开及合并复用上述任务关联和状态流转规则。卡片使用仓库内的 `iid`，API 详情请求单独解析全局 `id`。API 刷新会补全作者，并恢复漏收事件。CI 检查及冲突信息会在 MR 事件、访问任务页面和后台定期扫描时刷新。检查结果属于当前源提交，支持 fork 分支；提交变化后不会沿用旧检查结果。刷新失败时，已有结果会标为过期。缺失的审批或合并策略信息不会通过冲突状态推断。

智能体使用运行时主机上的社区工具 [gongfeng-cli](https://github.com/studyzy/gongfeng-cli)。
官方 Multica CLI `v0.6.1` 可使用此集成：服务端会随任务下发 `multica-platform`
中的工蜂操作指引，无需定制运行时。运行时主机仍需单独配置 Git 凭据和工蜂 CLI 认证。
已在 Apple 芯片 Mac 上使用官方 CLI 和 Codex 验证任务执行、MR 创建与更新、
检查状态同步及合并后的任务完成；Windows 和其他智能体需要另做实机验收。
直接从原作者的 [v0.5.0 下载页](https://github.com/studyzy/gongfeng-cli/releases/tag/v0.5.0)
获取对应系统的程序，提供 macOS arm64、Linux x86_64 和 Windows x86_64 版，
无需安装 Go。已安装 Go 时，也可安装同一个固定版本：

```sh
go install github.com/studyzy/gongfeng-cli/cmd/gongfeng@v0.5.0
```

运行时自行配置 Git 凭据和工蜂 CLI 认证，服务端保存的令牌不会传给智能体。
CLI 支持 `GONGFENG_TOKEN` 或用户主目录中的 `~/.gongfeng.json`。认证文件以明文
保存令牌；macOS/Linux 权限应为 `0600`，Windows 应限制文件 ACL 为本人访问。
部分智能体会过滤环境变量，需要在实际运行时中确认
认证可用。不要把令牌放入命令参数、仓库文件或任务评论。

仓库内的配置可以覆盖 API 地址和凭据。调用时明确指定官方地址，写操作前核对账号：

```sh
gongfeng --base-url https://git.code.tencent.com user me --json
gongfeng --base-url https://git.code.tencent.com --project-id <namespace/project> mr list --json
```

明确地址不能限制 HTTP 重定向。在不可信仓库中使用前，仍需加固社区 CLI 的凭据
加载和重定向处理。

先查看 `gongfeng --base-url https://git.code.tencent.com --project-id <namespace/project> mr create --help`，创建时明确
`--source-branch`、`--target-branch`、`--title` 和 `--description`。
CLI 的 `show`、`update`、`accept` 使用全局 MR `id`，须从 `mr list --json` 获取，
不能直接传卡片上的 `iid`。

MR 操作显示运行时 CLI 认证的工蜂账号，不会自动切换为任务发起人。同一系统账号下
的多个 Multica profile 仍会共用 CLI 凭据。要按成员本人追溯，每个成员需要独立的
个人运行时环境和凭据；Git 提交作者、SSH 推送账号也需要分别配置。

Multica 读取检查结果，不会执行仓库测试。长期自动检查需要接入 CI 执行器，并向
工蜂回写当前源提交 SHA 的检查状态。
