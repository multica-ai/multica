[项目](/projects)资源告诉智能体这组工作会用到哪些代码，以及在哪里执行。资源会持续关联在项目上，不必在每条任务中重复粘贴仓库地址或本地路径。

目前支持两种资源：

| 资源 | 适用场景 | 执行位置 |
|---|---|---|
| **GitHub 仓库** | 团队共享的代码库，希望由运行时管理 checkout | 运行时管理的工作目录 |
| **本地目录** | 已经存在的 checkout、很大的仓库，或需要直接查看本地改动 | 指定电脑上的原目录 |

## 资源进入执行的方式

当智能体处理项目内的任务时，Multica 会把项目名称、项目描述和资源列表加入执行上下文，并在工作目录中写入 `.multica/project/resources.json`。

工作区关联的仓库列表始终包含在执行上下文中。项目关联的仓库在此基础上指明这组工作使用的代码和默认 ref。

本地目录只对绑定它的守护进程有效。本次执行所在的守护进程有匹配的本地目录时，智能体直接进入该目录工作；其他电脑仍使用项目中的 GitHub 仓库或工作区仓库。

## 添加 GitHub 仓库

打开项目，在 **资源** 中选择"添加资源"。可以选择已关联到工作区的仓库，也可以粘贴 Git URL。工作区仓库在 **设置 → 代码** 中维护；连接 GitHub 后，可在同一页面通过 **从 GitHub 选择** 导入 App 已授权的仓库。

仓库不限于 GitHub：任何运行时能访问的 Git URL 都可以作为仓库资源。自部署的 Multica 还可以在 **设置 → 代码** 连接自托管的 Forgejo、Gitea 或 GitLab，见[自托管 Git 代码托管](/vcs-integration)。

创建项目时，也可以直接在 **Repos** 中选择仓库。一个项目可以关联多个 GitHub 仓库。

资源中的 `ref` 可以指定后续 checkout 默认使用的分支、tag 或 commit。`default_branch_hint` 只向智能体提供默认分支提示，不会强制切换分支。

## 添加本地目录

添加本地目录的界面只在 Desktop 中提供，因为浏览器不能选择电脑上的文件夹。

<Callout type="warning">
**这是特殊情况下的选项，不要因为方便就选它。** `local_directory` 是给那些"不得不这么开发"的人准备的，典型是一个 checkout 就几十 GB 的游戏项目，不可能每来一次运行就重新 clone 一份。

如果你的目录只是一个能正常 clone 的普通 git 仓库，请用 `github_repo`：它默认走 worktree 模式，同一个仓库上的运行可以同时进行，数量不受限制。`local_directory` 默认同一时间只进行一次运行；如果这个目录本身是 git 仓库，可以主动开启 worktree 模式恢复并发（见[运行如何共享这个目录](#运行如何共享这个目录)）。拿不准时，先对照页首的两种资源。
</Callout>

打开项目的 **资源**，或者创建项目对话框里的 **本地目录** 标签页。项目还没建出来时，也能在这里做同样的选择。

</Step>

</Step>

预选只作用于你此刻正在关联的目录。之前关联好的目录仍然保持保存时的模式，已有配置不会在你不知情时被切换。

目录必须是绝对路径，已经存在，并且当前守护进程可以读取和写入。以下路径会被拒绝：系统根目录和盘符根（`/`、`C:\`）、用户主目录本身及各主目录的上级（如 `/Users`、`/home`、`/root`），以及 `/etc`、`/var`、`/tmp`、`/usr`、`/opt` 等系统目录。如果所选路径是符号链接，会先解析为真实路径再按同样的规则校验一次，串行锁也按真实路径生效。

每个项目在同一台守护进程上最多关联一个本地目录。团队中的不同电脑可以分别为同一个项目关联各自的目录。

<Callout type="warning">
在默认的 `in_place` 模式下，本地目录不是隔离环境：智能体会直接看到并修改当前分支和未提交的文件，Multica 也不会自动切换分支、stash、commit、push 或创建 PR。worktree 模式不一样，见下面的[运行如何共享这个目录](#运行如何共享这个目录)。
</Callout>

## 运行如何共享这个目录

本地目录有两种执行模式，按资源逐个设置。在资源面板里可以直接切换，CLI 用 `--execution-mode`。Desktop 里这两种模式显示为 **原地** 和 **并行**；API、CLI 和本页其余部分都使用标识符。

<LocalDirModeDemo />

<Tabs items={["in_place（原地，默认）", "worktree（并行）"]}>
<Tab value="in_place（原地，默认）" id="in-place">

智能体直接在你的目录里工作，同一时间只进行一次运行。两次运行使用同一个真实目录时，后到的运行进入 `waiting_local_directory`，等前一次释放目录后继续。两个路径经不同符号链接指向同一目录时，同样串行。

等待不会修改目录。等待中的运行可以取消，否则会一直等到目录可用。

普通的非 git 目录只能用这种模式：worktree 模式只面向 git 仓库。

</Tab>
<Tab value="worktree（并行）" id="worktree">

每次运行拿到你仓库的一个独立 [git worktree](https://git-scm.com/docs/git-worktree)，建在运行时自己的工作区目录里。同一目录上的运行并发执行，谁都不用排队，也都不会写你的工作副本。

这个目录必须是至少有一次提交的 git 仓库；不满足时运行会明确报错，不会悄悄退回串行。

那台机器上的运行时也必须实现了该模式。运行时在连接时会声明这项能力，Multica 只看这个声明，不看版本号：一个开发构建完全可能带着看起来足够新的版本号，却没有对应的实现。这个声明会被检查两次。保存资源时，只要那台机器的运行时没有声明该能力，保存就会被拒绝，并提示去升级那台机器上的 App；每次运行被真正领取时，还会按领取它的运行时再检查一次，所以资源保存之后才降级的机器，其运行会被带原因取消，不会悄悄在原目录里跑掉。选择 `worktree` 就是在要求隔离，Multica 不会拿"直接改你的工作副本"来兜底。

智能体看到什么、你拿回什么：

<Accordions type="multiple">
<Accordion title="智能体从你眼前的状态开始，不是从 HEAD 开始" id="starts-from-your-working-state">

你未提交的改动和未跟踪的文件会被回放进 worktree，所以它不会去 review 一份你已经不用的代码。你自己的工作副本、暂存区和 stash 列表都不会被动到。

如果这个状态无法忠实还原，包括未跟踪内容超出回放上限（2000 个文件 / 200 MiB），运行会直接失败，不会从一棵你认不出来的树开始。通常的解决办法是把还没被忽略的构建产物加进 gitignore 或清理掉。

</Accordion>
<Accordion title="结果是你仓库里的一个分支" id="result-is-a-branch">

分支按任务而不是按每次执行来分：`agent/<agent>/<issue>`（chat 则是 `agent/<agent>/chat-<session>`）。本次运行的**详情**面板里会显示分支名（可直接复制），也可以用 `git branch` 找到它。用 `git log` / `git diff` review，然后自己决定 merge 还是 cherry-pick，Multica 不会替你合并。

`<agent>` 由智能体名字得来：转成小写后只保留英文字母和数字，其余字符换成 `-`，最长 30 个字符；名字里没有英文字母和数字时写作 `agent`。所以"运营助手"处理 OPS-21 时，分支是 `agent/agent/ops-21`。`<issue>` 是小写的任务编号。

中途失败的运行同样会报告它的分支，因为它已经把智能体做出来的部分提交进去了。

</Accordion>
<Accordion title="后续对话接着上一轮继续" id="follow-ups-continue-the-branch">

同一个任务的下一条评论会重新 check out 这个分支，智能体站在自己刚交付的成果上继续做，不会从 `HEAD` 重新开始、把上一轮的改动落在另一个分支上。只有你在上一轮之后改动的部分会被重放上去，其余部分分支里已经有了。把分支 merge 掉之后，下一轮又会从你的 `HEAD` 重新开始。

同一个任务上有两次执行重叠时，后一个会从前一个的成果分叉到 `agent/<agent>/<issue>-<task>`，因为 git 规定一个分支只能有一棵 worktree。

</Accordion>
<Accordion title="提交到本地 HEAD 的改动和未提交的改动分开处理" id="committed-head-changes-stay-separate">

两轮之间在本地做的 pull 或提交不会重放到任务分支上，需要时把这些提交明确 merge 进去。上一轮记下了未提交的改动时，要在新的 `HEAD` 上比较这些改动，需要 Git 2.40 或更高版本。

这些旧改动和新的已提交基线冲突时，运行时会记一条警告，只对受影响的路径改用当前 `HEAD`；其他草稿照常增量比较。所以把其中一份草稿完成并提交，不会阻塞之后的运行，也不会把你没动过的草稿再次拿去和智能体的成果比较。你当前的改动和智能体的成果之间若有冲突，仍然交给智能体解决。

</Accordion>
<Accordion title="你的改动和智能体的成果冲突时，由智能体来解决" id="conflicts-are-resolved-by-the-agent">

如果你重写了智能体也重写过的那几行，git 无法判断谁对，这一轮就会在一棵带冲突的 worktree 上启动，并被要求先把 merge 做完（在那棵 worktree 里 `git status` 会列出未合并的文件）。

只要还有文件没合完，这一轮就什么都不交付：运行失败、worktree 保留，下一轮会再次把同样的改动送上来，你的修改不会被悄悄丢掉。

</Accordion>
<Accordion title="只有 Multica 自己的分支才会被续接" id="only-multica-branches-resume">

是否续接由归属记录决定，跟分支名无关：记录里既写了属于哪个会话，也写了这条分支当时停在哪个 commit。你自己建的、恰好叫 `agent/<agent>/<issue>` 的分支永远不会被 check out、被追加提交，也不会被当成上一轮的成果读取；已经不包含记录中那个 commit 的分支同样如此。所以把 Multica 的分支删掉再自己建一条同名的，或者把它 force-move 到别的历史上，都是安全的，运行会改用 `agent/<agent>/<issue>-<id>`。在已交付的分支上继续提交则是正常用法，续接照常，你的提交下一轮就在那里。

每条分支还会以一个属于自己的 baseline commit 开头，标记第一轮开始时的目录状态。后续正是靠这个 commit 辨认这条分支，`git diff <baseline>..<branch>` 也恰好就是智能体做的改动。

如果某一轮没能记录它的分支，比如中途失败、记录写不进去，或者把 worktree reset 到了"把你的改动带进分支的那个 commit"之前，这一轮会报失败并保留 worktree，后续几轮会另起一条分支，不去续接一条无法证明归属的分支。

</Accordion>
<Accordion title="不会静默丢东西" id="nothing-is-silently-lost">

智能体留下的未提交改动，会在 worktree 被移除前提交到那个分支上，运行中途失败时同样如此。

极少数情况下连这次提交都做不了，例如仓库开了 `commit.gpgSign` 而运行时拿不到签名密钥。这时 worktree 会被刻意保留，运行标记为失败，在你仓库里执行 `git worktree list` 就能看到存放这些改动的目录。

</Accordion>
<Accordion title="没有产生改动的运行不留下任何东西" id="no-changes-leave-nothing">

它的分支会被删除，不会作为一个空条目留在 `git branch` 里；但如果这是承载了之前几轮成果的任务分支，它一定会保留。

</Accordion>
<Accordion title="留在你仓库里的分支和隐藏 ref" id="what-stays-in-your-repo">

worktree 位于运行时的工作区目录内，会按[正常的清理周期](/daemon-runtimes#cleanup)回收。留在你仓库里的有两样东西：分支，以及每条分支对应的一个隐藏 ref（在 `refs/multica/local-state/` 下），记录这条分支归谁所有、以及上次续接时你目录里的内容。

隐藏 ref 不会出现在 `git branch` 里，可以用 `git for-each-ref refs/multica` 查看。Multica 删除分支时会一并删掉它；你自己删掉的分支所对应的 ref，会在下一次该仓库上有运行开始时被清理。也可以用 `git for-each-ref --format='%(refname)' refs/multica | xargs -n1 git update-ref -d` 一次性清掉。

</Accordion>
</Accordions>

<Callout type="warn">
**自托管运维注意：** 该模式的隔离由服务端强制（保存资源时检查一次，运行时每次领取执行时再检查一次），所以无论何时降级运行时都会被拦住。唯一拦不住的组合是：把服务端回滚到本功能之前的版本，同时还连着没有实现该模式的运行时。旧服务端没有这道门禁，而这样的运行时会忽略 `execution_mode`、直接在原目录里执行。只要还存在 `worktree` 资源，就不要把服务端回滚到本版本之前，除非那些机器上的运行时全部升级到位。
</Callout>

</Tab>
</Tabs>

## 执行期间写入的内容

除了智能体产生的代码改动，运行时还可能在目录中写入当前 AI 编程工具所需的说明文件，以及 `.multica/project/resources.json`。不希望它们进入版本控制时，加入 `.gitignore` 即可。

Multica 清理执行环境时不会删除关联的本地目录。智能体对该目录的改动，与你在终端中直接运行 AI 编程工具的改动性质相同，需要同样的审查。

## 使用 CLI 管理资源

```bash
# 创建项目时关联仓库
multica project create \
 --title "Agent UX" \
 --repo https://github.com/multica-ai/multica

# 查看和添加资源
multica project resource list <project-id>
multica project resource add <project-id> \
 --type github_repo \
 --url https://github.com/multica-ai/multica \
 --ref main

# 关联指定守护进程上的本地目录
multica project resource add <project-id> \
 --type local_directory \
 --local-path /absolute/path/to/repo \
 --daemon-id <daemon-id>

# 关联一个本地 git 仓库，并让每次运行在各自的 worktree 中并发执行
multica project resource add <project-id> \
 --type local_directory \
 --local-path /absolute/path/to/repo \
 --daemon-id <daemon-id> \
 --execution-mode worktree

# 为已有的本地目录切换模式
multica project resource update <project-id> <resource-id> --execution-mode worktree
multica project resource update <project-id> <resource-id> --execution-mode in_place

# 移除资源
multica project resource remove <project-id> <resource-id>
```

资源变更会影响之后创建的运行，不会改写已经结束的执行记录。
