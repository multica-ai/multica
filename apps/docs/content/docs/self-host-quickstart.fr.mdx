L'auto-hébergement de Multica comporte deux parties :

| Partie | Ce qu'elle exécute | Où elle se trouve |
|---|---|---|
| **Service Multica** | Web, API et PostgreSQL | Une machine sur laquelle Docker est installé |
| **Ordinateur** | Le daemon Multica et les outils de codage IA | L'ordinateur sur lequel les développeurs travaillent réellement |

Il peut s'agir de la même machine ou de machines distinctes. L'auto-hébergement ne remplace que la partie Multica Cloud.

Ce guide utilise le Compose de développement du dépôt. Les candidats à examiner et les déploiements existants suivent la [procédure de build local](https://github.com/AstralSolipsism/multica/blob/main/docs/local-builds.md).

## Avant de commencer

La machine qui exécute le service Multica a besoin de :

- Docker Engine ou Docker Desktop, avec `docker compose` fonctionnel
- Git, Make, curl et OpenSSL
- Les ports `3000` et `8080` libres sur la machine

Vérifiez d'abord que Docker et Compose sont disponibles :

```bash
docker info
docker compose version
```

Multica utilise Compose v2, invoqué via `docker compose`. L'ancien `docker-compose` v1 n'est pas pris en charge.

L'ordinateur doit également disposer d'au moins un [outil de codage IA](/providers) installé et connecté, comme Claude Code, Codex ou Cursor. Le CLI Multica est installé à l'étape 5.

<Step>

## Démarrer Multica [#1-démarrer-multica]

Sur la machine qui fera tourner le service :

```bash
git clone https://github.com/AstralSolipsism/multica.git
cd multica
make selfhost
```

Relancer `make selfhost` réutilise le `.env` et les volumes existants ; les secrets ne sont pas régénérés.

<Accordions>
<Accordion title="Ce que fait make selfhost au premier lancement" id="what-make-selfhost-does">

1. Crée `.env` à partir de `.env.example`
2. Génère un `JWT_SECRET` aléatoire, un mot de passe PostgreSQL et une `MULTICA_VCS_SECRET_KEY` (la clé de chiffrement des intégrations Git auto-hébergées)
3. Compile le backend et le frontend depuis ce checkout ; télécharge PostgreSQL et les images de base de build et d’exécution si nécessaire
4. Crée des volumes persistants et démarre les trois conteneurs
5. Attend que le backend commence à répondre aux vérifications d'état

</Accordion>
</Accordions>

<Callout type="info">
`make selfhost` et `make selfhost-build` compilent les deux applications localement avec la même version `dev-<sha>[-dirty]` et le SHA source complet. Les images applicatives ne sont jamais téléchargées. Cette commande démarre les services et les migrations du stack de développement.

Avant une commande Compose directe, exportez le `MULTICA_IMAGE_TAG` affiché au démarrage, ou inscrivez-le dans `.env`. Retirez un ancien tag épinglé avant un nouveau build de développement. Les candidats examinés utilisent `make candidate-images` avec le tag et le SHA approuvés, selon la [procédure de build local](https://github.com/AstralSolipsism/multica/blob/main/docs/local-builds.md).
</Callout>

</Step>
<Step>

## Vérifier que les services sont prêts [#2-vérifier-que-les-services-sont-prêts]

Vérifiez l'état des conteneurs :

```bash
docker compose -f docker-compose.selfhost.yml ps
```

`postgres` doit afficher `healthy`, et `backend` et `frontend` doivent être en cours d'exécution. Vérifiez ensuite le backend, la base de données et les migrations :

```bash
curl -fsS http://localhost:8080/readyz
```

La réponse attendue est :

```json
{"status":"ok","checks":{"db":"ok","migrations":"ok"}}
```

Le conteneur backend exécute les migrations de base de données à chaque démarrage, avant de servir les requêtes ; il n'y a aucune commande de migration manuelle à lancer.

</Step>
<Step>

## Choisir le mode d'accès [#3-choisir-le-mode-daccès]

<Tabs items={["Accès local", "Accès distant"]}>
<Tab value="Accès local">

Ouvrez directement [http://localhost:3000](http://localhost:3000). Vous n'aurez pas non plus besoin de fournir d'URL lorsque vous lancerez `multica setup self-host` plus tard.

</Tab>
<Tab value="Accès distant" id="remote-access">

Docker Compose lie `3000` et `8080` uniquement à `127.0.0.1`. Ne remplacez pas cette valeur par `0.0.0.0` pour exposer les ports sur l'Internet public ; utilisez plutôt un proxy inverse avec HTTPS.

L'exemple ci-dessous utilise deux domaines :

- `app.example.com` : l'application web Multica
- `api.example.com` : l'API, les vérifications d'état et les connexions des daemons

Définissez d'abord les URL publiques dans `.env` :

```bash
FRONTEND_ORIGIN=https://app.example.com
MULTICA_APP_URL=https://app.example.com
MULTICA_PUBLIC_URL=https://api.example.com
```

Avec cette configuration, tout le trafic du navigateur reste sur le domaine de l'application : les cookies ne passent jamais d'un domaine à l'autre et `COOKIE_DOMAIN` n'est pas nécessaire. Si le navigateur communique plutôt directement avec le domaine de l'API, vous devez la définir ; consultez [Variables d'environnement](/environment-variables).

Configurez ensuite le DNS et placez Caddy en proxy devant les ports locaux. Caddy obtient les certificats TLS et relaie les WebSockets.

<Tabs items={["Deux domaines", "Origine unique"]}>
<Tab value="Deux domaines">

```text
app.example.com {
    # Transmettre directement les WebSockets du navigateur au backend
    @ws path /ws /ws/*
    handle @ws {
        reverse_proxy 127.0.0.1:8080 {
            flush_interval -1
        }
    }

    # Tout le reste va au frontend, qui relaie les requêtes d'API et de connexion
    handle {
        reverse_proxy 127.0.0.1:3000
    }
}

api.example.com {
    reverse_proxy 127.0.0.1:8080 {
        flush_interval -1
    }
}
```

</Tab>
<Tab value="Origine unique">

```text
multica.example.com {
    # Sonde d'accessibilité du CLI : `multica setup` envoie un GET à <server-url>/health et
    # attend un 200 ; les anciennes versions web ne le relaient pas, il faut donc le router directement
    handle /health {
        reverse_proxy 127.0.0.1:8080
    }

    # WebSocket temps réel du navigateur : l'image web ne peut pas relayer les upgrades WS
    handle /ws {
        reverse_proxy 127.0.0.1:8080 {
            flush_interval -1
        }
    }

    # WebSocket de connexion longue du daemon : les daemons se connectent à {server-url}/api/daemon/ws
    # (et non /ws). Sans cette route, la négociation échoue et le daemon se rabat
    # silencieusement sur le polling
    handle /api/daemon/ws {
        reverse_proxy 127.0.0.1:8080 {
            flush_interval -1
        }
    }

    # Tout le reste va au frontend, qui relaie les requêtes d'API et de connexion
    handle {
        reverse_proxy 127.0.0.1:3000
    }
}
```

</Tab>
</Tabs>

L'**origine unique** (un seul domaine, ou un seul hôte avec un seul port, courant sur les petits serveurs) route explicitement vers le backend les chemins indispensables au daemon et laisse le frontend gérer le reste. Faites alors pointer les deux URL vers elle : `FRONTEND_ORIGIN` et `MULTICA_APP_URL` dans `.env`, puis `--server-url` et `--app-url` dans `multica setup self-host`.

Après avoir modifié `.env`, recréez les conteneurs avec `up -d` pour que la nouvelle configuration soit prise en compte :

```bash
docker compose -f docker-compose.selfhost.yml up -d
curl -fsS https://api.example.com/readyz
curl -fsS https://app.example.com/api/config | grep -o '"daemon_server_url":"[^"]*"'
```

La dernière commande affiche `daemon_server_url`, l'URL que les daemons utilisent pour joindre l'API. S'il affiche une adresse `localhost`, `.env` contient encore les valeurs locales par défaut : définissez explicitement `FRONTEND_ORIGIN` et `MULTICA_APP_URL` avec les URL publiques au lieu de vous appuyer sur les références `${FRONTEND_PORT}` copiées depuis `.env.example`, puis recréez les conteneurs.

<Accordions>
<Accordion title="Comment daemon_server_url est déterminée" id="how-daemon-server-url-is-resolved">

`MULTICA_DAEMON_SERVER_URL` si elle est définie, puis `MULTICA_PUBLIC_URL`, sinon l'URL de l'application (`MULTICA_APP_URL`, avec `FRONTEND_ORIGIN` en repli). Lorsque ni `MULTICA_APP_URL` ni `FRONTEND_ORIGIN` n'est défini, le champ est entièrement omis de la réponse (le grep n'affiche donc rien), même si `MULTICA_DAEMON_SERVER_URL` ou `MULTICA_PUBLIC_URL` est défini.

</Accordion>
</Accordions>

<Callout type="warning">
`docker compose restart` ne fait que redémarrer les conteneurs existants et ne relit pas `.env`. Après une modification de configuration, exécutez `docker compose -f docker-compose.selfhost.yml up -d` pour relire `.env`.
</Callout>

## Se connecter et créer un espace de travail [#4-se-connecter-et-créer-un-espace-de-travail]

Ouvrez `http://localhost:3000` en local, ou le `https://app.example.com` que vous venez de configurer, puis saisissez votre adresse e-mail pour demander un code de vérification.

Aucun service d'e-mail n'est configuré par défaut. Après avoir demandé un code, lisez-le dans les journaux du backend :

```bash
docker compose -f docker-compose.selfhost.yml logs backend \
  | grep "Verification code"
```

Les journaux contiennent une ligne comme celle-ci :

```text
[DEV] Verification code for you@example.com: 123456
```

Saisissez le code et créez votre premier espace de travail. Une fois Resend ou SMTP configuré, les codes sont envoyés par e-mail et les membres n'ont plus besoin de lire les journaux des conteneurs ; consultez [Configuration de l'authentification](/auth-setup).

<Callout type="warning">
Les déploiements auto-hébergés utilisent par défaut `APP_ENV=production`, qui désactive les codes de vérification fixes. Ne définissez pas `MULTICA_DEV_VERIFICATION_CODE` sur une instance publique.
</Callout>

</Step>
<Step>

## Connecter un ordinateur [#5-connecter-un-ordinateur]

Lancez les commandes ci-dessous sur **l'ordinateur qui fait tourner vos outils de codage IA**, qui n'est pas forcément le serveur qui fait tourner Docker.

<Callout type="warning">
Les exécutions disposent de toutes les permissions de l'utilisateur qui fait tourner le daemon : elles peuvent lire et écrire tout ce à quoi cet utilisateur a accès. Faites tourner le daemon sous un utilisateur Unix dédié, dans un conteneur ou dans une VM plutôt que sous votre compte personnel. Consultez le [modèle de sécurité](/security-model).
</Callout>

Installez d'abord le CLI Multica :

<Tabs groupId="os" persist items={["macOS / Linux", "Windows"]}>
<Tab value="macOS / Linux">

```bash
curl -fsSL https://multica.outlune.com/downloads/install.sh | bash
```

</Tab>
<Tab value="Windows">

Téléchargez `multica-cli-<version>-windows-<arch>.zip` depuis la source de distribution interne `https://multica.outlune.com/downloads/cli/v<version>/` (version : `https://multica.outlune.com/downloads/latest.json`), puis placez `multica.exe` dans votre `PATH`.

</Tab>
</Tabs>

Reliez ensuite le CLI à votre service. Choisissez l'endroit où tourne le service Multica :

<Tabs items={["Sur cet ordinateur", "Sur une autre machine"]}>
<Tab value="Sur cet ordinateur">

```bash
multica setup self-host
```

</Tab>
<Tab value="Sur une autre machine">

```bash
multica setup self-host \
  --server-url https://api.example.com \
  --app-url https://app.example.com
```

</Tab>
</Tabs>

Si le service tourne sur une autre machine, passez les deux URL configurées précédemment. La commande vérifie d'abord `<server-url>/health`, puis ouvre un navigateur pour terminer la connexion. Une fois la connexion effectuée, elle enregistre les identifiants en local et démarre le daemon. Une erreur `Server not reachable` à cette étape signifie que la sonde n'a pas obtenu de 200 sur `/health`. Trois causes sont possibles : le proxy transmet tout à une version web qui ne relaie pas ce chemin ; le proxy ne route pas du tout `/health` vers le backend ; ou une défaillance de plus bas niveau (DNS, TLS, pare-feu, délai d'attente dépassé, 5xx renvoyé par le backend). Consultez [Dépannage](/troubleshooting#multica-setup-reports-the-server-is-not-reachable).

Vérifiez la connexion :

```bash
multica daemon status
```

La sortie doit afficher :

- `Daemon: running`
- `Agents`, qui liste les outils de codage IA installés sur cette machine
- `Workspaces` supérieur à `0`

</Step>
<Step>

## Terminer la première exécution [#6-terminer-la-première-exécution]

De retour dans Multica, dès qu'un runtime en ligne apparaît dans la liste des runtimes, créez un agent et assignez-lui votre première tâche.

Lorsque l'exécution apparaît comme terminée et que la réponse de l'agent s'affiche dans la chronologie, le service auto-hébergé, l'ordinateur et l'outil de codage IA sont tous connectés. Pour le détail, consultez les étapes 3 à 5 du [démarrage rapide](/cloud-quickstart).

</Step>
</Steps>

## Commandes d'administration courantes

Lancez-les toutes depuis le répertoire du dépôt `multica` :

```bash
# Vérifier l'état
docker compose -f docker-compose.selfhost.yml ps

# Suivre les journaux du backend
docker compose -f docker-compose.selfhost.yml logs -f backend

# Appliquer les modifications de .env
docker compose -f docker-compose.selfhost.yml up -d

# Arrêter les services en conservant les volumes
docker compose -f docker-compose.selfhost.yml down
```

<Callout type="warning">
`docker compose down` conserve `pgdata` et `backend_uploads`. Ajouter `-v` supprime ces volumes, base de données comprise ; n'exécutez pas `docker compose down -v`, sauf si vous avez l'intention d'effacer l'instance.
</Callout>

## Mise à niveau

<Steps>
<Step>

### Préparer une mise à niveau

Compilez le candidat depuis le SHA complet approuvé du fork, vérifiez les versions backend/Web et les Image ID locaux, puis vérifiez la surcharge d'images avec le Compose existant de l'opérateur. Suivez la [procédure de build local](https://github.com/AstralSolipsism/multica/blob/main/docs/local-builds.md). Master planifie séparément l'arrêt des écritures, la sauvegarde, les migrations et les changements de service. Ne remplacez pas les réseaux, volumes ou paramètres de production par l'exemple du dépôt.

</Step>
<Step>

### Sauvegarder Postgres

Les migrations ne vont que vers l'avant ; faites donc un dump avant de mettre à niveau un déploiement auquel vous tenez :

```bash
docker compose -f docker-compose.selfhost.yml exec -T postgres \
  pg_dump -U multica multica > multica-backup.sql && gzip multica-backup.sql
```

Utilisez vos propres `POSTGRES_USER` / `POSTGRES_DB` de `.env` si vous avez modifié les valeurs par défaut `multica`. Les données résident dans le volume nommé `multica_pgdata`, qui survit à `docker compose down`, mais pas à `down -v`.

<Callout type="warning">
**Ne redirigez pas `pg_dump` directement vers `gzip` par un pipe.** Un shell renvoie le code de sortie de la *dernière* commande d'un pipeline : `pg_dump … | gzip > backup.sql.gz` se termine donc avec `0` même si le dump a échoué, ce qui laisse une archive de 20 octets parfaitement valide, mais vide. Rediriger d'abord vers un fichier fait compter le code de sortie de `pg_dump` lui-même, et `&&` ne compresse qu'un dump qui a réellement réussi.
</Callout>

</Step>
<Step>

### Appliquer le build local approuvé

Après autorisation de la fenêtre de maintenance par Master, appliquez la surcharge d'images locales vérifiée à la configuration Compose existante et exécutez les migrations selon la [procédure de build local](https://github.com/AstralSolipsism/multica/blob/main/docs/local-builds.md). Conservez les réseaux, volumes et paramètres d'exécution existants. La commande de démarrage de développement ne sert pas à mettre à niveau la production.

</Step>
<Step>

### Vérifier avec `/readyz`, pas `/health`

```bash
curl -s localhost:8080/readyz
# {"status":"ok","checks":{"db":"ok","migrations":"ok"}}
```

Toute réponse autre qu'un HTTP 200 avec les deux vérifications à `ok` signifie que la nouvelle version n'a pas terminé ses migrations ; consultez les journaux du backend avant de lui envoyer du trafic.

`/health` est une sonde de **vivacité** (liveness) : elle renvoie `{"status":"ok"}` tant que le processus tourne, y compris lorsque les migrations ont échoué. `/readyz` (`readyHandler`, enregistré dans `server/cmd/server/router.go` ; `/healthz` en est un alias) vérifie la base de données et l'ensemble des migrations appliquées : c'est donc elle qui détecte une mise à niveau ratée.

</Step>
</Steps>

<Accordions type="multiple">
<Accordion title="Votre .env n'est pas écrasé" id="your-env-is-not-overwritten">

`make selfhost` ne génère `.env` que lorsque le fichier est **absent**. Le relancer sur une installation existante laisse votre `JWT_SECRET`, votre mot de passe Postgres, vos paramètres d'e-mail et `FRONTEND_ORIGIN` exactement tels qu'ils étaient.

</Accordion>
<Accordion title="Mettre à niveau sur Kubernetes" id="kubernetes">

La publication Helm reste désactivée. Le chart source utilise des noms d'images locales non configurés et la politique `Never`. Ce projet utilise le Compose personnalisé existant et la procédure de build local.

</Accordion>
</Accordions>

## Problèmes courants

| Symptôme | À vérifier en premier |
|---|---|
| `/readyz` ne renvoie pas `ok` | Exécutez `docker compose -f docker-compose.selfhost.yml logs backend postgres`. |
| Aucun code de vérification n'arrive | Demandez un code, puis cherchez `Verification code` dans les journaux du backend. |
| `setup self-host` signale que le serveur est injoignable | Depuis l'ordinateur, envoyez une requête à `https://api.example.com/health` pour confirmer que le DNS, le TLS et le proxy inverse sont tous joignables. Un 404 signifie que le proxy envoie `/health` à une ancienne version web qui ne le relaie pas : routez-le vers le backend ([Dépannage](/troubleshooting#multica-setup-reports-the-server-is-not-reachable)). |
| Le daemon n'affiche rien sous `Agents` | Vérifiez que les outils de codage IA sont dans le `PATH` et connectés, puis exécutez `multica daemon restart`. |
| Les tâches restent en file d'attente | Exécutez `multica daemon status` pour confirmer que le daemon tourne et qu'il est connecté à l'espace de travail. |

Pour d'autres scénarios, consultez [Dépannage](/troubleshooting).
