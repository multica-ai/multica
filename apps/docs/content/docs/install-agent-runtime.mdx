A local runtime has two parts: the Multica daemon, and one AI coding tool it can invoke. Install only the tool you intend to use — you do not need all of them.

<Steps>
<Step>

## Sign in on your machine [#2-sign-in-on-your-machine]

After installing, launch the tool once in a terminal on its own and complete its sign-in or model provider setup. If the tool cannot complete requests in the terminal, the daemon's invocations fail the same way.

Those login credentials are stored locally by the tool itself. Multica never receives login tokens from Claude, Codex, Cursor, or any other CLI.

Below the minimum version, the daemon does not register the corresponding runtime:

A few tools need extra setup beyond signing in:

<Accordions type="multiple">
<Accordion title="Amp" id="amp">

Install the latest [Amp CLI](https://ampcode.com/docs/cli) on the daemon machine. Amp supports macOS, Linux and Windows through WSL; run the daemon inside WSL when using Windows. Set an Amp access token in `AMP_API_KEY` in the daemon or agent environment, following the official non-interactive setup. Interactive login and saved login sessions alone are not supported by this adapter. Do not put credentials in prompts or custom arguments.

After discovery, select the Amp runtime when creating an agent and assign a task. `MULTICA_AMP_PATH` overrides the executable. Leave the model field empty for Amp's default, or enter an Amp **mode** such as `high`; `MULTICA_AMP_MODEL` sets the daemon default. Amp manages the underlying models. `MULTICA_AMP_ARGS` and agent custom arguments accept `--settings-file`, `--features`, `--fast`, `--plugin-ready-timeout <seconds>`, `--timings`, `--visibility`, `--label`, and `--no-archive-after-execute`.

Multica runs `amp --execute --stream-json --executor local`, sends the prompt through stdin, and resumes only the saved thread ID. Amp reads `AGENTS.md` and project skills from `.agents/skills/`. Configure MCP in Amp itself. Managed MCP, live message supplements, `max_turns`, orbs and remote runners are unsupported. Use the task timeout to bound execution. Transport, mode and executor overrides are filtered; extra prompts, subcommands and unverified options fail before launch.

Missing installations and startup errors appear as failures. Missing `AMP_API_KEY` fails before startup. For authentication errors, replace the access token in the execution environment. Only a successful terminal `result` can publish a final answer; a clean exit or assistant `end_turn` alone cannot. Amp gets up to ten seconds to finish cleanup after its terminal result. If Multica then has to stop the process, it keeps the final answer and logs a warning; a native nonzero exit observed during the grace still fails. Amp-reported permission denials appear as transcript warnings. Check `amp.permissions` in the execution machine's Amp settings if approved commands are denied in unattended runs. Cancellation and timeout terminate the owned local process tree and retain the observed thread ID. [Amp background subagents](https://ampcode.com/docs/cli/streaming-json) may survive CLI exit on Amp's service; their remote cancellation is not available through this adapter. Avoid asynchronous subagents when strict cancellation is required, and inspect any remaining work in the saved Amp thread.

</Accordion>
<Accordion title="Factory Droid" id="droid">

Install the native Droid CLI using the [official instructions](https://docs.factory.com/droid-exec/overview). Multica supports Droid 1.8.0 or later on macOS, Windows, and glibc-based Linux; Alpine is unsupported. Sign in with `droid`, or set `FACTORY_API_KEY` in the daemon environment or the agent's custom environment. Keep credentials out of prompts and custom arguments.

After the daemon discovers `droid`, select the Droid runtime when creating an agent and assign it an issue. The run streams assistant and tool messages, then publishes the final response. Models use Droid's default unless you enter a model ID in Multica. Optional daemon overrides are `MULTICA_DROID_PATH`, `MULTICA_DROID_MODEL`, and `MULTICA_DROID_ARGS`. Reasoning effort can be set through custom arguments, such as `--reasoning-effort high`.

Runs use `droid exec --output-format stream-json --auto high`, read `AGENTS.md`, and discover skills in `.factory/skills/`. Multica forwards a saved session ID for continuation in the same working directory. If continuation fails before Droid confirms a session or uses a tool, Multica may retry once with a fresh session; authentication and network failures keep the existing session without retrying.

Custom arguments also accept Droid's tool filters, spec-mode settings, `--settings`, session tags, and `--disable-builtin-skills`. Configure MCP, hooks, plugins, custom Droids, and BYOK models in Droid itself. Multica does not manage that configuration or implement Mission orchestration, live message supplements, or `max_turns`; use the task timeout to bound execution. Transport, working-directory, model, session, and Mission overrides are filtered from custom arguments. Unknown options and extra positional prompts are rejected before startup. Native `stream-json` output is supported; the deprecated `stream-json` input mode is not used.

Droid's command policy can still reject a task under `--auto high`; completed edits remain in the working tree after a failure. Use the [official permission-rule commands](https://docs.factory.com/autonomy-and-safety/permission-rules) to check your execution machine's policy before assigning unattended tasks.

If Droid is missing, install it on the daemon machine or set `MULTICA_DROID_PATH` to its native executable. If authentication fails, sign in or replace the API key in the execution environment. Permission, provider, and protocol failures appear as failed runs; cancellation and timeout stop the owned process tree and report their respective final states. A clean exit without a completion event is a failure, and intermediate narration is never published as the final result.

</Accordion>
<Accordion title="CodeArts" id="codearts">

Verify the non-interactive path with `codearts run --model provider/model "Reply OK"`, not only the TUI. The current CodeArts CLI can let a custom provider work in the TUI while `run`, `models`, and `serve` still require [`CODEARTS_CLI_AK` / `CODEARTS_CLI_SK`](https://support.huaweicloud.com/usermanual-cli/codeartsagent_cli_0026.html). Multica can discover custom models from `~/.codeartsdoer/codearts_cli.json` or `.jsonc`, but agent runs use `codearts run` and therefore follow its authorization requirements.

</Accordion>
<Accordion title="DeepSeek Harness" id="deepseek-harness">

Install Node.js 20+ and run `npm install -g @deepseek-ai/dsh`, then give it the Multica runtime profile — the bundle that implements the `--stdio` protocol Multica drives, and the reason a bare `dsh` is not usable on its own. Set `DEEPSEEK_API_KEY` (or store it in dsh's own settings) before starting the daemon.

**Installing the profile.** Set `MULTICA_DSH_PROFILE_BUNDLE` to the bundle to install and the daemon adds it for you, or add it yourself with `dsh plugin --profile multica add <bundle>`. `<bundle>` is anything `dsh plugin` accepts — an npm package name, a directory, or a packed tarball — and Multica's own bridge lives at [multica-ai/dsh-multica-runtime](https://github.com/multica-ai/dsh-multica-runtime). It is not on a public npm registry yet ([multica#6936](https://github.com/multica-ai/multica/issues/6936)), so today a self-hosted team builds it from that repository and points the variable at the build directory, or at the tarball `npm pack` produces — the latter if the machine running the daemon is not the machine that built it. A package name becomes the simplest option once the bridge is published.

**Migrating an existing profile.** Back up the profile and follow the bridge repository's README to build a bundle compatible with your DSH version. Install that directory or tarball manually, then ensure `dsh.profile.bundles` loads `@multica-ai/dsh-runtime`: replace `dsh-profile-multica` if present, or remove it if both bridges are listed. A dependency entry alone does not load the runtime. `MULTICA_DSH_PROFILE_BUNDLE` will not migrate an existing bridge configuration. Verify the result with `dsh --profile multica --probe`.

<Callout type="warning">
Prefer a bundle your own team publishes or builds: this value is installed into every daemon host's DSH home without further confirmation, so an unvetted third-party package is a supply-chain decision, not a convenience.
</Callout>

**DSH Desktop.** If you installed DeepSeek Harness Desktop instead of the npm package, the daemon also looks for the CLI shims that app generates, under its own per-user data directory — `~/Library/Application Support/DSH Desktop` on macOS, `%APPDATA%\DSH Desktop` on Windows. On Windows that is roaming application data, not the install directory: the app installs to Program Files or `%LOCALAPPDATA%\Programs`, but the CLI it drives lives beside its other per-user state. The version segment in those paths is a generated id, so the daemon enumerates them and prefers the newest. Nothing else is needed on `PATH` — a generated shim runs the Desktop app's own runtime by absolute path. If DSH Desktop is installed somewhere non-default, point `MULTICA_DSH_PATH` at the shim.

The daemon registers DeepSeek Harness only after `dsh --profile multica --probe` succeeds, and reports the missing profile on `/health` when it does not.

</Accordion>
<Accordion title="Devin CLI" id="devin-cli">

Devin runs locally through `devin acp`, not cloud Devin VMs. Run `devin auth login` first. Multica checks the binary's version, not ACP's `agentInfo.version` (which can be `0.0.0-dev`).

</Accordion>
<Accordion title="MiniMax Code" id="minimax-code">

Install a supported Node.js release (`>=22.19 <23` or `>=24 <27`) and run `npm install --global @minimax-ai/code@latest`. A global npm install places `mcode` on npm's global binary path; if `command -v mcode` or `Get-Command mcode` cannot find it, add that path to `PATH`. Then run `mcode login`. MiniMax Code owns the model selection; Multica cannot override it through ACP.

</Accordion>
<Accordion title="Muse Code" id="muse-code">

Muse Code requires 1.4.10 or later. Follow the [official installation and sign-in guide](https://dev.meta.ai/docs/muse-code), then confirm `muse` is on `PATH`. Multica discovers its models over MSP and supports continuing sessions.

</Accordion>
<Accordion title="QwenPaw" id="qwenpaw">

Choose the provider and model in QwenPaw's own configuration. Multica cannot override a QwenPaw model at run time.

</Accordion>
<Accordion title="Reasonix" id="reasonix">

Run `reasonix setup` and configure a default provider and model before starting the daemon.

</Accordion>
</Accordions>

## Confirm the daemon can find the command [#3-confirm-the-daemon-can-find-the-command]

Replace `<command>` with a command from the table, such as `claude`, `codex`, or `cursor-agent`. The first command prints the executable path.

<Tabs groupId="os" persist items={["macOS / Linux", "Windows"]}>
<Tab value="macOS / Linux">

On macOS, Linux, or WSL:

```bash
command -v <command>
<command> --version
```

</Tab>
<Tab value="Windows">

In Windows PowerShell:

```powershell
Get-Command <command>
<command> --version
```

</Tab>
</Tabs>

If the terminal finds the tool but Desktop or the background daemon does not, the two are usually using different `PATH` values. Restart the app, or set an absolute path through the matching `MULTICA_<PROVIDER>_PATH` environment variable; full configuration is in [Environment variables](/environment-variables#daemon-configuration).

</Step>
<Step>

## Re-detect and confirm the runtime is online [#4-re-detect-and-confirm-the-runtime-is-online]

<Tabs items={["CLI", "Desktop"]}>
<Tab value="CLI">

Start the daemon:

```bash
multica daemon start
```

If the daemon is already running, restart it after installing a new tool:

```bash
multica daemon restart
```

</Tab>
<Tab value="Desktop">

Quit and reopen Multica Desktop.

</Tab>
</Tabs>

Then open Multica's **Runtimes** page. The tool appears under the target computer and shows as online. You can now select this runtime when creating or editing an agent.

<Callout type="warning">
The daemon must detect at least one built-in supported CLI before it will start. Custom runtime profiles sync after the daemon is up, so they cannot be the sole startup condition on a blank machine. There is one exception: when the daemon has just begun installing the DSH runtime profile itself (`MULTICA_DSH_PROFILE_BUNDLE`), it starts with no runtimes and registers DeepSeek Harness once that install finishes. Without it, a host whose only tool is a DSH that needs the profile could never complete the install — the daemon would exit before it finished and take it down with it.
</Callout>

## No tools detected

Check in order:

1. Run the tool itself in a terminal to confirm installation and sign-in are complete.
2. Check the actual command name and path with `command -v` or `Get-Command`.
3. Run `multica daemon logs -f` and look for version, path, or authentication errors.
4. Restart the daemon so it re-reads the current environment.
5. Return to the **Runtimes** page and confirm the computer and the tool are online.

If the tool shows as online but runs still fail, open the issue's run record to see the exact error the CLI returned, or continue with [Troubleshooting](/troubleshooting).
