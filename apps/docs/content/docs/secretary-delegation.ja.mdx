あなたはチャットで一つのエージェント、**秘書**と働きます。スクワッドに関わる質問、たとえば「春のローンチは順調か、何が遅れさせるか」をすると、秘書は各部分の責任者に問い合わせ、回答を読み、弱そうな点に異議を唱え、一つの評価と、あなたに必要な判断事項をまとめて返します。判断も同じチャットで行えます。秘書はその後、各判断を実行するリーダーに渡します。

日次ブリーフは別物で、変わりません。[秘書とブリーフ](/secretary)で説明しています。

これはオンデマンドのフローの設計です。一部はまだ構築・検証中です。ランブックには、実機で確認済みの内容を手順ごとに記録しています。
</Callout>

## あなたがすること

- **質問する。** 有能な参謀に聞くように、秘書のチャットで質問してください。重要な場合は欲しい形も伝えます。数値、リスク一覧、判断事項の一覧、比較、早期警告など。
- **確認の質問に答える。** プロジェクトや期間が不明確なら、秘書は短い質問を一つして待ちます。推測して問い合わせを広げることはしません。
- **判断する。** 評価に判断事項が挙がったら、普段の言葉で返してください。たとえば「D1: Bにする、D2は保留」。秘書は判断ごとに理解した内容を繰り返し、違っていないか確認します。「はい」の一言で確定できます。
- **リーダーに求められたら対応する。** 判断が必要なリーダーは、まず秘書に尋ねます。秘書はそれに答えるか、別のリーダーに問い合わせるか、推奨案を添えてチャットであなたに持ち込みます。

フォームに記入する必要はなく、答えを得るために各スクワッドの状況をすべて読む必要もありません。

## 秘書が委任すること

秘書は部門の仕事そのものはしません。誰に聞くかを決め、その人に向けた依頼文を自分の言葉で書き、返ってきた内容を読みます。

| 秘書が決めること | 例 |
|---|---|
| 誰に聞くか。狭い質問は一人のスクワッドリーダーへ。フロア全体の質問は、フロアにチーフがいればそのチーフへ、いなければ各リーダーへ。 | 「リサーチはどうなっていますか」はリサーチのフロアチーフへ。 |
| 誰に聞かないか。答えがすでに読める落ち着いたスクワッドは外し、その旨を伝えます。 | 「Growth Lifecycleには未完了の作業がないため、問い合わせていません」。 |
| 何を聞くか。質問、その重要性、期間、すでに分かっていること、答えが必要な時期を書きます。 | リーダーには状況要約ではなく、完了の範囲と担当するリスクを尋ねます。 |

各宛先は、秘書プロジェクトの依頼課題の下の子課題を受け取ります。どれでも開けます。リーダーは自分の課題へのコメントで答え、答え終わったら閉じます。

リーダーは自分で分析します。課題、実行、プルリクエストを読み、メンバーに確認を頼むこともあり、自分の評価を書きます。秘書は事実を先に咀嚼して渡すことはしません。

## 秘書が回答を読む方法

すべての子課題が閉じられたとき、または依頼の期限が過ぎたとき、秘書は各回答を批判的に読み、それから比較します。秘書は次のことをします。

- 重要だが都合が良すぎる主張について、その根拠となる課題、コメント、実行を開いて確認する。
- 弱い回答には、リーダーの課題へのコメントで異議を唱え、リーダーが再回答する。
- 回答を横断して見る。リスクがどこに集中しているか、他が依存しているのはどのスクワッドか、進捗の主張が期日に合うか。
- 以前のブリーフと評価と比べる。

異議はコメントなので、リーダーには回答のために通知が届き、あなたもやり取りを読めます。異議の回数には上限があり、暴走を防ぎます。一つの課題で一定回数に達すると、秘書はその課題を未解決として閉じ、そう伝えます。

評価は同じチャットに戻ってきます。結論から始め、判断事項を挙げ、リスクを担当者つきで順位付けし、リーダー同士の意見の食い違いを示し、確認しなかった点を述べます。簡単な質問には短く答えます。依頼にかかった実行数とトークン数も報告します。

リーダーが期限内に答えなかった場合、秘書はそう伝えます。推測で穴を埋めることはしません。

## 指示

チャットで何かを決めたとき、秘書はそれをリーダーに**指示**として渡せます。指示は、スクワッドが持つプロジェクトの中で、リーダーまたはチーフに向けた課題です。含まれるもの:

- 指示を求めたチャットメッセージから引用した、あなた自身の言葉。
- 目的、あなたが与えた制約、優先度と期日。
- 指示の元になった報告と、秘書が考える「完了」の意味。

リーダーはコメントで指示を受領し、理解した内容を一行で示し、目的をプロジェクト内の課題に分解し、プロジェクトのワークフローで進めます。節目では秘書に報告し、ブロッカーが実際に生じたらすぐに知らせます。

安全のための三つのルール:

- **この方法で作業を作れるのはあなただけです。** 指示は秘書からのものだけを受け付け、かつワークスペースのオーナーまたは管理者のチャットメッセージで始まった実行の中でのみ有効です。定期ルーティン、オートパイロット、起床予約は作れません。
- **あなたの言葉は保存されます。** チャットメッセージと引用は指示に保存され、リーダーにも見えます。
- **一部の判断は独自のフローを保ちます。** 指示では提案や段階のゲートを承認できず、ローンチを開始することもできません。それらは**承認**と**却下**のボタンを保ちます。チャットでそれを求めた場合、秘書はそう伝えます。

<Callout type="info">
資金、範囲、例外をあなたに求めるスクワッドからの提案は、引き続き提案のフローを使います。[提案](/proposals)を参照してください。
</Callout>

## リーダーからの質問

自分のスクワッドから得られないものが必要なリーダーは、指示または対象の課題にコメントし、秘書にメンションします。すると秘書は通常のエージェントとして実行されます。自分の知識(以前のあなたの言葉、ナレッジベース、別のリーダーの回答)から答えるか、別のリーダーに問い合わせるか、あなたに持ち込みます。

あなたに尋ねられるのは、秘書が解決できない事柄だけです。リーダーと直接話したい場合は、自分でそのリーダーのチャットや課題を開いてください。それを妨げるものはありません。

## スキルの場所

秘書とリーダーはスキルに基づいて動きます。これらはワークスペースのスキルで、他と同じように[スキル](/skills)ページで編集でき、次の実行から反映されます。

| スキル | 使用者 | 内容 |
|---|---|---|
| `secretary-analysis` | 秘書 | 質問の理解、問い合わせ先の選定、依頼文の作成、批判的な読解と異議、スクワッド横断の分析、評価の作成、判断の番号付け、指示への変換の方法。 |
| `squad-reporting` | スクワッドリーダーとフロアチーフ | リーダーが扱える観点(完了、スケジュール、品質、リスク、依存関係、能力、成果、確度、推奨)と、良い回答と弱い回答の例。 |
| `directive-execution` | スクワッドリーダーとフロアチーフ | 指示の受領、計画、課題への分解、プロジェクトのワークフローの使用、マイルストーン、エスカレーション、クローズ。 |
| `business-metrics` | 目標を持つスクワッド | 目標と主要結果の読み方、期間に対する傾向、測っていないものの伝え方。 |

振る舞いは、平易な言葉でスキルに書いて調整できます。「必ず判断事項から始める」「Growthスクワッドは赤でない限り報告しない」「当社のリスク尺度を使う」。次の実行では新しい文章が使われます。初期版は保存されているので、元に戻せます。

<Callout type="warning">
初期スキルは一度だけインストールされる想定です。後の会社セットアップの実行では、あなたの編集を残すべきです。
</Callout>

## 組織マップ

秘書は会社の構造を記憶からではなく、組織マップから把握します。フロアとそのチーフ、スクワッドとそのリーダー、メンバー、スクワッドのプロジェクトとワークフロー、各スクワッドの未完了の作業を含みます。どのメンバーも読めます:

```bash
multica company map
multica company map --floor <floor-id>
```

機械可読な出力には `--output json` を付けます。エンドポイントは `GET /api/company/org-map` です。

## 制限

- 秘書はワークスペース全体を読め、どのスクワッドにも問い合わせられます。ただし課題のステータスや担当者を変更したり、何かを削除したり、提案を決めたりはできません。
- 会社の制御はリーダーの実行にも適用されます。会社が一時停止中のとき、またはクワイエットアワーの間は、秘書の回答が部分的であることと、その理由を示します。
- 予算と保留は、通常どおりすべての実行に適用されます。
- 一つの依頼で問い合わせるスクワッドの数(20)、未完了の依頼の数(8)、一つのチャットメッセージあたりの指示の数(5)には上限があります。これらの上限は現時点では固定です。一つの課題あたりの異議の上限は設計済みですが、まだ適用されていません。
