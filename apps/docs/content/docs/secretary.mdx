The Secretary is one agent for the whole workspace. It reads what your squads did, then writes one brief for you each day. The brief names what needs your decision, what is moving, and what is stuck. You do not get a report from each squad.

Squads do their work in issues, projects, and [proposals](/office) as usual. They never write status reports for you. The Secretary pulls the facts it needs, so the squads spend no runs on status.

<Callout type="warning">
The Office does not yet have a setup button, a brief card, or an **Ask** action. Until they ship, you read briefs through the inbox item **Brief ready** and the `multica brief` commands below. Setting up the Secretary is covered in the upgrade notes in [SELF_HOSTING.md](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING.md).
</Callout>

## Requirements

- An online Hermes runtime on the machine you choose. Install it with [Install an agent runtime](/install-agent-runtime), and configure a model in Hermes itself.
- The Secretary runs on that one runtime. Its memory is stored on that machine, so it does not move when the workspace does.

## What setup creates

Setup creates these objects, and it can be run again without duplicating them:

- An agent named **Secretary**, private to you, using Hermes on the runtime you chose, with one run at a time.
- An **Executive** floor and an **Executive Office** squad on it. The Secretary leads the squad, and you are a member.
- The workspace setting that names the Secretary.
- The **Daily brief** autopilot, active, and the **Weekly review** autopilot, paused.

## Daily brief and weekly review

Both are [autopilots](/autopilots) that run the Secretary.

| Autopilot | When | State after setup |
| --- | --- | --- |
| **Daily brief** | 08:00 each day, in the timezone chosen at setup | Active |
| **Weekly review** | Friday 17:00 | Paused. Turn it on from the autopilot page. |

If the machine was asleep at 08:00, that run is skipped, as any autopilot run is. Press **Run now** on the autopilot to get the brief at once.

When a brief is published, the workspace owners get one inbox item, **Brief ready**. It is the only routine notification from the Secretary.

## What a brief contains

A brief is Markdown with six sections, in this order:

1. **Headline**: at most three lines. On a quiet day it says so, and the brief stays short.
2. **Needs your decision**: pending proposals first, then any blocker only you can clear. Each item gives the situation, the options, the Secretary's recommendation, and a link. At most five are listed, and the rest are counted.
3. **Progress**: by floor, with only the squads that had news. A quiet squad takes one line.
4. **Blockers and risks**: each with a proposed way out.
5. **Watch**: market and product notes from the Research floor since the last brief.
6. **FYI**: cost, runtime, and failure anomalies.

A brief should take about two minutes to read. The server rejects a brief with a missing section and tells the Secretary which one, so the Secretary can fix it and publish again. A brief is limited to 20,000 characters.

## The digest

The digest is the set of facts the Secretary writes from. The server computes it from the database, so it is bounded and does not depend on the model:

- **Per squad**, ordered by what needs attention first: issues done, in progress, and blocked; issues in progress with no activity for 72 hours; failed runs; the leader's no-action count; pending proposals; and the most recent completed issues as links.
- **Quiet squads** in one list.
- **The workspace**: runs and cost in the period, and runtimes that are offline.

The digest covers at most 20 squads in full. Any others are ranked and counted. You can look back at most 35 days.

## Ask the Secretary in chat

The Secretary is an agent, so you can open a chat with it like any other agent. For a question about company status, it reads the digest first and answers from that, not from memory. For a question about what the company knows or decided, it searches the [knowledge base](/knowledge-base) first and cites what it finds.

The Secretary does not approve proposals for you. Its answer points you to the brief or to **Decisions** in the office.

## Limits on what it does

| The Secretary can | The Secretary cannot |
| --- | --- |
| Read the workspace through the `multica` CLI | Decide a proposal. The server refuses decisions from agents. |
| Publish briefs | Publish a brief as another agent. Only the Secretary or an admin member may publish. |
| Comment on an issue to ask a squad leader, at most three per brief | Run a squad's work. Its instructions limit it to reporting and asking. |
| Save drafts to the knowledge base | Publish knowledge. A person publishes drafts. |

## The CLI

The Secretary runs these commands from its runtime. `publish` requires the Secretary or an admin member.

```bash
multica brief digest --since 24h --json
multica brief publish --kind daily --title "Daily brief" --file brief.md --proposal <proposal-id>
multica brief list --kind daily --limit 10
multica brief show <brief-id>
```

| Command | What it does |
| --- | --- |
| `digest` | Prints the digest for `--since`, a duration such as `30m`, `24h`, or `7d`, or an RFC 3339 timestamp. Defaults to 24 hours. |
| `publish` | Publishes a Markdown file with `--kind daily`, `weekly`, or `ad_hoc`, a `--title`, and a `--file`, or `-` for stdin. Repeat `--proposal` for each proposal the brief raises, so the app can link it. |
| `list` | Lists briefs, newest first. Filter with `--kind`, and limit with `--limit` (up to 50). |
| `show` | Prints one brief by id. |

Add `--json` or `--output json` to any command for machine-readable output.

## Memory and privacy

The Secretary keeps your preferences and standing instructions in its Hermes memory. Every fact about the company comes from the digest and the issues it points to, at the time of the run. Memory can be lost, for example if the runtime is reclaimed or moved, so nothing in the workspace depends on it.

Because the Secretary can read the whole workspace, setup creates it as a private agent. The [access rules for private agents](/agents#permissions-and-access) decide who can run it.
