<Callout type="warn">
**Self-hosted Multica only.** This integration is available only when you run
Multica yourself; it is not offered on Multica Cloud. "Self-hosted" here means
**Multica** is self-hosted — typically so it can reach a Git instance on your own
network. A server operator must enable it (`MULTICA_VCS_INTEGRATION_ENABLED=true`)
and set `MULTICA_VCS_SECRET_KEY`; until then the section does not appear in
Settings → Code.
</Callout>

Self-hosted Multica connects **Forgejo**, **Gitea**, **GitLab**, or official **Tencent Gongfeng** per workspace. Once connected, any pull request (GitLab: merge request) whose branch name or title contains an issue identifier (for example `MUL-123`), or whose body names one after a closing keyword (`Closes MUL-123`), is **auto-linked** to that [issue](/issues) and appears under **Pull requests** in the issue sidebar. When every PR linked to the issue is merged, the issue moves to the status the workspace chose (**Done** by default). Forgejo/Gitea and GitLab CI for the head commit shows as a checks bar on the card.

These providers run alongside GitHub: a workspace can use any combination.

<Callout type="info">
Unlike GitHub, these providers have no "App" model. Each workspace stores its own instance URL plus an access token, and registers a webhook on its repository or organisation. The token and webhook secret are encrypted at rest.
</Callout>

## Prerequisites (server)

Turn the integration on for this deployment. It is off by default, so the section stays hidden until you set:

```sh
MULTICA_VCS_INTEGRATION_ENABLED=true
```

The official self-hosted `docker compose` file (`docker-compose.selfhost.yml`) sets this for you.

Then set a base64-encoded 32-byte key so the server can encrypt stored credentials. Without it, the connect form is disabled.

```sh
openssl rand -base64 32
```

```sh
MULTICA_VCS_SECRET_KEY=<base64 32-byte key>
```

Both are required: the switch decides whether the feature is offered, and the key encrypts the stored token and webhook secret. Connect, webhook, and rotate all require both.

Set `MULTICA_PUBLIC_URL` to the server's public base URL so Multica can show a ready-to-paste webhook URL. Without it, the UI shows only the webhook path and you prepend your own origin.

## Connect a workspace

1. Create an access token in your provider with read access to the repositories you want mirrored:
   - **Forgejo / Gitea**: Settings → Applications.
   - **GitLab**: a personal (or group/project) access token with the `read_api` scope.
2. In Multica, open **Settings → Code**, then click **Connect** in the **Git providers** row.
3. Choose the **provider**, enter the instance URL (for example `https://forgejo.example.com`) and the access token, then **Connect**. Multica validates the token against the instance before saving.
4. Copy the **webhook URL** and **webhook secret** shown after connecting.

<Callout type="warn">
The webhook secret is shown only once. Copy it before leaving the page. Reconnecting the same instance rotates the token and secret.
</Callout>

### Instance with a private CA

If **Connect** reports that the provider's certificate "is signed by a certificate authority this server does not trust", the instance's HTTPS certificate comes from an internal CA (or is self-signed) that the Multica server does not trust. A server operator adds that CA to the backend's trust store: with Helm, set `backend.extraCACerts.configMap`; with Docker Compose, mount the CA and set `SSL_CERT_DIR`. See [Private CA certificates](https://github.com/multica-ai/multica/blob/main/SELF_HOSTING_ADVANCED.md#private-ca-certificates-optional) for the steps.

Multica has no option to skip certificate verification, because the connect request carries your access token. If the message says the certificate does not match the host name, or failed verification (for example, it has expired), fix the certificate itself; trusting the CA does not help.

## Register the webhook

On the repository (or organisation/group, to cover every repo):

**Forgejo / Gitea** — Settings → Webhooks → Add Webhook → Forgejo/Gitea:

- **Target URL**: the webhook URL from the previous step.
- **HTTP method** `POST`, **content type** `application/json`.
- **Secret**: the webhook secret (used to verify the `X-Gitea-Signature` HMAC).
- **Trigger events**: select **Pull Request**, and **Commit Status** to mirror CI.

**GitLab** — Settings → Webhooks:

- **URL**: the webhook URL.
- **Secret token**: the webhook secret (sent as `X-Gitlab-Token` and compared verbatim).
- **Triggers**: enable **Merge request events**, and **Pipeline events** to mirror CI.

Multica authenticates every delivery against the stored secret, so a webhook without the matching secret is rejected.

## What gets mirrored

- **Pull / merge requests** — open, closed, merged, and draft state, author, branch, and (where the provider supplies them) diff stats.
- **Issue links** — an identifier in the title or branch links the PR to the issue, as does an identifier after a closing keyword in the body; a bare mention in the body links nothing. Once every PR linked to the issue is merged — across GitHub and self-hosted providers — the issue moves to the status the workspace chose, under the same setting and rules as [GitHub](/github-integration#when-merged-prs-move-an-issue). This page shows the same **After PRs merge, move the issue to** setting once a provider is connected.
- **CI** — Forgejo/Gitea commit statuses and GitLab pipelines aggregate into a passed/failed/pending checks bar for the head commit.

## Agents opening pull requests

Creating PRs needs no provider configuration in Multica. Agents check out repositories in the runtime and push branches and open PRs using the runtime host's own Git credentials. To let agents work against a provider, ensure the daemon host can authenticate to it — for example an SSH deploy key, or a token in the host's Git credential helper — and add the repository URL as usual. Repository checkout works with any Git URL, so no provider-specific wiring is required.

## Tencent Gongfeng

Choose **Tencent Gongfeng** in the provider selector. The official instance URL
is `https://git.code.tencent.com`; create a **Private Token** in your Gongfeng
account settings. Multica validates it through `/api/v3/user`.

After connecting, select **Gongfeng repositories**. Multica configures a merge-request webhook and imports existing MRs in the background. The token needs repository read access and permission to manage its webhooks; the Multica public URL must be reachable from Gongfeng over HTTPS. Repository selection also appears under **Add repository → Choose from Gongfeng**, where selected clone URLs are added to the workspace for agents.

The repository picker shows sync progress and permission errors. **Retry sync** imports the full history again and repairs the webhook. Rotating the webhook secret updates registered webhooks without creating duplicates. Stopping sync removes the registered webhook and preserves mirrored MRs; disconnecting removes the connection and its mirrored data. If a revoked token prevents remote webhook cleanup, the connection is still removed and Multica asks you to delete the remaining webhook in Gongfeng. For manual setup, regenerate the webhook secret and enable **Merge request events** with the provided URL and token. Deliveries use `X-Event: Merge Request Hook` and `X-Token`.

MR creation, update, close, reopen and merge reuse the linking and issue-status rules above. Cards display the repository-local `iid`; API detail requests resolve the global `id` separately. API refreshes fill in the author and recover missed events. CI checks and conflict information refresh on MR events, page visits and periodic background sweeps. Checks belong to the current source commit, including fork branches; changing the commit invalidates old checks. Failed refreshes mark last-known results as stale. Missing merge-policy or approval information is not inferred from conflict status.

For agents, install the community [gongfeng-cli](https://github.com/studyzy/gongfeng-cli)
on the runtime host and configure CLI authentication separately from Git credentials.
The official Multica CLI `v0.6.1` works with this integration: the server delivers
the Gongfeng reference in the `multica-platform` task skill bundle, so a custom
runtime build is not required. Real task execution with Codex on an Apple silicon
Mac covered MR creation and updates, check synchronization, and issue completion
after merge. Windows and other agent providers still require native acceptance.
Download `v0.5.0` from the original project's [Releases](https://github.com/studyzy/gongfeng-cli/releases/tag/v0.5.0).
Prebuilt packages are available for macOS arm64, Linux x86_64 and Windows x86_64;
Go is not required for these packages. With Go installed, use the same pinned version:

```sh
go install github.com/studyzy/gongfeng-cli/cmd/gongfeng@v0.5.0
```

Authenticate with `GONGFENG_TOKEN` or a private `~/.gongfeng.json` file (the token
is stored in plaintext; use mode `0600` on macOS/Linux or a personal file ACL on
Windows). Some agents filter environment variables;
confirm access inside the actual runtime. Keep tokens out of command arguments,
repository files and task comments. Repository-local configuration can override
the API address and credentials. Pass the official `--base-url` explicitly and
verify the account before writes:

```sh
gongfeng --base-url https://git.code.tencent.com user me --json
gongfeng --base-url https://git.code.tencent.com --project-id <namespace/project> mr list --json
```

The explicit address does not restrict HTTP redirects. The community CLI's
credential loading and redirect handling need separate hardening before using
it with untrusted repositories.

Use `gongfeng --base-url https://git.code.tencent.com --project-id <namespace/project> mr create --help` to check flags,
then specify `--source-branch`, `--target-branch`, `--title` and `--description`.
The CLI's `show`, `update` and `accept` commands use the global MR `id`; resolve
it with `mr list --json` instead of passing the displayed `iid`. The server's
stored token is not passed to agents.

MR actions use the CLI account on the runtime host. Multica does not switch to
the task creator's account, and separate Multica profiles under the same OS
account share CLI credentials. For personal attribution, each member needs an
isolated personal runtime and credentials. Git commit authors and SSH push
identities are configured separately.

Multica reads check results; it does not run repository tests. For ongoing
checks, configure a CI runner to report against the current source commit SHA.
