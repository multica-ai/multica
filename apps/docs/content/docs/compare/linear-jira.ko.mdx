Linear와 Jira 모두 태스크를 AI 에이전트에게 할당할 수 있습니다. 그래서 둘 중 하나를 이미 쓰는 팀이라면 "왜 Multica를 더해야 하지?"라고 묻는 것이 자연스럽습니다. 짧게 답하면, 차이는 **에이전트가 어디에서 오고 어디에서 실행되는가**에 있습니다. Linear와 Jira는 자체 내장 에이전트를 갖추고 서드파티 에이전트 서비스도 연결할 수 있는 트래커입니다. Multica는 팀이 이미 쓰는 AI 코딩 도구를 여러분이 연결한 컴퓨터에서 실행하고, 모든 실행을 태스크에 기록하는 워크스페이스입니다.

이 페이지의 Linear와 Jira에 관한 내용은 2026년 11월 기준 공개 문서를 바탕으로 합니다. 최신 내용은 [Linear의 에이전트 문서](https://linear.app/docs/agents-in-linear)와 [Atlassian의 발표 글](https://www.atlassian.com/blog/ai-at-work/your-jira-board-just-got-a-new-kind-of-teammate)에서 확인하세요.

## 짧은 답

- **Linear나 Jira를 계속 쓰세요**: 계획(사이클이나 스프린트, 로드맵, 팀 간 보고)이 프로세스의 중심이고, 쓰려는 에이전트가 이미 트래커와 연동된 호스팅 서비스라면.
- **Multica를 쓰세요**: Claude Code, Codex, Cursor Agent, Copilot 같은 CLI 기반 공용 에이전트 풀을 자기 컴퓨터나 서버에서 실행하고, 에이전트별 접근 제어와 전체 실행 로그를 갖추고, 모든 것을 자체 호스팅할 선택지까지 원한다면.
- **둘 다 쓰세요**: 계획은 Linear나 Jira에 두고 실행은 에이전트에게 맡기고 싶다면. Multica 에이전트는 MCP 서버를 통해 Linear를 읽고 수정할 수 있습니다. 둘 사이에 자동 동기화는 없습니다.

## 비교

| 무엇인가 | 사람과 에이전트가 태스크를 맡는 워크스페이스. 에이전트는 여러분의 런타임에서 실행 | 에이전트 플랫폼을 갖춘 태스크 관리·계획 도구 | Rovo 에이전트와 서드파티 에이전트를 갖춘 태스크·프로젝트 관리 도구 |
| 에이전트 작업을 하는 주체 | [32가지 AI 코딩 도구](/providers)로 설정한 에이전트. 여러분이 연결한 컴퓨터에서 Multica 데몬이 실행 | Linear Agent와 Linear 연동 디렉터리에서 설치한 서드파티 에이전트 | Rovo 에이전트와 GitHub Copilot, Cursor 같은 연결된 서드파티 에이전트 |

| 에이전트별 도구와 모델 선택 | 가능. 지원하는 어떤 도구든 쓸 수 있고, 에이전트마다 다른 도구 사용 가능 | 설치한 에이전트에 따라 다름 | 에이전트에 따라 다름 |

| 태스크에서 볼 수 있는 실행 정보 | 도구 호출, 명령, 오류가 담긴 전체 실행 로그와 타임스탬프 | 태스크의 에이전트 활동. 상세도는 에이전트에 따라 다름 | 작업 항목에 기록된 에이전트 동작 |

## Linear나 Jira가 더 맞는 경우

- 프로세스가 사이클이나 스프린트, 로드맵, 포트폴리오 보고에 의존합니다. Multica에는 프로젝트, 워크플로, 간트 보기가 있지만 사이클, 스프린트, 로드맵 계획은 없습니다.
- 제품, 디자인, 지원을 포함한 팀 대부분이 트래커에서 일하고, 일부 태스크만 에이전트에게 갑니다.
- GitHub Copilot의 coding agent나 Cursor의 클라우드 에이전트 같은 호스팅 에이전트를 선호하고, 자기 컴퓨터에서 에이전트를 돌리고 싶지 않습니다.
- 트래커의 연동 생태계나 이미 갖춰 둔 엔터프라이즈 관리 체계에 의존합니다.

## Multica가 더 맞는 경우

- **이미 코딩 CLI에 비용을 내고 있습니다.** Multica는 개발자들이 가진 Claude Code, Codex, Cursor Agent, Copilot CLI, Kimi 등의 구독을 그대로 구동합니다. 벤더마다 별도의 에이전트 서비스를 살 필요가 없습니다.
- **코드와 자격 증명이 자기 머신에 머물러야 합니다.** 에이전트는 여러분이 연결한 런타임에서 실행됩니다. Multica를 자체 호스팅하면 워크스페이스 데이터도 여러분의 서버에 남습니다. [보안 모델](/security-model)을 참고하세요.
- **여러 개발자가 같은 에이전트를 함께 씁니다.** 에이전트, 런타임, 스킬은 워크스페이스에 속하고, Access가 각 에이전트를 실행할 수 있는 사람을 정하며, 어떤 에이전트가 무엇을 하는지 보드에서 보입니다. [팀에서 에이전트 풀 공유하기](/team-agent-pool)를 참고하세요.
- **에이전트가 정확히 무엇을 했는지 보고 싶습니다.** 각 실행의 도구 호출과 명령이 태스크에 남고, 작업 중인 [실행에 끼어들어](/mentioning-agents#실행-중인-에이전트에게-끼어들기) 방향을 바꿀 수도 있습니다.
- **리뷰가 나중 일이 아니라 정해진 단계여야 합니다.** 에이전트는 `in_review`로 결과를 넘기고, [워크플로](/workflows)는 그 결과를 리뷰 에이전트나 동료에게 넘기며, 반려되면 되돌려 보냅니다.

## Linear나 Jira와 함께 쓰기

많은 팀이 계획에는 기존 트래커를 그대로 쓰고, 에이전트가 일하는 부분에 Multica를 씁니다.

1. 로드맵과 팀 간 계획은 Linear나 Jira에 그대로 둡니다.
2. 에이전트에게 맡길 엔지니어링 태스크를 Multica 프로젝트에 만들고, 저장소와 문서를 [프로젝트 리소스](/project-resources)로 붙입니다.
3. 에이전트가 작업 중에 Linear를 읽거나 수정하게 하려면, 워크스페이스 `owner`나 `admin`이 **설정 → MCP 서버**에서 Linear MCP 서버를 추가하고 해당 에이전트에 할당합니다. [워크스페이스에서 공유하는 MCP 서버](/agents-create#워크스페이스에서-공유하는-mcp-서버)를 참고하세요.

Multica는 Linear나 Jira에서 가져오기나 동기화를 하지 않으므로, 각 태스크를 어느 시스템이 맡을지 정해 두세요.
