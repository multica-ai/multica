这篇指南面向几名开发者组成的团队：大家想共用一组 AI 编程智能体，而不是每人在自己的终端里各跑各的。它把分散在多个页面的功能串起来：[角色](/members-roles)、智能体的 [Access](/agents#权限与-access)、[运行时共享](/daemon-runtimes#私有与公开)、[小队](/squads)和[工作流](/workflows)。

在 Multica 工作区里，成员和智能体处理的是同一批任务。任何任务都可以分配给一个人、一个智能体或一个小队；智能体用评论汇报进度，交付时把任务改为 `in_review`，每次运行都记录在任务上。

## 各部分负责什么

| 团队需要 | 用什么 | 在哪里设置 |
|---|---|---|
| 在一个地方看到人和智能体的全部工作 | 同一个工作区，提供列表、看板、表格、甘特图和泳道布局 | [任务](/issues) |
| 决定谁属于工作区、能管理什么 | 角色：`owner`、`admin`、`member`，以及按项目授权的访客 | [成员与权限](/members-roles) |
| 决定谁能运行某个智能体 | 智能体的 Access：**仅自己**、**整个工作区**或**指定成员** | [智能体](/agents#权限与-access) |
| 共用智能体运行所在的电脑 | 私有、公开或共享给指定成员的运行时 | [运行时共享](/daemon-runtimes#私有与公开) |
| 不必每次都挑选智能体，让任务自动交给合适的那个 | 小队，由队长智能体分派每个任务 | [小队](/squads) |
| 把工作从智能体交给审查人，再退回修改 | 审查状态、评论和工作流交接 | [工作流](/workflows) |
| 让多个智能体复用团队的做事方法 | 挂到智能体上的 Skills | [Skills](/skills) |
| 不用人发起也能跑重复性工作 | 按计划或 webhook 触发的自动化 | [自动化](/autopilots) |
| 关注成本和失败 | 按智能体统计的用量与错误报告 | [统计](/analytics) |

## 示例：10 人工程团队

下面的步骤为 10 名开发者搭建一组共用的 3 个智能体。名称和数量按你的团队调整。

1. **创建工作区并邀请成员。** `owner` 或 `admin` 把开发者邀请为 `member`，把一两位负责人设为 `admin`。只需要跟进一个项目的外包人员以[访客](/members-roles#访客)身份加入，并共享那个项目给他。
2. **连接电脑。** 想在自己电脑上跑智能体的开发者打开 [Multica 桌面端](/desktop-app)，它会把这台电脑注册为运行时。全队依赖的智能体放在一台共用机器上，例如一台云服务器：用 `multica setup` 连接，再由它的所有者把运行时设为公开，或共享给指定成员。共享运行时让别人能在上面运行智能体，但不会共享 AI 编程工具的登录账号。
3. **创建共用的智能体。** 例如基于 Claude Code 的 **Frontend** 智能体、基于 Codex 的 **Backend** 智能体，以及基于另一个工具的 **Reviewer** 智能体，都放在共用运行时上。为它们写好指令，挂上团队的 [Skills](/skills)。任何人都能用的智能体把 Access 设为**整个工作区**，持有敏感凭据的智能体设为**指定成员**。
4. **组建小队。** 把这 3 个智能体放进一个小队，并指定队长智能体。大家把任务分配给小队，由队长决定谁来做。
5. **设置审查环节。** 在项目里选用一个[工作流](/workflows)，例如**研发交付**：开发由工程智能体负责，审查由 Reviewer 智能体负责，QA 由一名成员负责。
6. **开始分配。** 开发者创建任务，分配给某个智能体、小队或同事。智能体在共用运行时上工作，把结果留在各自的任务上。

个人实验不会打扰别人：开发者在自己电脑上设为**仅自己**的智能体，不会出现在其他人的选择器里。

## 如何控制哪些成员可以使用哪个智能体？

每个智能体都有一名 owner 和一个 Access 设置。Access 决定谁可以运行它，也就是把任务分配给它、@它或和它对话：

| Access | 谁可以运行 |
|---|---|
| **仅自己**（默认） | 只有智能体 owner。 |
| **整个工作区** | 角色为 `owner`、`admin` 或 `member` 的成员。 |
| **指定成员** | 智能体 owner 和选中的成员。 |

对团队来说比较重要的几条规则：

- 工作区 `owner` 和 `admin` 能查看和管理所有智能体，但不能凭角色运行没有授权给自己的智能体。只有智能体 owner 能修改它的 Access。
- 访客不能运行或 @智能体。
- 负责人选择器和 @提及菜单只列出这个人能运行的智能体。
- 小队不会扩大权限：要把任务分配给小队或 @小队，必须有权运行它的队长。
- 移除成员时，会清除他在其他智能体 Access 名单里的授权。
- 智能体环境变量里的凭据只有工作区 `owner` 和 `admin` 能解锁查看，每次读取都会记入审计。见[环境变量与凭据](/agents-create#环境变量与凭据)。

私有项目是第二道边界。私有项目只对成员名单上的人可见；只有发起运行的人和智能体 owner 都在名单上时，这次运行才能看到它。见[私有项目](/projects#private-projects)。

## 人和智能体之间如何交接工作？

交接靠分配和评论完成，任务在各步之间保留完整上下文：

1. **智能体写代码。** 把任务分配给智能体。它开始时把状态改为 `in_progress`，过程中发评论，交付时改为 `in_review`，通常附上一个 pull request。
2. **同事审查。** 审查人在任务上查看这次运行的执行日志和关联的 PR。启用 [GitHub 集成](/github-integration)后，任务上会显示 PR 状态、CI 结果和冲突。
3. **智能体处理审查意见。** 审查人在任务上回复，并 @这个智能体或另一个智能体，说明要改什么。被 @的智能体接手同一个任务，能看到全部讨论。如果它还在运行，这条回复可以[插话到当前运行](/mentioning-agents#给正在运行的智能体插话)。
4. **收尾。** 默认情况下，智能体停在 `in_review`；`done` 留给人来设置，或交给 GitHub 集成：默认在所有关联 PR 合并后把任务改为 `done`。

想把这些步骤固定下来、而不是每次临时安排，就用[工作流](/workflows)。每个状态都可以交给一个智能体或一名成员，并写好这一步的说明，再设置**完成后进入**哪一步和**打回时退回到**哪一步。这样任务进入审查时会自动交给审查智能体，被打回时回到开发。

## 大家怎么看到每个智能体在做什么？

- 侧边栏的**执行中**视图列出整个工作区里正有智能体在运行的任务。
- 智能体列表显示每个智能体的可用状态（来自它的运行时）和工作负载：运行中、排队中或空闲。
- 每个任务都保留每次运行的执行日志：工具调用、命令和错误，带时间戳。见[运行](/tasks)。
- [收件箱](/inbox)会在有工作分配给你、智能体 @你或在你关注的任务上评论、运行失败时通知你，不会列出每一步。
- [统计](/analytics)展示整个工作区的成本、token、运行时长和失败运行，并按智能体排行，列出运行失败的原因。

<Callout type="info">
普通成员看不到别人设为"仅自己"的智能体。它们的用量在统计中合并为"其他智能体"一行，不显示名字。
</Callout>
