Multica signs users in with email verification codes by default; Google OAuth can be added on top. Existing users can always sign in again — signup restrictions only decide whether new accounts can be created.

## Email verification codes

After the user enters an email address, Multica sends a 6-digit verification code. The code is valid for 10 minutes; once it verifies, the browser receives a sign-in cookie.

Email can be delivered through Resend or SMTP. When both are configured, `SMTP_HOST` takes priority.

### Using Resend

1. Verify a sending domain and create an API key at [Resend](https://resend.com/).
2. Set:

   ```dotenv
   RESEND_API_KEY=re_xxxxxxxxxxxxxxxx
   RESEND_FROM_EMAIL=noreply@example.com
   ```

3. Restart the API service.

`RESEND_FROM_EMAIL` must belong to a domain already verified in Resend.

### Using SMTP

At minimum, set the host and sender address:

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=multica
SMTP_PASSWORD=<password>
SMTP_FROM_EMAIL=noreply@example.com
```

Common connection modes:

| Scenario | Configuration |
|---|---|
| Internal anonymous relay | `SMTP_PORT=25`, leave username and password empty |
| STARTTLS | `SMTP_PORT=587`; upgrades to TLS by default when the server supports it |
| Implicit TLS | `SMTP_PORT=465`, or set `SMTP_TLS=implicit` explicitly |

If `SMTP_FROM_EMAIL` is unset, it falls back to `RESEND_FROM_EMAIL`. Private CAs or self-signed certificates require adding the CA to the container trust store; `SMTP_TLS_INSECURE=true` skips certificate verification and should only be used temporarily on a trusted internal network.

Some strict relays also require a valid EHLO name:

```dotenv
SMTP_EHLO_NAME=mail.example.com
```

### Behavior without an email service

The server still starts, but verification codes and invitation links are only written to the log; no email is sent. This suits local development, not production.

The startup log states whether the current mode is `Resend API`, `SMTP relay`, or `DEV mode`.

## Fixed local verification code

Local automated tests can set a fixed verification code:

```dotenv
APP_ENV=development
MULTICA_DEV_VERIFICATION_CODE=888888
```

The code must be 6 digits. The fixed code is ignored when `APP_ENV=production`.

<Callout type="warning">
Do not enable a fixed code on a publicly reachable instance. The production combination is `APP_ENV=production` with an empty `MULTICA_DEV_VERIFICATION_CODE`.
</Callout>

## Google sign-in

1. Create an OAuth 2.0 client in the [Google Cloud Console](https://console.cloud.google.com/).
2. Add the Multica frontend's callback URL to **Authorized redirect URIs**:

   ```text
   https://multica.example.com/auth/callback
   ```

3. Set:

   ```dotenv
   GOOGLE_CLIENT_ID=xxxxx.apps.googleusercontent.com
   GOOGLE_CLIENT_SECRET=GOCSPX-xxxxxxxxxxxxxxx
   GOOGLE_REDIRECT_URI=https://multica.example.com/auth/callback
   ```

4. Restart the API service.

The URLs in the Google Console and in `GOOGLE_REDIRECT_URI` must match exactly, including protocol, port, and trailing slash. Once configured, the sign-in page shows a Google sign-in button; the frontend image needs no rebuild.

## Enterprise directory (LDAP) sign-in

Self-hosted Multica can accept the same username and password your corporate OpenLDAP or Active Directory already issues. It is a third sign-in front door, parallel to email verification codes and Google: on success it reuses the existing session pipeline, so nothing downstream (workspaces, invitations, tokens, the CLI) knows which door a person came through.

1. Point `LDAP_*` at the directory. Two limits are worth keeping in mind: the service account needs read/search permission on `LDAP_BASE_DN` and nothing else, and `LDAP_USER_FILTER` must contain exactly one `%s`.

```dotenv
LDAP_ENABLED=true
LDAP_URL=ldaps://openldap.corp.example.com:636
LDAP_BASE_DN=ou=people,dc=corp,dc=example,dc=com
LDAP_BIND_DN=cn=lookup,dc=corp,dc=example,dc=com
LDAP_BIND_PASSWORD=lookup-only-password
LDAP_USER_FILTER=(uid=%s)
```

2. Match the filter and attributes to your directory. OpenLDAP keys logins on `uid`, AD on `sAMAccountName`.

```dotenv
# OpenLDAP
LDAP_USER_FILTER=(uid=%s)

# Active Directory
LDAP_USER_FILTER=(sAMAccountName=%s)
```

3. Restart the API service.

Like `GOOGLE_CLIENT_ID`, the frontend learns whether directory login exists from `/api/config` at runtime, so the login page picks the tab up without rebuilding the web image.

### Behavior

- The login name is the directory's own identifier (`uid` / `sAMAccountName`), not an email. The request carries no email field, so a caller cannot claim somebody else's account by typing its address.
- Multica matches accounts on `users.email`. The value read from `LDAP_EMAIL_ATTR` is lowercased before the match; an existing account keeps its identity, and a first-time directory login creates one. `LDAP_NAME_ATTR` prefills the display name on a brand-new account only, and never overwrites the email of an existing one.
- A wrong password and an unknown username produce the same `401` with the same message, so the endpoint cannot be used to enumerate directory accounts. A username that matches several entries is treated the same way, with a server-side error telling you to fix the overlap in the directory rather than picking one at random.
- Directory login does not run the signup restriction check. `ALLOW_SIGNUP`, `ALLOWED_EMAILS`, and `ALLOWED_EMAIL_DOMAINS` do not apply here: a successful bind is itself the admission decision, which is why an existing account stays reachable when signup is closed.
- Directory groups are not mapped to Multica roles. A new account starts with no workspace membership and needs an invitation like anyone else.
- Neither the user's password nor the service-account password is written to a log, and the directory's own error text is summarised rather than forwarded. The login name is RFC 4515-escaped before substitution into `LDAP_USER_FILTER`, so filter metacharacters match literally and cannot widen the query.
- The endpoint shares the send-code and Google limiter (`RATE_LIMIT_AUTH`, 5 requests per minute per IP by default) rather than the more generous verification-code limit.

### Failures

What the person signing in sees and what you see in the server log differ on purpose:

| Status | Meaning |
|---|---|
| `400` | username or password was missing |
| `401` | the directory rejected the credentials, or no single entry matched |
| `403` | the Multica account is temporarily disabled |
| `502` | the directory could not be reached, or the config is incomplete |
| `503` | `LDAP_ENABLED` is not `true`, so the integration is off |

A `502` when a password was certainly correct is the one to read in the log: a service-account bind failure, an unparsable `LDAP_USER_FILTER`, or an entry whose `LDAP_EMAIL_ATTR` is empty all mean the deployment, not the person, needs fixing.

Directory login adds no database migration and no new table; accounts are matched on the existing `users.email` unique key.

`LDAP_TLS_INSECURE=true` skips certificate verification. It exposes directory traffic, including the service-account password, to interception, so treat it as temporary bring-up on a trusted internal network:

<Callout type="warning">
Add the directory's CA to the container trust store instead. `LDAP_TLS_INSECURE=true` is accepted only on `ldaps://` (or `ldapi://`) URLs: a plain `ldap://` connection has no certificate to verify and sends the password unencrypted, so the server refuses that combination rather than starting up half-protected.
</Callout>

The full variable list with defaults is in [Environment variables](/environment-variables#enterprise-directory-ldap).

## Signup restrictions

Three variables together decide whether a new account can be created:

| Variable | Effect |
|---|---|
| `ALLOWED_EMAILS` | Full email addresses allowed to sign up, comma-separated |
| `ALLOWED_EMAIL_DOMAINS` | Email domains allowed to sign up, comma-separated |
| `ALLOW_SIGNUP` | Whether signup is allowed when no allowlist is configured; defaults to `true` |

The evaluation order is:

1. The email matches `ALLOWED_EMAILS` — allow.
2. Or its domain matches `ALLOWED_EMAIL_DOMAINS` — allow.
3. With no match, if `ALLOW_SIGNUP=false` — reject.
4. With `ALLOW_SIGNUP=true` but any allowlist configured and no match — still reject.
5. With no allowlist configured and `ALLOW_SIGNUP=true` — allow.

Common configurations:

```dotenv
# Company domain only
ALLOW_SIGNUP=false
ALLOWED_EMAIL_DOMAINS=company.com

# Also admit one external collaborator
ALLOWED_EMAILS=partner@example.net
```

<Callout type="info">
Both allowlists also work as an explicit exception list when `ALLOW_SIGNUP=false`.
</Callout>

## Invitations and signup restrictions

Invitations do not automatically bypass signup restrictions:

- If the invitee already has a Multica account, they can sign in and accept the invitation.
- If they do not, their email must satisfy the signup rules above.

To invite a new member on an instance with open signup disabled, add their email to `ALLOWED_EMAILS` first. Once the account is created and the invitation accepted, you can remove the entry again.

## Session lifetime

Browser sign-ins last 30 days by default. Adjust with `AUTH_TOKEN_TTL`, which accepts a Go duration or a positive integer of seconds:

```dotenv
AUTH_TOKEN_TTL=720h
```

Restart the API service after changing it. The value only affects sign-in cookies and JWTs issued afterwards; it does not extend tokens that were already issued.
