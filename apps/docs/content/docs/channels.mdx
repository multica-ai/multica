Chat integrations let the team ask an agent questions, @-mention it in a group chat, or create issues from the chat window — without opening Multica.

Feishu/Lark, Slack, DingTalk, WeCom, and Telegram are supported today. They share the same session, identity, and execution mechanics but install differently.

## Choose a platform

| | Feishu / Lark | Slack | DingTalk | WeCom | Telegram |
|---|---|---|---|---|---|
| Installation | Generate a QR code in Multica and authorize by scanning it with Feishu | Create an app in Slack, then paste two tokens into Multica | Create an internal app and Stream-mode robot, then paste its AppKey and AppSecret into Multica | Create a smart bot with the long connection enabled in the WeCom admin console, then paste its Bot ID and Secret into Multica | Create a Bot with @BotFather, then paste its token into Multica |
| DM the agent | Supported | Supported | Supported | Supported | Supported |
| Groups or channels | Triggered by @-mentioning the Bot | Triggered by @-mentioning the Bot | Triggered by @-mentioning the Bot | Triggered by @-mentioning the Bot | Triggered by @-mentioning or replying to the Bot |
| Create issues | `/issue` message command; creates the issue from your input as-is | `/issue` slash command; the agent writes up the description before creating | `/issue` message command; creates the issue from your input as-is | `/issue` message command; creates the issue from your input as-is | `/issue` message command; creates the issue from your input as-is |
| Start a new Chat | `/new [message]` | DM: `/new [message]`; channel/thread: `@Multica /new [message]` | `/new [message]` | `/new [message]` | `/new [message]` |
| Clear the current Chat context | `/clear [message]` | DM: `/clear [message]`; channel/thread: `@Multica /clear [message]` | `/clear [message]` | `/clear [message]` | `/clear [message]` |
| Connection | Platform long connection | Socket Mode | Stream mode | Platform long connection | `getUpdates` long polling |

New connections are currently open only for mainland-China Feishu; existing international Lark connections keep working and can still be managed.

Each Bot is bound to one Multica agent. To use several agents on the same chat platform, connect a separate Bot for each.

DingTalk, WeCom, and Telegram are [community-maintained](/community-maintained): they ship in every release, but carry no official support SLA. Report problems in [GitHub issues](https://github.com/multica-ai/multica/issues).

WeCom handles text messages today. Voice, image, and file messages get a short reply explaining that, and are not passed to the agent.

Telegram handles text messages today. Unsupported media gets a short reply explaining that, and is not passed to the agent.

## How a message is processed

1. Multica resolves the Bot to its workspace and agent.
2. In a group or channel, only messages that explicitly @-mention the Bot continue; DMs need no mention.
3. Multica verifies the sender's account binding and workspace membership.
4. The message joins an [agent chat](/chat) session, and a task is created.
5. The agent's reply goes back to the original DM or thread.

Channel messages that don't @-mention the Bot never trigger the agent and are not added to its conversation context.

Ordinary messages follow this flow. `/issue` is a command, not a chat turn: Multica posts the result back to the originating platform but does not add the command to Multica Chat. Slack's native slash command continues through its separate asynchronous issue-creation flow.

## Conversation controls

`/new` creates a new Multica Chat and routes later messages from that external conversation to it. `/new <message>` creates the Chat and uses the message as its first turn. The previous Chat remains stored and usable in Multica.

`/clear` stays in the current Multica Chat but starts a new agent-visible context. The full Chat history remains available in Multica, while the agent cannot retrieve messages from before the boundary. `/clear <message>` uses the message as the first turn in the new context; a bare `/clear` applies to the next real message.

On Slack, `/new` and `/clear` are native slash commands in a DM. A native slash-command payload does not identify a channel thread, so use `@Multica /new [message]` or `@Multica /clear [message]` inside the target thread.

## Session isolation

- Feishu/Lark separates sessions by chat; later messages in the same chat continue the same session.
- Slack separates DMs by channel; in a channel, each thread holds its own session.
- DingTalk separates sessions by conversation; each DM or group continues its own session.
- WeCom separates sessions by chat; each DM or group chat continues its own session.
- Telegram separates sessions by chat; forum topics are isolated by topic.

Follow-ups in a channel still need a fresh @-mention. The agent only receives messages addressed to it — it never reads the whole channel history automatically.

## Account binding

The first time a member messages the Bot, they receive an account binding link. After signing in to Multica, the platform account is linked to their membership in the current workspace.

Multica only runs the agent after binding completes. Every message re-checks account binding and workspace membership; after leaving a workspace, the Bot can no longer be used to reach it.

<Callout type="info">
Account binding only confirms who the sender is. Other members on the chat platform are not automatically added to the Multica workspace.
</Callout>

## Manage connections

Workspace owners and admins can connect or disconnect Bots; for Feishu/Lark Bots, connecting and disconnecting is also open to the agent's owner. Regular members can view connected integrations and use the agents they have access to.

After disconnecting, the Bot stops receiving new messages. Existing Multica conversations and run records are kept.

## Self-hosting

A self-hosted deployment must configure a 32-byte encryption key for each platform before Multica opens its connection entry point:

```dotenv
MULTICA_LARK_SECRET_KEY=<base64-encoded 32-byte key>
MULTICA_SLACK_SECRET_KEY=<base64-encoded 32-byte key>
MULTICA_DINGTALK_SECRET_KEY=<base64-encoded 32-byte key>
MULTICA_WECOM_SECRET_KEY=<base64-encoded 32-byte key>
MULTICA_TELEGRAM_SECRET_KEY=<base64-encoded 32-byte key>
```

These keys encrypt stored Bot credentials. See [Environment variables](/environment-variables) for how to generate, store, and rotate them. Multica Cloud already has this configured.

WeCom's only outbound path is the WebSocket held by one process, so what happens to a reply produced on a *different* replica depends on the realtime relay:

- **Sharded or dual relay mode** (`REDIS_URL` set — the default with Redis): the reply is forwarded to the replica holding the connection and delivered. Multi-replica WeCom is supported.
- **Legacy relay mode, or no Redis**: the reply is dropped. Run the WeCom-enabled backend as a single replica in this configuration.

In every mode, a reply produced while *no* replica holds a live connection (all mid-reconnect) is not delivered. It is counted as `multica_wecom_outbound_dropped_total{reason="no_live_connection"}` by the replica that routed it, so the size of that window is measurable; if the loss is unacceptable, a single replica remains the most conservative deployment.
