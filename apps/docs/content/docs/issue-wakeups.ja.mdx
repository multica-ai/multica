作業によっては途中で待つしかありません。仕入れ先の見積もり、同僚の返事、サブタスクの完了などです。そんなときはタスクに**ウェイクアップ**のルールを追加します。「これが起きたら、このエージェントを起こして、これをさせる」というルールです。条件を満たすと、エージェントはそのタスクで通常の実行を始め、最新の状況を読み、結果をいつもどおりコメントで返します。

ルールはタスクに保存されるので、待っている間に動いている実行はありません。メンバーはタスクのサイドバーから、エージェントは実行中に [CLI](#cli) から次の確認を予約します。どちらも同じ種類のルールになります。

## ウェイクアップを作成する [#create]

<Steps>
<Step>

タスクを開き、サイドバーの**ウェイクアップ**欄の右にある **+** をクリックします。

</Step>
<Step>

**条件**で条件を選び、時刻、待つ相手、待つステータスなど、条件に必要な項目を埋めます。

</Step>
<Step>

**起こす**でエージェントを選びます。タスクの担当者がエージェントなら、最初から選ばれています。選べるのは、ランタイムに紐づいていて、あなたが実行する権限を持つエージェントだけです。[権限と Access](/agents#権限と-access) を参照してください。

</Step>
<Step>

**起動後に行うこと**に指示を書きます。たとえば「仕入れ先から見積もりがそろったか確認し、そろっていれば比較表にまとめる」。最大 12,000 バイトです。あとで編集でき、変更はそれ以降のウェイクアップにだけ反映されます。

</Step>
<Step>

**作成**をクリックします。

</Step>
</Steps>

ウェイクアップが始める実行は作成者の代理として動きます。実行が始まる前に、作成者がまだそのエージェントを実行できるかどうかを Multica が確認し直します。

次のタスクでは、運用アシスタントが見積もりを依頼し、仕入れ先の返信を待っています。ウェイクアップを追加して、起動時刻まで早送りしてみてください。「定期チェック」を選ぶと、まだ何も届いていない日にエージェントがコメントせずに確認を終える様子も見られます。

## 待てるもの [#conditions]

| グループ | 条件 | 起こすタイミング |
|---|---|---|
| 時間 | 指定した時刻 | 10 分後、1 時間後、明日 09:00、または指定した時刻。一度だけ起こします。 |
| 時間 | 定期チェック | 毎時、毎日 09:00、平日 09:00 のいずれかで、あなたのタイムゾーンで計算します。終了日が必須で、その日が終わると止まります。 |
| コラボレーション | 誰かが返信 | タスクに新しいコメントが付いたとき。特定のメンバーやエージェントに絞れます。 |
| コラボレーション | フィールドが特定の値になる | タスクのステータス、担当者、ラベル、カスタムプロパティが指定した値になったとき。 |
| 実行とサブタスク | エージェントの実行が終了 | このタスクで特定の（または任意の）エージェントの実行が成功、失敗、キャンセルになったとき。 |
| 実行とサブタスク | サブタスクが終わる | すべてのサブタスクが閉じた（`done` または `cancelled`）とき、または指定したステージまでがすべて閉じたとき。サブタスクがなければ起動しません。 |
| 関連 | 関連 PR の CI が終わる | PR のマージやマージコンフリクトも選べます。このタスクに直接関連付けた PR だけが対象で、複数あればどれか 1 つで条件を満たします。CI とコンフリクトは GitHub の PR だけに対応しています。 |
| 関連 | 別のタスクのステータス | 別のタスクが完了、完了またはキャンセル、レビュー中になったとき。 |
| | カスタムイベント | リアクション、添付ファイル、コメントの編集、スレッドの解決など、25 種類のイベントから選びます。 |

フィールド、サブタスク、PR、別のタスクの条件は Multica 自身が確認します。作成した時点で条件がすでに成り立っていれば、次の確認（約 30 秒以内）で起動します。CI だけは例外で、作成後に終わったチェックしか数えません。

時間以外の条件は「何かが起きるのを待つ」ルールで、設定がさらに 3 つあります。

- **トリガー回数**：既定は**一度だけ起動**です。**繰り返し起動**にした場合は、**最大**回数（5、10、20、50 回。既定は 20 回）も決めます。
- **最大待機**：1、3、7、30 日。既定は 7 日です。
- **期限後**：既定ではエージェントを起こして対応させます。待っていたことが起きなかったと伝わります。**そのまま終了**も選べます。

タスクの担当者がエージェントの場合、メンバーのコメントはもともとそのエージェントを起動します。同じエージェントに「誰かが返信」のウェイクアップを追加しても実行は増えず、コメントで始まる実行に合流するだけです。追加の指示を渡したいときだけ使ってください。

## 起動したあと [#after-wake]

- エージェントはタスクで通常の実行を始め、タスク、コメント、ウェイクアップの指示を読み、最後にコメントを 1 件投稿します。コメントには「起動」タグと条件が付き、[実行ログ](/tasks)にも同じきっかけが表示されます。
- 定期チェックで返信が必要なことが何もなければ、エージェントは**サイレントチェック**で終えられます。コメントは投稿せず、タスクのタイムラインとルールの起動履歴にメモだけを残します。続いたサイレントチェックはタイムラインで 1 件にまとまります。
- エージェント自身のコメントやタスクへの変更で、そのエージェントが起こされることはありません。
- 同じエージェントの実行がこのタスクで開始待ちなら、ウェイクアップはその実行に合流し、別の実行は始めません。
- ウェイクアップが待っている間、タスクのヘッダーには「運用アシスタント：返信待ち」のように、タスクが何を待っているかが表示されます。クリックするとウェイクアップ欄に移動します。

## 確認と管理 [#manage]

サイドバーのウェイクアップ欄には、このタスクのルールが並びます。条件、誰を起こすか、次の起動時刻、残り時間が表示されます。ルールをクリックすると、作成元、期限、指示、**起動履歴**（最近の実行、コメントしたかどうか、サイレントチェックの内容）を確認できます。

| 操作 | 結果 |
|---|---|
| スイッチをオフ | 以降のウェイクアップを止め、まだ始まっていない実行を取り下げます。始まった実行は続くので、必要なら実行ログで停止します。 |
| **今すぐ起こす** | 条件を待たずに、このルールで今すぐ 1 回起こします。 |
| 指示を編集 | 以降のウェイクアップにだけ反映されます。実行中の実行は変わりません。 |
| **削除** | ルールはもう起動しません。まだ始まっていない実行は取り下げ、始まったものは続きます。 |
| **再度有効にする** / **時刻を再設定** | 一度だけのルールを起動後にもう一度有効にします。時刻指定のルールは新しい時刻を選びます。 |

終わったルールは**ウェイクアップ履歴**に移ります。ルールを管理できるのは、作成者とワークスペースの owner、admin だけです。エージェントが実行中に作ったウェイクアップは、その実行を始めたメンバーのものとして扱われ、「運用アシスタント が作成（李雷 の代理）」と表示されます。

ワークスペース全体のウェイクアップは、**オートパイロット**ページの**タスクのウェイクアップ**タブで確認できます。状態（起動待ち・実行中、一時停止中、無効、終了）、トリガーの種類、作成元、エージェントで絞り込み、まとめて無効にしたり、タスクを選んでから新しく作成したりできます。

## 自動で終わる・止まる場合 [#limits]

- タスクが完了またはキャンセルになると、そのタスクのウェイクアップはすべて無効になり、まだ始まっていない実行は取り下げられます。タスクを開き直しても元には戻りません。完了またはキャンセルしたタスクには作成できません。
- 待つルールが**最大待機**に達すると、**期限後**の設定どおりに処理します。定期チェックは終了日で止まります。
- 繰り返すルールは最大回数に達すると自動で一時停止します。待つルールはさらに、ほかのウェイクアップと互いに起こし合ったとき（人を挟まずにトリガーの連鎖が 3 回目にそのルールを通ったとき）と、1 時間に 12 回を超えて起動したときにも一時停止します。一時停止したルールは誰かがオンに戻すまで止まったままで、回数は数え直しになります。
- 1 つのタスクで同時に有効にできるのは 32 件まで、ワークスペース全体では 1,000 件までです。

## サブタスクが終わったら親を起こす [#child-done]

サブタスクがあるタスクでは、ウェイクアップ欄に**システム**の印が付いたルールが表示されます。手で作る必要はありません。

- あるステージのサブタスクがすべて閉じ、後ろのステージがまだ待っているときに、親タスクの担当者を起こします。すべてのサブタスクが閉じたときにもう一度起こします。ステージのないサブタスクは、最後の 1 件が閉じたときに一度起こします。
- 担当者がエージェントならそのエージェントを、スクワッドならリーダーを起こします。メンバーには代わりにインボックスへ通知します。担当者がいなければ誰も起こしません。
- 親タスクが `backlog` の間は起こしません。`backlog` を出たときにまとめて一度起こします。
- 既定の指示は、どのステージが閉じ、次がどれかをエージェントに伝え、依存関係を確認してから次のステージのサブタスクを `backlog` から出すよう求めます。すべて閉じたときは、結果を親タスクにまとめます。

親タスクの担当者はこのルールで起こされるので、同じ目的で「サブタスクが終わる」のウェイクアップを追加する必要はありません。ステージの設定は[タスク](/issues#プロジェクトと子タスク)を参照してください。

個々のタスクでは、ワークスペースのメンバーなら誰でもこのルールをオフにしたり、指示（最大 4,000 バイト）を書き換えたりできます。エージェントは変更できません。変更したタスクは、ワークスペースの既定値に従わなくなります。

ワークスペースの owner と admin は、**設定 → ウェイクアップ**で既定値を決めます。既定でオンにするか（初期状態はオン）と既定の指示です。既定の指示が空なら組み込みの指示を使います。このページには、独自の設定を使っている進行中のタスクの数も表示されます。

## エージェントに自分で予約させる [#cli]

エージェントは実行中に `multica issue wakeup` でこのタスクの次の実行を予約し、今の実行を終えます。`--agent-id` を省くと、コマンドを実行しているエージェント自身を起こします。自分のターミナルから同じコマンドを使うこともでき、その場合は `--agent-id` でエージェントを指定します。

```bash
# 明日の 09:00（上海時間）にもう一度見る
multica issue wakeup create OPS-56 --kind at --at 2026-10-21T09:00:00+08:00 \
  --instruction "仕入れ先から見積もりがそろったか確認し、そろっていれば比較表にまとめる"

# 平日の毎朝 09:00 に確認し、1 週間で終える
multica issue wakeup create OPS-56 --kind cron --cron "0 9 * * 1-5" --timezone Asia/Shanghai \
  --expires-in 168h --instruction "見積もりメールを確認し、新しい見積もりがあれば比較表を更新する"

# 李雷の返信を最大 3 日待ち、期限になっても一度起こす
multica issue wakeup create OPS-56 --event comment.created \
  --filter-actor-type member --filter-actor-id <李雷のユーザー ID> \
  --expires-in 72h --on-timeout wake --instruction "李雷の回答に沿って進める"

# タスクがレビュー中になるまで待つ
multica issue wakeup create OPS-56 --until-status in_review --instruction "成果物を確認してまとめる"
```

- **時間**：`--kind at` に `--after 10m` または `--at <RFC3339 の時刻>`。`--kind every --every 1h` で一定間隔（最短 1 分）。`--kind cron --cron "<5 フィールドの式>"` には `--timezone` を付けます（既定は UTC）。
- **イベント**：`--event` のあとにイベント名をカンマ区切りで書きます。`multica issue wakeup events` ですべてのイベントとフィルターを一覧できます。`--mode continuous` で繰り返し起動になります。
- **条件**：`--until-status`、`--until-assignee`、`--until-label`、`--until-property`、`--until-children-done [--stage N]`、`--until-pr checks|merged|conflicts`、`--until-issue <タスク> --until-issue-state done|ended|in_review|blocked`。1 つのウェイクアップに使える `--until-*` は 1 つだけで、`--event` とは併用できません。
- **終わり方**：CLI は待つ期限を自動では付けません。`--expires-in 72h` か `--expires-at <RFC3339 の時刻>` で終わりを決めます。`--on-timeout wake` を付けると、イベントのルールは期限が来たときにもう一度起こします。`--max-fires N`（1〜1000）で繰り返すルールの実行回数に上限を付けます。
- **返信先**：`--parent <コメント ID>` を付けると、起動後の返信が元のスレッドに入ります。

既存のルールを管理するコマンド：

| コマンド | 内容 |
|---|---|
| `multica issue wakeup list <タスク>` | タスクのウェイクアップを一覧する |
| `multica issue wakeup get <タスク> <ウェイクアップ ID>` | 1 件の設定をすべて表示する |
| `multica issue wakeup runs <タスク> <ウェイクアップ ID>` | 最近の実行、起動理由、サイレントチェックのメモ、コメントしたかどうか |
| `multica issue wakeup update <タスク> <ウェイクアップ ID>` | `create` と同じフラグで設定全体を置き換え、オンに戻す |
| `multica issue wakeup disable <タスク> <ウェイクアップ ID>` | オフにして、まだ始まっていない実行を取り下げる |
| `multica issue wakeup trigger <タスク> <ウェイクアップ ID>` | 今すぐ 1 回起こす |
| `multica issue wakeup delete <タスク> <ウェイクアップ ID>` | ルールを削除し、まだ始まっていない実行を取り下げる |
| `multica issue wakeup checkin <タスク> <ウェイクアップ ID> --note "..."` | 返信が必要なことがない定期チェックを静かに終える。このルールが始めた実行からだけ呼べる |

`list`、`get`、`runs` は `--output table` で表形式になります。ほかのコマンドは [CLI を使う](/cli)を参照してください。

## オートパイロットとの違い [#vs-autopilots]

[オートパイロット](/autopilots)はスケジュールや Webhook から新しい作業を繰り返し始め、そのたびにタスクを作ることもできます。ウェイクアップは既存の 1 つのタスクに付き、決めた時刻や出来事のあとでエージェントをそのタスクに戻らせ、タスクが終わればウェイクアップも終わります。
