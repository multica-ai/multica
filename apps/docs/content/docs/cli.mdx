The Multica CLI both connects local runtimes and manages workspaces, issues, agents, and automations from the terminal. This page covers the common paths; the flags your installed version supports are always defined by each command's own `--help`.

## First connection

Pick the service you are connecting to:

<Tabs items={["Multica Cloud", "Self-hosted instance"]}>
<Tab value="Multica Cloud">

```bash
multica setup
```

</Tab>
<Tab value="Self-hosted instance">

```bash
multica setup self-host \
  --server-url https://api.example.com \
  --app-url https://app.example.com
```

</Tab>
</Tabs>

`setup` saves the server address, opens a browser to complete sign-in, and starts the daemon. When it finishes, check:

```bash
multica auth status
multica daemon status
```

If you only need to sign in again without overwriting other configuration, run `multica login`. On a machine without a browser, create a personal access token in the web settings first, then enter it with:

```bash
multica login --token
```

The command prompts you to paste the token in the terminal, keeping the full value out of shell history.

## Choosing a workspace

List workspaces and switch the default:

```bash
multica workspace list
multica workspace switch <slug>
```

Subsequent commands use this workspace. A single command can override it with `--workspace-id`, or you can set `MULTICA_WORKSPACE_ID`.

Invite members:

```bash
multica workspace member invite teammate@example.com
multica workspace member invite admin@example.com --role admin
```

## Common issue operations

```bash
# View and search
multica issue list
multica issue get MUL-123
multica issue search "login failure"

# Create and update
multica issue create --title "Fix login failure"
multica issue status MUL-123 in_progress
multica issue assign MUL-123 --to "Backend Agent"

# Comments and runs
multica issue comment list MUL-123
multica issue comment add MUL-123 --content "Check the regression tests first"
multica issue comment update <comment-id> --expected-revision 2 --content "Check the regression tests and release notes"
multica issue runs MUL-123
```

Read long descriptions or comments from stdin to avoid dealing with newlines and quoting:

```bash
multica issue create --title "Upgrade notes" --description-stdin < notes.md
multica issue comment add MUL-123 --content-stdin < review.md
multica issue comment update <comment-id> --expected-revision 2 --content-file revised-review.md
```

View the messages of a single run, or stop one:

```bash
multica issue run-messages <task-id> --issue MUL-123
multica issue cancel-task <task-id> --issue MUL-123
```

If an open issue with the same title (case-insensitive, extra spaces ignored) already exists under the same project and parent, `issue create` refuses and points to that issue. To create another one anyway, add `--allow-duplicate`. To mark an issue as a duplicate of another, run `multica issue status MUL-124 cancelled --duplicate-of MUL-123`.

### Timeline

`issue get` shows an issue as it is now. `issue timeline` lists, in order, the changes to status, priority, assignee, title, and dates and the run outcomes, interleaved with comments, which answers questions like "when did it move to in_review" or "how long has it been stuck in this status":

```bash
multica issue timeline MUL-123 --action status_changed
multica issue timeline MUL-123 --activity-only --output json
multica issue timeline MUL-123 --since 2026-08-19T00:00:00Z
```

`--activity-only` drops comments and keeps every activity record; `--action` returns only the given actions, is repeatable, and implies `--activity-only`. The server caps how far back it reads; when the result is truncated, a warning goes to stderr, and durations should not be inferred from it.

### Reading long comment threads

On an issue with many comments, reading them one by one costs an agent a lot of tokens. Scan the threads first, then open the one you need:

```bash
multica issue comment list MUL-123 --roots-only --summary --output json --compact
multica issue comment list MUL-123 --thread <comment-id> --tail 5 --output json --compact
```

- `--roots-only` returns only top-level comments, each with its reply count and last activity time.
- `--summary` clips each comment to a short preview.
- `--compact` applies to JSON output and drops fields that carry no information (such as the echoed `issue_id` and empty arrays).
- `--recent N` returns the N most recently active threads with every reply, which can be long.
- Resolved threads are folded to their root and conclusion by default; add `--full` for the complete text.

Lists can be trimmed to the fields you need, too: `multica issue list --output json --fields id,identifier,title,status`. The filtering happens in the CLI, so it shrinks output and context, not the request.

### Wakeups

A wakeup starts an ordinary run for an agent when an event happens, a condition becomes true, or a time arrives. The full rules are in [Issue wakeups](/issue-wakeups).

```bash
multica issue wakeup events
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --event comment.created --filter-actor-type member --filter-actor-id <user-id> \
  --instruction "When they reply, update the quote from their answer"
multica issue wakeup create MUL-123 --agent-id <agent-id> \
  --kind every --every 1h --expires-in 72h \
  --instruction "Check whether the supplier has replied"
multica issue wakeup list MUL-123
multica issue wakeup runs MUL-123 <wakeup-id>
```

Creating one from a terminal as a member requires `--agent-id`; an agent creating one inside its own run wakes itself by default.

## Agents and skills

```bash
multica agent list
multica agent get <agent-id>
multica agent create --help
multica agent update <agent-id> --help

multica skill list
multica skill get <skill-id>
multica skill import --url <skill-url>
multica agent skills add <agent-id> --skill-ids <skill-id>
```

When an import hits a skill with the same name, the default is to stop without modifying existing content. Pick by intent:

```bash
multica skill import --url <skill-url> --on-conflict overwrite
multica skill import --url <skill-url> --on-conflict rename
multica skill import --url <skill-url> --on-conflict skip
```

`overwrite` is only allowed for the skill's creator and preserves the original ID and agent bindings.

Environment variables and MCP configuration often carry tokens. Values typed on the command line stay in shell history and `ps` output, so pass them through the `-file` or `-stdin` forms:

```bash
multica agent create --name "Ops helper" --runtime-id <runtime-id> \
  --custom-env-file ./agent-env.json \
  --mcp-config-file ./mcp.json \
  --custom-args '["--max-turns", "40"]'

multica agent env set <agent-id> --custom-env-stdin < agent-env.json
multica agent update <agent-id> --mcp-config-file ./mcp.json
```

- The `--custom-env` flags exist only on `agent create`. Change variables later with `agent env set`, which replaces the whole set; keys whose value is `****` keep their existing value.
- `agent update --mcp-config null` clears the MCP configuration.
- `--custom-args` is a JSON array placed at the end of the launch arguments. Choose the model with `--model`; some tools reject `--model` inside custom arguments.
- `--permission-mode` controls who can invoke the agent: `private` for the owner only, or `public_to` with `--public-to-workspace` or `--public-to-member <user-id>`. `--visibility private|workspace` is the older form and maps onto `--permission-mode`; when both are given, `--permission-mode` wins.

### Agent run history

`multica agent tasks <agent-id> --limit 200` returns the newest page of runs.
The default and maximum page size is 200. If more runs exist, stderr prints a
cursor; pass it unchanged as `--before '<cursor>'` to read the next page.
`--output json` keeps the array output and includes usage for that page only.

The corresponding `GET /api/agents/{id}/tasks` endpoint accepts `limit` and
`before`, and keeps its JSON array response. The `X-Agent-Tasks-Next-Cursor`
response header supplies the next cursor; its absence marks the final page.
Cursors preserve `(created_at, id)` order, including timestamp precision.
Invalid limits or cursors return HTTP 400; limits above 200 are capped.
Clients that do not follow the cursor receive only the newest 200 runs.


## Daemon and runtimes

```bash
multica daemon start
multica daemon stop
multica daemon restart
multica daemon status --output json
multica daemon logs --follow

multica runtime list
multica runtime rename <runtime-id> "Office Mac"
multica runtime usage <runtime-id>
multica runtime activity <runtime-id>
```

```bash
multica daemon autostart enable
multica runtime usage <runtime-id> --days 30
multica runtime update <runtime-id> --target-version <version> --wait
multica runtime profile create --display-name "Internal Claude wrapper" \
  --command-name ccms --runtime-type claude
```

`daemon autostart` registers the current profile to start at login; see [Start at login](/daemon-runtimes#autostart) for platform details. `runtime usage` covers 90 days by default, and `--days` goes up to 365. `runtime update` asks the daemon on that computer to update its CLI to the given version; `--wait` keeps polling until the update finishes. `runtime profile create` takes the compatible tool through `--runtime-type` (the older `--protocol-family` still works); fixed arguments can currently be set only in the web app.

Deleting a runtime that still has active agents bound to it is refused by default. `multica runtime delete <id> --cascade` unbinds those agents, preserves their configuration and history, and cancels their active runs.

See [Daemon and runtimes](/daemon-runtimes) for how it works and for custom profiles.

## Projects, workspaces, and autopilots

```bash
multica project create --title "Summer campaign" --lead "Lei Li" \
  --repo https://github.com/acme/campaign-site
multica project resource add <project-id> --type github_repo \
  --url https://github.com/acme/brand-assets --default-branch-hint main

multica workspace create --name "Operations" --slug ops --issue-prefix OPS
multica workspace update --context-stdin < team-context.md

multica autopilot create --title "Weekly sales report" --agent "Ops helper" \
  --mode create_issue --issue-title-template "Sales report {{date}}"
multica autopilot trigger-add <autopilot-id> --cron "0 9 * * 1" --timezone Europe/London
```

- `--lead` takes the name of a member or an agent. `--default-branch-hint` only tells the agent the repository's default branch; it does not switch branches.
- A workspace's `--context` is provided to every agent in the workspace. `--slug` cannot be changed after creation. `--issue-prefix` is uppercased; changing it renumbers every existing issue, and old identifiers in external references stop resolving.
- `--issue-title-template` interpolates only `{{date}}` (UTC, `YYYY-MM-DD`) and rejects any other `{{...}}` token. A schedule trigger's `--timezone` defaults to UTC.

## IDs and output formats

Issues use keys like `MUL-123` or full UUIDs; short UUID prefixes are not accepted.

`list` commands for other resources usually print copyable short IDs and support `--full-id` for the full UUID. When a short ID is ambiguous, the CLI asks for more characters or the full UUID. Short task IDs also require `--issue` to identify the owning issue.

Many commands support structured output:

```bash
multica issue list --output json
multica agent list --output json
```

Scripts should use JSON output rather than parsing the terminal-oriented tables. The output formats and pagination flags each command supports are defined by `multica <command> --help`.

## Profiles and configuration

The default configuration lives in `~/.multica/config.json`. Use `--profile <name>` to isolate a separate set of server address, token, default workspace, and daemon state:

```bash
multica setup self-host --profile staging \
  --server-url https://api.staging.example.com \
  --app-url https://app.staging.example.com

multica issue list --profile staging
```

Named profiles live in `~/.multica/profiles/<name>/config.json`. Inspect the current values:

```bash
multica config show
multica config show --profile staging
```

Do not set `MULTICA_DAEMON_PORT` in the host shell, Compose service, or container entrypoint that starts a daemon. The host daemon normally derives its health port from `--profile`; if that port cannot be bound, it uses an available loopback port and injects the actual port into agent tasks itself. Remove the variable from older startup environments entirely: versions 0.4.22 and 0.4.23 otherwise mistake that shell for a managed task and reject login. Newer versions let guarded human login and `daemon status` recover when the port is the only task signal, but ordinary API and profile-resolving commands intentionally remain fail-closed until the variable is removed.

When the CLI runs inside a daemon-managed agent task, it does not load or modify these human-owned profile files. Multica API commands authenticate with the task-scoped credential injected by the daemon. `config show` and `config set` use private task-local state; human/local commands such as `login`, `logout`, `setup`, `workspace switch`, local runtime profile path changes, `daemon start` / `stop` / `restart`, `daemon logs`, and `daemon probe-runtimes` are unavailable. `auth status` does not print token material in this context.

`daemon status` and `daemon disk-usage` stay available so an agent can inspect the runtime hosting it, scoped to that runtime: `status` probes the health port the daemon injected, and `disk-usage` scans the workspaces root the daemon injected. Neither accepts `--profile`, `disk-usage` also rejects `--all-profiles` and `--workspaces-root`, and its STATUS column is blank because resolving it would require the human's stored token. Use `du` and `df` for anything outside that scope.

This protects implicit Multica CLI profile resolution while preserving the normal `HOME` and XDG variables used by other provider tools. It is not an OS filesystem boundary: processes running as the same system user may still open an explicitly known path. Use a dedicated user, container, VM, or equivalent isolation when that stronger guarantee is required.

<Callout type="warning">
CLI configuration files contain tokens that can access Multica as you. Don't commit them to a repository, upload them to logs, or share them with others.
</Callout>

## Command reference

The tables below cover every current top-level command, grouped the way the CLI itself groups them. All commands accept the global flags `--server-url`, `--workspace-id`, `--profile`, and `--debug`. `--output` is registered per command, and the default format varies: `list` commands default to a table, while `get` and `create` commands mostly default to JSON. Full flags are defined by `multica <command> --help`.

| `version` | — | Print version information | `--output` (`text` or `json`) |

## Driving Multica from another coding agent

If most of your work already happens inside Codex, Claude Code, or Cursor, you can operate Multica from there instead of switching to a terminal. The [Multica CLI skill](https://github.com/multica-ai/multica-cli) teaches those agents to drive the commands on this page safely: reading issues and comment threads without burning tokens, writing comments through a file, and handling the side effects that mentions, status changes, and assignments carry.

It runs entirely through your authenticated CLI and grants no access of its own — permissions still come from your login, selected profile, and workspace. It requires CLI v0.4.26 or newer. The repository README covers installation for the Claude Code plugin marketplace, the Codex skill installer, Cursor, and any other tool that loads Markdown instructions.
