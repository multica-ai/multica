Multica는 기본적으로 이메일 인증 코드로 로그인하며 Google OAuth를 추가할 수도 있습니다. 기존 사용자는 언제든 다시 로그인할 수 있습니다. 가입 제한은 새 계정을 만들 수 있는지만 결정합니다.

## 이메일 인증 코드

사용자가 이메일을 입력하면 Multica가 6자리 인증 코드를 보냅니다. 코드는 10분 동안 유효하며 인증에 성공하면 브라우저에 로그인 cookie가 발급됩니다.

이메일은 Resend 또는 SMTP로 보낼 수 있습니다. 둘 다 설정하면 `SMTP_HOST`가 우선합니다.

### Resend 사용

1. [Resend](https://resend.com/)에서 발신 도메인을 인증하고 API key를 만듭니다.
2. 다음을 설정합니다.

   ```dotenv
   RESEND_API_KEY=re_xxxxxxxxxxxxxxxx
   RESEND_FROM_EMAIL=noreply@example.com
   ```

3. API 서비스를 다시 시작합니다.

`RESEND_FROM_EMAIL`은 Resend에서 인증한 도메인에 속해야 합니다.

### SMTP 사용

최소한 host와 발신 주소를 설정해야 합니다.

```dotenv
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=multica
SMTP_PASSWORD=<password>
SMTP_FROM_EMAIL=noreply@example.com
```

일반적인 연결 방식은 다음과 같습니다.

| 환경 | 설정 |
|---|---|
| 내부 네트워크 익명 relay | `SMTP_PORT=25`, 사용자 이름과 비밀번호는 비워 둠 |
| STARTTLS | `SMTP_PORT=587`, 서버가 지원하면 기본적으로 TLS로 업그레이드 |
| 암시적 TLS | `SMTP_PORT=465` 또는 `SMTP_TLS=implicit` 명시 |

`SMTP_FROM_EMAIL`을 설정하지 않으면 `RESEND_FROM_EMAIL`을 사용합니다. 사설 CA 또는 자체 서명 인증서를 사용하려면 컨테이너 신뢰 저장소에 CA를 추가해야 합니다. `SMTP_TLS_INSECURE=true`는 인증서 검증을 건너뛰므로 신뢰할 수 있는 내부 네트워크에서만 임시로 사용하세요.

일부 엄격한 relay에는 유효한 EHLO 이름도 필요합니다.

```dotenv
SMTP_EHLO_NAME=mail.example.com
```

### 이메일 서비스가 없을 때의 동작

서버는 계속 시작되지만 인증 코드와 초대 링크가 이메일로 전송되지 않고 로그에만 기록됩니다. 로컬 개발에는 적합하지만 프로덕션 환경에는 적합하지 않습니다.

시작 로그에는 현재 `Resend API`, `SMTP relay`, `DEV mode` 중 무엇을 사용하는지 표시됩니다.

## 로컬 고정 인증 코드

로컬 자동화 테스트에서는 고정 인증 코드를 설정할 수 있습니다.

```dotenv
APP_ENV=development
MULTICA_DEV_VERIFICATION_CODE=888888
```

인증 코드는 6자리 숫자여야 합니다. `APP_ENV=production`에서는 고정 코드가 무시됩니다.

<Callout type="warning">
공개 인터넷에 노출된 인스턴스에서 고정 인증 코드를 사용하지 마세요. 프로덕션 환경에서는 `APP_ENV=production`을 사용하고 `MULTICA_DEV_VERIFICATION_CODE`를 비워 둡니다.
</Callout>

## Google 로그인

1. [Google Cloud Console](https://console.cloud.google.com/)에서 OAuth 2.0 client를 만듭니다.
2. Multica 프런트엔드의 callback 주소를 **Authorized redirect URIs**에 추가합니다.

   ```text
   https://multica.example.com/auth/callback
   ```

3. 다음을 설정합니다.

   ```dotenv
   GOOGLE_CLIENT_ID=xxxxx.apps.googleusercontent.com
   GOOGLE_CLIENT_SECRET=GOCSPX-xxxxxxxxxxxxxxx
   GOOGLE_REDIRECT_URI=https://multica.example.com/auth/callback
   ```

4. API 서비스를 다시 시작합니다.

Google Console과 `GOOGLE_REDIRECT_URI`의 주소는 프로토콜, 포트, 마지막 슬래시까지 완전히 같아야 합니다. 설정이 적용되면 로그인 페이지에 Google 로그인 버튼이 표시됩니다. 프런트엔드 이미지를 다시 빌드할 필요는 없습니다.

## 기업 디렉터리(LDAP) 로그인

자체 호스팅한 Multica는 회사 OpenLDAP나 Active Directory에서 쓰는 사용자 이름·비밀번호로 로그인할 수 있습니다. 이메일 인증 코드, Google 로그인과 나란히 놓인 세 번째 로그인 입구이며, 성공하면 기존 세션 처리 과정을 그대로 탑니다. 따라서 하위 기능(워크스페이스, 초대, token, CLI)은 어느 입구로 로그인했는지 알지 못합니다.

1. `LDAP_*`로 디렉터리를 지정합니다. 기억할 경계는 둘입니다. 서비스 계정에 필요한 권한은 `LDAP_BASE_DN` 하위의 읽기/검색 권한뿐이고, `LDAP_USER_FILTER`에는 `%s`가 정확히 하나 있어야 합니다.

   ```dotenv
   LDAP_ENABLED=true
   LDAP_URL=ldaps://openldap.corp.example.com:636
   LDAP_BASE_DN=ou=people,dc=corp,dc=example,dc=com
   LDAP_BIND_DN=cn=lookup,dc=corp,dc=example,dc=com
   LDAP_BIND_PASSWORD=lookup-only-password
   LDAP_USER_FILTER=(uid=%s)
   ```

2. 디렉터리 종류에 맞춰 필터와 속성을 정합니다. OpenLDAP는 `uid`, AD는 `sAMAccountName`을 사용합니다.

   ```dotenv
   # OpenLDAP
   LDAP_USER_FILTER=(uid=%s)

   # Active Directory
   LDAP_USER_FILTER=(sAMAccountName=%s)
   ```

3. API 서비스를 다시 시작합니다.

`GOOGLE_CLIENT_ID`와 마찬가지로 프런트엔드가 실행 중 `/api/config`에서 활성화 여부를 알기 때문에, 웹 이미지를 다시 빌드하지 않아도 로그인 페이지에 탭이 나타납니다.

### 동작

- 로그인 이름은 디렉터리 고유의 식별자(`uid` / `sAMAccountName`)이지 이메일이 아닙니다. 요청에는 이메일 항목이 없으므로, 누군가의 주소를 입력해 계정을 탈취할 수 없습니다.
- Multica는 `users.email`로 계정을 대조합니다. `LDAP_EMAIL_ATTR` 값은 소문자로 만든 뒤 대조하며, 기존 계정은 그대로 두고 첫 디렉터리 로그인에서 새로 만듭니다. `LDAP_NAME_ATTR`는 완전히 새 계정의 표시 이름만 채우고, 기존 계정의 이메일을 덮어쓰지 않습니다.
- 비밀번호가 틀린 경우와 사용자 이름이 없는 경우 모두 같은 `401`과 같은 문구를 반환합니다. 이 엔드포인트로 디렉터리 계정을 열거할 수 없습니다. 한 사용자 이름이 여러 항목에 일치할 때도 같은 `401`이며, 아무거나 고르지 않고 서버 로그에서 중복을 정리하라고 알려줍니다.
- 디렉터리 로그인은 가입 제한 검사를 호출하지 않습니다. `ALLOW_SIGNUP`, `ALLOWED_EMAILS`, `ALLOWED_EMAIL_DOMAINS`는 여기서 작동하지 않습니다. bind 성공 자체가 허용 판단이므로, 가입을 닫아도 기존 계정은 로그인할 수 있습니다.
- 디렉터리 그룹과 Multica 역할의 대응은 만들지 않습니다. 새 계정은 어떤 워크스페이스에도 속하지 않으므로 다른 사람과 똑같이 초대를 받아야 합니다.
- 사용자 비밀번호와 서비스 계정 비밀번호 모두 로그에 남기지 않고, 디렉터리가 준 오류 문도 요약해서 기록합니다. 사용자 이름은 `LDAP_USER_FILTER`에 대입되기 전에 RFC 4515로 이스케이프되므로, 특수문자는 쿼리가 아닌 문자 그대로 일치하고 검색 범위가 넓어지지 않습니다.
- 이 엔드포인트는 인증 코드 전송·Google 로그인과 같은 속도 제한(`RATE_LIMIT_AUTH`, 기본 IP당 분당 5회)을 공유합니다. 더 넉넉한 verify-code 한도를 쓰지 않습니다.

### 오류

사용자에게 보이는 내용과 서버 로그에 남는 내용은 의도적으로 분리했습니다:

| 상태 | 의미 |
|---|---|
| `400` | 사용자 이름 또는 비밀번호를 입력하지 않음 |
| `401` | 디렉터리가 자격 증명을 거부했거나 유일한 항목을 찾지 못함 |
| `403` | Multica 계정이 일시적으로 비활성화됨 |
| `502` | 디렉터리에 연결할 수 없거나 설정이 불완전함 |
| `503` | `LDAP_ENABLED`가 `true`가 아니라 연동이 꺼진 상태 |

비밀번호가 분명히 맞는데 `502`가 나온다면 서버 로그를 보세요. 서비스 계정 bind 실패, `LDAP_USER_FILTER` 해석 실패, 항목의 `LDAP_EMAIL_ATTR`가 비어 있는 경우라면 모두 배포 측 문제이지 로그인하는 사람의 문제가 아닙니다.

디렉터리 로그인은 DB 마이그레이션이나 새 테이블을 추가하지 않습니다. 계정은 기존 `users.email` 고유 키로 대조합니다.

`LDAP_TLS_INSECURE=true`는 인증서 검증을 건너뜁니다. 디렉터리 통신(서비스 계정 비밀번호 포함)이 도청될 수 있으므로, 신뢰할 수 있는 내부 네트워크에서 임시로 연동할 때만 사용하세요:

<Callout type="warning">
디렉터리의 CA를 컨테이너 신뢰 저장소에 추가하세요. `LDAP_TLS_INSECURE=true`는 `ldaps://`(또는 `ldapi://`) 주소에서만 허용합니다. 평문 `ldap://`는 검증할 인증서 자체가 없고 비밀번호도 평문으로 전송되므로, 서버가 해당 조합을 시작 단계에서 거부합니다.
</Callout>

변수 전체와 기본값은 [환경 변수](/environment-variables#기업-디렉터리ldap)를 참고하세요.

## 가입 범위 제어

세 변수가 새 계정을 만들 수 있는지 함께 결정합니다.

| 변수 | 역할 |
|---|---|
| `ALLOWED_EMAILS` | 허용할 전체 이메일 주소, 여러 값은 쉼표로 구분 |
| `ALLOWED_EMAIL_DOMAINS` | 허용할 이메일 도메인, 여러 값은 쉼표로 구분 |
| `ALLOW_SIGNUP` | allowlist가 없을 때 가입 허용 여부, 기본값 `true` |

판단 순서는 다음과 같습니다.

1. 이메일이 `ALLOWED_EMAILS`와 일치하면 허용합니다.
2. 또는 도메인이 `ALLOWED_EMAIL_DOMAINS`와 일치하면 허용합니다.
3. 어느 것과도 일치하지 않고 `ALLOW_SIGNUP=false`이면 거부합니다.
4. `ALLOW_SIGNUP=true`여도 하나 이상의 allowlist가 설정되어 있고 일치하지 않으면 거부합니다.
5. allowlist가 없고 `ALLOW_SIGNUP=true`이면 허용합니다.

일반적인 설정:

```dotenv
# 회사 도메인만 허용
ALLOW_SIGNUP=false
ALLOWED_EMAIL_DOMAINS=company.com

# 외부 협업자 한 명 추가 허용
ALLOWED_EMAILS=partner@example.net
```

<Callout type="info">
`ALLOW_SIGNUP=false`일 때도 두 allowlist를 명시적인 예외 목록으로 사용할 수 있습니다.
</Callout>

## 초대와 가입 제한

초대는 가입 제한을 자동으로 우회하지 않습니다.

- 상대방에게 이미 Multica 계정이 있으면 로그인하고 초대를 수락할 수 있습니다.
- 상대방에게 계정이 없으면 이메일이 위의 가입 규칙을 만족해야 합니다.

공개 가입을 닫은 인스턴스에서 새 멤버를 초대할 때는 먼저 상대방 이메일을 `ALLOWED_EMAILS`에 추가하세요. 계정을 만들고 초대를 수락한 뒤 목록에서 다시 제거할 수 있습니다.

## 로그인 유효 기간

브라우저 로그인은 기본적으로 30일 동안 유지됩니다. `AUTH_TOKEN_TTL`로 조정할 수 있으며 Go duration 또는 양의 정수 초를 지원합니다.

```dotenv
AUTH_TOKEN_TTL=720h
```

변경 후 API 서비스를 다시 시작해야 합니다. 이 값은 이후 발급되는 로그인 cookie와 JWT에만 적용되며 이미 발급된 token의 기간은 연장하지 않습니다.
