Halaman ini adalah sumber kebenaran tunggal untuk naming kode, glosarium terjemahan i18n, dan panduan gaya bahasa Tionghoa. Apa pun yang sebelumnya berada di `packages/views/locales/glossary.md` atau tersebar di berbagai komentar, sekarang berada di sini.

Jika Anda menulis kode Multica, mengubah terjemahan, atau menulis copy produk dalam bahasa Tionghoa, inilah halaman yang menjadi acuan.

## 1. Naming kode

### Route

Route pre-workspace (route yang ada sebelum pengguna masuk ke ruang kerja) HARUS menggunakan satu kata saja atau pola `/{noun}/{verb}`.

- ✅ `/login`, `/inbox`, `/workspaces/new`
- ❌ `/new-workspace`, `/create-team`, `/accept-invite`

Kelompok kata berhubung tanda strip (hyphenated) di root akan bertabrakan dengan slug ruang kerja yang dipilih pengguna dan memaksa audit reserved-slug yang tak berkesudahan. Me-reserve kata benda (`workspaces`) secara otomatis melindungi seluruh subtree `/workspaces/*`.

### Route yang di-scope ke ruang kerja

Selalu berada di bawah `/{slug}/{section}` — `/{slug}/issues`, `/{slug}/agents`, `/{slug}/settings`. Jangan pernah menduplikasi logika routing ruang kerja; gunakan `useNavigation().push()` dari kode bersama, jangan pernah API link yang spesifik framework.

### Package dan module

Monorepo ini menegakkan boundary package yang ketat:

| Package | Boleh bergantung pada | TIDAK BOLEH bergantung pada |
| --- | --- | --- |
| `packages/core` | tidak ada yang spesifik app | `react-dom`, `localStorage`, `process.env`, `next/*`, UI libraries |
| `packages/ui` | tidak ada | `@multica/core`, logika bisnis |
| `packages/views` | `core/`, `ui/` | `next/*`, `react-router-dom`, store |
| `apps/web/platform/` | `next/*` | app lain |
| `apps/desktop/.../platform/` | `react-router-dom`, electron | app lain |
| `apps/mobile/` | types dan pure functions dari `@multica/core` | Halaman React Web/Desktop, store, dan implementasi platform |

Jika logika muncul di kedua app, logika itu HARUS diekstrak ke package bersama. Tidak ada pengecualian untuk duplikasi yang "kecil". Mobile memiliki UI, data layer, dan proses rilis yang terpisah; Mobile hanya membagikan types dan pure functions.

### Berkas dan komponen

- Berkas: `kebab-case.tsx` / `kebab-case.ts` (contoh: `agent-row-actions.tsx`)
- Komponen: `PascalCase` (contoh: `AgentRowActions`)
- Hooks: `useCamelCase` (contoh: `useWorkspaceId`)
- Test: diletakkan berdampingan sebagai `<file>.test.ts(x)`
- Store (Zustand): `<feature>-store.ts`, diekspor sebagai `use<Feature>Store`

### Database (Go + sqlc)

- Tabel: `snake_case` tunggal (`user`, `workspace`, `agent_runtime`)
- Kolom: `snake_case` (`workspace_id`, `created_at`, `last_seen_at`)
- Foreign key: `<table>_id`
- Boolean: `is_<state>` atau `<state>_at` (bentuk timestamp lebih disukai untuk perubahan state)
- Berkas migrasi: `NNN_descriptive_name.up.sql` + `.down.sql` — selalu sediakan kedua arah
- Jangan membuat foreign key database atau menggunakan cascade delete atau update; terapkan relasi dan cleanup di lapisan aplikasi.
- Setiap index harus menggunakan `CREATE INDEX CONCURRENTLY` atau `CREATE UNIQUE INDEX CONCURRENTLY`, dengan setiap index concurrent berada dalam berkas migrasi single-statement-nya sendiri.

### Go

- Standar `gofmt` + `go vet`. Tidak ada pengecualian.
- Berkas handler mencerminkan domain: `agent.go`, `auth.go`, `runtime.go`
- Test: `<file>_test.go` diletakkan berdampingan
- Untuk parsing UUID di handler, ikuti aturan di `AGENTS.md` root — `parseUUIDOrBadRequest` untuk input boundary, `parseUUID` (yang panic) untuk round-trip yang terpercaya, jangan pernah `util.ParseUUID` secara langsung tanpa memeriksa error-nya.

### TypeScript

- Respons API di wire menggunakan `snake_case`; api client mengonversinya ke `camelCase` di boundary. Di dalam kode TS, **selalu camelCase**.
- Types: `PascalCase` (`Issue`, `AgentRuntime`); jangan pernah prefix `I`, jangan pernah suffix `_t`.
- Enum: lebih diutamakan string literal union; simpan `enum` untuk kasus yang perlu di-iterasi saat runtime.
- TanStack Query key: factory function di `<feature>/queries.ts`, contoh `issueKeys.detail(id)`.

### Boundary API

- Parsing respons network dengan `parseWithFallback` dan skema zod dari `packages/core/api/schema.ts`; jangan men-cast-nya langsung dengan `as T`.
- Saat menambah atau mengubah endpoint, perbarui skemanya dan cakup field yang hilang atau malformed dalam test.
- UI downstream harus menyediakan default untuk field opsional, dan setiap `switch` atas enum server harus menyertakan branch `default`.
- Klien Desktop yang sudah terpasang mungkin terhubung ke backend yang lebih baru; jangan pernah mengasumsikan bahwa versi frontend dan backend selalu cocok.

### Nama tampilan runtime

`AgentRuntime.name` adalah nama teknis mentah dari daemon (contoh: `Codex (host)`); alias milik pengguna berada di `custom_name`. Copy yang terlihat pengguna tidak boleh pernah me-render `runtime.name` secara langsung — gunakan helper bersama agar alias dan provider tetap konsisten (MUL-5248, #5260):

- Label runtime mandiri (list, chip, confirm dialog, judul dokumen): `runtimeDisplayLabel(runtime)` → alias + provider, fallback ke nama daemon.
- Ketika icon/teks provider sudah berada di sebelahnya: `runtimeDisplayName(runtime)` → alias saja, tanpa duplikasi provider.
- Di dalam machine group: header machine menggunakan `machine.title`, baris anak menggunakan `runtimeRowLabel(runtime, machine.title)`.
- Runtime selector mengelompokkan berdasarkan machine melalui `buildRuntimeMachines`; jangan membuat flat list dari nama mentah.

`runtime.name` mentah hanya diperbolehkan untuk identitas internal — parsing hostname, pengelompokan, search haystack, dan protocol payload — jangan pernah untuk teks JSX, parameter i18n, label `<Select>`, atau judul window.

### Key Tugas

Setiap Tugas memiliki key yang mudah dibaca manusia seperti `MUL-123`: `issue_prefix` ruang kerja (huruf kapital dan digit, biasanya 3 karakter, maksimal 10) + nomor urut. Admin ruang kerja dapat mengubah prefix di Settings → General; mengubahnya akan menomori ulang setiap Tugas yang sudah ada, sehingga referensi eksternal yang menyematkan prefix lama (judul PR, nama branch, link di docs dan chat) berhenti bisa diselesaikan (resolve).

### Komentar di kode

Hanya bahasa Inggris. Repo ini menegakkan ini untuk Go maupun TypeScript. Jika Anda menemukan komentar bahasa Tionghoa di kode, itu adalah bug — gantilah.

### Pesan commit

Format konvensional: `feat(scope)`, `fix(scope)`, `refactor(scope)`, `docs`, `test(scope)`, `chore(scope)`. Commit atomik yang dikelompokkan berdasarkan intent.

## 2. Glosarium terjemahan i18n

Ini adalah glosarium **wajib** untuk setiap PR terjemahan. Dulunya berada di `packages/views/locales/glossary.md`; berkas itu telah dihapus dan halaman ini menggantikannya.

### Perbedaan inti: kata benda sehari-hari vs istilah khusus Multica

Kata benda produk Multica terbagi menjadi dua kategori:

- **Kata benda sehari-hari** — kata yang akan diucapkan pengguna secara lisan untuk menyebutnya. **Terjemahkan secara penuh**, baik itu entitas database atau bukan: `issue` → 任务, `workspace` → 工作区, `project` → 项目.
- **Istilah khusus Multica** — sebuah konsep yang tidak memiliki kata lokal yang pas (`skill`), atau pengenal level-skema yang mungkin harus diketik atau dicocokkan oleh pengguna (`todo`, `in_progress`, `task_id`). Tuliskan sebagai **English huruf kecil** agar terbaca seperti nama type.

Halaman bahasa Tionghoa di bawah `apps/docs/content/docs/*.zh.mdx` menjadi standar gaya bahasa de facto untuk hal lain di halaman ini. Prosa `*.zh.mdx`, `*.ja.mdx`, dan `*.ko.mdx` sekarang juga mengikuti tabel di bawah ini.

### `issue` adalah task milik produk — terjemahkan

`issue` adalah nama produk dalam bahasa Inggris untuk hal yang diajukan pengguna dan dikerjakan oleh agent. Di setiap locale lain, ini adalah **kata sehari-hari untuk "task"**:

| Entitas | en | zh-Hans | ja | ko | fr |
| --- | --- | --- | --- | --- | --- |
| unit pekerjaan yang dilacak (`issue`) | Issue | **任务** | **タスク** | **태스크** | **Tâche** |
| satu record eksekusi agent (`task` di API / DB) | **Run** | **运行** | **実行** | **실행** | **Exécution** |

Kedua konsep ini terlihat oleh pengguna dan **bukan** hal yang sama — satu Tugas dapat memiliki banyak Eksekusi. Jangan pernah membiarkan satu locale menuliskan keduanya dengan kata yang sama. `Task` bukan lagi kata benda produk yang user-facing untuk sebuah Eksekusi agent; kata ini hanya tetap digunakan sebagai pengenal internal yang sudah mapan.

Yang tidak berubah:

- **Field API / DB** tetap menggunakan `issue` / `task` / `skill` di mana saja: `issue_status`, `task_id`, `skill_uuid`. Prosa developer menyebut objek produk tersebut sebagai Run dan dapat memperjelasnya sebagai "Run (`task_id` di API)" ketika identifier-nya penting.
- **Referensi kode dan literal command** tetap bahasa Inggris: `multica issue ...`, slash command `/issue` di Slack dan Lark.
- **`skill`** tetap English huruf kecil dalam teks bahasa Tionghoa — konsep khusus Multica yang belum memiliki istilah bahasa Tionghoa yang mapan; judul dapat menuliskannya dengan kapital sebagai `Skills`.
- **`issue` dalam arti "masalah"** (runtime health) adalah kata benda biasa, bukan entitas: `{{count}} issues` pada machine card adalah `{{count}} 个异常` / `問題 {{count}} 件` / `문제 {{count}}개`, jangan pernah menggunakan kata entitas.

**Mengapa `issue` diterjemahkan sementara `skill` tidak**: pengguna mengajukan dan membaca Tugas setiap hari, dan kata "issue" tidak memiliki arti dalam bahasa Tionghoa, Jepang, atau Korea di luar jargon developer. Kata sehari-hari untuk "task" itulah yang sudah diucapkan orang untuk menyebutnya. `skill` adalah konsep khusus Multica di mana tidak ada kata lokal yang membawa makna tersebut.

Kata benda produk lainnya mengikuti tes "terjemahkan apa yang memiliki kata lokal yang sudah mapan" yang sama:

- **`project` → "项目"**: kata bahasa Tionghoa mainstream yang sudah mapan. Feishu / Tower / Teambition / PingCode / GitHub Projects — setiap produk bahasa Tionghoa menerjemahkannya. Tidak ada produk yang mempertahankan `project` dalam konteks bahasa Tionghoa.
- **`autopilot` → "自动化"**: dalam bahasa Tionghoa, "autopilot" diasosiasikan dengan "自动驾驶" milik Tesla dan tidak cocok dengan apa yang dilakukan fitur ini (memulai Eksekusi agent berdasarkan jadwal). Notion dan Feishu keduanya menggunakan "自动化"; itulah konsensus industri.

### Role dan status enum (English huruf kecil, tidak diterjemahkan)

Ini adalah pengenal level-skema; tuliskan sebagai English huruf kecil bahkan dalam konteks bahasa Tionghoa.

- Role: `owner` / `admin` / `member`
- Status Tugas: `backlog` / `todo` / `in_progress` / `in_review` / `done` / `blocked` / `cancelled`
- Kategori status Tugas: `unstarted` / `started` / `done` / `closed`

Di UI, tampilkan dalam bahasa Inggris (opsional dibungkus `code-style`):

- "你需要 owner 权限"
- "已切换到 in_progress"

### Aturan kombinasi kata

Selalu beri **satu spasi** di antara kata bahasa Inggris (entity / brand / akronim) dan teks bahasa Tionghoa di sekitarnya:

- "Create new issue" → "新建任务"（`任务` adalah bahasa Tionghoa, sehingga tidak perlu spasi)
- "Assign to agent" → "分配给智能体"
- "Configure runtime" → "配置运行时"
- "Stop daemon" → "停止守护进程"

### Plural dan hitungan

i18next menggunakan `_one` / `_other`; bahasa Tionghoa tidak memiliki grammatical number, jadi hanya isi `_other`.

```json
// en/issues.json
{
  "issue_count_one": "{{count}} issue",
  "issue_count_other": "{{count}} issues"
}

// zh-Hans/issues.json
{
  "issue_count_other": "{{count}} 个任务"
}
```

Format hitungan yang umum:

- `{{count}} issues` → `{{count}} 个任务`
- `{{count}} agents` → `{{count}} 个智能体`
- `{{count}} workspaces` → `{{count}} 个工作区`
- `{{count}} comments` → `{{count}} 条评论`
- `{{count}} members` → `{{count}} 位成员`
- `{{count}} skills` → `{{count}} 个 skill`

### Interpolasi

Gunakan `{{var}}`. Terjemahan bahasa Tionghoa dapat mengubah urutan demi alur kalimat yang natural.

```json
// en
{ "welcome_message": "Welcome back, {{name}}!" }

// zh-Hans
{ "welcome_message": "欢迎回来，{{name}}！" }
```

### Naming key terjemahan

Nesting tiga level: `feature.component.action`.

```json
{
  "feature_or_component": {
    "subcomponent_or_section": {
      "action_or_label": "..."
    }
  }
}
```

Contoh:

- `issues.toolbar.batch_update_success`
- `issues.detail.comment_form.placeholder`
- `inbox.empty.title`
- `settings.preferences.language.title`

### Copy khusus web / khusus desktop

- Copy bersama: level teratas dari JSON namespace
- Khusus web: section `web`
- Khusus desktop: section `desktop`

Lihat `auth.json` untuk contoh kanonikalnya (section `web` berisi `prefer_desktop` / `desktop_handoff.*`).

## 3. Gaya dan nada bahasa Tionghoa

### Tanda baca

- Tanda baca full-width dalam bahasa Tionghoa: `，。：；！？`
- Tanda kutip: tanda kutip ganda lurus `"..."` untuk menyesuaikan sumber bahasa Inggris. Jangan gunakan `「」` atau tanda kutip lengkung (curly quotes).
- Elipsis: tiga titik `...`, bukan karakter tunggal `…`. Sesuaikan dengan sumber bahasa Inggris.
- Campuran Tionghoa-Inggris: satu spasi di setiap sisi kata bahasa Inggris (lihat Aturan kombinasi kata).

### Prinsip gaya

- **Ringkas dan langsung.** Hindari "translation-ese" (gaya terjemahan yang kaku): "对于 X 来说"、"作为 X"、"我们的"。
- **Pesan error**: lembut tetapi jelas. "无法保存修改" lebih baik daripada "保存修改失败了！".
- **Button**: kata kerja di awal, 2–4 karakter. "取消"、"保存修改"、"立即同步".
- **Tooltip**: kalimat pendek yang lengkap. "复制链接到剪贴板".
- **Placeholder**: bergaya contoh. "输入任务标题...".

### Deskripsi UI

Deskripsi bersifat opsional dan secara default dihilangkan. Sebelum menambahkannya, tanyakan: **Apa yang akan disalahpahami atau dilakukan secara salah oleh pengguna tanpa kalimat ini?** Jika judul, label, control, value, atau button sudah menjawabnya, hilangkan kalimat tersebut.

- Nyatakan satu fakta sekali saja, di sebelah control yang relevan. Jangan mengulanginya di seluruh deskripsi page, section, row, empty state, dan dialog.
- Lebih utamakan label atau contoh yang presisi dibandingkan paragraf yang menjelaskan tindakan yang sudah jelas. Hindari instruksi generik seperti "Buat satu untuk mulai", "Klik di bawah", atau "Anda dapat mengubahnya nanti" kecuali itu menyelesaikan ambiguitas yang nyata.
- Jaga agar izin, biaya, konsekuensi destruktif, prasyarat eksekusi, batasan input, dan pemulihan error tetap terlihat jika relevan. Jangan menyembunyikannya di help yang hanya muncul saat hover.
- Tampilkan panduan pengantar hanya di tempat yang dibutuhkan. Letakkan penggunaan tingkat lanjut dan diagnostik di help yang eksplisit dan mudah diakses, bukan di body halaman default.
- Pertahankan label input, accessible name, dan asosiasi deskripsi yang dibutuhkan. Jangan memindahkan seluruh prosa yang terlihat dan redundan ke teks screen-reader-only.
- Review copy bahasa Inggris dan hasil terjemahannya bersamaan, termasuk string independen milik mobile. Dalam PR review, periksa informasi yang ditambahkan, repetisi dalam screen yang sama, kondisi tampil, dan batasan yang dipertahankan. Panjang adalah sinyal review, bukan aturan penghapusan otomatis.

Komponen settings bersama sudah menerima deskripsi opsional. Contoh dan call site baru sebaiknya menghilangkannya kecuali ada justifikasi; jangan menambahkan prop deskripsi yang wajib atau policy copy yang terpisah.

### Ke mana harus melihat jika ragu

Ketika glosarium tidak mencakup suatu istilah, lihat:

1. `apps/docs/content/docs/*.zh.mdx` — standar gaya bahasa Tionghoa de facto, 20+ halaman terjemahan yang konsisten
2. `packages/views/locales/zh-Hans/auth.json` dan `editor.json` — struktur JSON + pola selector API
3. `packages/views/auth/login-page.tsx` — call site selector API tingkat komponen
4. `packages/views/settings/components/preferences-tab.tsx` — referensi language switcher
