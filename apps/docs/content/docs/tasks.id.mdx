Setiap kali seorang agent mulai bekerja, Multica membuat sebuah **eksekusi** yang mencatat apa yang memicu pekerjaan itu, agent mana yang menerimanya, seberapa jauh progresnya, dan apakah berhasil.

## Tugas dan eksekusi

Sebuah tugas menyimpan tujuan, diskusi, penerima tugas, dan status akhir dari sebuah pekerjaan; sebuah eksekusi mencatat satu kali agent berjalan terhadap pekerjaan tersebut.

| | Tugas | Eksekusi |
| --- | --- | --- |
| Apa yang dicatat | Sebuah pekerjaan yang terus berjalan | Satu kali agent berjalan |
| Berapa lama berlangsung | Dapat didiskusikan, diubah, dan ditugaskan ulang berulang kali | Dari pemicu hingga selesai, gagal, atau dibatalkan |
| Kardinalitas | Satu tugas dapat mencakup banyak eksekusi | Setiap eksekusi mendapat catatannya sendiri |

Tugas yang sama dapat diserahkan ke agent yang berbeda secara bergantian, atau dijalankan lagi setelah gagal. Setiap eksekusi menghasilkan catatan eksekusi baru; catatan sebelumnya tidak pernah ditimpa.

## Sumber pemicu

Setiap hal berikut memicu sebuah eksekusi:

- Menugaskan sebuah tugas ke agent atau Squad.
- Mention seorang agent di komentar.
- Mengirim pesan ke agent di obrolan.
- Sebuah Autopilot yang berjalan terjadwal atau dari peristiwa eksternal.
- Sebuah [wakeup tugas](/issue-wakeups) yang berjalan pada peristiwa, waktu, atau kondisinya.

Agent mendapat konteks yang berbeda tergantung titik masuknya, tetapi eksekusinya berjalan dengan cara yang sama: Multica membuat eksekusi, sebuah runtime mengklaimnya, dan runtime menjalankan alat pengkodean AI yang dikonfigurasikan pada agent tersebut.

## Siklus hidup eksekusi

Sebuah eksekusi biasanya melalui state berikut:

| State | Arti |
| --- | --- |
| `deferred` | Dijadwalkan untuk berjalan nanti; masuk antrean pada waktu yang ditentukan |
| `queued` | Menunggu sebuah runtime mengklaimnya |
| `dispatched` | Sebuah runtime telah mengklaimnya dan sedang memulai alat pengkodean AI |
| `waiting_local_directory` | Menunggu direktori lokal target atau slot eksekusi daemon sebelum dimulai |
| `running` | Alat pengkodean AI sedang berjalan |
| `completed` | Eksekusi selesai secara normal |
| `failed` | Eksekusi mengalami error atau terinterupsi |
| `cancelled` | Eksekusi dihentikan secara manual |

Saat runtime online, eksekusi baru biasanya mulai dengan cepat; jika runtime menjadi offline setelah eksekusi masuk antrean, eksekusi itu tetap dalam antrean sampai runtime pulih. Menunggu lama tidak membuat eksekusi yang diantrekan kedaluwarsa: runtime yang terus mengirim heartbeat berarti sibuk, bukan hilang, sehingga antreannya dapat terurai selama diperlukan. Sebuah eksekusi yang diantrekan hanya gagal ketika **kedua** kondisi terpenuhi: runtime-nya telah diam lebih lama dari masa tenggang reconnect, **dan** eksekusi itu sendiri sudah diantrekan selama itu juga. Kondisi kedua ini mencakup pekerjaan yang ditugaskan ke komputer yang sudah tertidur: alih-alih langsung gagal, eksekusi tersebut mendapat masa tenggang penuh bagi Anda untuk menghidupkan komputer itu.

<Callout type="info">
Jika sistem sudah tahu runtime target sedang offline sebelum pemicu terjadi, beberapa tindakan langsung melaporkan bahwa eksekusi tidak dapat dimulai sekarang, alih-alih membuat eksekusi yang tidak dapat diklaim siapa pun.
</Callout>

Runtime dengan heartbeat yang sehat dapat menjalankan eksekusi yang lama; server tidak pernah memaksa mengakhiri sebuah eksekusi hanya karena sudah berjalan cukup lama. Runtime yang menentukan apakah prosesnya sudah macet berdasarkan aktivitas sebenarnya; lihat [Environment variables](/environment-variables#konfigurasi-daemon) untuk pengaturan terkait.

## Melihat riwayat eksekusi

Setiap eksekusi yang dihasilkan sebuah tugas terdaftar di bagian **Execution log** pada sidebar kanan tugas tersebut. Bagian ini terbuka secara default: eksekusi yang aktif tetap disematkan di atas, diikuti 3 eksekusi selesai terbaru di bawah **Latest**; klik **Open timeline** untuk yang lebih lama. Setiap baris menunjukkan sumber pemicu, agent yang mengeksekusi, dan state. Jika Anda tidak melihat bagian ini, buka sidebar dengan tombol panel di header tugas; pada layar sempit bagian ini dimulai dalam keadaan terlipat.

Selama halaman terbuka, log memperbarui diri melalui koneksi realtime: eksekusi baru, perubahan status, dan komentar agent muncul tanpa memuat ulang.

Selama agent bekerja, header tugas juga menampilkan chip langsung seperti "Engineer is working". Mengarahkan kursor ke chip itu menunjukkan eksekusi aktif yang sama, sehingga Anda dapat memeriksa progres tanpa meninggalkan halaman.

Di execution log Anda dapat:

- Klik **View transcript** pada sebuah baris untuk melihat pesan agent, pemanggilan tool, dan output error. Untuk eksekusi yang masih berjalan, transcript tetap mengalir selama dialog terbuka, dan toggle **Newest first** membalik urutan peristiwa.
- Menghentikan eksekusi yang berstatus queued, starting, menunggu direktori lokal, atau working.
- Mencoba ulang eksekusi yang gagal atau dibatalkan.

Demo di bawah ini menunjukkan satu siklus penuh: sebuah eksekusi diantrekan, dimulai, lalu gagal; Anda mencoba ulang dan eksekusi baru selesai. Setelah eksekusi baru dimulai, Anda juga dapat mencoba menghentikannya di tengah jalan.

Header execution log menampilkan apa yang sudah dihabiskan tugas sejauh ini. **Open timeline** membuka dialog **Runs**, yang menjumlahkan **Spent**, **Tokens**, dan **Agent time**, menampilkan grafik biaya per eksekusi atau kumulatif, membaginya menurut agent dan model, serta menghitung eksekusi yang gagal dan dibatalkan. Biaya merupakan estimasi; lihat [Analytics](/analytics#biaya-tugas) untuk cara penghitungannya dan untuk penggunaan di seluruh ruang kerja.

## Kegagalan dan percobaan ulang otomatis

Gangguan sementara — runtime yang sebentar offline, daemon yang restart, timeout eksekusi, atau gangguan jaringan pada alat pengkodean AI — dapat memicu percobaan ulang otomatis. Sebuah eksekusi reguler secara default berjalan paling banyak dua kali; gangguan jaringan tool mendapat hingga tiga kali percobaan.

Error yang dikembalikan oleh agent itu sendiri biasanya tidak dicoba ulang secara otomatis. Kredensial yang kedaluwarsa, kuota yang habis, kesalahan konfigurasi, atau model yang tidak dapat menyelesaikan permintaan semuanya perlu diperbaiki penyebabnya dulu, lalu dicoba ulang secara manual.

Mode **run only** pada sebuah Autopilot tidak mencoba ulang secara otomatis, untuk menghindari tumpang tindih dengan eksekusi terjadwal selanjutnya. Mode **create issue** menghasilkan eksekusi tugas biasa, sehingga kegagalan infrastruktur tetap mendapat percobaan ulang menurut aturan di atas. Kedua mode menampilkan hasil akhirnya di riwayat eksekusi Autopilot.

Ketika sebuah tugas tidak memiliki eksekusi aktif lain dan tidak ada percobaan ulang baru yang menunggu, kegagalan memindahkan tugas berstatus `in_progress` kembali ke `todo`.

## Percobaan ulang manual

Mengklik tombol retry pada sebuah baris di execution log memanggil **agent yang menangani eksekusi itu pada saat itu**. Bahkan jika tugas sudah ditugaskan ulang sejak itu, percobaan ulang tidak beralih ke penerima tugas yang baru.

Sebuah percobaan ulang mempertahankan file yang sudah ditulis eksekusi sebelumnya ke direktori lokal sedapat mungkin. Jika sesi aslinya masih aman dan runtime yang sama mengklaim percobaan ulang itu, sesi tersebut dilanjutkan. Error yang merusak sesi, seperti context overflow atau permintaan yang tidak valid, memulai sesi baru di atas direktori kerja aslinya. Saat direktori aslinya sudah tidak ada lagi, direktori kerja baru digunakan.

Temukan eksekusi sumbernya dan coba ulang dari CLI:

```bash
multica issue runs <issue-id> --full-id
multica issue rerun-task <run-id>
```

UUID eksekusi lengkap berfungsi tanpa `--issue`; prefiks pendek memerlukan `--issue` untuk memilih tugasnya. Ini mengulang agent dan konteks pemicu asli dengan aturan kontinuitas yang sama seperti tombol retry. Tambahkan `--fresh` untuk memulai sesi dan direktori kerja baru.

Perintah lama `multica issue rerun <issue-id>` sudah deprecated dan disembunyikan dari help. Perintah itu tetap tersedia untuk skrip yang sudah ada dan masih memulai penerima tugas saat ini dengan sesi serta direktori kerja yang baru.

## Selesainya eksekusi dan selesainya tugas

`completed` hanya berarti eksekusi tertentu ini berakhir secara normal; ini tidak memastikan bahwa tujuan tugas sudah tercapai. Setelah eksekusi berakhir, Anda masih dapat meninjau hasilnya, terus berdiskusi, menambah persyaratan, atau memicu agent itu lagi. Apakah tugas sudah selesai ditunjukkan oleh statusnya.

## Referensi cepat state dan timeout

Angka-angka di bawah ini adalah default server.

| State | Arti | Timeout dan konsekuensi |
| --- | --- | --- |
| `deferred` | Dijadwalkan untuk berjalan nanti | Masuk `queued` pada waktu yang dijadwalkan, lalu aturan di bawah berlaku |
| `queued` | Menunggu sebuah runtime mengklaimnya | Menunggu selama runtime-nya terus mengirim heartbeat, dan dalam setiap kasus setidaknya satu masa tenggang reconnect setelah diantrekan; hanya gagal ketika kedua jendela waktu sudah lewat, dan tidak dicoba ulang secara otomatis |
| `dispatched` | Diklaim; tool sedang memulai | Dianggap gagal setelah lebih dari **5 menit** dalam state ini |
| `waiting_local_directory` | Menunggu direktori lokal dan kapasitas eksekusi | Tidak memiliki timeout sendiri; melanjutkan startup setelah direktori dan slot eksekusi daemon tersedia |
| `running` | Alat pengkodean AI sedang berjalan | Tidak ada batas durasi tetap; keberlangsungannya mengikuti heartbeat runtime — satu setiap 15 detik; runtime yang kehilangan heartbeat ditandai offline paling lambat sekitar 3 menit. Eksekusinya gagal hanya setelah heartbeat hilang lebih lama dari masa tenggang reconnect (`MULTICA_RUNTIME_RECONNECT_GRACE`, 3 jam secara default); restart daemon mengklaim kembali eksekusi tersebut secara langsung |

Percobaan ulang otomatis hanya mencakup gangguan sementara di bawah ini, dan hanya berlaku untuk eksekusi yang terikat pada sebuah tugas atau obrolan (tidak termasuk mode **run only** Autopilot):

| Alasan kegagalan yang dapat dicoba ulang otomatis | Batas percobaan |
| --- | --- |
| Runtime offline | 2 secara default (eksekusi pertama + 1 percobaan ulang) |
| Diklaim kembali setelah daemon restart | 2 secara default |
| Timeout eksekusi yang dinilai platform | 2 secara default |
| Codex macet tanpa output bermakna | 2 secara default |
| Kegagalan unduhan paket skill | 2 secara default (proses agent belum dimulai pada titik ini; paket yang sudah terunduh berasal dari cache lokal) |
| Gangguan jaringan tool | Hingga 3; percobaan terakhir dimulai setelah penundaan sekitar 5 detik |

Semua alasan kegagalan lainnya (autentikasi, kuota, konfigurasi, model, dan sebagainya) tidak pernah dicoba ulang secara otomatis; perbaiki penyebabnya dulu, lalu coba ulang secara manual.
