태스크는 Multica에서 작업을 계획하는 기본 단위입니다. 기능 하나, 버그 하나, 조사 하나처럼 멤버나 에이전트가 책임지고 진행해야 하는 모든 작업이 태스크가 될 수 있습니다. 관련 논의, 상태 변경, 모든 실행이 한곳에 남으므로 채팅 기록이나 터미널 로그에서 컨텍스트를 다시 조합할 필요가 없습니다.

## 태스크의 구성

| 내용 | 용도 |
|---|---|
| **제목과 설명** | 목표, 배경, 요구 사항, 인수 조건입니다. |
| **상태와 우선순위** | 작업이 어느 단계에 있고 무엇을 먼저 처리할지 나타냅니다. |
| **담당자** | 워크스페이스 멤버, 에이전트 또는 스쿼드입니다. |
| **날짜, 라벨, 사용자 지정 속성** | 계획, 분류, 팀 고유 필드입니다. |
| **프로젝트와 상하위 관계** | 더 큰 작업 범위에 포함하거나 하위 태스크로 나눕니다. |
| **활동과 실행 로그** | 댓글, 상태 변경, 작업, 에이전트가 반환한 결과입니다. |

![태스크 상세: 설명, 논의, 오른쪽 속성, 실행 로그](/images/docs/quickstart-run-result.webp)

## 태스크 만들기

**태스크** 페이지나 프로젝트에서 새 태스크를 만들고 제목을 입력합니다. 다른 속성은 언제든 보충할 수 있습니다.

각 태스크에는 `MUL-123` 같은 번호가 있습니다. 숫자는 워크스페이스 안에서 증가합니다. 관리자가 워크스페이스의 태스크 접두사를 바꾸면 번호가 새 접두사로 표시됩니다. 자세한 내용은 [워크스페이스](/workspaces#워크스페이스-만들기)를 참고하세요.

## 담당자 선택

| 담당자 | 결과 |
|---|---|
| **멤버** | 해당 멤버가 후속 작업을 책임지며 작업은 생성되지 않습니다. |
| **에이전트** | 해당 에이전트의 작업이 생성됩니다. |
| **스쿼드** | 스쿼드 리더가 먼저 받은 뒤 누구에게 맡길지 결정합니다. |

에이전트나 스쿼드에 할당할 때 태스크가 `backlog` 상태가 아니면 즉시 큐에 들어갑니다. 런타임이 오프라인이면 작업은 큐에서 기다립니다. 보관된 에이전트와 스쿼드는 할당할 수 없습니다.

할당은 에이전트의 접근 범위(Access)를 우회하지 않습니다. 스쿼드에 할당하면 리더의 Access를 확인합니다. 자세한 내용은 [태스크를 에이전트에게 할당하기](/assigning-issues)를 참고하세요.

## 상태

모든 워크스페이스에는 기본 상태 7개가 준비되어 있습니다. 이 7개는 곧 7개의 **카테고리**, 즉 Multica가 알고 있는 동작의 집합이기도 하며 그 수는 고정되어 있습니다. 각 기본 상태가 자기 카테고리의 이름인 셈입니다.

| 상태 | 의미 |
|---|---|
| `backlog` | 지금은 시작하지 않습니다. 에이전트에게 할당된 태스크도 `backlog`에서 벗어나야 작업이 생성됩니다. |
| `todo` | 작업이 명확하며 시작을 기다립니다. |
| `in_progress` | 처리 중입니다. |
| `in_review` | 결과가 있으며 검토를 기다립니다. |
| `done` | 완료되었습니다. |
| `blocked` | 지금은 계속 진행할 수 없습니다. |
| `cancelled` | 더 이상 진행하지 않으며 기록은 유지합니다. |

상태 사이에는 고정된 전환 순서가 없으며 멤버와 에이전트 모두 상태를 직접 변경할 수 있습니다.

<Callout type="info">
다음 두 가지 변경은 시스템이 수행합니다.

- 실행이 실패하고 해당 태스크에 다른 실행이 없으며 재시도도 트리거되지 않으면 `in_progress`가 `todo`로 돌아갑니다.
- 연결된 GitHub PR이 종료 의도를 포함한 채 병합되고, 여전히 open 또는 draft 상태인 다른 연결 PR이 없으면 태스크가 `done`으로 바뀝니다.
</Callout>

### 사용자 지정 상태

워크스페이스의 owner 또는 admin은 **설정 → 태스크 상태**에서 `Code Review`, `QA`, `Rework` 같은 상태를 직접 추가할 수 있습니다. 새 상태는 7개 카테고리 중 하나를 고르고, 그 카테고리의 동작을 그대로 물려받습니다.

| 카테고리 | 해당 카테고리의 상태가 공통으로 하는 일 |
|---|---|
| `backlog` | 보류. 에이전트에게 할당해도 실행이 시작되지 않습니다. 이 카테고리 밖으로 옮길 때 실행이 시작되며, 대상이 `done`이나 `cancelled`이면 시작되지 않습니다. |
| `todo` | 시작 대기. `backlog`와 달리 이 카테고리의 태스크는 에이전트를 할당하는 즉시 실행이 시작됩니다. |
| `in_progress` | 작업 중으로 간주합니다. 다른 실행이 없는 상태에서 실행이 실패하면 태스크가 `todo`로 돌아갑니다. |
| `in_review` | 전달 완료, 리뷰 대기로 간주합니다. [오토파일럿](/autopilots) 실행을 마무리하고, 이전의 "실행 실패" 알림도 자동으로 보관됩니다. |
| `done` | 완료로 간주합니다. 하위 태스크의 단계를 끝내고 상위 태스크의 진행도에 반영됩니다. |
| `blocked` | 외부 의존성으로 멈춘 상태이며 저절로 재개되지 않습니다. |
| `cancelled` | 더 이상 진행하지 않지만 기록은 남깁니다. 하위 태스크 단계에서는 마찬가지로 종료로 취급합니다. |

그래서 `in_review` 카테고리의 `Code Review` 상태는 `in_review`와 똑같이 오토파일럿 실행을 마무리하고, 태스크를 `backlog`에서 `todo` 카테고리의 `Rework` 상태로 옮기면 `todo`로 옮길 때와 똑같이 담당 에이전트가 시작됩니다.

이름은 팀이 읽는 것이고, 플랫폼이 따르는 것은 카테고리입니다. 이 문서의 다른 곳에서 어떤 상태가 무언가를 트리거한다고 설명하면 그 규칙은 카테고리의 것이므로 같은 카테고리의 사용자 지정 상태에도 적용됩니다. 반대 방향은 성립하지 않습니다. 플랫폼이 스스로 상태를 지정할 때, 예를 들어 위의 `todo`로 되돌리는 동작이나 병합된 PR의 `done`은 그 카테고리의 사용자 지정 상태가 아니라 기본 상태를 기록합니다.

여기에서 네 가지가 따라옵니다.

- **카테고리는 상태를 만든 뒤에는 바꿀 수 없습니다.** 나중에 바꾸면 이미 그 상태인 모든 태스크의 동작을 조용히 다시 쓰게 되므로, 편집 화면에서 읽기 전용입니다. 동작을 먼저 정하고 이름을 붙이세요.
- **보드의 열은 상태가 아니라 카테고리입니다.** 상태를 추가해도 열이 늘지 않고, 카테고리마다 열이 하나씩 있습니다. 사용자 지정 상태는 자기 카테고리의 열에 들어가고, 카드에는 상태 이름이 적힌 작은 칩이 붙어 In Review 열 안에서도 `Code Review`와 `QA`를 구분할 수 있습니다.
- **기본 상태는 잠겨 있습니다.** 이름, 색, 카테고리를 바꿀 수 없고 보관할 수도 없습니다. 이 페이지를 한 번도 열지 않은 워크스페이스의 보드는 예전과 완전히 동일합니다.
- **보관은 비활성화이지 삭제가 아닙니다.** 이미 그 상태인 태스크는 이름도 색도 동작도 그대로 유지합니다. 다음에 누군가 상태를 지정할 때 선택지로 나오지 않을 뿐입니다.

기본 상태는 인터페이스 언어로 번역되지만, 사용자 지정 상태는 입력한 이름이 그대로 표시됩니다. API와 CLI는 키로 참조합니다: `multica issue status MUL-42 code_review`. 설정 페이지는 이름에서 키를 생성하고, API는 키를 직접 지정할 수 있으며 생략했을 때만 이름에서 생성합니다. 어느 쪽이든 키는 만들 때 확정되며, 나중에 이름을 바꿔도 키는 바뀌지 않습니다.

## 태스크와 작업

태스크는 계속 유지되는 작업 기록이고 [작업(task)](/tasks)는 에이전트가 한 번 실행한 기록입니다. 하나의 태스크에서 첫 구현, 추가 수정, 재검토처럼 여러 작업이 차례로 생성될 수 있습니다. 작업이 "완료됨"인 것은 이번 실행이 끝났다는 뜻일 뿐이며, 태스크의 완료 여부는 태스크 상태를 기준으로 판단합니다.

## 프로젝트와 하위 태스크

하나의 태스크는 최대 하나의 [프로젝트](/projects)에 속할 수 있습니다. 프로젝트는 그 안의 실행에 공유 설명과 리소스를 제공합니다. 다른 프로젝트로 옮겨도 복사본이 만들어지지 않습니다.

큰 작업은 하위 태스크로 나눌 수 있습니다. 상위 태스크에는 전체 목표를 남기고 하위 태스크는 각각 독립적으로 진행합니다. 상위와 하위 태스크의 상태는 서로 연동되지 않습니다.

하위 태스크에는 **단계**(stage)를 지정해 1, 2, 3처럼 묶어서 진행할 수 있습니다. 현재 가장 이른 미완료 단계의 모든 하위 태스크가 `done` 또는 `cancelled`가 되면 상위 태스크에 "하위 태스크 완료" 알림이 전달됩니다. 상위 태스크 담당자가 에이전트이면 에이전트가 깨어나 다음 단계로 진행할지 결정합니다. 단계를 지정하지 않은 하위 태스크는 같은 묶음으로 간주하며 모두 끝났을 때 한 번 알립니다.

## 보기 전환

태스크 페이지에서는 목록, 보드, 표, 간트 차트, 스윔레인 다섯 가지 보기를 제공합니다. 상태, 담당자, 프로젝트, 기타 속성으로 필터링하고 정렬할 수 있으며 모두 같은 태스크 집합을 표시합니다.

## 태스크 삭제

모든 워크스페이스 멤버가 태스크를 삭제할 수 있습니다.

<Callout type="warning">
삭제는 복구할 수 없습니다. 태스크와 댓글, 첨부 파일, 관련 기록이 영구적으로 제거되고 끝나지 않은 작업도 취소됩니다. 더 이상 진행하지 않으려면 상태를 `cancelled`로 바꾸세요. 논의와 결과는 계속 확인할 수 있습니다.
</Callout>
