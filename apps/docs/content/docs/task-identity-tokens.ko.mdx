작업 아이덴티티 토큰은 에이전트가 사내 시스템(ERP, 관리자 백엔드, wiki)에 **실행을 트리거한 본인**으로서 접근하도록 합니다. 공유 서비스 계정을 거치지 않습니다.

클레임 시점에 서버가 해당 실행의 책임자를 명시한 단명 JWT에 서명하고, 데몬이 이를 에이전트 프로세스에 주입합니다. 에이전트는 그 토큰을 사내 시스템에 제시하고, 시스템은 그 사람이 보낸 요청으로 인식해 이미 그 사람에게 설정된 권한을 적용합니다.

설정하지 않으면 비활성입니다. 미설정 배포는 이전과 완전히 동일하게 동작하며 **아이덴티티 토큰** 탭도 숨겨진 채로 유지됩니다.

<Callout type="info">
이것은 셀프 호스팅 기능입니다. 서명되는 것은 **다른 신뢰 도메인**의 자격 증명입니다 —— Multica 외부의, 이를 받아들이기로 선택한 시스템을 위한 것입니다. 에이전트의 Multica 자체 API 접근은 변하지 않고 소유자 권한 범위로 유지됩니다.
</Callout>

## 서비스 계정으로는 부족한 이유

에이전트를 사내 시스템에 연결하려면 보통 서비스 계정을 발급하게 되는데, 이는 두 가지를 동시에 무너뜨립니다.

- **권한이 한 단계로 붕괴됩니다.** 모든 사용자의 에이전트가 동일한 고정 신원으로 동작하며, 신입 엔지니어의 에이전트도 서비스 계정이 도달할 수 있는 모든 것에 도달할 수 있습니다.
- **감사가 익명이 됩니다.** 사내 시스템에는 "봇이 했다"는 기록만 남습니다. 실제로 누가 요청했는지가 사라지는데, 그것이야말로 감사가 가장 필요로 하는 한 가지입니다.

작업 아이덴티티 토큰은 이 트레이드오프를 제거합니다. 권한 모델은 바뀌지 않습니다. 시스템은 여전히 이것이 누구인지 확인하고, 그 권한을 적용하고, 그 이름을 기록합니다 —— 받는 대상이 공유 봇이 아니라 실제 사람이 될 뿐입니다.

## 동작 방식

1. **사람이 실행을 트리거합니다** —— issue 배정, 댓글, 위임.
2. **서버가 책임자를 해석하고**(실행의 귀속 정보에서), 에이전트가 활성화한 각 아이덴티티 토큰에 대해 그 사람을 `sub`에, 실행하는 에이전트를 `act_*` 클레임에 담아 JWT에 서명합니다.
3. **데몬이 토큰을 주입합니다** —— 템플릿에 지정된 변수 이름(예: `BOT_TOKEN_ERP`)으로 에이전트 프로세스 환경에 넣습니다.
4. **에이전트가 시스템을 호출합니다** —— 토큰을 bearer 자격 증명으로 실어서.
5. **시스템이 토큰을 검증합니다** —— 게시된 공개 키로 서명을 검증하고, `sub`를 자체 사용자 레코드에 매핑하고, 그 사용자의 기존 권한과 감사를 적용합니다.

1〜3단계는 Multica 내부에서 일어나고, 4〜5단계가 [직접 구축하는 연동](#두-가지-연동-경로)입니다. Multica는 시스템에 대한 어떠한 권한도 얻지 않습니다 —— 누가 요청하는지, 어떤 에이전트가 대신 실행하는지를 검증 가능하게 진술할 뿐입니다.

<Callout type="info">
정확히 말하면 이것은 [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693) 의미의 **위임 기반 사용자 대행**입니다. `sub`는 위임하는 사람, `act_sub` / `act_name`은 그를 대신해 실행하는 에이전트입니다. GitHub Actions OIDC 같은 워크로드 증명이 **아니며**, 위임이 수반하는 신뢰 의무를 전제로 검토해야 합니다.
</Callout>

## 누가 신원을 얻는가

신원은 실행의 귀속 정보에서 오며, **정밀한 출처만 서명됩니다** —— 아무도 승인하지 않은 실행은 토큰을 받지 못하고, 실행은 정상적으로 진행되며, 토큰이 필요했던 쪽에는 일반적인 "미인가"가 보일 뿐 작업 실패가 되지 않습니다.

| 출처 | 서명 |
| --- | --- |
| `direct_human`, `delegation`, `comment_source`, `trigger_owner`, `rule_owner` | 예 |
| `owner_fallback`, `backfill`, `unattributed` | 아니오 |

서명이 성공할 때마다 활동 로그에 `agent_task_tokens_issued` 행이 기록됩니다 —— 책임자, 에이전트, task, 각 토큰의 `jti`와 만료 시각. 그리고 fail-closed입니다. 이 행을 쓸 수 없으면 토큰은 발급되지 않습니다.

## 두 가지 연동 경로

이 기능에는 서로 다른 두 부류의 독자가 있고, 각각 저장소에 해당 가이드가 있습니다.

### 1. 활성화하기 (운영자)

워크스페이스 소유자 또는 관리자가 두 단계로 활성화합니다.

1. **서버를 설정합니다.** `MULTICA_TASK_TOKEN_PRIVATE_KEY`(PEM 서명 키)와 `MULTICA_TASK_TOKEN_TEMPLATES`(무엇을, 어느 변수에, 어떤 클레임으로 서명할 수 있는지 정의하는 JSON 카탈로그)를 설정합니다. [환경 변수](/environment-variables)를 참조하세요. 한쪽만 설정하면 시작 오류이고, 둘 다 설정하지 않으면 기능은 꺼집니다.
2. **에이전트별로 활성화합니다.** **설정 → 에이전트 →** 대상 에이전트 **→ 아이덴티티 토큰**을 열고, 그 에이전트에 필요한 만큼만 켭니다. 카탈로그는 서버 설정에만 존재하므로, UI는 운영자가 허용한 범위에서 고를 수 있을 뿐 무엇을 서명할지는 정의할 수 없습니다.

카탈로그 형식, 보간 변수, `allowed_domains` 허용 목록, 보안 경계(영향 범위, 서버 침해가 무엇을 의미하는지, 키 교체), 문제 해결을 포함한 운영자 전체 가이드는 저장소의 [`TASK_IDENTITY_TOKENS.md`](https://github.com/multica-ai/multica/blob/main/TASK_IDENTITY_TOKENS.md)에 있습니다.

<Callout type="warn">
`sub`는 전체 회사 이메일을 기본값으로 하고, 검증된 회사 이메일을 전제 조건으로 하세요 —— 전체 신뢰 체인의 뿌리는 Multica가 보관하는 그 주소입니다. 이메일 로컬 부분에 매핑한다면 반드시 템플릿의 `allowed_domains`와 함께 써서 자기 도메인만 서명되도록 하세요.
</Callout>

### 2. 토큰 검증하기 (수신 시스템 개발자)

이 토큰을 받는 시스템은 Multica가 인증 없이 게시하는 JWK Set으로 검증합니다.

```
GET https://<당신의-multica-host>/.well-known/jwks.json
```

주요 JWT 라이브러리는 이를 직접 소비합니다. 사내 시스템이 API 게이트웨이(Kong, APISIX, nginx, 클라우드 게이트웨이) 뒤에 있다면 검증은 대개 코드가 필요 없습니다. 게이트웨이의 bearer-JWT 검증을 기대하는 `iss`와 이 URL(`jwks_uri`)로 향하게 하면 됩니다.

연동 자체가 보안 경계입니다 —— 알고리즘 허용 목록 고정, `sub`를 자동 프로비저닝 없이 로컬 사용자에 매핑, 감사 추적에 사람과 대행 에이전트를 모두 기록. 단계별 가이드, 동작하는 검증 코드, 실제로 발목을 잡는 함정은 [`TASK_IDENTITY_TOKENS_AI.md`](https://github.com/multica-ai/multica/blob/main/TASK_IDENTITY_TOKENS_AI.md)에 있으며, 이는 당신의 레거시 코드베이스 안에서 작업하는 AI 에이전트에게 건네도록 작성되었습니다.

<Callout type="warn">
검증 측에서 명시적인 알고리즘 허용 목록을 고정하세요. 토큰이 자칭하는 `alg`를 신뢰하는 검증기는 손쉽게 위조됩니다 —— `alg: none`, 또는 공개 키를 HMAC 비밀로 사용하는 `HS256`. 공개 JWKS 때문에 대칭 알고리즘을 허용하면 이 두 공격이 공짜로 성립합니다.
</Callout>
