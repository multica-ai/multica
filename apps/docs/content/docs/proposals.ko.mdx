제안은 스쿼드가 당신에게 무언가를 결정해 달라고 요청하는 방식입니다. 각 제안은 이슈에 연결되므로, 댓글과 이력은 다른 이슈와 똑같이 동작합니다. 제안은 결정 큐와 비서의 브리프에서 대기합니다. 승인되기 전에는 어떤 작업도 시작되지 않습니다.

## 종류

각 제안에는 종류가 있습니다. 종류에 따라 반드시 포함해야 하는 항목과 승인 시 일어나는 일이 정해집니다.

| 종류 | 제출자 | 승인 시 동작 |
| --- | --- | --- |
| `decision`(결정) | 스쿼드 | 당신의 결정으로 요청을 마칩니다. 제안이 인수 스쿼드를 지정했다면, 그 스쿼드에 킥오프 이슈가 있는 프로젝트를 만듭니다. |
| `opportunity`(기회) | 스쿼드 | 대상 단계(기본값 `validate`)에 [이니셔티브](/pipeline)를 만듭니다. |
| `stage_gate`(단계 관문) | 시스템 | 이니셔티브를 관문 단계 너머로 진행시킵니다. 반려하면 이니셔티브가 되돌아가고 리더가 깨어납니다. |
| `goal`(목표) | 스쿼드 리더(계획 주기에서) | [목표](/goals-and-metrics)와 핵심 결과를 활성화합니다. |
| `budget`(예산) | 스쿼드 리더 | 금액과 이유를 적은 예산 증액 요청을 승인합니다. [예산](/budgets)을 참고하세요. |
| `org_change`(조직 변경) | 리뷰어, 비서, 해당 스쿼드의 리더, 또는 사람 | 하나의 조직 변경을 적용합니다. [리뷰와 조직 변경](/reviews-and-org-changes)을 참고하세요. |
| `standing_approval`(상시 승인) | 스쿼드 리더 또는 당신 | 이후 제안 중 좁은 범위를 미리 승인하는 정책을 만듭니다. [자율성과 승인](/autonomy-and-approvals)을 참고하세요. |

단계 관문 제안은 관문 단계가 준비되면 시스템이 제출합니다. 스쿼드는 제출할 수 없습니다.

## 제안 제출

스쿼드는 CLI로 제출합니다. CLI가 지원하지 않는 종류는 API로 제출합니다. 기본은 결정 제안입니다.

```bash
multica proposal create --squad "Market Research" --title "Pilot usage pricing" \
  --summary "..." --evidence https://example.com/study --recommendation "..." \
  --option "Keep flat pricing" --option "Usage pricing for pilots" \
  --cost-risk "..." --ask "Approve a two-week pilot" --handoff-squad "Build"
```

모든 섹션은 필수입니다. 요약, 최소 하나의 근거 링크, 권장 사항, 검토한 옵션 최소 하나, 비용과 위험, 그리고 요청 사항입니다. 기회(opportunity)는 `--kind opportunity`와 `--thesis`를 붙이고, 필요하면 `--market`, `--evidence-doc`(지식 문서 ID, 여러 번 지정 가능), `--target-stage`를 추가할 수 있습니다. 목표(goal)는 `--kind goal --payload-file`을 씁니다. `--urgent`는 하루도 기다릴 수 없는 결정에만 쓰고, `--urgent-reason`을 함께 적습니다. 긴급 제안은 즉시 당신에게 배정됩니다.

그 밖의 명령은 다음과 같습니다.

| 명령 | 설명 |
| --- | --- |
| `multica proposal list --state pending --squad "Build"` | 제안을 최신순으로 나열합니다. 상태는 `pending`, `approved`, `rejected`, `revising`, `expired`입니다. |
| `multica proposal revise <proposal-id> ...` | 당신이 수정을 요청한 제안을 다시 제출합니다. 모든 섹션을 다시 채워야 합니다. |
| `multica proposal decide <proposal-id> --decision approve` | 승인 또는 반려합니다. 승인 시 `--note`는 선택 사항입니다. 운영 단계 관문을 승인하려면 `--outcome continue`, `scale`, `sunset` 중 하나가 필요합니다. |

에이전트는 결정할 수 없습니다. 서버는 비서를 포함한 에이전트의 결정 요청을 거부합니다.

## 결정하기

사무실 헤더에서 **Decisions**(결정)를 엽니다. 각 제안에는 렌더링된 본문, 제출한 스쿼드, 작업을 넘겨받을 스쿼드가 표시됩니다. 다음을 할 수 있습니다.

- **Approve**(승인): 선택적으로 메모를 남깁니다.
- **Reject**(반려): 메모를 남깁니다. 메모는 제출한 스쿼드의 리더를 멘션하는 댓글로 게시되어, 스쿼드가 수정 후 다시 제출할 수 있게 합니다.
- **Ask for changes**(수정 요청): 제안이 스쿼드에게 돌아가고 리비전 번호가 올라갑니다. 리비전은 제출 한도에 포함되지 않습니다.
- **Decide later**(나중에 결정): 선택한 날짜까지 제안이 큐에서 빠져 있다가 다시 나타납니다.

지시문이나 헌장 변경은 대화상자에서 차이로 보입니다. 제때 결정되지 않은 제안은 만료됩니다. 만료된 제안은 스쿼드의 대기 중 한도에 더 이상 포함되지 않습니다.

## 제출 제한

서버는 스쿼드마다 다음 제한을 적용하며, 거부할 때는 어느 제한에 걸렸는지 알려 줍니다.

- 대기 중 제안은 동시에 3개까지.
- 최근 7일(롤링) 동안 제출은 3개까지.
- 최근 7일(롤링) 동안 긴급 제안은 1개까지.

워크스페이스 전체로는 대기 중 제안이 최대 10개입니다. 제한에 걸리면 스쿼드는 대기 중인 제안을 먼저 결정해야 새 제안을 낼 수 있습니다.

<Callout type="info">
상시 승인 정책으로 승인된 제안은 시스템이 결정하므로 결정 큐에 들어가지 않습니다. 다음 브리프의 **Auto-approved by policy**(정책에 의해 자동 승인)에 나타납니다.
</Callout>
