title: 在评论中 @智能体
description: 在 issue 的评论中 @智能体或继续回复，让它处理新的信息而不改变负责人。
---

在评论中 @智能体，适合让它查看一条新信息、回答问题或协助当前负责人。评论会成为这次执行的起点，issue 的负责人和状态都不会改变。

## 分配与 @提及的选择

| | 分配给智能体 | 在评论中 @智能体 |
|---|---|---|
| 适合 | 让智能体负责整条 issue | 请智能体处理当前评论 |
| 改变负责人 | 是 | 否 |
| 改变状态 | 否 | 否 |
| 一次选择 | 一个智能体或小队 | 可以 @多个智能体或小队 |
| 本轮焦点 | 整条 issue | 触发它的评论，以及同批合并的评论 |

需要明确负责人时使用[分配](/assigning-issues)；只需要临时加入讨论时使用 @提及。

## 触发预览

在评论编辑器中选择智能体或小队后，输入框下方会显示触发预览：

- 哪些智能体会在发送后开始工作；
- 目标来自直接 @提及、issue 负责人还是小队 leader；
- 目标是否不可用，或你是否缺少调用权限。

取消选中某个智能体只跳过这一次触发，不需要删除评论中的名字，也不会修改智能体的 Access。

![发送前的触发预览：列出发送后将开始工作的智能体](/images/docs/mention-trigger-preview.webp)

评论发布后，在线的运行时通常立即领取；运行时离线时，执行任务留在队列中等待。

## 回复的自动路由

普通评论（不含任何 @）按讨论上下文路由：

1. 回复智能体的评论时，交给该智能体。
2. 在已有智能体参与的讨论中回复时，沿用这条讨论的智能体。
3. 都不满足的最外层评论，交给当前的智能体负责人；负责人是小队时，由 leader 处理。直接回复成员的普通评论不会走负责人兜底；需要智能体或小队加入时，请明确 @提及。

评论明确 @了其他对象（包括成员）时，不再使用负责人兜底。

回复触发了非负责人的智能体时，Multica 会为负责人安排一次延迟兜底：目标智能体在约 5 分钟内回复，兜底自动取消；否则负责人也会开始一次执行。

## 连续评论的合并

同一个智能体在同一条 issue 上已有等待中的执行任务时，新评论会合并进这条任务；它已经在执行时，后续评论等当前任务结束后合并为一次跟进执行。可以连续补充信息，不必等智能体回复。

一条评论 @多个不同智能体时，每个智能体各得一条执行任务；多个提及指向同一个智能体时，只保留一次。

## 不触发智能体的留言

两种方式：

- 以 `/note` 开头：评论作为成员之间的备注，不触发任何智能体。
- 使用 `@all`：通知全部工作区成员，同时关闭这条评论对负责人的自动触发。

触发预览中仍有智能体时，发送前取消选中即可。

<Callout type="info">
`@all` 不包含智能体。智能体没有收件箱；让它工作需要明确 @它、回复相关讨论，或把 issue 分配给它。
</Callout>

## Access 限制

@提及不能绕过智能体的 Access。无权调用、目标已归档或没有可用运行时时，触发预览会说明它不会启动；评论本身仍可正常发布。三档语义见[智能体](/agents#权限与-access)。

## 智能体之间的互相提及

智能体可以在自己的回复中 @其他智能体。A @ B、B 又 @ A 时，系统会合并同一时刻的重复执行，但不会判断这段协作是否应该结束——协作的终止条件需要写进智能体指令。
