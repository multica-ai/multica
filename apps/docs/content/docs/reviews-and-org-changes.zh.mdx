评审与组织变更构成闭环。**评分卡**衡量智能体或小队的表现。**评审**读取评分卡并提出建议。**组织变更**在你批准后应用这些建议。变更随后进入**试用期**，平台会记录它是否有效。

## 评分卡

每晚任务会为每个智能体、每个小队和整个公司计算评分卡。它覆盖最近一个已完成的周或月。在该周期内运行数量过少的评分卡会被标记为 `insufficient`（数据不足），且永远不会被评审。

评估指标包括：

- 运行次数和成功率，失败按原因区分。守护进程离线导致的失败不计入智能体；
- 已完成的议题数、首次通过率（完成后未被重新打开）、周期时间和每个完成议题的成本；
- 人工干预率，即智能体标记完成后的人工评论或编辑；
- 提案采纳率、例行任务合规率和知识贡献；
- 秘书的简报有用度。

部分数据是代理指标。完成时间是议题最后一次进入完成状态的时间。首次通过率和干预率使用已完成运行的次数和成员评论。成本只统计提供商报告的部分。重新打开次数根据议题的完成历史统计，从本版本开始记录，之前的重新打开次数无从得知。

所有者、管理员和小队负责人可以查看评分卡：

```bash
multica review scorecards --subject-type squad --subject-id <squad-id> --period month
```

## 评审

治理楼层上的 **People & Performance**（人员与绩效）小队持有一名评审智能体。每月，它会评审数据充足的每个小队，以及评分卡或抽样标记为 `below`（低于预期）的每个智能体。每份评审包括评级（`exceeds`（超出预期）、`meets`（符合预期）、`below`（低于预期）或 `at_risk`（有风险））、叙述，以及建议。评审必须引用其依据的评分卡数据及相关证据。

评审是工作工具，而不是排名。所有者、管理员和该对象所在小队的负责人可以查看。评审中的指标会说明它们衡量的内容。

评审员用 JSON 文件发布：

```bash
multica review publish --file review.json
multica review list
```

发布评审时，其中每项建议都会提交为一份 `org_change` 提案，你可以在相关证据旁边做决定。**治理**中的 Reviews 标签页列出评审，并显示提案 ID 而非链接。简报的 **People** 部分列出新的评审及其建议。

## 组织变更

`org_change` 提案有以下八种类型：

| 类型 | 变更内容 | 应用方式 |
| --- | --- | --- |
| `instruction_change` | 智能体的指令 | 先写入旧文本的修订，再更新智能体 |
| `skill_change` | 智能体的技能 | 添加或移除技能 |
| `charter_change` | 小队的章程 | 更新章程，并生成修订 |
| `autonomy_change` | 小队的自主等级 | 设置等级 |
| `hire` | 向小队添加智能体 | 根据模板创建智能体，并以该小队为所属小队 |
| `retire` | 移除智能体或小队 | 归档。排队任务被取消，运行中的任务继续完成，知识保留。 |
| `move` | 智能体所属的小队 | 变更成员关系和所属小队 |
| `merge_squads` | 两个小队 | 成员和例行任务迁移，来源小队被归档。章程文本由你在对话框中合并。 |

组织变更由评审员、秘书、受变更影响小队的负责人，或某个人提交。它们从不自动批准，也永远不会落入标准授权。决定对话框会以差异形式显示指令或章程变更。

## 指令修订与回滚

对智能体指令的每次更新都会写入一条修订，无论来自哪个途径：应用、CLI、模板、导入，或已应用的组织变更。修订记录文本、来源（`human`、`proposal` 或 `rollback`），以及相关提案（如有）。

在智能体页面上，历史记录会列出修订。恢复某条修订会写入一条内容为旧文本的新修订，因此不会丢失任何内容。

```bash
curl -H "Authorization: Bearer $MULTICA_TOKEN" -H "X-Workspace-ID: $WORKSPACE_ID" \
  "$MULTICA_API/api/agents/<agent-id>/instruction-revisions"
curl -X POST -H "Authorization: Bearer $MULTICA_TOKEN" -H "X-Workspace-ID: $WORKSPACE_ID" \
  "$MULTICA_API/api/agents/<agent-id>/instruction-revisions/<revision>/restore"
```

修订历史从第一次记录的变更开始，之前的变更不在其中。构建者承载智能体不被跟踪。

## 试用期

已应用的变更进入为期 **14 天的试用期**。到期时，评审员比较变更前后的评分卡，并记录以下结果之一：

| 结果 | 含义 |
| --- | --- |
| `improved`（改善） | 指标朝正确方向变化 |
| `neutral`（持平） | 没有明显变化 |
| `worse`（变差） | 指标朝错误方向变化，会提交一份回滚提案 |
| `insufficient`（数据不足） | 数据太少，结果推迟 |

试用期适用于全部八种类型。只有可撤销的变更才能回滚。`hire`、`retire` 和 `merge_squads` 不能撤销，因此这些变更得到"变差"结果时不会提交回滚提案。创建小队首份章程的变更也无法撤销。批准前请考虑这些限制。

<Callout type="info">
组织变更提案计入注意力上限。每项已应用的变更和每个结果都记录在[治理日志](/controls-and-log)中。
</Callout>
