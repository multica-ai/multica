Multica ne remplace pas l'outil de codage IA que vous utilisez : un runtime invoque l'outil déjà installé et connecté sur l'ordinateur, puis renvoie la progression et les résultats dans la tâche. Si vous utilisez déjà l'un de ces outils, vous pouvez généralement le garder. Si vous n'avez pas encore choisi, regardez quatre points :

- s'il est déjà installé sur l'ordinateur ;
- quels modèles votre compte peut utiliser ;
- si Multica doit configurer MCP pour lui ;
- quels skills l'équipe souhaite réutiliser.

Les étapes d'installation se trouvent dans [Installer les outils de codage IA](/install-agent-runtime).

« MCP géré par Multica » signifie que vous pouvez définir des serveurs MCP dans la configuration de l'agent et que Multica les transmet à l'outil avant une exécution. Cette colonne indique seulement si Multica peut s'en charger, pas si l'outil dispose d'autres moyens de configurer MCP.

Pour les outils marqués — dans « Modèle choisi dans Multica », le modèle se choisit dans la configuration propre à l'outil ; voir [Sources des modèles](#sources-des-modèles).

## Sources des modèles

Devin utilise ACP en local et prend en charge les serveurs MCP stdio. HTTP/SSE ne sont transmis que si le CLI annonce leur prise en charge. L'import des skills inclut aussi `~/.codeium/<channel>/skills` (`windsurf`, `windsurf-next`, `windsurf-insiders`), après les répertoires Devin/Cognition et avant `~/.agents/skills`.

Le catalogue Devin peut inclure des modèles indisponibles pour votre compte. Choisissez un identifiant complet, un nom de modèle de session ou un slug/alias de famille non ambigu (par exemple `opus`), ou laissez le champ vide pour le modèle par défaut. Multica confirme le modèle de session avant d'envoyer le prompt et refuse un repli vers une autre famille. Pour les noms ambigus, les noms partiels ou les variantes indisponibles, utilisez un identifiant complet. L'usage est attribué au modèle retourné ; Adaptive reste associé à son identifiant de routage, sans déduire le modèle sous-jacent.

Devin utilise `WINDSURF_API_KEY` s'il est défini, sinon les identifiants enregistrés par `devin auth login`. Une méthode d'authentification ACP inconnue ne bloque pas cette connexion. Multica conserve le mode de session configuré sans augmenter les permissions : si le mode par défaut est `plan`, passez à un mode d'édition dans Devin avant d'envoyer une tâche qui modifie des fichiers.

Lorsque vous créez un agent, la liste des modèles provient du runtime correspondant. Certains outils exposent un ensemble fixe de noms de modèles ; d'autres renvoient les modèles disponibles selon la configuration locale, le compte connecté et les droits de l'abonnement.

Si vous ne choisissez pas de modèle, Multica utilise le modèle par défaut de l'outil. Si la liste est vide, vérifiez que le runtime est en ligne et que l'outil est connecté, puis actualisez la liste des modèles.

QwenPaw, MiniMax Code et ZeroClaw font exception : ils n'acceptent pas de modèle choisi depuis Multica, donc le sélecteur est inactif et affiche « Géré par le runtime ». Choisissez plutôt le modèle dans la configuration propre à l'outil. Pour ces outils, une liste de modèles vide est normale et n'indique pas que le runtime est hors ligne.

DeepSeek Harness publie son catalogue de modèles depuis le runtime lui-même (`dsh --profile multica --list-models`). Ses identifiants de modèle utilisent la forme `provider/model` (par exemple `deepseek-official/deepseek-chat`) ; sélectionnez donc l'identifiant complet dans la liste.

<Callout type="info">
Les noms de modèles ne sont pas communs d'un outil à l'autre. Après un changement d'outil de codage IA, la valeur de modèle précédente n'est plus valide dans le nouvel outil et doit être sélectionnée à nouveau.
</Callout>

## Reprise de session

Les outils marqués ✓ permettent de poursuivre une session existante lors d'une exécution ultérieure, à condition que la session d'origine existe toujours et que l'exécution soit effectuée par un runtime qui peut y accéder. MiniMax Code 0.1.2 n'annonce aucune capacité de chargement de session via ACP, donc Multica démarre une nouvelle session MCode pour une exécution ultérieure.

Multica stocke l'identifiant de session renvoyé par l'outil. La prochaine fois que le travail se poursuit sur la même tâche, le runtime tente de reprendre cette session ; s'il n'y parvient pas, il crée une nouvelle session et continue. Pi stocke le chemin d'un fichier de session local ; il dépend donc davantage de l'ordinateur et du fichier d'origine.

Les règles de relance et de reprise de session se trouvent dans [Exécutions](/tasks#relance-manuelle).

## Configuration MCP

Antigravity, GitHub Copilot CLI, DevEco Code, Muse Code et ZeroClaw ne lisent pas encore la configuration MCP d'un agent ; le champ n'est donc pas affiché lors de la création d'agents pour ces outils.

La transmission d'une configuration MCP gérée à Pi nécessite Pi 0.99.0 ou une version ultérieure. Les versions antérieures de Pi continuent d'exécuter les agents sans configuration MCP.

<Callout type="warning">
Les commandes, arguments et variables d'environnement des serveurs MCP sont enregistrés côté serveur avec la configuration de l'agent. N'écrivez pas dans la configuration des identifiants locaux que vous n'avez pas besoin de partager.
</Callout>

Les serveurs MCP déjà configurés sur la machine du runtime sont fusionnés sur cette machine avec la configuration de l'agent ; voir [Configuration MCP locale](/daemon-runtimes#local-mcp).

## Injection des skills

Avant le démarrage d'une exécution, Multica écrit les skills rattachés à l'agent dans les chemins du tableau ci-dessus, afin que chaque outil les découvre par son propre mécanisme natif.

Les skills qui existent déjà dans le dépôt ne sont jamais écrasés. En cas de conflit de nom, Multica utilise un autre nom de répertoire pour la copie injectée ; après l'exécution, il ne nettoie que les fichiers qu'il a créés.

Codex, Hermes et OpenClaw sont traités un peu différemment :

- Codex utilise un `CODEX_HOME` propre à chaque exécution ; les skills ne sont donc jamais écrits dans le répertoire Codex au niveau du système.
- Hermes utilise un `HERMES_HOME` propre à chaque exécution. La configuration locale existante reste lisible, mais les skills rattachés et les données de session sont isolés par exécution. Cette isolation ne s'applique que lorsque des skills sont rattachés à l'agent ; les exécutions sans skill rattaché utilisent le répertoire Hermes d'origine de la machine.
- OpenClaw utilise `skills/` sous le répertoire de travail de l'exécution en cours, et la configuration propre à l'exécution définit ce répertoire comme espace de travail.

Pour créer et rattacher des skills, consultez [Skills](/skills).
