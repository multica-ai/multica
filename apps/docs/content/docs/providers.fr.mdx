Multica ne remplace pas l'outil de codage IA que vous utilisez. Un runtime invoque l'outil déjà installé et connecté sur l'ordinateur, puis renvoie la progression et les résultats dans la tâche.

Si vous utilisez déjà l'un de ces outils, vous pouvez généralement le conserver tel quel. Quatre points à prendre en compte pour choisir :

- s'il est déjà installé sur l'ordinateur ;
- quels modèles votre compte peut utiliser ;
- si Multica doit configurer MCP pour lui ;
- quels skills l'équipe souhaite réutiliser.

Les étapes d'installation se trouvent dans [Installer les outils de codage IA](/install-agent-runtime).

« MCP géré par Multica » signifie que vous pouvez définir des serveurs MCP dans la configuration de l'agent et que Multica les transmet à l'outil avant une exécution. Cela ne signifie pas que l'outil n'a pas d'autre moyen de configurer MCP.

## Sources des modèles

Lorsque vous créez un agent, la liste des modèles provient du runtime correspondant. Certains outils exposent un ensemble fixe de noms de modèles ; d'autres renvoient les modèles disponibles selon la configuration locale, le compte connecté et les droits de l'abonnement.

Si vous ne choisissez pas de modèle, Multica utilise le modèle par défaut de l'outil. Si la liste est vide, vérifiez que le runtime est en ligne et que l'outil est connecté, puis actualisez la liste des modèles.

QwenPaw et MiniMax Code font exception : ils n'acceptent pas de modèle choisi depuis Multica, donc le sélecteur est inactif et affiche « Géré par le runtime ». Choisissez plutôt le modèle dans la configuration propre à l'outil. Une liste de modèles vide y est normale et n'indique pas que le runtime est hors ligne.

DeepSeek Harness publie son catalogue de modèles depuis le runtime lui-même (`dsh --profile multica --list-models`). Ses identifiants de modèle utilisent la forme `provider/model` (par exemple `deepseek-official/deepseek-chat`) ; sélectionnez donc l'identifiant complet dans la liste.

<Callout type="info">
Les noms de modèles peuvent différer d'un outil à l'autre. Après un changement d'outil de codage IA, la valeur de modèle précédente n'est plus valide dans le nouvel outil et doit être sélectionnée à nouveau.
</Callout>

## Reprise de session

Tous les outils marqués ✓ permettent de poursuivre une session existante lors d'une exécution ultérieure. Les prérequis : la session d'origine existe toujours et l'exécution est effectuée par un runtime qui peut y accéder. MiniMax Code 0.1.2 n'annonce aucune capacité de chargement de session via ACP, donc Multica démarre une nouvelle session MCode pour une exécution ultérieure.

Multica stocke l'identifiant de session renvoyé par l'outil. La prochaine fois que le travail se poursuit sur la même tâche, le runtime tente de reprendre cette session ; s'il n'y parvient pas, il crée une nouvelle session et continue. Pi stocke le chemin d'un fichier de session local ; il dépend donc davantage de l'ordinateur et du fichier d'origine.

Les règles de relance et de reprise de session se trouvent dans [Exécutions](/tasks#relance-manuelle).

## Configuration MCP

Antigravity, GitHub Copilot CLI et DevEco Code ne lisent pas encore la configuration MCP d'un agent ; le champ n'est donc pas affiché lors de la création d'agents pour ces outils.

### MCP géré pour Pi

Pi prend en charge le MCP géré par Multica lorsque le daemon détecte une installation compatible et activée de `pi-mcp-adapter`. Les versions prises en charge sont **2.37.0** et **3.1.0** ; les autres versions ne sont pas présumées compatibles. Installez une version prise en charge sur l'ordinateur du runtime, puis redémarrez le daemon pour actualiser la détection :

```bash
pi install npm:pi-mcp-adapter@2.37.0
```

L'onglet MCP est disponible uniquement pour les runtimes Pi qui déclarent cette capacité. Un ancien daemon, un adaptateur absent ou incompatible le laisse indisponible ; les exécutions Pi ordinaires sans MCP géré restent possibles. Multica n'installe ni n'active automatiquement l'adaptateur.

Pour une exécution gérée, Multica transmet uniquement la configuration MCP résolue de l'agent via `createMcpAdapter({ config })`. Les configurations MCP globales et du projet ne sont pas fusionnées. Un répertoire temporaire privé contient la configuration et l'état de l'adaptateur ; il est supprimé à la fin de l'exécution, en cas d'échec au démarrage ou d'annulation. Les paramètres Pi globaux et les fichiers MCP ne sont pas modifiés.

- Une configuration MCP non définie (`null`) conserve le démarrage habituel de Pi.
- Une configuration explicitement vide (`{}` ou `{"mcpServers": {}}`) lance une exécution gérée isolée sans serveur MCP.
- Les exécutions gérées désactivent la découverte automatique des extensions et chargent uniquement le pont MCP de Multica. Les autres extensions, y compris les fournisseurs de modèles qu'elles ajoutent, sont indisponibles. Les skills natifs et du projet, les chemins de skills configurés et les skills des packages npm ou locaux installés sont conservés.

Les packages Pi doivent être des packages npm déjà installés ou des répertoires de packages locaux avec un chemin absolu. Les sources Git et les chemins relatifs font échouer la préparation de l'exécution gérée ; Multica ne télécharge pas de packages pour conserver leurs ressources. La configuration des modèles et l'authentification sont copiées pour chaque exécution, mais les identifiants renouvelés ne sont pas réécrits dans les fichiers d'origine. Une rotation des jetons de renouvellement peut nécessiter une nouvelle authentification. MCP utilise les en-têtes et variables d'environnement explicitement configurés ; les identifiants OAuth globaux de l'adaptateur ne sont pas importés.

#### Vérifier sur l'ordinateur du runtime

Utilisez des serveurs MCP de test et un compte de modèle que vous êtes autorisé à utiliser ; les exécutions réelles peuvent consommer des crédits.

1. Activez une version prise en charge de l'adaptateur, redémarrez le daemon et vérifiez que l'agent Pi affiche l'onglet MCP. Sans adaptateur compatible, vérifiez que les exécutions ordinaires fonctionnent et que l'onglet est indisponible.
2. Attribuez des serveurs MCP de test différents à deux agents, lancez-les simultanément et demandez à chacun de lister ses outils MCP. Chacun doit voir uniquement son serveur attribué. Avec une configuration explicitement vide, aucun outil MCP ne doit apparaître.
3. Rattachez un skill, sélectionnez un modèle authentifié et terminez une exécution gérée. Poursuivez la même tâche pour vérifier la reprise de session ; testez aussi une annulation et un échec au démarrage de MCP.
4. Comparez les sommes de contrôle des paramètres Pi globaux et des fichiers MCP avant et après. Vérifiez la suppression du répertoire temporaire après chaque exécution terminée, échouée ou annulée. N'incluez aucun identifiant dans les journaux ou captures d'écran.

<Callout type="warning">
Les commandes, arguments et variables d'environnement des serveurs MCP sont enregistrés côté serveur avec la configuration de l'agent. N'écrivez pas dans la configuration des identifiants locaux que vous n'avez pas besoin de partager.
</Callout>

## Injection des skills

Avant le démarrage d'une exécution, Multica écrit les skills rattachés à l'agent dans les chemins du tableau ci-dessus, afin que chaque outil les découvre par son propre mécanisme natif.

Les skills qui existent déjà dans le dépôt ne sont jamais écrasés. En cas de conflit de nom, Multica utilise un autre nom de répertoire pour la copie injectée ; après l'exécution, il ne nettoie que les fichiers qu'il a créés.

Codex, Hermes et OpenClaw sont traités un peu différemment :

- Codex utilise un `CODEX_HOME` propre à chaque exécution ; les skills ne sont donc jamais écrits dans le répertoire Codex au niveau du système.
- Hermes utilise un `HERMES_HOME` propre à chaque exécution. La configuration locale existante reste lisible, mais les skills rattachés et les données de session sont isolés par exécution. Cette isolation ne s'applique que lorsque des skills sont rattachés à l'agent ; les exécutions sans skill rattaché utilisent le répertoire Hermes d'origine de la machine.
- OpenClaw utilise `skills/` sous le répertoire de travail de l'exécution en cours, et la configuration propre à l'exécution définit ce répertoire comme espace de travail.

Pour créer et rattacher des skills, consultez [Skills](/skills).
