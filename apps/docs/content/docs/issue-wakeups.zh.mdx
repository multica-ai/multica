有些工作做到一半只能等：等供应商回报价，等同事答复，等子任务做完。这时可以在任务上加一条**唤醒**规则："当某件事发生时，唤醒某个智能体，让它做什么"。条件满足后，智能体在这条任务上开始一次普通运行，读取任务的最新情况，结果照常以评论写回任务。

规则保存在任务上，等待期间没有运行在跑。成员在任务侧栏里创建唤醒；智能体在运行中用 [CLI](#cli) 给自己安排下一次检查，两种方式创建的是同一种规则。

## 新建唤醒 [#create]

<Steps>
<Step>

打开任务，点任务侧栏**唤醒**区域右侧的 **+**。

</Step>
<Step>

在**当**后面选择条件，再补齐条件需要的参数，例如时间、要等的人或要等的状态。

</Step>
<Step>

在**唤醒**后面选择智能体。任务负责人是智能体时，这里已经预选了它。只能选已绑定运行时、并且你有权限运行的智能体，见[权限与 Access](/agents#权限与-access)。

</Step>
<Step>

在**唤醒后要做什么**里写下指令，例如"看供应商是否都回了报价，回齐了就整理成对比表"。指令最多 12,000 字节，之后可以修改，只影响以后的唤醒。

</Step>
<Step>

点**创建**。

</Step>
</Steps>

唤醒开始的运行代表创建者执行，开始前会再确认创建者仍有权限运行这个智能体。

下面这条任务里，运营助手已经发出询价，正在等供应商回复。给它加一条唤醒，再快进到唤醒时间。选"定期检查"还能看到第一天没有消息时，智能体怎样不发评论就结束。

## 可以等什么 [#conditions]

| 分组 | 条件 | 什么时候唤醒 |
|---|---|---|
| 时间 | 在某个时间 | 10 分钟后、1 小时后、明天 09:00，或自定义时间。只唤醒一次。 |
| 时间 | 定期检查 | 每小时、每天 09:00 或工作日 09:00，按你的时区计算。必须设截止日，截止日当天结束后停止。 |
| 协作 | 有人回复 | 任务上出现新评论；可以限定为某位成员或某个智能体。 |
| 协作 | 字段变为某个值 | 任务的状态、负责人、标签或自定义属性变成指定的值。 |
| 运行与子任务 | 智能体的运行结束 | 这条任务上某个智能体（或任意智能体）的运行成功、失败或被取消。 |
| 运行与子任务 | 子任务完成 | 全部子任务结束（`done` 或 `cancelled`），或某个阶段及之前的阶段全部结束。没有子任务时不会触发。 |
| 关联 | 关联 PR 的 CI 结束 | 也可以选 PR 合并、出现合并冲突。只看直接关联到这条任务的 PR，有多个时任意一个满足即可。CI 结束和合并冲突只支持 GitHub 上的 PR。 |
| 关联 | 其他任务的状态变化 | 另一条任务完成、完成或取消，或进入审核中。 |
| | 自定义事件 | 从 25 种原始事件里勾选，例如表态、附件、评论被编辑或讨论被解决。 |

字段、子任务、PR 和其他任务这几类条件由平台自己去查：条件在创建时已经成立的，下一次检查（约 30 秒内）就会唤醒；"CI 结束"例外，它只认创建之后才出结果的检查。

时间以外的条件都是"等某件事发生"，还有三项设置：

- **触发次数**：默认**仅触发一次**；选**重复唤醒**时，再设**最多触发**几次（5、10、20 或 50 次，默认 20）。
- **最多等待**：1、3、7 或 30 天，默认 7 天。
- **超时后**：默认唤醒智能体处理，它会知道要等的事没有发生；也可以选直接结束。

任务负责人是智能体时，成员发评论本来就会触发它。给负责人再加一条"有人回复"的唤醒，不会多跑一次，只会并入那次运行，所以只在想附加指令时才需要。

## 唤醒之后 [#after-wake]

- 智能体在任务上开始一次普通运行，读取任务、评论和唤醒指令，结束时发一条评论。评论带有"由唤醒触发"标签和触发条件，[执行日志](/tasks)里也能看到触发来源。
- 定期检查没发现需要回复的事，智能体可以**静默检查**后结束：不发评论，只在任务时间线和这条唤醒的触发记录里留一条说明。连续几次静默检查在时间线里合并成一条。
- 智能体自己发的评论、自己对任务的修改，不会唤醒它自己。
- 同一个智能体在这条任务上已经有一次运行在等待开始，新的唤醒会并入那次运行，不再另起一次。
- 有唤醒在等时，任务标题旁会显示任务在等什么，例如"运营助手 在等回复"，点一下跳到唤醒区域。

## 查看和管理 [#manage]

任务侧栏的唤醒区域列出这条任务上的规则：条件、唤醒谁、下次什么时候、还剩多久。点一条规则查看详情，包括来源、有效期、指令和**触发记录**（最近的运行，有没有发评论，静默检查写了什么）。

| 操作 | 结果 |
|---|---|
| 关闭开关 | 停止后续唤醒，撤回还没开始的运行。已经开始的运行继续，需要时在执行日志里停止。 |
| **立即唤醒** | 现在就按这条规则唤醒一次，不等条件。 |
| 编辑指令 | 只影响以后的唤醒，正在执行的运行不变。 |
| **删除** | 规则不再唤醒，还没开始的运行被撤回，已经开始的继续。 |
| **再次启用** / **重新设置时间** | 单次规则触发过后重新启用；单次定时的规则需要选一个新时间。 |

结束的规则收进**历史唤醒**。只有规则的创建者和工作区 owner、admin 可以管理它。智能体在运行中创建的唤醒，记在发起那次运行的成员名下，显示为"运营助手 创建（代表 李雷）"。

要看整个工作区的唤醒，打开**自动化**页面，切到**任务唤醒**标签。这里可以按状态（待唤醒或执行中、已暂停、已关闭、已结束）、触发方式、来源和智能体筛选，批量关闭，或者先选任务再新建唤醒。

## 自动结束和暂停 [#limits]

- 任务完成或取消时，上面的唤醒全部关闭，还没开始的运行被撤回；任务重新打开后不会自动恢复。已完成或已取消的任务不能新建唤醒。
- 等待类规则到了最多等待时间，按**超时后**的设置处理；定期检查到截止日停止。
- 重复唤醒的规则达到最多触发次数后自动暂停。等待类规则还有两种保护：和其他唤醒规则互相触发（触发链第三次经过它，中间没有人参与），或 1 小时内触发超过 12 次，都会自动暂停。暂停的规则保持关闭，有人重新开启后恢复，次数重新计算。
- 一条任务最多同时开启 32 条唤醒，一个工作区最多 1000 条。

## 子任务结束时唤醒父任务 [#child-done]

任务有子任务时，唤醒区域会出现一条带**系统**标记的规则，它不用手动创建：

- 某个阶段的子任务全部结束、后面还有阶段在等时，唤醒父任务的负责人；全部子任务结束时再唤醒一次。没有分阶段的子任务，全部结束时唤醒一次。
- 负责人是智能体时唤醒它，是小队时唤醒队长，是成员时改发收件箱通知；没有负责人就不唤醒。
- 父任务在 `backlog` 时暂不唤醒，移出 `backlog` 后补一次。
- 默认指令告诉智能体哪个阶段结束了、下一个是哪个：先检查依赖，再把下一阶段的子任务移出 `backlog`；全部结束时把结果汇总到父任务上。

父任务的负责人已经由这条规则唤醒，不需要再为同一件事加"子任务完成"条件。阶段怎么设置见[任务](/issues#项目和子任务)。

在单条任务上，工作区成员可以关闭这条规则，或者改写它的指令（最多 4,000 字节），智能体不能改。改过之后，这条任务不再跟随工作区默认值。

工作区 owner 和 admin 在**设置 → 唤醒**里设置默认值：是否默认开启（默认开启）和默认指令，默认指令留空时使用内置指令。页面上会显示有多少进行中的任务用了自己的设置。

## 让智能体自己安排唤醒 [#cli]

智能体在运行中用 `multica issue wakeup` 给这条任务安排下一次运行，然后结束当前运行。不写 `--agent-id` 时，唤醒的就是执行命令的智能体自己。你也可以在自己的终端里用同一组命令，这时要用 `--agent-id` 指定智能体。

```bash
# 明天上午 9 点（北京时间）再看一次
multica issue wakeup create OPS-56 --kind at --at 2026-10-21T09:00:00+08:00 \
  --instruction "看供应商是否都回了报价，回齐了就整理成对比表"

# 工作日每天 9 点检查，一周后结束
multica issue wakeup create OPS-56 --kind cron --cron "0 9 * * 1-5" --timezone Asia/Shanghai \
  --expires-in 168h --instruction "查看询价邮件，有新报价就更新对比表"

# 等李雷回复，最多等 3 天，超时也唤醒一次
multica issue wakeup create OPS-56 --event comment.created \
  --filter-actor-type member --filter-actor-id <李雷的用户 ID> \
  --expires-in 72h --on-timeout wake --instruction "按李雷的答复继续"

# 等任务进入审核中
multica issue wakeup create OPS-56 --until-status in_review --instruction "检查交付物并汇总"
```

- **时间**：`--kind at` 配 `--after 10m` 或 `--at <RFC3339 时间>`；`--kind every --every 1h` 按固定间隔，最短 1 分钟；`--kind cron --cron "<5 段表达式>"` 配 `--timezone`，时区默认 UTC。
- **事件**：`--event` 后面写事件名，多个用逗号分隔，`multica issue wakeup events` 列出全部事件和过滤参数。`--mode continuous` 改成重复唤醒。
- **条件**：`--until-status`、`--until-assignee`、`--until-label`、`--until-property`、`--until-children-done [--stage N]`、`--until-pr checks|merged|conflicts`、`--until-issue <任务> --until-issue-state done|ended|in_review|blocked`。一条唤醒只能用一个 `--until-*`，不能和 `--event` 同时用。
- **结束方式**：CLI 不会自动给等待加期限，用 `--expires-in 72h` 或 `--expires-at <RFC3339 时间>` 设结束时间；`--on-timeout wake` 让事件规则在超时时再唤醒一次。`--max-fires N`（1–1000）限制重复规则最多运行几次。
- **结果放在哪**：`--parent <评论 ID>` 让唤醒后的回复留在原来的评论串里。

管理已有规则：

| 命令 | 作用 |
|---|---|
| `multica issue wakeup list <任务>` | 列出任务上的唤醒 |
| `multica issue wakeup get <任务> <唤醒 ID>` | 查看一条唤醒的完整配置 |
| `multica issue wakeup runs <任务> <唤醒 ID>` | 最近的运行、触发原因、静默检查说明，以及是否发了评论 |
| `multica issue wakeup update <任务> <唤醒 ID>` | 用和 `create` 相同的参数替换整份配置，并重新开启 |
| `multica issue wakeup disable <任务> <唤醒 ID>` | 关闭，撤回还没开始的运行 |
| `multica issue wakeup trigger <任务> <唤醒 ID>` | 立即唤醒一次 |
| `multica issue wakeup delete <任务> <唤醒 ID>` | 删除规则，撤回还没开始的运行 |
| `multica issue wakeup checkin <任务> <唤醒 ID> --note "..."` | 定期检查没发现需要回复的事时静默结束，只能由这条规则开始的运行调用 |

`list`、`get` 和 `runs` 加 `--output table` 输出表格。其他命令见[使用 CLI](/cli)。

## 和自动化的区别 [#vs-autopilots]

[自动化](/autopilots)按时间表或 Webhook 反复开始新的工作，每次可以新建一条任务；唤醒挂在一条已有任务上，让智能体在约定的时间或事件之后回到这条任务接着做，任务结束时它也跟着结束。
