既存のチャット連携では、Multica を開かずにエージェントへ質問し、グループで @メンションし、イシューを作成できます。

<Callout type="info">
  新しいエージェント単位の Bot 接続と再割り当ては廃止されました。既存接続、本人確認コールバック、メッセージ実行は維持されます。
</Callout>

## 保持される動作

| | Feishu / Lark | Slack | DingTalk | WeCom |
|---|---|---|---|---|
| DM | 対応 | 対応 | 対応 | 対応 |
| グループ / チャンネル | @メンションで実行 | @メンションで実行 | @メンションで実行 | @メンションで実行 |
| イシュー作成 | `/issue` | `/issue` slash command | `/issue` | `/issue` |
| 接続方式 | 長時間接続 | Socket Mode | Stream mode | 長時間接続 |

各 Bot は既存のエージェント対応を維持します。DingTalk の検出済みグループルートも実行用に維持されますが、ブラウザーでは読み取り専用です。

## メッセージ処理

1. Multica が Bot からワークスペースとエージェントを解決します。
2. グループでは明示的な @メンションだけを処理します。
3. 本人確認とワークスペース所属を確認します。
4. [Chat](/chat) セッションに入り、タスクを作成します。
5. 元の DM または thread に返信します。

## 本人確認

最初のメッセージで一度だけ使える本人確認リンクが返る場合があります。この callback / broker 契約は新しいエージェント接続とは独立して維持され、毎回ワークスペース所属を確認します。

## 保持された接続を管理する

workspace owner と admin は **Settings → Integrations** で既存 Bot を確認・切断できます。切断後も会話と監査記録は保持されます。

## セルフホスト

保存済み Bot 認証情報には各プラットフォームの 32 バイト暗号化キーが必要です：

```dotenv
MULTICA_LARK_SECRET_KEY=<base64-encoded 32-byte key>
MULTICA_SLACK_SECRET_KEY=<base64-encoded 32-byte key>
MULTICA_DINGTALK_SECRET_KEY=<base64-encoded 32-byte key>
MULTICA_WECOM_SECRET_KEY=<base64-encoded 32-byte key>
```

保持された認証情報を復号できるようキーを安定して維持してください。
