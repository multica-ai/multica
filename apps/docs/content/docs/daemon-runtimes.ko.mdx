Multica는 작업을 기록하고 조율하며, 연결된 컴퓨터가 실행을 담당합니다. 컴퓨터의 **데몬**(daemon)이 실행을 가져간 뒤 로컬에 설치된 AI 코딩 도구를 호출합니다.

## 개념 구분

- **데몬**은 한 컴퓨터에서 실행되는 Multica 백그라운드 프로그램입니다. 서버 연결, 로컬 도구 검색, 실행 수령, 결과 반환을 담당합니다.
- **런타임**은 워크스페이스가 사용할 수 있는 구체적인 실행 환경을 나타냅니다. 컴퓨터 한 대와 그 컴퓨터의 AI 코딩 도구 하나 또는 사용자 지정 런타임 설정의 조합입니다.

예를 들어 한 컴퓨터에 Claude Code와 Codex가 모두 설치되어 있고 두 워크스페이스에 연결되어 있다면 데몬이 워크스페이스마다 Claude Code 런타임과 Codex 런타임을 하나씩 등록합니다. 데몬을 다시 시작하면 기존 기록이 업데이트되며 같은 조합의 런타임이 계속 새로 생기지 않습니다.

## 실행 위치와 데이터 경계

로컬 런타임이 호출하는 AI 코딩 도구, 도구 자체의 로그인 자격 증명, 로컬 코드 디렉터리는 연결된 컴퓨터에 남습니다. Multica 서버가 로컬 도구를 대신해 명령을 실행하거나 전체 작업 디렉터리를 자동으로 업로드하지 않습니다.

팀 협업을 위해 서버에는 태스크, 댓글, 에이전트 설정, 실행 컨텍스트, 실행 기록, 에이전트가 반환한 결과가 저장됩니다. 이 내용에는 에이전트가 직접 읽고 답변에 포함한 코드 조각이나 다른 프로젝트 컨텍스트가 들어갈 수 있습니다.

<Callout type="warning">
"로컬 실행"이 모든 secret이 로컬에만 존재한다는 뜻은 아닙니다. 에이전트의 사용자 지정 환경 변수와 MCP 설정은 서버에 저장되며 민감 정보 규칙에 따라 표시가 제한됩니다. 사용자 지정 환경 변수는 실행할 때 런타임으로 전송됩니다.
</Callout>

## 데몬 시작

```bash

```

데몬은 기본적으로 백그라운드에서 실행됩니다. 자주 사용하는 명령:

| 명령 | 역할 |
| --- | --- |
| `multica daemon status` | 데몬과 연결 상태 확인 |
| `multica daemon logs -f` | 로그 계속 보기 |
| `multica daemon restart` | 데몬을 다시 시작하고 로컬 도구 다시 감지 |
| `multica daemon stop` | 데몬 중지 |
| `multica daemon start --foreground` | 디버깅을 위해 현재 터미널에서 실행 |

실행용 작업 디렉터리를 다른 디스크에 두려면 `multica config set workspaces_root <path>`로 현재 profile의 루트를 저장하거나 `daemon start` 또는 `daemon restart`에 `--workspaces-root <path>`를 전달합니다. flag는 `MULTICA_WORKSPACES_ROOT`보다 우선하고, 환경 변수는 profile 설정보다 우선합니다. 루트를 변경해도 기존 작업 디렉터리는 이동되지 않습니다.

시작할 때 데몬은 `PATH`에서 지원되는 AI 코딩 도구를 감지하고 사용자가 연결할 권한이 있는 워크스페이스에 런타임을 등록합니다. 도구를 방금 설치하거나 로그인했다면 데몬을 다시 시작하면 다시 감지됩니다.

데몬을 시작하려면 기본 지원 AI 코딩 도구를 하나 이상 감지해야 합니다. 설치 방법과 실행 파일 이름은 [AI 코딩 도구 설치](/install-agent-runtime)를 참고하세요.

### 로그인 시 자동 시작 [#autostart]

CLI로 시작한 데몬은 컴퓨터를 다시 시작해도 저절로 다시 켜지지 않습니다. 자동으로 시작하게 하려면 현재 프로필을 등록하세요.

```bash
multica daemon autostart enable
multica daemon autostart status
multica daemon autostart disable
```

등록되는 명령은 해당 프로필의 `multica daemon start --foreground`이며 로그인할 때 OS가 실행합니다. Windows에서는 현재 사용자의 Run 레지스트리 값, macOS에서는 `~/Library/LaunchAgents`의 LaunchAgent, Linux에서는 systemd 사용자 유닛을 쓰고, systemd 사용자 세션이 없으면 XDG autostart 항목을 씁니다. 이름 있는 프로필은 `--profile <name>`을 붙이며, 프로필마다 따로 등록됩니다.

- 등록을 만드는 것은 `enable`뿐입니다. `multica daemon start`는 스스로 등록하지 않고, 등록이 없을 때 한 줄짜리 안내만 출력합니다. Multica가 만든 등록이 있으면 그 안의 실행 파일 경로를 갱신하므로 CLI를 업그레이드하거나 옮겨도 `enable`을 다시 할 필요가 없습니다.
- macOS와 Linux에서는 `enable`할 때 셸의 `PATH`만 로그인 세션으로 전달됩니다. 셸에서 export한 다른 변수(API 키, `HTTPS_PROXY` 등)는 전달되지 않습니다. 데몬 설정은 `multica config set`으로 저장하고 다른 변수는 사용자 환경에 두세요.
- systemd 사용자 유닛은 로그인할 때 시작됩니다. 로그인하지 않아도 부팅 시 시작하려면 `enable` 출력의 안내대로 `loginctl enable-linger <사용자 이름>`을 실행하세요.
- `multica daemon stop`은 실행 중인 데몬만 멈추고 등록은 남겨 둡니다.
- 같은 위치에 Multica가 만들지 않은 파일(직접 작성한 systemd 유닛 등)이 있으면 `enable`과 `disable` 모두 그 파일을 수정하지 않습니다.
- Desktop이 시작한 데몬은 Desktop이 관리합니다. `daemon start`는 이 데몬에 대해 안내를 출력하거나 등록을 갱신하지 않습니다.

## 디스패치와 온라인 상태

런타임이 등록되면 연결을 계속 유지합니다. 새 실행이 큐에 들어오면 서버가 해당 데몬에 알리고, 연결이 끊겼을 때를 대비해 데몬도 주기적으로 폴링합니다. 런타임이 온라인이고 여유 용량이 있으면 실행은 보통 즉시 시작됩니다.

데몬은 15초마다 하트비트를 보냅니다. 서버는 하트비트와 연결 상태를 함께 사용해 런타임의 온라인 여부를 판단합니다. 데몬이 예기치 않게 종료되면 늦어도 약 3분 안에 오프라인으로 판단됩니다. **런타임** 페이지에서는 연결이 끊긴 뒤 처음 5분 동안 "최근 연결 끊김"으로, 그 뒤에는 "오프라인"으로 표시됩니다.

런타임이 오프라인일 때는 다음과 같이 처리됩니다.

- 이미 큐에 들어간 실행은 런타임이 복구될 때까지 기다리며 다른 컴퓨터로 넘어가지 않습니다. 해당 런타임이 재연결 유예를 넘겨 하트비트를 멈추고 **동시에** 실행 자체도 그만큼 기다린 뒤에만 실패합니다. 단지 바쁜 런타임은 밀린 실행을 그대로 유지하고, 이미 오프라인인 런타임에 배정된 실행도 온전한 유예를 한 번 갖습니다.
- 진행 중인 실행은 바로 실패하지 않습니다. 런타임의 하트비트가 재연결 유예(`MULTICA_RUNTIME_RECONNECT_GRACE`, 기본 3시간)를 넘겨 끊긴 뒤에야 `runtime_offline`으로 실패합니다. 조건을 만족하는 태스크 또는 대화 실행은 자동으로 재시도될 수 있습니다.
- 데몬이 다시 시작되면 런타임을 재등록하고 이전에 정상적으로 끝나지 않은 실행을 회수합니다.
- 7일 넘게 오프라인이고 연결된 에이전트가 하나도 없는 런타임은 보관된 에이전트까지 확인한 뒤 자동으로 정리됩니다.

아래 데모에서는 컴퓨터가 오프라인일 때 할당한 실행이 큐에서 계속 기다리다가, 컴퓨터가 다시 온라인이 된 뒤에야 런타임에 수령됩니다.

## 동시 실행 제한

데몬 한 대는 기본적으로 실행을 최대 20개까지 동시에 처리하며, 에이전트 한 명은 기본적으로 최대 6개까지 처리합니다. 실제 동시 실행 수에는 둘 중 더 작은 값이 적용됩니다.

상한에 도달하면 새 실행은 계속 큐에서 기다립니다. 에이전트 설정에서 개별 에이전트의 동시 실행 수를 조정할 수 있고 `MULTICA_DAEMON_MAX_CONCURRENT_TASKS`로 컴퓨터 전체 상한을 조정할 수도 있습니다. 병렬 실행은 컴퓨터 성능, 도구 계정 사용량, 같은 작업 디렉터리를 동시에 사용합니다.

실행에 쓰인 토큰, 비용, 실패는 워크스페이스별로 [분석](/analytics) 페이지에 모여 있습니다. 런타임 하나의 토큰 사용량은 `multica runtime usage <runtime-id>`로도 볼 수 있습니다.

## 로컬 MCP 설정 [#local-mcp]

에이전트에 MCP 설정이 저장되어 있지 않으면 Multica는 MCP 설정을 전혀 전달하지 않고, 도구는 평소처럼 그 컴퓨터에 있는 자체 설정을 읽습니다.

에이전트에 MCP 설정이 있으면(빈 설정이라도) Multica는 실행마다 전용 설정을 만들어 도구에 넘깁니다. 예를 들어 Claude Code는 strict 모드로 이 설정만 읽습니다. 컴퓨터에 이미 있던 서버가 이 때문에 쓸 수 없게 되지 않도록, 데몬은 런타임 컴퓨터에서 도구의 사용자 수준 MCP 설정을 읽어 에이전트 설정과 병합합니다. 이름이 같은 서버는 다음 순서에서 먼저 나오는 것을 씁니다.

1. 에이전트 **MCP** 탭에서 Multica가 관리하거나 워크스페이스 MCP 라이브러리에서 할당한 서버
2. 도구의 사용자 수준 설정 파일
3. Claude Code만 해당: 활성화된 Claude Code 플러그인에 포함된 MCP 서버. 플러그인은 `~/.claude/settings.json`의 `enabledPlugins`에서 정해지며, 각 플러그인의 `.mcp.json`과 매니페스트에 선언된 MCP 파일을 읽습니다.

| 도구 | 읽는 사용자 수준 설정 |
|---|---|
| Claude Code | `~/.claude.json`의 `mcpServers`와 활성화된 플러그인의 MCP 서버 |
| Codex | `$CODEX_HOME/config.toml`(기본값 `~/.codex/config.toml`)의 `mcp_servers` |
| Cursor Agent | `~/.cursor/mcp.json`의 `mcpServers` |
| OpenCode | `$XDG_CONFIG_HOME/opencode/opencode.json`(기본값 `~/.config/opencode/opencode.json`)의 `mcp` |
| OpenClaw | `$CLAWDBOT_CONFIG_PATH` 또는 `$OPENCLAW_STATE_DIR/openclaw.json`(기본값 `~/.openclaw/openclaw.json`)의 `mcp.servers` |
| CodeArts | `~/.codeartsdoer/codearts_cli.json` 또는 `codearts_cli.jsonc`의 `mcp` |

CodeBuddy, Kimi CLI, Pi는 시작할 때 사용자 수준 설정을 직접 읽고 Multica가 보낸 설정과 합칩니다. 데몬이 미리 병합하면 같은 서버가 두 번 시작되므로 이 도구들에는 병합하지 않습니다. CodeBuddy는 이름이 겹치면 Multica가 보낸 쪽을 씁니다. 표에 없는 다른 도구는 에이전트 설정만 받습니다.

병합은 런타임 컴퓨터에서 이루어지며 로컬 서버의 명령, URL, 헤더, 환경 변수는 업로드되지 않습니다. 에이전트 **MCP** 탭의 "런타임에서 상속" 목록에는 서버 이름, 전송 방식, 출처, 활성화 여부만 표시되고, 에이전트의 같은 이름 서버에 가려진 항목에는 "Multica에서 재정의"가 표시됩니다. 로컬 설정 파일을 해석할 수 없으면 데몬은 경고를 로그에 남기고 해당 실행은 에이전트 설정만 사용합니다.

## 정리와 보존 [#cleanup]

데몬은 시작하고 약 30초 뒤에 처음 정리하고, 그 뒤로는 2시간마다 정리합니다. 진행 중인 실행이 쓰는 디렉터리는 정리하지 않습니다. `multica daemon disk-usage`로 워크스페이스별, 실행별 사용량을 볼 수 있습니다. 아래 기간은 기본값이며 해당 `MULTICA_GC_*` 변수는 [환경 변수](/environment-variables#gc)에 있습니다.

### 실행 디렉터리

실행마다 작업 디렉터리 루트(기본값 `~/multica_workspaces`) 아래에 디렉터리가 생기고, 체크아웃한 코드와 출력, 로그가 들어갑니다. 같은 태스크의 후속 실행은 이 디렉터리를 이어서 씁니다. 디렉터리 전체는 다음 시점에 삭제됩니다.

| 실행 출처 | 삭제 시점 |
|---|---|
| 태스크 | 태스크가 `done` 또는 `closed` 분류의 상태가 되고 24시간 동안 업데이트가 없을 때 |
| 채팅 | 세션을 보관하고 24시간 뒤. 세션을 삭제하면 다음 정리 때. 보관하지 않은 동안에는 유지 |
| 오토파일럿(실행만), 빠른 생성 | 실행이 끝난 뒤 다음 정리 때 |
| 소속을 찾을 수 없음(메타데이터가 없거나 서버에 해당 기록이 없음) | 디렉터리가 72시간 동안 변경되지 않았을 때 |

태스크가 아직 닫히지 않았다면 실행 완료 12시간 뒤에 다시 만들 수 있는 내용만 지웁니다. 대상은 `node_modules`, `.next`, `.turbo` 디렉터리와 데몬이 Codex용으로 준비한 캐시이며 나머지는 남습니다. Multica Cloud에 연결된 데몬은 태스크가 닫혔는지와 관계없이 실행 완료 14일 뒤에 디렉터리 전체도 삭제합니다. 셀프 호스팅에서는 기본적으로 이 단계를 하지 않습니다.

프로젝트 로컬 디렉터리에서의 실행은 사용자 자신의 디렉터리에서 작업하며 데몬은 그 디렉터리를 건드리지 않습니다. Multica가 그 실행을 위해 따로 만드는 기록 디렉터리(로그 등)도 유지되고, 그 안의 다시 만들 수 있는 캐시만 정리됩니다.

### 공유 저장소 캐시

데몬은 워크스페이스 저장소마다 bare 저장소 캐시를 하나 둡니다. 위치는 작업 디렉터리 루트 아래의 `.repos/<워크스페이스 ID>/`입니다. 이 컴퓨터에서 같은 워크스페이스의 실행은 이 캐시를 함께 쓰며, 체크아웃할 때마다 캐시에서 git worktree를 만들고 새 커밋만 가져옵니다. 다시 클론하지 않습니다. 예외는 Linux와 Windows의 Codex 실행으로, 작업 디렉터리 안에 `.git`이 있는 독립 클론을 받습니다. Codex의 workspace-write 샌드박스에서는 작업 디렉터리 밖의 Git 메타데이터가 읽기 전용이기 때문입니다.

캐시는 세 가지가 모두 충족될 때만 삭제됩니다. 어떤 워크스페이스나 프로젝트도 이 저장소를 참조하지 않고, 남은 worktree가 없고, 30일 동안 어떤 실행도 이 캐시에서 체크아웃하지 않았을 때입니다. 필요하면 다시 클론됩니다. 오래된 에이전트 브랜치를 지운 뒤에는 진행 중인 실행이 없을 때 캐시에 `git reflog expire --expire=30.days --all`과 `git gc --prune=30.days`를 실행합니다.

### 세션, 메모리, 임시 디렉터리

| 데이터 | 위치 | 보존 |
|---|---|---|
| Codex 세션 기록(에이전트와 태스크마다 하나) | Codex 홈(기본값 `~/.codex`)의 `multica-sessions/` | 14일 동안 쓰지 않으면 삭제. 이후 해당 태스크의 실행은 이전 Codex 세션을 이어 가지 못함 |
| Hermes 세션 기록 | Multica 설정 디렉터리(기본값 `~/.multica`, 이름 있는 프로필은 `~/.multica/profiles/<name>`)의 `hermes-sessions/` | 14일 동안 쓰지 않으면 삭제 |
| Hermes 메모리(에이전트마다 하나) | 같은 디렉터리의 `hermes-state/` | 90일 동안 쓰지 않으면 삭제 |
| 실행마다 쓰는 전용 임시 디렉터리(`TMPDIR`) | 시스템 임시 디렉터리의 `multica-task-*` | 실행이 끝나면 삭제. 데몬이 강제 종료된 경우 이후 정리에서 삭제 |

Hermes의 태스크 및 채팅 실행은 대화의 영구 디렉터리를 격리된 `HERMES_HOME`으로 사용하며, 일반 파일인 `state.db`와 SQLite 저널을 그 안에 둡니다. 이 구조는 기존의 프로세스 내 ACP와 Gateway 기반 ACP를 모두 지원합니다. 기존 세션 기록은 그대로 재사용하고, 실행 로컬 디렉터리의 기록은 다음 실행 전에 이전합니다.

Multica는 실행마다 홈의 스킬과 파생 설정을 갱신합니다. 모델 제공업체의 인증은 유지하고, 관리되는 실행의 메시징 어댑터와 HTTP 수신 기능은 비활성화합니다. 호스트의 Gateway 상태, 로그, 세션, cron 작업은 격리됩니다. 실행이 끝나면 해당 실행의 Gateway를 중지하여 다음 실행이 자체 실행 환경을 사용하도록 합니다.

### Codex 기본 메모리와 하위 에이전트 [#codex-memory]

데몬이 관리하는 Codex 실행에서는 Codex 기본 메모리가 기본적으로 꺼집니다. 이 컴퓨터나 이전 실행의 메모리가 다른 워크스페이스로 넘어가지 않게 하기 위해서입니다. 설정은 해당 실행 전용 `CODEX_HOME/config.toml`에만 기록되고(`features.memories`, `memories.generate_memories`, `memories.use_memories` 모두 `false`), `~/.codex/config.toml`은 바뀌지 않습니다. 기본 메모리를 유지하려면 데몬 환경에 `MULTICA_CODEX_MEMORY=1`을 설정하세요.

Codex 기본 하위 에이전트도 기본적으로 꺼져 있습니다. Multica는 상위 스레드가 끝나면 실행이 끝난 것으로 보므로 아직 작업 중인 하위 에이전트의 결과는 사라집니다. 이 위험을 감수한다면 `MULTICA_CODEX_MULTI_AGENT=1`을 설정하세요.

## 런타임 공유 [#비공개와-공개]

로컬 런타임의 기본값은 **비공개**입니다. 그 위에 에이전트를 만들 수 있는 사람은 런타임 owner뿐이며, 워크스페이스 owner와 admin도 예외가 아닙니다. 런타임은 다른 멤버의 컴퓨터이고, 거기서 에이전트를 실행하면 그 멤버의 컴퓨터와 도구 자격 증명을 쓰게 됩니다.

**공개**로 바꿀 수 있는 사람은 런타임 owner뿐입니다. 워크스페이스 관리자는 런타임의 이름을 바꾸거나 삭제할 수 있지만, 공유 여부는 owner가 결정합니다. 공개하면 워크스페이스의 다른 멤버도 이 런타임을 선택해 에이전트 실행을 해당 컴퓨터로 라우팅할 수 있습니다. 기반 AI 코딩 도구의 로그인 자격 증명은 공유되지 않습니다.

일부 멤버에게만 공유하려면 런타임 상세에서 **멤버**를 고르고, 워크스페이스 멤버를 한 명 이상 선택한 뒤 **저장**합니다. 선택된 멤버는 이 런타임을 골라 에이전트를 만들 수 있습니다. 목록은 owner만 바꿀 수 있으며, 목록에 있다고 해서 런타임의 이름 변경·삭제·관리 권한이 생기지는 않습니다.

소유자가 공유 멤버를 빼거나, 공개 런타임을 지정 멤버로 좁히거나, 다시 **비공개**로 전환하면 Multica는 에이전트 빌더 세션을 포함하여 영향을 받는 에이전트와 활성 실행을 표시합니다. 확인하면 다른 멤버의 해당 에이전트 연결을 해제하고, 대기 중·배포됨·실행 중·로컬 디렉터리 대기·지연 중인 실행을 `runtime_access_revoked`로 취소합니다. 해당 에이전트에 할당된 활성 오토파일럿도 일시 중지합니다. 소유자와 계속 접근할 수 있는 멤버의 에이전트와 실행에는 영향을 주지 않습니다. 대상이 바뀌면 다시 확인해야 하며, 채팅이 동시에 변경되는 경우 재시도가 필요할 수 있습니다. 작업을 재개하려면 에이전트를 사용 가능한 런타임에 연결한 후 일시 중지된 오토파일럿을 직접 재개하세요.

취소해도 채팅 기록은 유지되며 초안·첨부 파일 복원 데이터는 서버에 저장됩니다. 웹과 데스크톱은 기존 초안 복원 UI를 사용하지만 모바일에는 아직 해당 UI가 없습니다. 이미 시작했지만 출력이 없는 실행은 데몬의 취소 확인 또는 서버의 유예 기간 종료 후 입력 복원 여부를 결정합니다. 연결된 데몬은 일반 확인 과정에서 취소를 받습니다. 오프라인에서도 서버의 접근 권한은 즉시 취소되지만, 로컬 프로세스는 다시 연결되어 취소를 받을 때까지 계속될 수 있으므로 즉시 원격 중단을 보장할 수 없습니다.

## 사용자 지정 런타임 설정 [#사용자-지정-런타임-프로필]

팀에서 내부 wrapper, 고정 버전 실행 파일을 사용하거나 호환 도구에 고정 인수를 추가해야 한다면 **사용자 지정 런타임 설정**을 만들 수 있습니다.

사용자 지정 설정이 새 통신 프로토콜을 추가하지는 않습니다. 만들 때 Multica가 이미 지원하는 프로토콜 계열 중 하나를 선택해야 하며(도구 연동 프로토콜 유형은 [AI 코딩 도구 비교](/providers) 참고), 명령 자체도 해당 프로토콜과 호환되어야 합니다.

### 작업 런타임 환경

데몬이 에이전트 작업을 시작하면 작업 컨텍스트를 런타임 프로세스에 주입합니다. 이 값은 데몬이 관리하므로 에이전트의 사용자 지정 환경에서 `MULTICA_` 변수나 작업 임시 디렉터리 변수를 덮어쓸 수 없습니다.

다음 표는 사용자 지정 런타임이 현재 사용할 수 있는 변수를 보여 줍니다. 전체 목록이 아니며 버전이 보장되는 API도 아닙니다. 연동에는 **연동 계약**으로 표시된 5개 변수만 사용하세요. 나머지는 참고 정보이며 변경될 수 있습니다.

| 변수 | 작업에서의 값 | 안정성 |
| --- | --- | --- |
| `MULTICA_TOKEN` | 작업 범위 `mat_` API 자격 증명 | **연동 계약** |
| `MULTICA_TASK_ID` | 실행 중인 작업의 ID | **연동 계약** |
| `MULTICA_AGENT_ID` | 할당된 에이전트의 ID | **연동 계약** |
| `MULTICA_WORKSPACE_ID` | 작업이 속한 워크스페이스의 ID | **연동 계약** |
| `MULTICA_SERVER_URL` | 데몬이 선택한 Multica 서버 URL | **연동 계약** |
| `MULTICA_TASK_CONFIG_ROOT` | 비공개 작업 로컬 Multica CLI 설정 루트 | 참고 정보 |
| `MULTICA_TASK_WORKSPACES_ROOT` | 데몬이 관리하는 작업 워크스페이스의 루트 | 참고 정보 |
| `MULTICA_AGENT_NAME` | 할당된 에이전트의 표시 이름 | 참고 정보 |
| `MULTICA_DAEMON_PORT` | `multica repo checkout` 같은 작업 전용 명령이 사용하는 로컬 데몬 상태/API 포트 | 참고 정보 |
| `MULTICA_TASK_SLOT` | 데몬 전체 동시 실행 풀의 슬롯. GPU 같은 슬롯 번호 기반 리소스에 사용 가능 | 참고 정보 |
| `MULTICA_REPO_CHECKOUT_MODE` | Linux와 Windows의 Codex 실행에서만 `isolated`로 설정되어, `multica repo checkout`이 작업 디렉터리 안에 `.git`이 있는 독립 클론을 만듭니다. 다른 실행에서는 설정되지 않습니다 | 참고 정보 |
| `TMPDIR` | 실행 중인 작업의 비공개 임시 디렉터리. `TMP`와 `TEMP`로도 제공하지만, Windows에서는 Git Bash의 공유 `/tmp`를 위해 작업이 사용자 temp 경로를 상속합니다. Windows Claude Code는 `CLAUDE_CODE_TMPDIR`의 기본값을 작업 임시 디렉터리로 지정 | 참고 정보 |

`MULTICA_TOKEN`을 사용하는 요청의 작성자는 서버가 결정하며, 태스크 댓글 같은 쓰기는 할당된 에이전트와 실행 중인 작업에 귀속됩니다. 자격 증명의 전체 바인딩, 권한, 귀속, 최대 24시간의 유효 기간 및 정리 동작은 [에이전트 실행용 임시 토큰](/auth-tokens#에이전트-실행용-임시-토큰)을 참고하세요.

<Callout type="warning">
이 값은 런타임 프로세스의 실제 환경에 존재합니다. 런타임이 시작하는 모든 자식 프로세스는 기본적으로 `MULTICA_TOKEN`을 포함한 모든 값을 상속합니다. 자식 프로세스가 자격 증명을 보유하면 안 되는 경우 명시적으로 제거하세요. 존재하지 않는 프로세스 격리를 전제로 하면 안 됩니다. 반대로 자체적으로 하위 프로세스 환경을 필터링하는 도구에는 명시적인 변수 허용 규칙이 필요할 수 있습니다. 예를 들어 Codex의 shell 도구는 이름에 `TOKEN`, `KEY`, `SECRET`이 포함된 변수를 제거하므로 데몬은 필요한 작업 변수를 허용하는 관리형 shell 정책을 설정합니다. 토큰은 프로세스 환경에만 두고 prompt, 로그, 저장소 파일 또는 영구 설정에 기록하지 마세요. 자식 프로세스는 상위 작업의 ID와 권한을 공유하며 독립된 새 범위 ID를 받지 않습니다.
</Callout>

### 설정 만들기

워크스페이스 owner와 admin만 사용자 지정 런타임 설정을 만들고 수정하거나 삭제할 수 있습니다.

1. **런타임**을 열고 해당 명령이 설치된 컴퓨터로 들어갑니다.
2. **사용자 지정 런타임 추가**를 클릭합니다.
3. 명령이 실제로 호환되는 프로토콜 계열을 선택합니다.
4. 이름, 명령, 고정 인수를 입력하고 저장합니다.

설정은 워크스페이스에서 공유됩니다. 연결된 각 컴퓨터가 이 명령을 개별적으로 찾으며 `PATH`에서 명령을 확인할 수 있는 컴퓨터만 해당 런타임을 등록합니다. 설정을 만든다고 명령이 자동으로 설치되거나 다른 멤버의 도구 로그인이 완료되지는 않습니다.

여기에는 shell script가 아니라 실행 파일과 인수를 입력합니다. 일반 인수, 따옴표, 백슬래시 이스케이프는 사용할 수 있지만 파이프, 리디렉션, `&&`, `;`, 역따옴표, 환경 변수 확장은 사용할 수 없습니다. 이런 동작이 필요하면 wrapper script에 넣고 해당 스크립트를 명령으로 입력하세요.

### 인수 순서

명령 칸에 입력한 내용은 실행 파일 바로 뒤, Multica가 추가하는 인수보다 앞에 놓입니다.

```text
<사용자 명령> <사용자 고정 인수> <Multica 프로토콜 인수> <에이전트 사용자 지정 인수>
```

하위 명령 방식의 wrapper는 이 순서 덕분에 동작합니다. 명령이 `ccms start q36`이면 도구는 먼저 `start q36`을 받아 Multica의 `-p` 등이 도착하기 전에 하위 명령을 고릅니다. 이런 wrapper는 이 순서만 받아들입니다.

예전에는 여기에 입력한 인수가 맨 뒤에 붙었습니다. flag 형식의 명령은 대부분 어느 위치든 똑같이 해석하지만, 전역 flag와 하위 명령 flag를 구분하는 명령은 flag 위치에 영향을 받습니다. 고정 인수가 있는 설정을 이미 쓰고 있다면 업그레이드 후 한 번 실행해 정상적으로 시작되는지 확인하세요.

그 밖에 다음 두 가지가 있습니다.

- **충돌하면 Multica의 값이 적용됩니다.** 고정 인수에 Multica도 설정하는 flag가 있으면 Multica의 값이 뒤에 와서 최종 적용됩니다. 가장 흔한 예는 에이전트에서 고른 모델이 설정에 고정한 `--model`을 덮어쓰는 경우입니다. 모든 사람에게 같은 모델을 고정하려면 에이전트의 모델 칸을 비워 두세요.
- **프로토콜 필수 flag는 무시됩니다.** `-p`, `--output-format`, `--input-format`, `--permission-mode`와 다른 프로토콜 계열의 대응 flag는 고정 인수에서 제거됩니다. 이 값을 덮어쓰면 데몬과 도구 사이의 통신이 끊기기 때문입니다. 하위 명령과 그 밖의 위치 인수는 항상 그대로 전달됩니다.

Desktop이 시작한 데몬에서 터미널에서는 실행되는 명령을 찾지 못한다면 현재 컴퓨터에 절대 경로를 설정할 수 있습니다.

```bash
multica runtime profile set-path <profile-id> --path /absolute/path/to/command
```

경로 덮어쓰기를 제거하려면 다음을 실행합니다.

```bash
multica runtime profile unset-path <profile-id>
```

설정 변경은 이후 가져가는 실행에만 적용됩니다. 설정을 삭제하기 전에 해당 런타임에 계속 연결된 활성 에이전트를 먼저 처리해야 합니다. 특정 컴퓨터의 런타임 인스턴스만 삭제해도 설정은 삭제되지 않으며 실행 중인 데몬이 다시 등록합니다.

## Qoder Cloud Agents 원격 런타임

Qoder Cloud Agents는 할당된 태스크를 원격 세션으로 실행합니다. Multica 서버가 기존 데몬 프로토콜을 사용하는 브리지를 관리하므로 사용자가 로컬 데몬을 실행할 필요가 없습니다.

### 시작하기 전에

- 워크스페이스 관리자 권한이 필요합니다. Qoder 연결은 워크스페이스마다 하나입니다.
- Qoder 개인 액세스 토큰(PAT), 하나 이상의 실행 환경, Qoder Cloud Agents에서 사용할 에이전트를 만드세요. 모델, 도구, 스킬은 Multica가 아니라 Qoder Cloud Agents의 원격 에이전트에서 설정합니다.
- 셀프 호스팅에서는 서버에 `MULTICA_VCS_SECRET_KEY`(base64로 인코딩한 32바이트 키, 재시작해도 같은 값 유지)를 설정해야 합니다. 설정하지 않으면 **추가** 메뉴에 Qoder Cloud Agents가 나타나지 않습니다.

### Qoder 연결하기

1. **런타임** 페이지에서 **추가**를 클릭하고 **클라우드 서비스** 아래의 **Qoder Cloud Agents**를 선택합니다.
2. **리전**에서 PAT를 발급한 사이트를 고릅니다: **글로벌(qoder.com)** 또는 **중국(qoder.com.cn)**. PAT는 발급한 사이트에서만 동작합니다. 거부되면 다른 사이트로 다시 시도하는 버튼을 사용하세요.
3. **개인 액세스 토큰**에 PAT를 붙여 넣습니다. 확인이 끝나면 Qoder에서 **실행 환경** 목록을 불러옵니다. 환경이 하나뿐이면 자동으로 선택되고, 여러 개면 직접 선택합니다.
4. 선택 사항: **GitHub authorization**을 열고 에이전트가 클론할 저장소마다 URL과 토큰을 추가합니다. 에이전트는 여기서 승인한 저장소만 클론할 수 있습니다.
5. 선택 사항: **실행 설정**을 열어 동시 실행 수(기본 3, 최대 10)와 실행 제한 시간(기본 60분, 5~240분)을 설정합니다.
6. **연결**을 클릭합니다. Qoder Cloud Agents가 런타임 페이지의 클라우드 영역에 나타나고 몇 초 안에 온라인이 됩니다.

### 에이전트 추가하기

런타임 페이지에서 Qoder Cloud Agents를 열고 **이것으로 에이전트 만들기**를 클릭합니다. 평소처럼 에이전트를 만들면서 Qoder 런타임을 선택해도 됩니다. 에이전트 양식의 **원격 에이전트**에서 원격 에이전트를 선택하세요. 기존 에이전트는 **Qoder Cloud Agents** 탭에서 Qoder Cloud Agents 에이전트나 기본 저장소를 바꿀 수 있습니다. 여러 Multica 에이전트가 하나의 연결을 공유하면서 각각 다른 Qoder Cloud Agents 에이전트에 연결될 수 있습니다.

자격 증명은 암호화되어 워크스페이스 내에서 공유됩니다. 관리자가 연결을 관리하고, 멤버는 접근 가능한 Qoder Cloud Agents 에이전트를 선택할 수 있습니다. 저장소와 시작 브랜치는 프로젝트에서 선택하며, 해당 저장소의 토큰은 Qoder Cloud Agents 세션 생성 시 전달됩니다. 저장된 PAT는 브라우저로 다시 반환되지 않습니다.

관리자는 Qoder Cloud Agents 페이지에서 연결과 저장소를 편집할 수 있습니다. **일시 중지**는 자격 증명과 에이전트를 유지한 채 새 태스크 전송을 멈추고, **연결 해제**는 저장된 토큰을 삭제하고 런타임을 제거하며 에이전트 연결을 해제합니다.

### 실행 방식

동시 실행 한도를 넘는 태스크는 대기열에서 기다립니다. 같은 태스크의 후속 실행은 이전 세션이 유휴 상태이면 해당 Qoder 세션을 이어서 사용합니다. 에이전트에 기본 저장소를 설정할 수 있으며, 태스크의 프로젝트에 저장소가 없을 때 사용됩니다. 에이전트는 태스크 식별자가 포함된 브랜치 이름과 식별자로 시작하는 PR 제목을 사용하도록 안내받으므로 PR이 태스크에 자동으로 연결됩니다.

초기 버전은 태스크 실행, 진행 상황 동기화, 취소, 영구 실행 기록을 통한 복구를 지원합니다. 채팅, 로컬 디렉터리, 첨부 파일, Qoder Cloud Agents 에이전트 생성은 지원하지 않습니다. 자세한 내용은 [README](https://github.com/multica-ai/multica/blob/main/server/cmd/qoder-runtime/README.md)를 참고하세요.

## 런타임 오프라인 문제 해결

다음 순서로 확인하세요.

1. `multica daemon status`를 실행해 데몬이 시작되었는지 확인합니다.
2. `multica daemon logs -f`를 실행해 로그인, 네트워크, 도구 감지 오류를 확인합니다.
3. 같은 실행 환경에서 `command -v <도구 명령>`을 실행해 데몬이 도구를 찾을 수 있는지 확인합니다.
4. Multica의 **런타임** 페이지를 열고 대상 컴퓨터와 해당 AI 코딩 도구가 온라인으로 표시되는지 확인합니다.
5. 도구를 방금 설치했거나 경로 또는 설정을 변경했다면 `multica daemon restart`를 실행합니다.

그래도 해결되지 않으면 [문제 해결](/troubleshooting)을 참고하세요.
