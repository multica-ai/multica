Multica 不会替代你使用的 AI 编程工具。运行时会调用电脑上已经安装并登录的工具，再把执行进度和结果写回任务。

如果你已经在使用其中一款，通常可以直接沿用。选择工具时的四个判断维度：

- 电脑上是否已经安装；
- 账号可以使用哪些模型；
- 是否需要由 Multica 配置 MCP；
- 团队要复用哪些 skill。

安装方法见 [安装 AI 编程工具](/install-agent-runtime)。

## 模型来源

创建智能体时，模型列表来自对应的运行时。有些工具提供固定的模型名称，有些会根据本机配置、登录账号和订阅权益返回可用模型。

不选择模型时，Multica 使用该工具的默认设置。列表为空时，先确认运行时在线并且工具已经登录，再刷新模型列表。

QwenPaw 和 MiniMax Code 是例外：它们不接受在 Multica 侧选择的模型，因此选择框不可用，显示为"由运行时管理"。请改在工具自身的配置里选择模型。模型列表为空属于正常情况，并不表示运行时离线。

DeepSeek Harness 的模型目录由运行时自身提供（`dsh --profile multica --list-models`）。它的模型 id 采用 `provider/model` 形式（例如 `deepseek-official/deepseek-chat`），请从列表中选择完整 id。

<Callout type="info">
不同工具可能使用不同的模型名称。更换 AI 编程工具后，原有的模型值在新工具中无效，需要重新选择。
</Callout>

## 会话恢复

表格中标记 ✓ 的工具支持在后续执行中继续已有会话。前提是原来的会话仍然存在，并且运行由能够访问它的运行时执行。MiniMax Code 0.1.2 尚未通过 ACP 声明会话加载能力，因此后续执行会新建 MCode 会话。

Multica 会保存工具返回的会话标识。下一次在同一任务中继续工作时，运行时会尝试恢复这段会话；无法恢复时，会创建一个新会话继续执行。Pi 保存的是本地会话文件路径，因此更依赖原来的电脑和文件。

有关重试和会话恢复的规则，见 [运行](/tasks#手动重试)。

## MCP 配置

Antigravity、GitHub Copilot CLI 和 DevEco Code 暂不读取智能体中的 MCP 配置，因此创建智能体时不会显示这一项。

### Pi 受管 MCP

守护进程检测到已启用且兼容的 `pi-mcp-adapter` 后，Pi 才支持 Multica 管理 MCP。目前支持的插件版本为 **2.37.0** 和 **3.1.0**，其他版本不视为兼容。请在运行时所在电脑安装支持的版本，再重启守护进程以刷新检测结果：

```bash
pi install npm:pi-mcp-adapter@2.37.0
```

只有上报了此能力的 Pi 运行时才会显示 MCP 页签。旧版守护进程、插件缺失或版本不兼容时，该页签不可用；未使用受管 MCP 的普通 Pi 运行仍可正常执行。Multica 不会自动安装或启用插件。

受管运行通过插件的 `createMcpAdapter({ config })` 接口，只传入智能体解析后的 MCP 配置，不合并电脑上的全局或项目 MCP 配置。每次运行的配置与插件状态保存在私有临时目录中，运行结束、启动失败或取消后清理。全局 Pi 设置和 MCP 文件不会被修改。

- 未设置 MCP 配置（`null`）时，保留 Pi 原有启动行为。
- 显式空配置（`{}` 或 `{"mcpServers": {}}`）会启动隔离的受管运行，不加载任何 MCP server。
- 受管运行关闭扩展自动发现，只加载 Multica 的 MCP 桥接扩展。其他扩展及其提供的模型服务不可用。Pi 原生和项目 skill、配置中的 skill 路径，以及已安装 npm 包或本地包中的 skill 会保留。

Pi 包必须是已安装的 npm 包或使用绝对路径的本地包目录。Git 来源和相对路径会导致受管运行准备失败；Multica 不会为保留包资源而下载包。模型配置和认证按运行复制，刷新的凭据不会写回；如果 refresh token 发生轮换，可能需要重新认证。MCP 认证使用显式配置的 headers 和环境变量，不导入插件的全局 OAuth 凭据。

#### 在运行时电脑上验证

使用测试 MCP server 和已获授权的模型账号；真实运行可能消耗模型额度。

1. 启用支持的插件版本并重启守护进程，确认 Pi 智能体显示 MCP 页签。再检查无兼容插件的情况：页签不可用，普通运行仍可执行。
2. 为两个智能体分配不同的测试 MCP server，并发运行，让它们分别列出可用的 MCP 工具。每个智能体应只能看到自己分配的 server。再使用显式空配置，确认没有 MCP 工具。
3. 绑定一个 skill，选择已认证的模型，完成一次受管运行。继续同一任务以检查会话恢复，并验证取消运行和 MCP 启动失败的情况。
4. 比较执行前后全局 Pi 设置和 MCP 文件的校验和。确认完成、失败或取消的运行均已清理临时目录。日志和截图不要包含凭据。

<Callout type="warning">
MCP server 的命令、参数和环境变量会随智能体配置保存在服务器端。不要把不需要共享的本地凭据直接写入配置。
</Callout>

## Skill 注入方式

执行开始前，Multica 会把智能体绑定的 skill 写入上表对应的位置，让工具通过自己的原生机制发现它们。

仓库里原本存在的 skill 不会被覆盖。如果名称冲突，Multica 会为注入的副本使用另一个目录名；执行结束后，只清理自己创建的文件。

Codex、Hermes 和 OpenClaw 的处理稍有不同：

- Codex 使用单次执行的 `CODEX_HOME`，不会把 skill 写进系统级 Codex 目录。
- Hermes 使用单次执行的 `HERMES_HOME`。已有的本地配置仍然可以被读取，但绑定的 skill 与会话数据按运行隔离。这套隔离只在智能体绑定了 skill 时启用，没有绑定 skill 的运行使用本机原有的 Hermes 主目录。
- OpenClaw 使用当前执行工作目录下的 `skills/`，并由单次执行配置把该目录设为工作区。

如何创建和绑定 skill，见 [Skills](/skills)。
