Multica 在程序啟動時讀取環境變數。修改後通常需要重啟對應的 API、Web 或守護程序。Docker Compose 的 `docker compose restart` 不會重新讀取 `.env`，要用 `up -d` 重建容器才能生效。

本頁按分組列出面向部署者的配置，測試變數和內部執行變數不在這裡展開。完整部署步驟見[自託管快速上手](/self-host-quickstart)。

## 生產環境最小配置

```dotenv
DATABASE_URL=postgres://user:password@postgres:5432/multica?sslmode=require
JWT_SECRET=<long-random-secret>
APP_ENV=production
FRONTEND_ORIGIN=https://multica.example.com
MULTICA_APP_URL=https://multica.example.com
MULTICA_PUBLIC_URL=https://api.multica.example.com
```

還需要選擇一種郵件服務，否則驗證碼和邀請只會寫入服務端日誌。

<Callout type="warning">
`JWT_SECRET` 在生產環境為必填：當 `APP_ENV=production` 時，後端會在金鑰為空或等於已知佔位值時拒絕啟動（用 `openssl rand -hex 32` 生成）。也不要在生產環境設定 `MULTICA_DEV_VERIFICATION_CODE`。
</Callout>

## API 與資料庫

| 變數 | 預設值 | 說明 |
|---|---|---|
| `DATABASE_URL` | 本地 `multica` 資料庫 | PostgreSQL 連線地址 |
| `DATABASE_MAX_CONNS` | `25` | 單個 API 程序的最大資料庫連線數 |
| `DATABASE_MIN_CONNS` | `5` | 單個 API 程序保留的最小連線數 |
| `DATABASE_SEARCH_WORK_MEM_MB` | `64` | 每個搜尋計劃運算元的 PostgreSQL `work_mem` 上限（MB）；設為 `1`–`64` 可調低，設為 `0` 則沿用資料庫/會話預設值 |
| `DATABASE_REPLICA_URL` | 空 | 可選的 PostgreSQL 只讀從庫連線地址；新連線會強制校驗只讀狀態，業務仍需在程式碼中顯式選擇最終一致讀取 |
| `DATABASE_REPLICA_MAX_CONNS` | `10` | 單個 API 程序的最大從庫連線數 |
| `DATABASE_REPLICA_MIN_CONNS` | `0` | 單個 API 程序保留的最小從庫連線數 |
| `MULTICA_DATABASE_STARTUP_TIMEOUT` | `3m` | 容器啟動過程中，migration 與 API 共享的暫時性資料庫故障重試時長；設為 `0` 時每個階段只嘗試一次 |
| `MULTICA_DATABASE_CONNECT_TIMEOUT` | `5s` | 啟動期間單次資料庫連線的兜底超時；pgx 原生 `connect_timeout`、`PGCONNECT_TIMEOUT` 或 service 配置優先 |
| `PORT` | `8080` | API 監聽埠 |
| `JWT_SECRET` | 生產環境必填 | 登入 JWT、部分簽名流程使用的金鑰；生產環境對空值或已知佔位值拒絕啟動 |
| `APP_ENV` | 空 | 生產環境設為 `production` |
| `AUTH_TOKEN_TTL` | `720h`（30 天） | 瀏覽器 JWT 與 cookie 有效期；接受 Go duration 或正整數秒數。會話會滑動續期：剩餘有效期過半後，持續使用的會話會被續期而不是到期。低於 `60s` 的取值會按 `60s` 處理 |
| `LOG_LEVEL` | 應用預設 | 日誌級別 |
| `MULTICA_SHUTDOWN_HOLD_DURATION` | `0` | 收到終止訊號後，開始優雅退出前等待多久 |
| `MULTICA_RUNTIME_RECONNECT_GRACE` | `3h` | 執行時離線後可重新連線且不終止在途執行的寬限時間；低於 `150s` 時按 `150s` 處理 |

在 Kubernetes 中設定 shutdown hold 時，`terminationGracePeriodSeconds` 要大於 hold 與實際退出所需時間之和。

主庫與從庫的連線上限彼此獨立，需要按全部 API 程序的連線數總和預留 PostgreSQL 叢集連線額度。從庫連線預設五分鐘回收一次，以便在提升後重新校驗只讀狀態。從庫連線失敗時，基礎設施會透明回退主庫並短暫開啟被動熔斷器，不會增加後臺資料庫探測。應用不保證從庫資料的最大陳舊時間；請在資料庫層監控複製延遲，一致性敏感的讀取繼續走主庫。

## 對外地址與瀏覽器訪問

| 變數 | 預設值 | 說明 |
|---|---|---|
| `FRONTEND_ORIGIN` | 空 | 使用者訪問的前端 origin；用於 CORS、cookie 和邀請連結 |
| `MULTICA_APP_URL` | 回退到 `FRONTEND_ORIGIN` | 使用者可訪問的 Web 地址；CLI 登入和帳號繫結連結使用它 |
| `MULTICA_PUBLIC_URL` | 空 | 公網 API 地址；用於 webhook URL 和執行時連線說明 |
| `MULTICA_DAEMON_SERVER_URL` | 回退到 `MULTICA_PUBLIC_URL`，再回退到 `MULTICA_APP_URL` / `FRONTEND_ORIGIN` | API 程序寫入 `multica setup self-host` 命令的服務端地址；守護程序訪問 API 的地址與公網 webhook 地址不同時設定 |
| `CORS_ALLOWED_ORIGINS` | 空 | 額外允許的 HTTP origin，逗號分隔 |
| `ALLOWED_ORIGINS` | 回退到 CORS / 前端地址 | WebSocket origin 白名單，逗號分隔 |
| `COOKIE_DOMAIN` | 空 | 前後端不同 host 且瀏覽器直接訪問 API 域時必須設定；單域部署保持為空 |

<Callout type="warning">
`MULTICA_DAEMON_SERVER_URL` 會由無需認證的 `/api/config` 介面返回，客戶端可以讀取。請將它視為公開配置，切勿填入憑據、令牌或其他金鑰。
</Callout>

前端和 API 使用不同 host、且瀏覽器直接訪問 API 域時，必須設定 `COOKIE_DOMAIN`，否則瀏覽器讀不到 CSRF cookie——所有寫請求返回 `403 CSRF validation failed`，而讀請求一切正常。取值用能同時覆蓋兩個 host 的最窄父域（`.agent.example.com` 優於 `.example.com`）。它會把登入會話 cookie 擴散到該域下的所有 host，只有這些 host 都由同一可信主體運維時才可用。修改後需要在兩個 host 上清除舊 cookie 並重新登入。若採用[自託管快速上手](/self-host-quickstart#remote-access)的同源配方（瀏覽器只訪問 app 域），保持為空即可。不要填寫 IP 地址，瀏覽器會忽略帶 IP Domain 的 cookie。

<Callout type="warning">
自託管部署需要設定 `FRONTEND_ORIGIN`。缺少它時，邀請連結、cookie 安全屬性和 WebSocket origin 校驗都可能與實際網域不一致。
</Callout>

| 變數 | 預設值 | 說明 |
|---|---|---|

| `RATE_LIMIT_INVITATION_WORKSPACE_24H` | `50` | 同一工作區內所有管理員在 24 小時滑動視窗內可建立的邀請總數；設為 `0` 可關閉此項限流 |
| `RATE_LIMIT_INVITATION_RECIPIENT_24H` | `6` | 同一規範化收件信箱跨工作區在 24 小時滑動視窗內可收到的邀請數；設為 `0` 可關閉此項限流 |
| `RATE_LIMIT_TRUSTED_PROXIES` | 空 | 允許提供 `X-Forwarded-For` 的代理 CIDR，逗號分隔 |
| `MULTICA_TRUSTED_PROXIES` | 空 | 自動化 webhook 與實時連線使用的可信代理 CIDR |

反向代理後的部署需要填寫真實代理網段。不要直接信任所有來源，否則客戶端可以偽造轉發 IP。

認證限流需要配置 `REDIS_URL`；未配置時，啟動日誌會提示認證限流已關閉。邀請限流在沒有 Redis 時仍使用程序記憶體，配置 Redis 後則在多個副本間共享額度。如果已配置的 Redis 臨時不可用，認證限流仍選擇放行，而邀請建立會返回可重試的 `503`，不會在失去防護時傳送郵件。

## 服務端 LLM

這組配置用於服務端的輔助生成能力，例如對話標題；它不是 AI 代理執行時使用的 AI 程式設計工具憑據。

| 變數 | 預設值 | 說明 |
|---|---|---|
| `MULTICA_LLM_API_KEY` | 空 | OpenAI 相容 API key |
| `MULTICA_LLM_BASE_URL` | 空 | OpenAI 相容 endpoint |
| `MULTICA_LLM_DEFAULT_MODEL` | `gpt-6-luna` | 請求未指定模型時使用 |
| `MULTICA_LLM_MAX_RETRIES` | `2` | 單次呼叫的重試上限；`0` 表示禁用重試，`1`–`5` 表示最多重試 N 次 |
| `MULTICA_LLM_DISABLE_THINKING` | `false` | 在每個請求中附帶 `chat_template_kwargs: {"enable_thinking": false}`，供支援該欄位的閘道器關閉模型思考 |

`MULTICA_LLM_MAX_RETRIES` 是重試策略的唯一配置源。不設定時使用預設的 2 次；設為 `0` 表示每次呼叫只發一個請求；設為 1–5 表示最多重試這麼多次。它是上限而不是配額：只有可重試的失敗才會消耗它，請求成功或呼叫方自身的超時都會讓呼叫提前結束。其它取值（負數、非數字、大於 5）會讓服務啟動失敗，不會被靜默糾正。上限是一個延遲預算：退避從 0.5s 開始翻倍，上限 8s，更大的預算會超出呼叫方自身的超時，把可重試的失敗變成超時失敗。重試覆蓋連線失敗以及 HTTP 408、409、429 和 5xx；其餘 4xx 直接返回。服務啟動時會以 `llm retry policy` 列印生效策略，其中不包含任何憑據。

`MULTICA_LLM_DISABLE_THINKING` 面向"模型會先跑一段推理（thinking）並吃掉輔助呼叫延遲預算"的閘道器。設為 `true`（或 `1`）時，服務端會在每個請求體中附帶 `chat_template_kwargs: {"enable_thinking": false}`；支援透傳該欄位的閘道器（vLLM/sglang 類部署、部分 GLM/Qwen 系的 LiteLLM 路由）會因此跳過思考階段。標準 OpenAI 端點會拒絕未知的請求體欄位，所以僅在上游接受時啟用。GPT-5.6 系模型和 GPT-6 Luna 在後續提問建議請求中已由服務端附帶 `reasoning_effort: none`。會話自動命名不傳送推理欄位；只有當所配置的上游接受 `chat_template_kwargs` 時，此項才會影響它。可接受的取值為 `true`/`false` 和 `1`/`0`（不區分大小寫）；其它取值會讓服務啟動失敗。啟動日誌會在重試策略旁列印生效狀態。

有兩個功能會使用這一層，它們都會把聊天內容傳送到你配置的 endpoint：

- **對話標題自動生成** —— 傳送新對話中使用者的第一條訊息，原文傳送。附件不會包含在內。
- **後續提問建議**（AI 代理回覆下方的按鈕）—— 傳送對話末尾的內容：最多 6 條訊息，其中被追問的那條回覆上限 3000 字元，更早的每條上限 800 字元。

API key 與 base URL 都為空時，這一層關閉，不會發出任何上游請求——上面兩個功能都不再傳送內容。如果你的政策不允許這一層把聊天內容發到部署之外，這就是受支援的配置方式：對話繼續使用客戶端根據第一條訊息生成的標題，後續提問按鈕不再出現，其餘功能不受影響。

<Callout type="info">
這只覆蓋輔助生成這一層。AI 代理執行是另一條資料路徑：AI 代理回覆對話時，由你的守護程序呼叫該 AI 代理的 AI 程式設計工具，用的是那個工具自己的憑據，守護程序不會把上面的 `MULTICA_LLM_*` 配置傳給它。（AI 代理自身需要的執行級 Multica 連線變數由守護程序單獨注入。）把上面的變數留空不影響這條路徑——它由 AI 代理的執行時配置決定。
</Callout>

### 清理與保留 [#gc]

守護程序定期清理執行工作目錄、倉庫快取、會話記錄和臨時目錄，各類資料的刪除條件見[清理與保留](/daemon-runtimes#cleanup)。時長接受 Go duration，另外支援 `d` 表示天（如 `14d`、`1d12h`）。

| 變數 | 預設值 | 說明 |
|---|---|---|
| `MULTICA_GC_ENABLED` | `true` | 設為 `false` 或 `0` 關閉整個清理迴圈 |
| `MULTICA_GC_INTERVAL` | `2h` | 兩輪清理之間的間隔；守護程序啟動約 30 秒後先清理一次 |
| `MULTICA_GC_TTL` | `24h` | 任務進入 `done` 或 `closed` 分類、或聊天會話歸檔後，再過多久刪除對應執行目錄 |
| `MULTICA_GC_COMPLETED_TASK_TTL` | `14d` | 任務執行完成多久後刪除整個目錄，不論任務是否關閉；`0` 表示關閉。不作用於專案本地目錄上的執行 |
| `MULTICA_GC_ORPHAN_TTL` | `72h` | 找不到歸屬的目錄多久沒有改動後刪除 |
| `MULTICA_GC_ARTIFACT_TTL` | `12h` | 從執行結束到守護程序清理可重新生成內容的時間。下一行的目錄名稱規則適用於未關閉的任務，以及使用受管理工作目錄的未歸檔聊天。守護程序管理的 Codex 快取也適用相同時長。設為 `0` 可保留這些快取 |
| `MULTICA_GC_ARTIFACT_PATTERNS` | `node_modules,.next,.turbo` | 按目錄名匹配的可再生成內容，逗號分隔。設定後**替換**預設列表，要保留預設項就一併寫上；含 `/` 或 `\` 的項會被忽略 |
| `MULTICA_GC_REPO_TTL` | `30d` | 不再被引用、也沒有 worktree 的裸倉庫快取，多久沒有檢出後刪除；`0` 表示不刪 |
| `MULTICA_GC_REPO_MAINTENANCE_ENABLED` | `true` | 刪掉過期的 AI 代理分支後，是否對倉庫快取執行 `git reflog expire` 和 `git gc`；設為 `false` 只關掉這一步 |
| `MULTICA_GC_CODEX_SESSION_TTL` | `14d` | Codex 會話記錄多久未使用後刪除；`0` 表示不刪 |
| `MULTICA_GC_HERMES_SESSION_TTL` | `14d` | Hermes 會話記錄多久未使用後刪除；`0` 表示不刪 |
| `MULTICA_GC_HERMES_MEMORY_TTL` | `90d` | Hermes 記憶多久未使用後刪除；`0` 表示不刪 |
| `MULTICA_GC_TASK_TEMP_LEGACY_TTL` | `0` | 只針對舊版守護程序留下、沒有執行鎖的臨時目錄：多久沒有改動後刪除。`0` 表示不刪。帶執行鎖的臨時目錄在執行結束後就會刪除，不受它影響 |

### 守護程序日誌 [#daemon-logs]

守護程序在後臺執行（不連著終端）時，日誌寫入 `~/.multica/daemon.log`，命名 profile 為 `~/.multica/profiles/<name>/daemon.log`，並按大小輪轉，輪轉出的檔案用 gzip 壓縮。

| 變數 | 預設值 | 說明 |
|---|---|---|
| `MULTICA_DAEMON_LOG_MAX_SIZE_MB` | `20` | `daemon.log` 達到多少 MB 時輪轉 |
| `MULTICA_DAEMON_LOG_MAX_BACKUPS` | `5` | 最多保留幾個輪轉檔案 |
| `MULTICA_DAEMON_LOG_MAX_AGE_DAYS` | `30` | 輪轉檔案保留的天數 |

三個變數都要求正整數；`0`、負數或無法解析的值按預設值處理，不會變成"不限制"。保留數量和天數哪個先到就按哪個刪除。崩潰輸出寫在同目錄的 `daemon.err.log`，啟動時超過 5 MB 就改名為 `daemon.err.log.1`。

### DeepSeek Harness 的 profile 安裝

`MULTICA_DSH_PROFILE_BUNDLE` 指定 `multica` profile 缺失時要安裝的 bundle，多個候選用逗號分隔、按序嘗試，每項可以是 npm 包名、目錄或打包好的 tarball。該變數預設不設定。Multica 驅動的 `--stdio` 協議正是由這個 profile 提供，所以不設定時不會改動 DSH 的安裝，守護程序會報告缺少 profile，不會註冊一個不可用的執行時。

Multica 自己的橋接還沒有釋出到公共 npm registry，如何選取值見[安裝 AI 代理執行時](/install-agent-runtime)。這裡填的東西會在沒有二次確認的情況下裝進每一臺守護程序宿主的 DSH 家目錄，請當作供應鏈決策來對待。

這項安裝被刻意限制了範圍：每個守護程序生命週期最多執行一次，只在探測確認 profile 確實缺失時執行；失敗時會把包管理器自身的輸出記入日誌，且只有重啟守護程序後才會重試。探測超時、或返回本守護程序不支援的協議版本時，只做報告，絕不覆蓋安裝：守護程序不會覆蓋一個明顯是刻意裝上去的 profile。排查時在守護程序日誌中搜尋 `DSH runtime profile`；要撤銷安裝，刪除 `$DSH_HOME/profiles/multica`（預設 `~/.dsh/profiles/multica`）。

`MULTICA_DSH_PLUGIN_PATH` 用於覆蓋安裝時解析 pnpm 的目錄。`dsh plugin` 轉發到的那個 pnpm 由 DSH Desktop 放在它私有的 runtime-commands 目錄裡，macOS 和 Windows 都是如此，守護程序會自動找到並加到 PATH 最前，較新版 Desktop 採用的帶版本號目錄結構也能找到。所以只有守護程序找不到的安裝位置、或者你想讓安裝使用自己的 pnpm 時，才需要這個變數。一旦設定就完全取代自動查詢：目錄不存在時，安裝會退回使用守護程序 `PATH` 上的 pnpm，不會用內建的那個。Linux 上沒有 DSH Desktop，安裝始終使用 `PATH`。

### Cursor 後臺程序清理

Cursor 已驗證的後臺清理需要 Linux 6.9 及以上（程序組 pidfd）、macOS 核心對程序身份查詢與 audit token 發訊號的支援，或 Windows 上成功分配的巢狀 Job Object。在 macOS 上，每個程序都按核心校驗的 PID version 發訊號，不需要加入同一 session 的程序組；這些 macOS 介面是私有的，會在捕獲時做探測。無法認領的後臺啟動會返回它原本的工具結果並回到普通的 idle watchdog，工具 watchdog 為 `0` 時同樣如此。已經認領的工作在清理無法確認時會繼續算作執行中。當工具 watchdog 設為 `0` 時則完全沒有這個邊界：已認領的後臺工作只要還活著就一直讓執行處於執行中，此時執行僅受 `MULTICA_AGENT_TIMEOUT` 約束，而它預設也是 `0`。

執行正常結束時，被認領的 Cursor 後臺程序同樣會被停止，因此該次執行啟動的後臺服務不會有意留到收尾之後。macOS 可以透過保留的原始父程序身份識別後期產生的子程序，但無法證明中間程序在被觀察到之前就已消失的那條鏈路。這類程序、離開被追蹤程序組的工作，以及持續的歸屬或發訊號錯誤，都可能留下殘餘的後臺工作。未確認的清理會被記錄下來，且永遠不會換取一次"清理成功"的恢復視窗；不會僅憑數字 PID 或程序組就去殺掉未知程序。

### 守護程序配置的持久化

守護程序側的常用配置也可以寫入 `~/.multica/config.json`，不必依賴 shell 環境變數；命名 profile 的配置檔案在 `~/.multica/profiles/<name>/config.json`：

```bash
multica config set poll_interval 10s
multica config show
```

支援的鍵：

| 鍵 | 預設值 | 說明 |
|---|---|---|
| `server_url` | `ws://localhost:8080/ws` | Multica API / WebSocket 地址 |
| `app_url` | 空 | 瀏覽器登入使用的 Web 地址 |
| `workspace_id` | 空 | 預設工作區 |
| `device_name` | 主機名 | 執行時列表中的裝置名 |
| `runtime_name` | `Local Agent` | 執行時顯示名 |
| `workspaces_root` | `~` 下按 profile 區分的路徑 | 執行工作目錄的根目錄 |
| `max_concurrent_tasks` | `20` | 併發執行上限；`0` 或留空表示未設定 |
| `poll_interval` | `30s` | 執行輪詢間隔 |
| `ws_claim_poll_interval` | `3m` | 健康 WebSocket 下 claim 安全輪詢的上限，與 `poll_interval` 獨立配置；Daemon 會應用向下抖動 |
| `heartbeat_interval` | `15s` | 心跳間隔 |
| `agent_timeout` | 不限制 | 單次執行的絕對時限 |
| `agent_idle_watchdog` | `2h` | 沒有工具執行時的靜默上限；`0s` 關閉守護程序的整套 watchdog，`agent_tool_watchdog` 也隨之失效 |
| `agent_tool_watchdog` | 同 `agent_idle_watchdog` | 工具執行期間的靜默上限；`0s` 表示守護程序的 watchdog 不會因工具靜默而停止執行，此時執行只受 `agent_timeout` 限制，而它預設不限制 |
| `codex_semantic_inactivity_timeout` | 派生 | Codex 語義靜默閾值。未設定時取 idle 與 tool watchdog 預算中較大的那個；tool 預算為 `0` 時回落到 idle 預算；只有整套 watchdog 關閉時才保留 Codex 自己的 `10m` |
| `codex_handshake_timeout` | `30s`；`thread/start`、`thread/resume`：`60s` | Codex app-server 啟動握手上限；顯式設定後會統一覆蓋兩類預算 |
| `disable_auto_update` | 跟隨環境 | `true` 關閉自動更新；`false` 清除本地覆蓋，回到環境變數或預設 |
| `auto_update_check_interval` | `6h` | 檢查更新的間隔 |
| `disable_auto_reload` | 跟隨環境 | `true` 讓守護程序不再跟隨磁碟上被替換的二進位制；`false` 清除本地覆蓋。與 `disable_auto_update` 分開解析 |

幾條取值規則：

- duration 類鍵接受正的 Go duration（如 `10s`、`2h`），負值一律拒絕。只有 `agent_timeout`、`agent_idle_watchdog`、`agent_tool_watchdog` 還接受 `0s`：`agent_timeout` 設為 `0s` 表示明確關閉執行時限，兩個 watchdog 鍵設為 `0s` 關閉什麼見上表。
- 傳空字串清除已持久化的值，回到環境變數或內建預設，例如 `multica config set poll_interval ""`。
- `max_concurrent_tasks` 要求非負整數。
- 相對的 `workspaces_root` 值在儲存時會轉換為絕對路徑。

## 觀測與統計

| 變數 | 預設值 | 說明 |
|---|---|---|
| `DO_NOT_TRACK` | 空（預設開啟遙測） | 設為 `1` 或 `true`（不區分大小寫）後，停止首方匿名自託管遙測的採集與傳送 |
| `ANALYTICS_DISABLED` | `false` | 設為 `true` 關閉 PostHog 上報 |
| `POSTHOG_API_KEY` | 空 | 不設定時統計上報關閉；接入自己的 PostHog 專案時填寫 |
| `POSTHOG_HOST` | `https://us.i.posthog.com` | PostHog 地址 |
| `METRICS_ADDR` | 空 | Prometheus metrics 監聽地址；空表示不啟動 |
| `REALTIME_METRICS_TOKEN` | 空 | 保護 `/health/realtime` 的 bearer token |

首方自託管遙測每天按 UTC 傳送一份部署級快照，固定且不可配置的地址為 `https://telemetry.multica.ai/v1/telemetry/events`。快照只包含正式釋出版本、工作區數/去重成員數/活躍 AI 代理數/過去 24 小時活躍守護程序數的分桶，過去 24 小時執行的開始、完成、失敗和取消總數，以及過去 1、7、28 個完整 UTC 日內登入後開啟過網頁端或桌面端的成員數、親自發起過 AI 代理執行（分配、@、評論、聊天、手動執行或重跑；不含 autopilot 和 AI 代理之間的委派）的成員數的分桶。成員只在本部署內計數，不會被識別。不會傳送名稱、信箱或網域、IP、業務識別符號、主機或裝置資訊、程式碼倉庫、模型或 plugin、prompt/output、評論或聊天、檔案路徑、token/費用、憑據、錯誤文字、stack 或日誌。此資料只用於瞭解自託管版本採用、部署規模區間、聚合使用量與成員活躍情況，不用於計費、授權、認證或安全決策。

`DO_NOT_TRACK` 與 `ANALYTICS_DISABLED` 相互獨立：前者控制這份首方匿名快照，後者控制可選的 PostHog 整合。
