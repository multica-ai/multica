连接 GitHub 后，Multica 根据任务编号自动关联 pull request。任务详情中可直接查看 PR 状态、改动规模、CI 结果和合并冲突。

GitHub 集成只作用于安装时授权的仓库，App 不会自行向 GitHub 写入任何内容。每一次写操作，例如合并或批准 PR，都由某位 Multica 用户以自己的身份在 Multica 中发起，详见[在 Multica 中操作 PR](#在-multica-中操作-pr)。

自部署的 Multica 还可以并行连接自托管的 Forgejo、Gitea 或 GitLab 实例，获得同样的 PR 自动关联、合并后改状态和 CI 展示，入口在 **设置 → 代码**，详见[自托管 Git 代码托管](/vcs-integration)。Multica Cloud 不提供该入口。

## 连接 GitHub

工作区 owner 或 admin 可以完成连接：

<Steps>
<Step>
打开 **设置 → 代码**。
</Step>
<Step>
在 **GitHub** 一行点击 **连接 GitHub**。
</Step>
<Step>
在 GitHub 中选择账号或组织，并授权全部仓库或指定仓库。
</Step>
<Step>
安装完成后回到 Multica。
</Step>
</Steps>

连接状态会显示在同一页面。普通成员可以查看状态，但不能连接、断开或修改开关。

<Callout type="info">
**GitHub 连接**决定 Multica 从哪些仓库接收 PR 事件；**代码仓库**设置决定智能体运行时可以选择哪些仓库。两者用途不同，需要分别配置。
</Callout>

## 功能开关

**设置 → 代码** 的 **PR 与任务联动** 中有以下设置。在 GitHub 一行的 **⋯** 菜单中选择 **暂停 GitHub 功能** 后，下面三项开关不再生效，但不会断开 GitHub App。

| 设置 | 作用 |
|---|---|
| PR 侧栏 | 在任务详情中显示关联的 pull request。 |
| Co-authored-by | 在智能体创建的 commit 中加入 `Co-authored-by: multica-agent <github@multica.ai>`。 |
| 自动关联 PR | 分支名或标题含任务编号、或正文中关闭语句后写了任务编号的 PR，会关联到对应任务。 |
| PR 合并后，任务状态改为 | 任务关联的 PR 全部合并后，把任务改成某个状态（默认 `Done`），或者不改。见[PR 合并后怎样改状态](#pr-合并后怎样改状态)。 |
| PR 卡片 → CI 与可合并性 | 对每个关联的 PR，Multica 以 App 身份从 GitHub API 拉取快照，把 CI 状态和可合并性显示在卡片上，见[在任务中查看 PR](#在任务中查看-pr)。 |

**PR 合并后，任务状态改为** 对所有代码托管平台生效，包括[自托管 Git 代码托管](/vcs-integration)。

## 让 PR 关联到任务

最简单的做法，是把任务编号写进分支名或 PR 标题。例如任务为 `MUL-123`：

```text
mul-123-fix-login-redirect
```

```text
MUL-123 修复登录后的跳转
```

Multica 会忽略大小写，并且只匹配当前工作区的任务前缀。一个 PR 可以关联多个任务。

只在 PR 正文中写编号时，需要使用 GitHub 的关闭语句：

```text
Closes MUL-123
Fixes MUL-123
Resolves MUL-123
```

正文中的普通提及，例如 `Related to MUL-123`，不会与该任务建立关联。Commit message 和 PR 评论也不会触发关联。

也可以手动关联：在任务的 **Pull requests** 区块点 **+**，粘贴 PR 链接。要把 PR 从任务上移除，打开这一行的 **⋯** 菜单，选择 **移除关联**；之后 Multica 不会再根据标题或分支把它关联回来。

## 在任务中查看 PR

关联成功后，PR 会出现在任务详情的 **Pull requests** 区块。每条记录会显示：

- 仓库、编号、标题和作者；
- `Open`、`Draft`、`Merged` 或 `Closed` 状态；
- 新增、删除行数和改动文件数；
- CI 状态：全部通过（带计数）、若干个失败（点名失败的 check），或若干个进行中；没有配置任何 check 的 PR 不显示这一项，"没有 check"不会被当成通过；
- 可合并性：可合并（仅当 GitHub 报告合并状态为 clean）、有冲突、blocked 或 behind。

CI 状态和可合并性来自 Multica 从 GitHub API 拉取的快照，两者互相独立；已合并或已关闭的 PR 不再显示这两项。GitHub 暂时不可用时，卡片保留上一次的快照并标记为过期。

列表下方有一行说明接下来会发生什么，例如"等待 #19 合并后改为 已完成"，或者哪个 PR 已关闭、未合并。工作区设置为不改变、或者任务已经是目标状态时，不显示这行说明。

点击记录可以打开 GitHub 上的 PR。关闭 **PR 侧栏** 只会隐藏这个区块，不会断开连接。

## 在 Multica 中操作 PR

成员不用离开 Multica，就能对关联的 PR 执行合并、关闭、批准、请求评审、更新分支和重跑失败的 check。每位成员需要先连接一次自己的 GitHub 账号；这个连接属于成员本人，在其加入的所有工作区中通用。

可以在 **设置 → 个人资料 → 已连接账号** 中连接，也可以在第一次操作 PR 时按提示连接。检查失败和合并冲突需要改代码，这类 PR 会提供交给智能体修复的入口：Multica 会在任务下起草一条可编辑的评论，并提及任务的智能体。

Multica 以点击操作的成员身份把每个操作发送到 GitHub，所以 GitHub 会照常应用这个人的仓库权限和分支保护规则，与在 github.com 上操作完全一致，操作记录上的作者也是这个人。智能体无法使用成员的 GitHub 账号。合并或关闭 PR 还会以该成员的名义写入任务时间线。

在 Multica 中断开 GitHub 账号时，也会同时撤销 Multica 在 GitHub 上的访问权限。

## PR 合并后怎样改状态

PR 合并不一定代表任务已完成，所以由工作区决定合并后做什么：**设置 → 代码 → PR 合并后，任务状态改为**。可以选 `Done`（新工作区的默认值）、其他"已开始"或"已完成"类的状态（也可以是自定义状态，例如"待回归"），或者**不改变**。这项设置出现之前就已存在的工作区保持原来的行为：如果以前的合并并不总会完成任务，初始值就是**不改变**。

以下条件同时成立时，任务会改为选定的状态：

1. 所有关联 PR 都是 `Merged`。仍为 `Open` 或 `Draft` 的 PR 会让任务继续等待；关闭但未合并的 PR 也一样，直到你把它从任务上移除；
2. 任务当前不是 `done` 或 `cancelled`，不在 Triage 中，还不是目标状态，也没有单独设置合并后不改状态（**Pull requests → ⋯ → 此任务合并后不改状态**）。

<PrLinkDemo />

PR 是怎么关联上的，不影响结果：标题、分支名和正文里的 `Closes MUL-123` 只负责关联。如果一个 PR 只交付了任务的一部分，或者合并后还要发布、验证，就在这个任务的 **Pull requests** 菜单里设置合并后不改状态。

只有 PR 事件会触发判断：关联 PR 合并、新增关联或移除关联。重新打开任务后，它不会被改回去，下一个关联 PR 合并时才会。修改这项设置，也不会改动此前已合并的任务。

状态变化会以系统操作写入时间线并列出相关 PR，订阅该任务的成员会收到通知。

## 多个工作区

同一个 GitHub App installation 可以连接到多个 Multica 工作区。GitHub 事件会分别进入每个工作区，再按照各自的任务前缀匹配。

例如一个 PR 同时引用 `MUL-1` 和 `ENG-2`，它可以在两个不同前缀的工作区中分别关联。工作区之间不会看到对方的任务。

如果同一个编号在多个已连接的工作区中都对应到任务（前缀相同时可能出现），Multica 不会在任何一个工作区自动关联，避免合并时完成无关的任务。请在正确的工作区手动关联。

## 断开连接

在 **设置 → 代码** 的 GitHub 一行，从 **⋯** 菜单选择 **断开**，只会移除当前 Multica 工作区与该 installation 的关系，不会替你从 GitHub 卸载 App。已有 PR 记录会保留，新的事件不再进入该工作区。

撤销 GitHub 侧的仓库授权，需到个人或组织的 GitHub App installations 页面卸载或调整仓库范围。卸载后，与该 installation 关联的所有 Multica 工作区都会停止接收事件。

## 自托管配置

Multica Cloud 无需执行本节。自托管需要先创建自己的 GitHub App。

<Steps>
<Step>

### 创建 GitHub App [#1-创建-github-app]

在 GitHub 的 **Developer settings → GitHub Apps** 中创建 App，并填写：

| 字段 | 值 |
|---|---|
| Homepage URL | Multica 前端地址，例如 `https://multica.example.com` |
| Callback URL | `https://<api-host>/api/github/user/callback`，成员连接 GitHub 账号时使用 |
| Expire user authorization tokens | 保持启用 |
| Request user authorization (OAuth) during installation | 保持关闭 |
| Setup URL | `https://<api-host>/api/github/setup`，并启用 **Redirect on update** |
| Webhook URL | `https://<api-host>/api/webhooks/github` |
| Webhook secret | 一段长期保存的随机字符串 |

Repository permissions：

| 权限 | 级别 |
|---|---|
| Metadata | Read-only |
| Contents | Read & write；用于合并 PR、更新 PR 分支和删除已合并的分支 |
| Pull requests | Read & write；用于合并、关闭、批准和请求评审 |
| Actions | Read & write；用于重跑失败的 check |
| Checks | Read-only；用于显示 CI 状态 |
| Commit statuses | Read-only；用于汇总 legacy status 形式的 CI |

订阅以下事件：

- **Pull request**；
- **Check suite**、**Check run** 和 **Status**，用于触发 CI 与可合并性刷新。

PR 快照只读取数据，通过 Pull requests、Checks 和 Commit statuses 的 API 获取。写权限只会在成员从 Multica 操作 PR 时，配合该成员自己的 GitHub 授权使用。

创建 App 后，在设置页的 **Client secrets → Generate a new client secret** 生成一个 client secret，并与上方显示的 **Client ID** 一起保存。

<Callout type="info">
**升级已有的 App**：补加写权限后，GitHub 会请各 installation 的所有者批准。所有者批准之前，该 installation 下仓库的 PR 操作会失败，并提示 App 缺少权限；CI 状态、可合并性和自动关联不受影响。
</Callout>

<Callout type="warning">
这里需要的是 **Webhook secret**，不是 OAuth Client secret。两边填写的 Webhook secret 不一致时，GitHub delivery 会返回 `401 invalid signature`。
</Callout>

</Step>
<Step>

### 配置环境变量 [#2-配置环境变量]

从 App 的公开地址取得 slug。例如 `https://github.com/apps/multica-acme` 的 slug 是 `multica-acme`。

```dotenv
GITHUB_APP_SLUG=multica-acme
GITHUB_WEBHOOK_SECRET=<创建 App 时填写的 webhook secret>
FRONTEND_ORIGIN=https://multica.example.com
```

`GITHUB_APP_SLUG` 和 `GITHUB_WEBHOOK_SECRET` 缺少任意一个时，连接按钮会被禁用，webhook 接口也会拒绝处理事件。

PR 卡片要显示 CI 状态与可合并性，还需要下面两个变量，Multica 用它们以 App 身份鉴权并拉取快照：

```dotenv
GITHUB_APP_ID=<GitHub App 的数字 ID>
GITHUB_APP_PRIVATE_KEY=<完整 PEM 私钥，保留 BEGIN/END 行和换行>
```

私钥在 GitHub App 的 **Private keys → Generate a private key** 中生成。不配置这两个变量时，PR 照常镜像，任务照常自动关联并在合并时改状态，只是 PR 卡片不显示 CI 或合并状态。

要让成员[在 Multica 中操作 PR](#在-multica-中操作-pr)，还需要配置下面三个变量，以及 API 的公网地址，让 GitHub 能跳转回上面的 Callback URL：

```dotenv
GITHUB_APP_CLIENT_ID=<App 的 Client ID>
GITHUB_APP_CLIENT_SECRET=<你生成的 client secret>
MULTICA_GITHUB_SECRET_KEY=<openssl rand -base64 32 的输出>
MULTICA_PUBLIC_URL=https://<api-host>
```

`MULTICA_GITHUB_SECRET_KEY` 用于加密成员保存的 GitHub 授权；更换它会断开所有成员的 GitHub 账号。三个变量缺少任意一个时，成员无法连接 GitHub 账号，其他功能照常工作。

</Step>
<Step>

### 更新数据库并连接 [#3-更新数据库并连接]

升级已有部署时，先执行常规数据库迁移：

```bash
make migrate-up
```

重启 API 服务，再到 **设置 → 代码** 完成连接。

</Step>
</Steps>

## 常见问题

- **连接按钮不可用**：检查 `GITHUB_APP_SLUG` 和 `GITHUB_WEBHOOK_SECRET` 是否已进入 API 进程。
- **Webhook 返回 401**：确认 GitHub App 与 API 使用同一个 Webhook secret，然后在 GitHub 的 **Recent Deliveries** 中重新投递。
- **PR 没有关联**：检查仓库是否在 App 授权范围内、自动关联是否开启、编号是否属于当前工作区，以及是否有人把它从任务上移除过。
- **正文写了编号但没关联**：改用 `Closes MUL-123`，或把编号放到分支名、PR 标题中，或者手动关联。
- **没有 CI 状态**：确认 `GITHUB_APP_ID` 和 `GITHUB_APP_PRIVATE_KEY` 已配置，App 具有上文列出的 Pull requests、Checks 与 Commit statuses 权限并订阅了对应事件。给已安装的 App 补加权限后，需要各 installation 的所有者在 GitHub 上批准才会生效。
- **PR 操作提示 App 缺少权限**：该 installation 还没有批准 App 的写权限。installation 的所有者需要在 GitHub 个人或组织的 **Settings → GitHub Apps** 中批准。
- **成员无法连接 GitHub 账号**：检查 `GITHUB_APP_CLIENT_ID`、`GITHUB_APP_CLIENT_SECRET` 和 `MULTICA_GITHUB_SECRET_KEY` 是否已进入 API 进程，以及 App 的 Callback URL 是否为 `https://<api-host>/api/github/user/callback`。
- **PR 合并后任务状态没变**：看任务 **Pull requests** 列表下方的说明，它会指出仍未合并或已关闭未合并的 PR，或者说明此任务合并后不改状态。没有这行说明，表示工作区设置为**不改变**，或者任务已经是目标状态。
