本地執行時由兩部分組成：Multica 守護程序，和它能呼叫的一款 AI 程式設計工具。只裝你準備用的那一款就行，不必全部安裝。

<Step>

## 在本機完成登入 [#2-在本機完成登入]

安裝後，先在終端裡單獨啟動一次工具，按它自己的流程登入或配置模型服務。工具在終端中完成不了請求，守護程序呼叫它也會失敗。

這些登入憑據由工具儲存在本機。Multica 不會接收 Claude、Codex、Cursor 或其他 CLI 的登入 token。

低於最低版本時，守護程序不會註冊對應執行時：

| 工具 | 最低版本 |
| --- | --- |
| Antigravity | 1.1.10 |
| Claude Code | 2.0.0 |
| Codex | 0.100.0 |
| Copilot | 1.0.0 |
| Grok | 0.2.89 |
| Qwen Code | 0.20.0 |
| MiniMax Code | 0.1.2 |
| Muse Code | 1.4.10 |
| OpenCode | 1.1.54 |
| Dim | 0.3.10 |
| Devin CLI | 3000.3.22 |
| ZeroClaw | 0.8.0 |
| ZCode | 0.16.0 |

以下工具除了登入，還要額外配置：

<Accordions type="multiple">
<Accordion title="CodeArts" id="codearts">

用 `codearts run --model provider/model "只回復 OK"` 驗證非互動模式，只驗證 TUI 不夠。當前 CodeArts CLI 可能允許自定義 provider 在 TUI 中工作，但 `run`、`models` 和 `serve` 仍要求配置 [`CODEARTS_CLI_AK` / `CODEARTS_CLI_SK`](https://support.huaweicloud.com/usermanual-cli/codeartsagent_cli_0026.html)。Multica 可以從 `~/.codeartsdoer/codearts_cli.json` 或 `.jsonc` 發現自定義模型，但每次執行都使用 `codearts run`，因此仍遵循該命令的授權要求。

</Accordion>
<Accordion title="DeepSeek Harness" id="deepseek-harness">

先安裝 Node.js 20+ 並執行 `npm install -g @deepseek-ai/dsh`，再為它安裝 Multica 執行時 profile。這個 bundle 實現了 Multica 驅動的 `--stdio` 協議，單獨的 `dsh` 因此無法直接使用。啟動守護程序前，設定 `DEEPSEEK_API_KEY`（或儲存在 dsh 自身的設定中）。

**安裝 profile。** 把 `MULTICA_DSH_PROFILE_BUNDLE` 設為要安裝的 bundle，守護程序會替你安裝；也可以自己執行 `dsh plugin --profile multica add <bundle>`。`<bundle>` 可以是 `dsh plugin` 接受的任意形式：npm 包名、目錄，或打包好的 tarball。Multica 自己的橋接實現在 [multica-ai/dsh-multica-runtime](https://github.com/multica-ai/dsh-multica-runtime)，目前還沒有釋出到公共 npm registry（[multica#6936](https://github.com/multica-ai/multica/issues/6936)）。現階段自託管團隊從該倉庫自行構建，把變數指向構建產物目錄；執行守護程序的機器和構建機器不是同一臺時，指向 `npm pack` 產出的 tarball。橋接釋出之後，直接填包名最省事。

**遷移現有 profile。** 先備份 profile，按橋接倉庫 README 構建與你的 DSH 版本相容的 bundle。手動安裝這個目錄或 tarball，再確認 `dsh.profile.bundles` 載入了 `@multica-ai/dsh-runtime`：有 `dsh-profile-multica` 時替換它；兩者都有時移除 `dsh-profile-multica`。只在依賴列表宣告包名不會載入執行時。`MULTICA_DSH_PROFILE_BUNDLE` 不會遷移現有橋接配置。完成後用 `dsh --profile multica --probe` 驗證。

<Callout type="warning">
優先使用你們自己釋出或構建的產物。這個值會在沒有二次確認的情況下裝進每一臺守護程序宿主的 DSH 家目錄，填一個未經審查的第三方包，就是做了一次供應鏈決策。
</Callout>

**DSH Desktop。** 裝的是 DeepSeek Harness Desktop 而不是 npm 包時，守護程序也會去找這個應用生成的 CLI shim，位置在它自己的使用者級資料目錄下：macOS 是 `~/Library/Application Support/DSH Desktop`，Windows 是 `%APPDATA%\DSH Desktop`。Windows 上這是漫遊應用資料目錄，不是安裝目錄：應用本身裝在 Program Files 或 `%LOCALAPPDATA%\Programs`，它驅動的 CLI 則和其他使用者級狀態放在一起。這些路徑裡的版本層是生成的 id，守護程序會逐個列舉，優先取最新的一份。PATH 上不需要別的東西，生成的 shim 會用絕對路徑呼叫應用自帶的執行時。DSH Desktop 裝在非預設位置時，用 `MULTICA_DSH_PATH` 指向那個 shim。

守護程序只有在 `dsh --profile multica --probe` 成功後才註冊 DeepSeek Harness；失敗時會在 `/health` 報告缺少 profile。

</Accordion>
<Accordion title="Devin CLI" id="devin-cli">

Devin 透過 `devin acp` 在本機執行，不是雲端的 Devin VM。先執行 `devin auth login`。Multica 檢查的是二進位檔的版本，不是 ACP 的 `agentInfo.version`（它可能是 `0.0.0-dev`）。

</Accordion>
<Accordion title="MiniMax Code" id="minimax-code">

安裝受支援的 Node.js 版本（`>=22.19 <23` 或 `>=24 <27`），並執行 `npm install --global @minimax-ai/code@latest`。全域性 npm 安裝會把 `mcode` 放進 npm 的全域性可執行目錄；`command -v mcode` 或 `Get-Command mcode` 找不到它時，把該目錄加入 `PATH`。然後執行 `mcode login`。模型由 MiniMax Code 管理，Multica 無法透過 ACP 覆蓋。

</Accordion>
<Accordion title="Muse Code" id="muse-code">

Muse Code 需要 1.4.10 或更高版本。按[官方安裝和登入指南](https://dev.meta.ai/docs/muse-code)操作，並確認 `muse` 已加入 `PATH`。Multica 透過 MSP 獲取模型列表，支援繼續已有會話。

</Accordion>
<Accordion title="QwenPaw" id="qwenpaw">

在 QwenPaw 自身的配置裡選擇模型服務和模型。Multica 無法在執行時覆蓋 QwenPaw 的模型。

</Accordion>
<Accordion title="Reasonix" id="reasonix">

先執行 `reasonix setup`，配置預設的模型服務和模型，再啟動守護程序。

</Accordion>
</Accordions>

</Step>

## 確認守護程序能夠找到命令 [#3-確認守護程序能夠找到命令]

把 `<command>` 換成表格中的命令，例如 `claude`、`codex` 或 `cursor-agent`。第一條命令返回可執行檔案路徑。

<Tabs groupId="os" persist items={["macOS / Linux", "Windows"]}>
<Tab value="macOS / Linux">

在 macOS、Linux 或 WSL 中執行：

```bash
command -v <command>
<command> --version
```

</Tab>
<Tab value="Windows">

在 Windows PowerShell 中執行：

```powershell
Get-Command <command>
<command> --version
```

</Tab>
</Tabs>

終端能找到工具，Desktop 或後臺守護程序卻找不到，通常是兩者用的 `PATH` 不同。可以重啟應用，或透過對應的 `MULTICA_<PROVIDER>_PATH` 環境變數指定絕對路徑；完整配置見[環境變數](/environment-variables#守護程序配置)。

</Step>
<Step>

## 重新檢測並確認上線 [#4-重新檢測並確認上線]

<Tabs items={["CLI", "Desktop"]}>
<Tab value="CLI">

啟動守護程序：

```bash
multica daemon start
```

守護程序已經在執行時，安裝新工具後重新啟動：

```bash
multica daemon restart
```

</Tab>
<Tab value="Desktop">

退出並重新開啟 Multica Desktop。

</Tab>
</Tabs>

然後開啟 Multica 的**執行時**頁面，目標電腦下面會出現對應工具，並顯示為線上。之後建立或編輯 AI 代理時，就可以選這條執行時。

<Callout type="warning">
守護程序啟動時必須先檢測到至少一款內建支援的 CLI。自定義執行時配置在守護程序啟動後才同步，所以在一臺空白機器上不能只靠它啟動。只有一個例外：守護程序剛開始自行安裝 DSH 執行時 profile（`MULTICA_DSH_PROFILE_BUNDLE`）時，會在沒有任何執行時的情況下啟動，安裝完成後再註冊 DeepSeek Harness。否則，一臺只裝了需要該 profile 的 DSH 的機器永遠裝不完：守護程序會在安裝結束前退出，把安裝程序一起帶走。
</Callout>

</Step>
</Steps>

## 未檢測到工具

依次檢查：

1. 在終端執行工具本身，確認安裝和登入都已完成。
2. 用 `command -v` 或 `Get-Command` 檢查實際命令名和路徑。
3. 執行 `multica daemon logs -f`，檢視版本、路徑或認證錯誤。
4. 重啟守護程序，讓它重新讀取當前環境。
5. 回到**執行時**頁面，確認電腦和工具都已上線。

工具顯示線上、執行卻仍然失敗時，開啟任務的執行記錄檢視 CLI 返回的具體錯誤，或繼續看[故障排查](/troubleshooting)。
