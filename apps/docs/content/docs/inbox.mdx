The inbox collects the work activity that concerns you and flags where something changed that needs your attention. It isn't a full activity log; the full story stays on the corresponding issue.

## What lands in the inbox

Common notifications include:

- an issue is assigned to you, or moved away from you;
- an issue you subscribe to gets a new comment, or its assignee, status, priority, or dates change;
- someone @-mentions you in an issue description or comment;
- an issue or comment you created gets a reaction;
- an agent run fails on an issue you subscribe to;
- [creating an issue through an agent](/issues#create-with-agent) completes or fails;
- an autopilot you subscribe to creates a new issue, or is paused after consecutive failures.

Your own actions don't notify you. Multiple notifications on the same issue merge into one entry; open it to see the issue's recent changes.

## Sources of automatic subscription

These participants subscribe to an issue automatically:

- the issue's creator;
- a new assignee;
- anyone who comments;
- anyone newly @-mentioned in the issue description;
- subscribers preconfigured in an autopilot.

Changing the assignee does not remove existing subscriptions. Subscribe or unsubscribe anytime on the issue page; after unsubscribing, ordinary updates stop reaching your inbox, while direct @-mentions still notify you individually.

<Callout type="info">
When a sub-issue's status changes, subscribers of the parent issue are notified as well. Sub-issue comments, priority, and date changes do not bubble up to the parent.
</Callout>

## Agents don't use the inbox

The inbox is only for workspace members. Even when an agent is the assignee or a subscriber, it never reads inbox notifications.

@-mentioning an agent in a comment, assigning an issue to it, or triggering an autopilot creates a run directly; no notification is left for the agent. `@all` notifies members only.

## Handle notifications

Selecting a notification marks it as read. Archive it when you're done; archiving doesn't modify or delete the corresponding issue.

<InboxDemo />

Once an issue reaches a status that hands it back to a person, its **Run failed** notifications archive automatically. Those statuses are `in_review`, custom statuses in the `started` category, and any status in the `done` or `closed` category. `blocked` is the exception: it hands the issue over too, but the work is still stuck, so the earlier failures are still worth reading.

Right-click a notification for **Mark as read** / **Mark as unread** and **Archive** (**Unarchive** in the Archived view). Mark as unread is the "I looked, but I'm not done with this" action: the notification goes back to unread and raises the unread count again, and it stays unread even while you keep it open; opening it again later marks it read as usual. Archived notifications keep their read state, so restoring one brings it back exactly as you left it.

From the inbox menu you can also:

- mark all as read;
- archive all, or archive all read;
- archive notifications for issues in `done` or `cancelled`;
- open Archived and restore a notification.

Open **Archived** at the bottom of the inbox to browse older notifications. More records load as you scroll. Filters apply to the entire archive, including records that have not loaded yet.

## Tune notification types

Open **Settings → Notifications** to toggle each group separately:

- assignments;
- status changes;
- comments;
- mentions;
- priority and dates;
- agent activity.

Turning a group off doesn't stop the changes from being recorded on the issue — it only stops the inbox notifications. A few types, such as reactions, quick-create results, and autopilot pauses, sit outside these six groups and are always delivered. System and browser notifications control desktop banners and don't change the inbox itself.

## WeCom group notifications (self-hosted)

To move one member's **task notifications** out of their WeCom DM,
set all three backend environment variables and restart the backend:

| Variable | Value |
|---|---|
| `MULTICA_WECOM_NOTIFICATION_WEBHOOK_URL` | The group's `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=…` URL; treat it as a secret |
| `MULTICA_WECOM_NOTIFICATION_WORKSPACE_ID` | The workspace UUID |
| `MULTICA_WECOM_NOTIFICATION_MEMBER_ID` | The member's user UUID (`recipient_id` in their inbox), not the workspace membership row ID |

Set `WECOM_APP_URL`, `MULTICA_APP_URL`, or `FRONTEND_ORIGIN` to the user-reachable
HTTP(S) web address for the card's task link. Localhost, loopback and unspecified
listen addresses are rejected. Both the visible "View task" entry and the card
itself open the same workspace-scoped issue URL. A complete, valid configuration
replaces private-bot delivery of task notifications, including status changes,
comments, assignments, unassignments, mentions, priority/date updates, reactions
and run failures. Conversations with the smart bot keep their existing route. The group webhook does not require `MULTICA_WECOM_SECRET_KEY`.
Cards separate the task title and paragraph-preserving excerpt from aligned priority, due date, actor and event/notification time fields. Missing due dates stay unavailable.
Assignment cards name the person involved; assignee changes show the previous and new person. Mentions identify the comment or issue description and show readable names instead of internal mention links.
Apply the same redirect configuration to every backend replica.
Empty configuration leaves delivery unchanged; partial or invalid configuration
logs an error and retains the original route. Remove all three variables and
restart to roll back.

The group receives only what this member's inbox would receive: subscriptions,
mute preferences, membership and exclusion of their own actions still apply.
This is not a broadcast of every workspace event. Check the group's audience
before redirecting personal inbox content to it.

Each event is one `text_notice` template card with task details, status before
and after (when provided), author and time, and a task link. Long comments are
summarized by truncation, not by a model; open the task for the full comment.
Group webhooks send complete notifications; smart-bot conversation streaming
continues independently.

Delivery is best-effort, using the existing in-process inbox event bus. A bounded
64-item queue and a single worker pace requests below 20/minute per process;
replayed inbox IDs are deduplicated in a bounded 2048-ID memory window. There is
no persistent outbox, restart replay, or cross-replica deduplication/rate limiter.
Only explicit rate-limit rejections get one retry; an uncertain network result
is not retried automatically. Queue overflow and failed or uncertain delivery
are logged with an inbox ID and outcome, without message content or webhook
credentials. Failures do not silently fall back to DM; the in-app inbox remains
available. Monitor these logs; use a single sender process if the group requires
the combined deployment to stay below the platform limit.
