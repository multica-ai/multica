任务身份令牌让智能体以**触发这次运行的人**的身份访问你的内部系统 —— ERP、后台、wiki —— 而不是走一个共享服务账号。

在认领任务时，服务端签发一枚短时效 JWT，其中写明这次运行的问责人；守护进程再把它注入智能体进程。智能体拿这枚令牌请求你的内部系统，系统看到的是这个人发来的请求，并套用它早已为这个人配好的权限。

未配置则不启用。未配置的部署行为与之前完全一致，**身份令牌**标签页也会隐藏。

<Callout type="info">
这是一个自托管特性。它签发的是一个属于**另一个信任域**的凭证 —— Multica 之外、自愿接受它的系统。智能体对 Multica 自身 API 的访问不受影响，仍然限定在拥有者权限内。
</Callout>

## 为什么服务账号不够用

把智能体接到内部系统，通常意味着给它发一个服务账号，而这会同时破坏两件事：

- **权限被压平成一个层级。** 每个人的智能体都用同一个固定身份 —— 一个初级工程师的智能体能够到服务账号能够到的一切。
- **审计变匿名。** 内部系统记下的是「机器人干的」。到底是谁发起的丢失了 —— 而这往往正是审计最需要的那一条。

任务身份令牌消掉了这个取舍。你的权限模型不变：系统照旧检查这是谁、套用他的权限、记下他的名字 —— 只是收到的是一个真实的人，而不是一个共享机器人。

## 工作原理

1. **一个人触发运行** —— 指派任务、评论、委派。
2. **服务端解析出问责人**（来自这次运行的归因），并为智能体启用的每个身份令牌签发一枚 JWT，把这个人写进 `sub`、把执行的智能体写进 `act_*` 声明。
3. **守护进程注入令牌** 到智能体进程环境里，变量名取自模板（如 `BOT_TOKEN_ERP`）。
4. **智能体请求你的系统**，把令牌作为 bearer 凭证带上。
5. **你的系统验证令牌**：用发布出来的公钥验签，把 `sub` 映射到自己的用户记录，再套用这个用户既有的权限与审计。

第 1–3 步在 Multica 内完成；第 4–5 步是[你要做的对接](#两条对接路径)。Multica 从不获得对你系统的任何权限 —— 它只是可验证地陈述：是谁在请求、由哪个智能体代为执行。

<Callout type="info">
准确地说，这是 [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693) 意义上的**委派式用户模拟**：`sub` 是委派方（人），`act_sub` / `act_name` 是代其执行的智能体。它**不是** GitHub Actions OIDC 那种工作负载证明，评审时应按委派应尽的信任义务来看待。
</Callout>

## 谁会获得身份

身份来自**授权**这次运行的人 —— 记在 `originator_user_id` 里，没有人出借权限时该列为 NULL。旁边那个审计标签几乎能为每次运行解析出一个人，自动驾驶触发的也不例外；那是标签而不是授权，也不是签发的依据。没有人授权的运行不会拿到令牌，运行照常进行，需要令牌的那一方看到的是普通的「未授权」，绝不会变成任务失败。

| 来源 | 是否签发 |
| --- | --- |
| `direct_human`、`delegation`、`comment_source` | 是 |
| `trigger_owner`、`rule_owner` —— 自动驾驶触发器自行触发 | 否 |
| `owner_fallback`、`backfill`、`unattributed` | 否 |

只有声明自己能注入令牌（`task-identity-tokens-v1`）的 daemon 才会拿到签发，所以启用该功能前先升级 daemon：给旧 daemon 签发，只会在审计里留下一条谁都没收到的签发记录。

每次成功签发都会往活动日志写一行 `agent_task_tokens_issued` —— 问责人、智能体、task，以及每枚令牌的 `jti` 和过期时间 —— 并且 fail-closed：这行写不进去，令牌就不发。

## 两条对接路径

这个特性面向两类不同的读者，各自在仓库里有对应的指南。

### 1. 启用它（运维方）

工作区拥有者或管理员分两步启用：

1. **配置服务端。** 设置 `MULTICA_TASK_TOKEN_PRIVATE_KEY`（PEM 签名私钥）和 `MULTICA_TASK_TOKEN_TEMPLATES`（一个 JSON 目录，定义能签什么、注入到哪个变量、带哪些声明）。见[环境变量](/environment-variables)。只设其中一个是启动错误；两个都不设则特性关闭。
2. **按智能体启用。** 打开 **设置 → 智能体 →** 选中智能体 **→ 身份令牌**，开启这个智能体需要的子集。目录只存在于服务端配置里，所以 UI 只能从运维方允许的范围里挑选，永远无法定义能签什么。

完整的运维指南 —— 目录格式、插值变量、`allowed_domains` 域名白名单、安全边界（影响面、服务端被攻破意味着什么、密钥轮换）与排障 —— 见仓库里的 [`TASK_IDENTITY_TOKENS.md`](https://github.com/multica-ai/multica/blob/main/TASK_IDENTITY_TOKENS.md)。

<Callout type="warn">
`sub` 默认用完整企业邮箱，并把「已验证的企业邮箱」作为前提 —— 整条信任链的根就是 Multica 存的这个地址。如果改用邮箱本地部分（@ 前面那段），务必配上模板的 `allowed_domains`，让只有你自己的域名能被签发。
</Callout>

### 2. 验证令牌（接收系统的开发者）

接收这些令牌的系统，凭 Multica 无鉴权发布的 JWK Set 来验签：

```
GET https://<你的-multica-host>/.well-known/jwks.json
```

任何主流 JWT 库都能直接消费它。如果你的内部系统在 API 网关后面（Kong、APISIX、nginx、云网关），验证往往零代码：把网关的 bearer-JWT 校验指向预期的 `iss` 和这个 URL 作为 `jwks_uri` 即可。

对接本身是一条安全边界 —— 固定算法白名单、把 `sub` 映射到本地用户而不自动建号、在审计里同时记下人和代其执行的智能体。分步指南、可运行的验签代码、以及那些真会咬人的坑，都在 [`TASK_IDENTITY_TOKENS_AI.md`](https://github.com/multica-ai/multica/blob/main/TASK_IDENTITY_TOKENS_AI.md) 里，这份文档就是写来交给一个在你老系统里干活的 AI 智能体的。

<Callout type="warn">
在验签方固定一个显式的算法白名单。信任令牌自报 `alg` 的验签方极易被伪造 —— `alg: none`，或用公钥当 HMAC 密钥的 `HS256`。公开的 JWKS 会让这两种攻击在允许对称算法时唾手可得。
</Callout>
