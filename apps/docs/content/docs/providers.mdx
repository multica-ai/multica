Multica does not replace the AI coding tool you use. A runtime invokes the tool already installed and signed in on the computer, then writes progress and results back to the issue.

If you already use one of these tools, you can usually keep it as-is. Four things to weigh when choosing:

- whether it is already installed on the computer;
- which models your account can use;
- whether Multica needs to configure MCP for it;
- which skills the team wants to reuse.

Install steps are in [Install AI coding tools](/install-agent-runtime).

## Model sources

When you create an agent, the model list comes from the corresponding runtime. Some tools expose a fixed set of model names; others return available models based on local configuration, the signed-in account, and subscription entitlements.

If you do not pick a model, Multica uses the tool's own default. If the list is empty, confirm the runtime is online and the tool is signed in, then refresh the model list.

QwenPaw and MiniMax Code are exceptions: they do not accept a model chosen from Multica, so the picker is inert and shows "Managed by runtime". Choose the model in the tool's own configuration instead. An empty model list is expected there and is not a sign that the runtime is offline.

DeepSeek Harness advertises its model catalog from the runtime itself (`dsh --profile multica --list-models`). Its model ids use the `provider/model` form (for example `deepseek-official/deepseek-chat`), so select the full id from the list.

<Callout type="info">
Different tools may use different model names. After switching AI coding tools, the previous model value is invalid in the new tool and needs to be selected again.
</Callout>

## Session resumption

All tools marked ✓ support continuing an existing session in a later run. The prerequisites are that the original session still exists and the run is executed by a runtime that can reach it. MiniMax Code 0.1.2 advertises no session-loading capability over ACP, so Multica starts a fresh MCode session for a later run.

Multica stores the session identifier the tool returns. The next time work continues on the same issue, the runtime tries to resume that session; when it cannot, it creates a new session and keeps going. Pi stores a local session file path, so it depends more on the original computer and file.

Retry and session-resumption rules are in [Runs](/tasks#manual-retry).

## MCP configuration

Antigravity, GitHub Copilot CLI, and DevEco Code do not read the MCP configuration on an agent yet, so the field is not shown when creating agents for them.

### Pi managed MCP

Pi supports Multica-managed MCP when the daemon detects an enabled, compatible `pi-mcp-adapter` installation. Supported adapter versions are **2.37.0** and **3.1.0**. Other versions are not assumed compatible. Install a supported version on the runtime computer, then restart the daemon to refresh detection:

```bash
pi install npm:pi-mcp-adapter@2.37.0
```

Local MCP discovery reports the same non-secret summary fields as other runtimes: name, transport, source, and enabled status. It reads shared user MCP files and the compatible adapter’s user configuration, honoring `PI_CODING_AGENT_DIR` and `PI_MCP_CONFIG_MODE=exclusive`. Project files, compatibility imports, and package-contributed servers are outside this user-level inventory. Displaying a local server does not add it to a managed run.

The MCP tab is available only for Pi runtimes that report this capability. An older daemon, a missing adapter, or an incompatible adapter leaves it unavailable; ordinary Pi runs without managed MCP still work. Multica does not install or enable the adapter automatically.

For a managed run, Multica supplies only the agent's resolved MCP configuration through the adapter's `createMcpAdapter({ config })` interface. It does not merge the computer's global or project MCP configuration. A private temporary directory holds the run's configuration and adapter state and is removed when the run ends, fails to start, or is cancelled. Global Pi settings and MCP files are not modified.

- An unset MCP configuration (`null`) preserves Pi's existing startup behavior.
- An explicit empty configuration (`{}` or `{"mcpServers": {}}`) starts an isolated managed run with no MCP servers.
- Managed runs disable automatic extension discovery and load only Multica's MCP bridge. Other extensions, including model providers supplied by extensions, are unavailable. Native and project skills, configured skill paths, and skills from installed npm or local packages are retained.

Pi packages must already be installed npm packages or absolute local package directories. Git and relative package sources fail managed-run preparation; Multica does not download packages to preserve their resources. Model configuration and authentication are copied per run, but refreshed credentials are not written back. If refresh tokens rotate, you may need to authenticate again. MCP authentication uses explicitly configured headers and environment variables; the adapter's global OAuth credentials are not imported.

#### Verify on a runtime computer

Use test MCP servers and a model account you are authorized to use; real runs can consume model credits.

1. Restart the daemon with a supported adapter enabled and confirm the Pi agent exposes the MCP tab. Repeat without a compatible adapter and confirm ordinary runs still work while the tab is unavailable.
2. Give two agents different test MCP servers, run them concurrently, and ask each to list its available MCP tools. Each must see only its own assigned server. Repeat with an explicit empty configuration and confirm no MCP tools appear.
3. Bind a skill, select an authenticated model, and complete a managed run. Continue the same issue to check session resumption; also test a cancelled run and an MCP startup failure.
4. Compare global Pi settings and MCP file checksums before and after. Check that each completed, failed, or cancelled run removes its temporary directory. Do not include credentials in logs or screenshots.

<Callout type="warning">
MCP server commands, arguments, and environment variables are saved server-side with the agent configuration. Do not write local credentials you have no need to share into the configuration.
</Callout>

## Skill injection

Before a run starts, Multica writes the skills bound to the agent into the paths in the table above, so each tool discovers them through its own native mechanism.

Skills that already exist in the repository are never overwritten. On a name collision, Multica uses a different directory name for the injected copy; after the run, it cleans up only the files it created.

Codex, Hermes, and OpenClaw are handled slightly differently:

- Codex uses a per-run `CODEX_HOME`, so skills are never written into the system-level Codex directory.
- Hermes uses a per-run `HERMES_HOME`. Existing local configuration is still readable, but bound skills and session data are isolated per run. This isolation kicks in only when the agent has skills bound; runs without bound skills use the machine's original Hermes home.
- OpenClaw uses `skills/` under the current run's working directory, and the per-run configuration sets that directory as the workspace.

For creating and binding skills, see [Skills](/skills).
