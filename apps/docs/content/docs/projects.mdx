Projects organize work that takes multiple [issues](/issues) to finish — a product launch, a migration, or a feature delivered in stages.

Work that a single issue can describe does not need a project. Projects fit a group of work that shares a goal, needs its progress tracked together, or needs shared repositories and working directories.

## Parts of a project

| Part | Purpose |
|---|---|
| **Name, icon, and description** | Goal, scope, and long-lived requirements; the description enters the execution context of agents working inside the project. |
| **Status** | `planned`, `in_progress`, `paused`, `completed`, or `cancelled`. |
| **Priority** | `urgent`, `high`, `medium`, `low`, or `none`. |
| **Lead** | A member or an agent — who coordinates the project. |
| **Start and target dates** | The project's planned time range. |
| **Issues and progress** | The work in the project and how much of it is finished. |
| **Resources** | Linked GitHub repositories or local directories on specific computers. |
| **Workflow** | The steps its issues follow and who takes over at each step. |

## Projects and issues

A project can contain any number of issues; an issue belongs to at most one project. Create issues directly inside the project, or pick or change the project from the issue's properties.

Project progress is computed automatically from linked issues:

```text
progress = issues whose status is in the done or closed category ÷ all issues in the project
```

Among the built-in statuses that means `done` and `cancelled`; custom statuses in those two categories count as well. `cancelled` means that work has been closed out of the project's scope, so it counts toward progress.

Project status and issue status are independent: finishing every issue does not set the project to `completed`, and changing the project's status does not bulk-change its issues.

## Project description and execution context

When an agent runs an issue inside a project, the project's name and description are added to that run's context. Put what every related run needs to know in the description — the goal, technical boundaries, delivery conventions — and keep requirements for a single issue in that issue.

## Add resources

Project resources tell agents which code and working directories to use:

- **GitHub repositories**: provide a repo the runtime can check out, with an optional ref.
- **Local directories**: let the runtime on a specific computer work in an existing directory, whose contents the agent modifies directly.

See [Project resources](/project-resources) for how to choose and for the safety boundaries.

## Choose a workflow

Choose the project’s **Workflow** to set its board columns and who takes over at each step. For example, development can go to one agent, review to another, and acceptance to a team member. Projects without another choice use **Default**: every status is available and nothing is handed off automatically. See [Workflows](/workflows) for setup and switching an existing project.

## Project lead

The lead can be a member or an agent; a member who is the lead can also switch the project’s workflow. Making someone the lead does not assign issues to them or start any work. To hand a step to the lead, set that step's handler to **Project lead** in the workflow.

## Pin to the sidebar

A pinned project appears in your sidebar. Pinning is a personal preference and does not affect other members.

## Create, edit, and delete

Any workspace member can create and edit projects. Members can delete projects they created or that an agent they currently own created; agents can delete only their own projects. Human `owner` and `admin` members can delete any project, including older projects with an unknown creator.

<Callout type="warning">
Deleting a project does not delete its issues: they detach and stay in the workspace. The project's description, status, and resources are permanently deleted.
</Callout>

## Move to another workspace

Use the [CLI](/cli#move-a-project) to move one project. This is a Draft feature: ordinary writes are not fenced during a move. Do not use it with concurrent writers until the concurrency design is agreed. You must be the source workspace `owner` and an `owner` or `admin` in the target; agents cannot move projects.

The preview lists blockers, member access changes, catalog mappings, and source cleanup. Active runs, enabled wakeups, project automations, open linked PRs, cross-project issue links, and local-directory resources block a move. Resolve them before confirming.

Issues, comments, attachments, and authorship move together. Labels match by name; statuses fall back to their lifecycle category; unmatched custom properties/options and assignees, leads, or subscribers outside target membership are cleared. Source pins, views, inbox items, unread marks, disabled wakeups, closed PR links, and chat project context are removed. The project switches to the target workspace's default workflow.

Issues receive target numbers in their original order. Old keys resolve through `GET /api/moves/resolve?issue=OLD-7` with the source workspace header. Source-only members see only that the issue moved; target members also receive its current location. Returning to a previous workspace restores its original numbers when available. Old project references use `?project=<uuid>`.

Run history retains the original agents. Target members can read issue runs and their messages; deleting the source workspace still deletes its agents' run history and incurred usage. Attachment object keys remain unchanged. Authenticated downloads follow the attachment's current workspace; local `/uploads/*` remains public by design. Move audit and key-alias history are retained after ordinary deletion; the resolver only returns locations of live objects.
