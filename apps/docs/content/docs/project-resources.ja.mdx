[プロジェクト](/projects)のリソースは、この一連の作業がどのコードを使い、どこで実行するかをエージェントに伝えます。リソースはプロジェクトに紐づいたまま保たれるため、リポジトリの URL やローカルパスをタスクごとに貼り直す必要はありません。

現在サポートされているリソースは 2 種類です。

| リソース | 適した場面 | 実行場所 |
|---|---|---|
| **GitHub リポジトリ** | チームで共有するコードベースで、checkout をランタイムに管理させたい場合 | ランタイムが管理する作業ディレクトリ |
| **ローカルディレクトリ** | 既存の checkout、非常に大きなリポジトリ、またはローカルの変更を直接確認したい場合 | 特定のコンピュータ上の元のディレクトリ |

## リソースが実行に入る仕組み

エージェントがプロジェクト内のタスクを処理するとき、Multica はプロジェクト名、プロジェクトの説明、リソース一覧を実行コンテキストに追加し、作業ディレクトリに `.multica/project/resources.json` を書き込みます。

ワークスペースに紐づくリポジトリ一覧は、常に実行コンテキストに含まれます。プロジェクトに紐づくリポジトリは、それに加えて、この一連の作業で使うコードとデフォルトの ref を指定します。

ローカルディレクトリは、それを紐づけたデーモンに対してのみ有効です。実行を担当するデーモンに一致するローカルディレクトリがある場合、エージェントはそのディレクトリに直接入って作業します。ほかのコンピュータは引き続き、プロジェクトの GitHub リポジトリまたはワークスペースのリポジトリを使います。

## GitHub リポジトリの追加

プロジェクトを開き、**リソース** で「リソースを追加」を選択します。ワークスペースに紐づけ済みのリポジトリを選ぶことも、Git URL を貼り付けることもできます。ワークスペースのリポジトリは **設定 → コード** で管理します。GitHub を接続すると、同じページの **GitHub から選択** で、App が認可済みのリポジトリをインポートできます。

リポジトリは GitHub に限定されません。ランタイムがアクセスできる Git URL であれば、どれでもリポジトリリソースとして使えます。セルフホストの Multica では、**設定 → コード** でセルフホストの Forgejo、Gitea、GitLab も接続できます。詳細は[セルフホスト Git ホスティング](/vcs-integration)を参照してください。

プロジェクトの作成時に、**リポジトリ** で直接リポジトリを選ぶこともできます。1 つのプロジェクトには複数の GitHub リポジトリを紐づけられます。

リソースの `ref` には、以後の checkout がデフォルトで使うブランチ、タグ、またはコミットを指定できます。`default_branch_hint` はエージェントにデフォルトブランチのヒントを与えるだけで、ブランチの切り替えを強制しません。

## ローカルディレクトリの追加

ローカルディレクトリを追加する UI は Desktop でのみ提供されます。ブラウザからはコンピュータ上のフォルダを選択できないためです。

<Callout type="warning">
**特別な事情があるときの選択肢です。便利そうだからという理由で選ばないでください。** `local_directory` はほかに選択肢がない人のためのものです。典型例は、チェックアウトが数十ギガバイトになるゲームプロジェクトで、実行のたびにクローンし直すのは現実的ではありません。

対象のディレクトリが普通にクローンできる通常の git リポジトリなら、`github_repo` を使ってください。既定でワークツリーモードで動作するため、同じリポジトリに対する実行を数の制限なく同時に進められます。`local_directory` は既定では一度に 1 つの実行だけを処理します。ディレクトリ自体が git リポジトリであれば、ワークツリーモードを有効にして並行処理を取り戻せます（[実行がディレクトリを共有する方法](#実行がディレクトリを共有する方法)を参照）。迷ったら、ページ冒頭の 2 種類のリソースの比較を見てください。
</Callout>

初期選択は、いま紐づけようとしているディレクトリにだけ適用されます。以前に紐づけたディレクトリは保存時のモードのままで、既存の設定が知らないうちに切り替わることはありません。

ディレクトリは絶対パスで、すでに存在し、現在のデーモンが読み書きできる必要があります。次のパスは拒否されます: システムのルートとドライブのルート（`/`、`C:\`）、ホームディレクトリ自体と各ホームディレクトリの親（`/Users`、`/home`、`/root` など）、および `/etc`、`/var`、`/tmp`、`/usr`、`/opt` などのシステムディレクトリ。選択したパスがシンボリックリンクの場合は、まず実体のパスに解決してから同じルールでもう一度検証されます。直列ロックも実体のパスに対して働きます。

同じデーモンに紐づけられるローカルディレクトリは、プロジェクトごとに最大 1 つです。チーム内の別々のコンピュータは、同じプロジェクトにそれぞれ自分のディレクトリを紐づけられます。

<Callout type="warning">
既定の `in_place` モードでは、ローカルディレクトリは隔離された環境ではありません。エージェントは現在のブランチと未コミットのファイルをそのまま参照・変更し、Multica がブランチの切り替え、stash、commit、push、PR の作成を自動で行うこともありません。ワークツリーモードでは事情が異なります。下の[実行がディレクトリを共有する方法](#実行がディレクトリを共有する方法)を参照してください。
</Callout>

## 実行がディレクトリを共有する方法

ローカルディレクトリには 2 つの実行モードがあり、リソースごとに設定します。リソースパネルから切り替えられるほか、CLI では `--execution-mode` を使います。Desktop での表示は **直接** と **並行** で、API・CLI とこのページの以降では識別子を使います。

<LocalDirModeDemo />

<Tabs items={["in_place（直接、既定）", "worktree（並行）"]}>
<Tab value="in_place（直接、既定）" id="in-place">

エージェントはあなたのディレクトリで直接作業し、実行は一度に 1 つずつ進みます。2 つの実行が同じ実体のディレクトリを使う場合、後から来た実行は `waiting_local_directory` に入り、先の実行がディレクトリを解放してから続行します。異なるシンボリックリンク経由で同じディレクトリに到達する 2 つのパスも、同じように直列化されます。

待機中にディレクトリが変更されることはありません。待機中の実行はキャンセルできます。キャンセルしなければ、ディレクトリが使えるようになるまで待ち続けます。

git 管理外の通常のディレクトリはこのモードしか使えません。ワークツリーモードは git リポジトリ専用です。

</Tab>
<Tab value="worktree（並行）" id="worktree">

各実行が、あなたのリポジトリの独立した [git ワークツリー](https://git-scm.com/docs/git-worktree) を受け取ります。ワークツリーはランタイム自身のワークスペースディレクトリ内に作成されます。同じディレクトリに対する実行は並行して進み、待機は発生しません。どの実行もあなたの作業コピーには書き込みません。

このモードには、コミットが 1 つ以上ある git リポジトリであることが必要です。そうでない場合、実行は黙って直列実行に戻らず、明示的なエラーで失敗します。

そのマシンのランタイムも、このモードを実装している必要があります。ランタイムは接続時にその能力を宣言し、Multica はバージョン番号ではなくこの宣言だけで判定します。開発ビルドは、実装がないまま十分に新しく見えるバージョン文字列を持ちうるからです。この宣言は 2 回検証されます。リソースの保存時、そのマシンのランタイムが能力を宣言していなければ保存は拒否され、そのマシンのアプリを更新するよう促されます。さらに各実行が実際に受け取られるとき、受け取ったランタイムに対して再度検証されます。そのため、リソース保存後にダウングレードされたマシンでは、実行が元のディレクトリで黙って処理されることはなく、理由付きでキャンセルされます。`worktree` を選ぶことは隔離を求めることであり、Multica が「作業コピーを直接書き換える」ことで代用することはありません。

エージェントが見るもの、あなたが受け取るもの:

<Accordions type="multiple">
<Accordion title="エージェントは HEAD ではなく、あなたが今見ている状態から始める" id="starts-from-your-working-state">

未コミットの変更と未追跡ファイルがワークツリーに再現されるため、すでに手元にないコードをレビューすることはありません。あなた自身の作業コピー、インデックス、stash リストが変更されることはありません。

その状態を忠実に再現できない場合（再現の上限である 2000 ファイル / 200 MiB を超える未追跡コンテンツがある場合を含む）、実行は見覚えのないツリーから始めずに失敗します。通常の対処法は、まだ無視されていないビルド成果物を gitignore に加えるか削除することです。

</Accordion>
<Accordion title="成果物はあなたのリポジトリ内のブランチ" id="result-is-a-branch">

ブランチは実行ごとではなくタスクごとに 1 本で、`agent/<agent>/<issue>`（チャットなら `agent/<agent>/chat-<session>`）という名前が付きます。実行の「実行詳細」パネルにブランチ名が表示され（コピーも可能）、`git branch` でも見つけられます。`git log` / `git diff` でレビューし、マージするか cherry-pick するかは自分で決めます。Multica が代わりにマージすることはありません。

`<agent>` はエージェント名から作られます。小文字にしたうえで英字と数字だけを残し、それ以外の文字は `-` に置き換え、最大 30 文字です。英字も数字も含まない名前は `agent` になります。そのため「運用アシスタント」が OPS-21 を処理すると、ブランチは `agent/agent/ops-21` です。`<issue>` は小文字にしたタスク番号です。

途中で失敗した実行もブランチを報告します。エージェントが作った分はすでにコミットされているからです。

</Accordion>
<Accordion title="続きのコメントは前回の続きから始まる" id="follow-ups-continue-the-branch">

同じタスクへの次のコメントはそのブランチを再びチェックアウトするので、エージェントは直前に納品した成果の上で作業します。`HEAD` からやり直して前回の変更が別ブランチに取り残されることはありません。再適用されるのは前回以降にあなたが自分のディレクトリで変えた分だけで、それ以外はブランチがすでに持っています。ブランチをマージすれば、次の実行はまたあなたの `HEAD` から始まります。

同じタスクで 2 つの実行が重なった場合、あとの実行は前の実行の成果から `agent/<agent>/<issue>-<task>` に分岐します。git では 1 つのブランチに 1 つの worktree しか持てないためです。

</Accordion>
<Accordion title="ローカル HEAD へのコミットは、未コミットの変更とは分けて扱う" id="committed-head-changes-stay-separate">

ターンの合間に行った pull やローカルコミットは、タスクのブランチには再適用されません。必要なら、それらのコミットを明示的にブランチへマージしてください。前回の実行が未コミットの作業を取り込んでいた場合、それを新しい `HEAD` 上で比較するには Git 2.40 以降が必要です。

その古い変更が新しくコミットされたベースラインと衝突した場合、ランタイムは警告をログに残し、影響を受けるパスだけ現在の `HEAD` を使います。ほかの下書きは差分での比較を続けます。そのため、下書きの 1 つを仕上げてコミットしても、以降の実行が止まったり、変えていない下書きがエージェントの成果に対してもう一度持ち込まれたりはしません。今の変更とエージェントの成果の衝突は、これまでどおりエージェントに解決を任せます。

</Accordion>
<Accordion title="あなたの変更がエージェントの成果と衝突したら、エージェントが解決する" id="conflicts-are-resolved-by-the-agent">

エージェントが書き換えたのと同じ行をあなたが書き換えた場合、git はどちらが正しいか決められません。その実行は衝突したままのワークツリーで始まり、何より先にマージを終わらせるよう指示されます（そのワークツリーで `git status` を実行すると未マージのファイルが並びます）。

未マージのファイルが残ったままの実行は何も納品しません。実行は失敗し、ワークツリーは保持され、次の実行が同じ変更をもう一度提示するので、あなたの変更が黙って消えることはありません。

</Accordion>
<Accordion title="引き継ぐのは Multica 自身のブランチだけ" id="only-multica-branches-resume">

引き継ぐかどうかは名前ではなく所有記録で決まります。記録にはどの対話のものかに加えて、そのブランチが最後に置かれたコミットも書かれています。あなたが自分で作った、たまたま `agent/<agent>/<issue>` という名前のブランチが、チェックアウトされることも、追記されることも、前回の成果として読まれることもありません。記録されたコミットをもう含まないブランチも同様です。そのため、Multica のブランチを削除して同名のものを作り直したり、別の履歴へ force-move したりしても安全で、その場合の実行は `agent/<agent>/<issue>-<id>` を使います。納品済みブランチの上にコミットするのは通常の使い方で、引き継ぎはそのまま続き、あなたのコミットは次の実行にそのまま含まれます。

各ブランチはそれ自身のベースラインコミットから始まります。最初の実行が開始した時点のツリーを示すもので、あとでブランチを識別するのはこのコミットです。`git diff <baseline>..<branch>` はちょうどエージェントの変更になります。

ブランチを記録できなかった実行（途中で失敗した、記録の書き込みに失敗した、あるいはあなたの変更をブランチに取り込んだコミットより前にワークツリーをリセットした場合）は、失敗として報告されワークツリーを残します。以降の実行は、自分のものだと証明できないブランチを引き継がず、新しいブランチから始めます。

</Accordion>
<Accordion title="黙って失われるものはない" id="nothing-is-silently-lost">

エージェントが未コミットのまま残した変更は、ワークツリーが削除される前にそのブランチへコミットされます。実行が途中で失敗した場合も同様です。

ごくまれに、そのコミット自体ができないことがあります。たとえば `commit.gpgSign` が有効で、ランタイムが署名鍵を利用できないリポジトリです。その場合ワークツリーは削除されずに意図的に保持され、実行は失敗として報告されます。あなたのリポジトリで `git worktree list` を実行すると、その変更を保持しているディレクトリが表示されます。

</Accordion>
<Accordion title="何も変更しなかった実行は、何も残さない" id="no-changes-leave-nothing">

そのブランチは `git branch` に空の項目として残らず、削除されます。ただし、それまでの実行の成果を持つタスクのブランチは常に残ります。

</Accordion>
<Accordion title="リポジトリに残るブランチと隠し ref" id="what-stays-in-your-repo">

ワークツリーはランタイムのワークスペースディレクトリ内にあるため、[通常のクリーンアップ周期](/daemon-runtimes#cleanup)で回収されます。あなたのリポジトリに残るのは 2 つ、ブランチと、ブランチごとの隠し ref（`refs/multica/local-state/` 配下）です。後者はそのブランチの所有者と、最後に引き継いだ時点のあなたのディレクトリの内容を記録します。

隠し ref は `git branch` には現れず、`git for-each-ref refs/multica` で一覧できます。Multica はブランチと一緒に削除し、あなたが自分で消したブランチの ref は、そのリポジトリで次の実行が始まるときに片付けます。`git for-each-ref --format='%(refname)' refs/multica | xargs -n1 git update-ref -d` で一括削除もできます。

</Accordion>
</Accordions>

<Callout type="warn">
**セルフホスト運用者向け:** このモードの分離はサーバー側で強制されます（リソース保存時と、ランタイムが各実行を取得する時点の二重チェック）。そのため、ランタイムをいつダウングレードしても検出されます。検出できない唯一の組み合わせは、このモードを実装していないランタイムが接続されたまま、サーバーをこの機能より前のビルドへロールバックすることです。古いサーバーにはこのゲートがなく、そうしたランタイムは `execution_mode` を無視して実行を元のディレクトリで直接処理してしまいます。`worktree` リソースが存在する間は、対象マシンのランタイムがすべて最新でない限り、サーバーをこのリリースより前へロールバックしないでください。
</Callout>

</Tab>

## 実行中に書き込まれるもの

エージェントによるコードの変更のほかに、ランタイムは、現在の AI コーディングツールが必要とする指示ファイルと `.multica/project/resources.json` をディレクトリに書き込むことがあります。バージョン管理に含めたくない場合は `.gitignore` に追加してください。

Multica が実行環境をクリーンアップするとき、紐づけたローカルディレクトリを削除することはありません。エージェントによるこのディレクトリへの変更は、あなたがターミナルで AI コーディングツールを直接実行したときの変更と同じ性質のものであり、同じようにレビューが必要です。

## CLI でリソースを管理する

```bash
# プロジェクト作成時にリポジトリを紐づける
multica project create \
  --title "Agent UX" \
  --repo https://github.com/multica-ai/multica

# リソースの一覧表示と追加
multica project resource list <project-id>
multica project resource add <project-id> \
  --type github_repo \
  --url https://github.com/multica-ai/multica \
  --ref main

# 特定のデーモン上のローカルディレクトリを紐づける
multica project resource add <project-id> \
  --type local_directory \
  --local-path /absolute/path/to/repo \
  --daemon-id <daemon-id>

# ローカル git リポジトリを紐づけ、実行を各自のワークツリーで並行処理する
multica project resource add <project-id> \
  --type local_directory \
  --local-path /absolute/path/to/repo \
  --daemon-id <daemon-id> \
  --execution-mode worktree

# 既存のローカルディレクトリのモードを切り替える
multica project resource update <project-id> <resource-id> --execution-mode worktree
multica project resource update <project-id> <resource-id> --execution-mode in_place


# リソースを削除する
multica project resource remove <project-id> <resource-id>
```

リソースの変更は、その後に作成される実行に反映されます。すでに終了した実行の記録が書き換えられることはありません。
