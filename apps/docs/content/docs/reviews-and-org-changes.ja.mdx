レビューと組織変更は、ループを閉じる仕組みです。**スコアカード** は、エージェントまたはスクワッドのパフォーマンスを測定します。**レビュー** はスコアカードを読み、変更を推奨します。**組織変更** は、あなたが承認した推奨を適用します。その変更は **試用期間** に入り、プラットフォームは変更が役立ったかどうかを記録します。

## スコアカード

夜間ジョブが、各エージェント、各スクワッド、会社全体についてスコアカードを計算します。対象は直近の完了した週または月です。その期間の実行数が少なすぎるスコアカードは `insufficient`（不足）とマークされ、レビューされることはありません。

指標は次のとおりです。

- 実行数と成功率。失敗は原因別に分けられます。ランタイムがオフラインだった失敗はエージェントの減点になりません。
- 完了した Issue 数、初回成功率（差し戻されずに完了したもの）、サイクルタイム、完了 Issue あたりのコスト。
- 人の介入率。エージェントが完了とマークした後の、人によるコメントや編集。
- プロポーザルの採択率、ルーティンの遵守率、ナレッジへの貢献。
- 秘書については、ブリーフの有用性。

一部の数値は代理指標です。完了時刻は、Issue が最後に完了ステータスに入った時刻です。初回成功率と介入率は、完了した実行の件数とメンバーのコメントを使います。コストはプロバイダーが報告した分だけです。再オープンの回数は、この版から記録される Issue の完了履歴に基づいて数えます。それ以前の再オープンは分かりません。

オーナー、管理者、対象のリーダーはスコアカードを閲覧できます。

```bash
multica review scorecards --subject-type squad --subject-id <squad-id> --period month
```

## レビュー

フロア Governance にある **People & Performance** スクワッドは、レビュアーのエージェントを持ちます。毎月、十分なデータがあるすべてのスクワッドと、スコアカードまたはサンプリングで `below`（基準未満）とされたすべてのエージェントをレビューします。各レビューには、評価（`exceeds`（期待を上回る）、`meets`（期待どおり）、`below`（基準未満）、`at_risk`（リスクあり））、説明文、推奨が含まれます。レビューは、拠り所とするスコアカードの数値と、その根拠（Issue、実行、ドキュメント）を引用しなければなりません。

レビューは仕組みを働かせるための道具であり、順位付けではありません。オーナー、管理者、対象スクワッドのリーダーが閲覧できます。各指標は、何を測っているのかを示しています。

レビュアーは JSON ファイルで公開します。

```bash
multica review publish --file review.json
multica review list
```

レビューを公開すると、推奨された変更はそれぞれ `org_change` プロポーザルとして提出されます。あなたは根拠を横に見ながら判断できます。**Governance** の Reviews タブにはレビューが一覧され、リンクではなくプロポーザル ID が表示されます。ブリーフの **People** セクションには、新しいレビューとその推奨が一覧されます。

## 組織変更

`org_change` プロポーザルには、次の八つの種類があります。

| 種類 | 変更対象 | 適用方法 |
| --- | --- | --- |
| `instruction_change` | エージェントの指示 | 旧テキストのリビジョンを先に書き込み、その後エージェントを更新 |
| `skill_change` | エージェントのスキル | スキルを追加・削除 |
| `charter_change` | スクワッドの憲章 | 憲章を更新し、リビジョンを作成 |
| `autonomy_change` | スクワッドの自律性レベル | レベルを設定 |
| `hire` | スクワッドにエージェントを追加 | テンプレートからエージェントを作成し、そのスクワッドを所属スクワッドにする |
| `retire` | エージェントまたはスクワッドを削除 | アーカイブします。キュー中のタスクはキャンセルされ、実行中のタスクは完了し、ナレッジは残ります。 |
| `move` | エージェントのスクワッド | 所属と所属スクワッドを変更 |
| `merge_squads` | 二つのスクワッド | メンバーとルーティンを移動し、元のスクワッドをアーカイブします。憲章の文面はダイアログであなたが統合します。 |

組織変更は、レビュアー、秘書、変更の対象スクワッドのリーダー、または人が提出します。自動承認されることはなく、常時承認の対象にもなりません。決定ダイアログでは、指示や憲章の変更は差分として表示されます。

## 指示のリビジョンと巻き戻し

エージェントの指示を更新するたびに、経路にかかわらずリビジョンが書き込まれます。経路とは、アプリ、CLI、テンプレート、インポート、適用された組織変更のいずれかです。リビジョンには、テキスト、ソース（`human`、`proposal`、`rollback`）、関連するプロポーザル（あれば）が記録されます。

エージェントのページで、履歴にリビジョンが並びます。あるリビジョンを復元すると、古いテキストを持つ新しいリビジョンが書き込まれるので、何も失われません。

```bash
curl -H "Authorization: Bearer $MULTICA_TOKEN" -H "X-Workspace-ID: $WORKSPACE_ID" \
  "$MULTICA_API/api/agents/<agent-id>/instruction-revisions"
curl -X POST -H "Authorization: Bearer $MULTICA_TOKEN" -H "X-Workspace-ID: $WORKSPACE_ID" \
  "$MULTICA_API/api/agents/<agent-id>/instruction-revisions/<revision>/restore"
```

リビジョンの履歴は、最初に記録された変更から始まります。それより前の変更は含まれません。ビルダーのキャリアエージェントは追跡されません。

## 試用期間

適用された変更は、**14日間の試用期間** に入ります。期間の終わりに、レビュアーが変更前と変更後のスコアカードを比較し、次のいずれかの結果を記録します。

| 結果 | 意味 |
| --- | --- |
| `improved`（改善） | 指標が望ましい方向に動いた |
| `neutral`（変化なし） | はっきりした変化はない |
| `worse`（悪化） | 指標が望ましくない方向に動いた。巻き戻しのプロポーザルが提出される。 |
| `insufficient`（不足） | データが少なすぎる。結果は保留される。 |

試用期間は八つの種類すべてに適用されます。巻き戻しができるのは、取り消し可能な変更だけです。`hire`、`retire`、`merge_squads` は取り消せないため、これらについて「悪化」と判定されても巻き戻しのプロポーザルは提出されません。スクワッドの最初の憲章を作る憲章変更も取り消せません。承認する前にこれらの制約を考慮してください。

<Callout type="info">
組織変更のプロポーザルは、注意の上限にカウントされます。適用された各変更と各結果は、[ガバナンスログ](/controls-and-log)に記録されます。
</Callout>
