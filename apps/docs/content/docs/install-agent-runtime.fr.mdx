Un runtime local comporte deux éléments : le daemon Multica et un outil de codage IA qu'il peut invoquer. N'installez que l'outil que vous comptez utiliser — inutile de tous les installer.

<Steps>
<Step>

## Choisir un outil [#1-choisir-un-outil]

Un outil déjà installé et connecté ne nécessite aucune configuration supplémentaire. Les outils diffèrent par leurs modèles, MCP, la reprise de session et la prise en charge des skills ; les détails figurent dans [Comparatif des outils de codage IA](/providers).

## Se connecter sur votre machine [#2-se-connecter-sur-votre-machine]

Après l'installation, lancez une première fois l'outil seul dans un terminal et terminez sa connexion ou la configuration de son fournisseur de modèles. Si l'outil ne parvient pas à traiter des requêtes dans le terminal, les invocations du daemon échoueront de la même manière.

Ces identifiants de connexion sont stockés localement par l'outil lui-même. Multica ne reçoit jamais les jetons de connexion de Claude, Codex, Cursor ni d'aucun autre CLI.

En dessous de la version minimale, le daemon n'enregistre pas le runtime correspondant :

| Outil | Version minimale |
| --- | --- |
| Antigravity | 1.1.10 |
| Claude Code | 2.0.0 |
| Codex | 0.100.0 |
| Copilot | 1.0.0 |
| Grok | 0.2.89 |
| Qwen Code | 0.20.0 |
| MiniMax Code | 0.1.2 |
| OpenCode | 1.1.54 |
| Dim | 0.3.10 |
| ZeroClaw | 0.8.0 |

Quelques outils demandent une configuration en plus de la connexion :

<Accordions type="multiple">
<Accordion title="CodeArts" id="codearts">

Vérifiez le chemin non interactif avec `codearts run --model provider/model "Reply OK"`, et pas seulement la TUI. Le CLI CodeArts actuel peut laisser un fournisseur personnalisé fonctionner dans la TUI alors que `run`, `models` et `serve` exigent toujours [`CODEARTS_CLI_AK` / `CODEARTS_CLI_SK`](https://support.huaweicloud.com/usermanual-cli/codeartsagent_cli_0026.html). Multica peut découvrir des modèles personnalisés depuis `~/.codeartsdoer/codearts_cli.json` ou `.jsonc`, mais les exécutions d'agent utilisent `codearts run` et suivent donc ses exigences d'autorisation.

</Accordion>
<Accordion title="DeepSeek Harness" id="deepseek-harness">

Installez Node.js 20+ et exécutez `npm install -g @deepseek-ai/dsh`, puis fournissez-lui le profil de runtime Multica : le bundle qui implémente le protocole `--stdio` piloté par Multica, et la raison pour laquelle un `dsh` nu n'est pas utilisable seul. Définissez `DEEPSEEK_API_KEY` (ou enregistrez-la dans les paramètres propres de dsh) avant de démarrer le daemon.

**Installer le profil.** Définissez `MULTICA_DSH_PROFILE_BUNDLE` sur le bundle à installer et le daemon l'ajoute pour vous, ou ajoutez-le vous-même avec `dsh plugin --profile multica add <bundle>`. `<bundle>` peut être tout ce que `dsh plugin` accepte (un nom de paquet npm, un répertoire ou une archive tarball empaquetée), et le pont de Multica se trouve dans [multica-ai/dsh-multica-runtime](https://github.com/multica-ai/dsh-multica-runtime). Il n'est pas encore publié sur un registre npm public ([multica#6936](https://github.com/multica-ai/multica/issues/6936)) : aujourd'hui, une équipe auto-hébergée le compile donc depuis ce dépôt et fait pointer la variable vers le répertoire de build, ou vers la tarball produite par `npm pack` si la machine qui exécute le daemon n'est pas celle qui l'a compilé. Un nom de paquet deviendra l'option la plus simple une fois le pont publié.

**Migrer un profil existant.** Sauvegardez le profil et suivez le README du dépôt du pont pour compiler un bundle compatible avec votre version de DSH. Installez manuellement ce répertoire ou cette tarball, puis vérifiez que `dsh.profile.bundles` charge `@multica-ai/dsh-runtime` : remplacez `dsh-profile-multica` s'il est présent, ou supprimez-le si les deux ponts sont listés. Une entrée dans les dépendances ne suffit pas à charger le runtime. `MULTICA_DSH_PROFILE_BUNDLE` ne migre pas une configuration de pont existante. Vérifiez le résultat avec `dsh --profile multica --probe`.

<Callout type="warning">
Privilégiez un bundle que votre propre équipe publie ou compile : cette valeur est installée dans le répertoire personnel DSH de chaque hôte du daemon sans autre confirmation, si bien qu'un paquet tiers non vérifié relève d'une décision de chaîne d'approvisionnement.
</Callout>

**DSH Desktop.** Si vous avez installé DeepSeek Harness Desktop plutôt que le paquet npm, le daemon recherche aussi les shims CLI que génère cette application, dans son propre répertoire de données par utilisateur : `~/Library/Application Support/DSH Desktop` sur macOS, `%APPDATA%\DSH Desktop` sur Windows. Sous Windows, il s'agit des données d'application itinérantes (roaming), pas du répertoire d'installation : l'application s'installe dans Program Files ou dans `%LOCALAPPDATA%\Programs`, mais le CLI qu'elle pilote se trouve à côté de ses autres données par utilisateur. Le segment de version de ces chemins est un identifiant généré ; le daemon les énumère donc et privilégie le plus récent. Rien d'autre n'est nécessaire dans le `PATH` : un shim généré exécute le runtime propre de l'application Desktop par chemin absolu. Si DSH Desktop est installé à un emplacement non standard, faites pointer `MULTICA_DSH_PATH` vers le shim.

Le daemon n'enregistre DeepSeek Harness qu'après la réussite de `dsh --profile multica --probe`, et signale le profil manquant sur `/health` en cas d'échec.

</Accordion>
<Accordion title="MiniMax Code" id="minimax-code">

Installez une version de Node.js prise en charge (`>=22.19 <23` ou `>=24 <27`) et exécutez `npm install --global @minimax-ai/code@latest`. Une installation npm globale place `mcode` dans le chemin des binaires globaux de npm ; si `command -v mcode` ou `Get-Command mcode` ne le trouve pas, ajoutez ce chemin au `PATH`. Exécutez ensuite `mcode login`. C'est MiniMax Code qui gère le choix du modèle ; Multica ne peut pas le remplacer via ACP.

</Accordion>
<Accordion title="Muse Code" id="muse-code">

Muse Code nécessite la version 1.4.10 ou ultérieure. Suivez le [guide officiel d'installation et de connexion](https://dev.meta.ai/docs/muse-code), puis vérifiez que `muse` est dans le `PATH`. Multica découvre ses modèles via MSP et permet de reprendre les sessions.

</Accordion>
<Accordion title="QwenPaw" id="qwenpaw">

Choisissez le fournisseur et le modèle dans la configuration propre de QwenPaw. Multica ne peut pas remplacer le modèle de QwenPaw au moment de l'exécution.

</Accordion>
<Accordion title="Reasonix" id="reasonix">

Exécutez `reasonix setup` et configurez un fournisseur et un modèle par défaut avant de démarrer le daemon.

</Accordion>
</Accordions>

</Step>

## Vérifier que le daemon trouve la commande [#3-vérifier-que-le-daemon-trouve-la-commande]

Remplacez `<command>` par une commande du tableau, comme `claude`, `codex` ou `cursor-agent`. La première commande affiche le chemin de l'exécutable.

<Tabs groupId="os" persist items={["macOS / Linux", "Windows"]}>
<Tab value="macOS / Linux">

Sous macOS, Linux ou WSL, exécutez :

```bash
command -v <command>
<command> --version
```

</Tab>
<Tab value="Windows">

Dans Windows PowerShell, exécutez :

```powershell
Get-Command <command>
<command> --version
```

</Tab>
</Tabs>

Si le terminal trouve l'outil mais que Desktop ou le daemon en arrière-plan ne le trouve pas, c'est généralement qu'ils utilisent des valeurs de `PATH` différentes. Redémarrez l'application, ou définissez un chemin absolu via la variable d'environnement `MULTICA_<PROVIDER>_PATH` correspondante ; la configuration complète figure dans [Variables d'environnement](/environment-variables#configuration-du-daemon).

</Step>
<Step>

## Relancer la détection et vérifier que le runtime est en ligne [#4-relancer-la-détection-et-vérifier-que-le-runtime-est-en-ligne]

<Tabs items={["CLI", "Desktop"]}>
<Tab value="CLI">

Démarrez le daemon :

```bash
multica daemon start
```

Si le daemon tourne déjà, redémarrez-le après avoir installé un nouvel outil :

```bash
multica daemon restart
```

</Tab>
<Tab value="Desktop">

Quittez puis rouvrez Multica Desktop.

</Tab>
</Tabs>

Ouvrez ensuite la page **Runtimes** de Multica. L'outil apparaît sous l'ordinateur cible et s'affiche comme en ligne. Vous pouvez désormais sélectionner ce runtime lors de la création ou de la modification d'un agent.

<Callout type="warning">
Pour démarrer, le daemon doit détecter au moins un CLI intégré pris en charge. Les profils de runtime personnalisés se synchronisent une fois le daemon lancé ; ils ne peuvent donc pas être l'unique condition de démarrage sur une machine vierge. Il existe une exception : lorsque le daemon vient lui-même de commencer à installer le profil de runtime DSH (`MULTICA_DSH_PROFILE_BUNDLE`), il démarre sans aucun runtime et enregistre DeepSeek Harness une fois cette installation terminée. Sans cela, un hôte dont le seul outil est un DSH ayant besoin du profil ne pourrait jamais terminer l'installation : le daemon s'arrêterait avant la fin et l'interromprait avec lui.
</Callout>

</Step>
</Steps>

## Aucun outil détecté

Vérifiez dans l'ordre :

1. Exécutez l'outil lui-même dans un terminal pour confirmer que l'installation et la connexion sont terminées.
2. Vérifiez le nom réel de la commande et son chemin avec `command -v` ou `Get-Command`.
3. Exécutez `multica daemon logs -f` et recherchez des erreurs de version, de chemin ou d'authentification.
4. Redémarrez le daemon pour qu'il relise l'environnement actuel.
5. Revenez à la page **Runtimes** et vérifiez que l'ordinateur et l'outil sont en ligne.

Si l'outil apparaît en ligne mais que les exécutions échouent toujours, ouvrez l'enregistrement d'exécution de la tâche pour voir l'erreur exacte renvoyée par le CLI, ou poursuivez avec [Dépannage](/troubleshooting).
