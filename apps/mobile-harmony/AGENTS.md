# HarmonyOS App Instructions

These rules apply only to `apps/mobile-harmony/`, in addition to the [root instructions](../../AGENTS.md). Paths below are relative to `apps/mobile-harmony/`.

Current status: **vertical slice**. Sign-in (email code), workspace selection, and a read-only inbox with realtime updates run on the HarmonyOS simulator against staging. Everything else is unported; see the roadmap in [README.md](README.md) before promising parity with `apps/mobile`.

## Platform Matrix and Native Shell

- The JS app runs on RNOH pinned to the **0.82-stable line**: `react-native 0.82.1`, `react 19.1.1`, `@react-native-oh/react-native-harmony 0.82.30`, CLI `0.82.33`, metro `0.83.5`. These move together. Do NOT downgrade to 0.77 to match the oh-tpl packages: the 0.77 C++ renderer composes nothing on the API 26 emulator (blank screen with a clean JS log); the 0.77-built oh-tpl packages work fine on 0.82 via the adapter classes in `PackageProvider.ets`.
- `harmony/` is committed source (unlike Expo's generated `ios/`). Build outputs inside it — `entry/src/main/ets/RNOHPackagesFactory.ets`, `entry/src/main/cpp/autolinking.cmake`, `entry/src/main/cpp/generated/`, `oh_modules/`, `build/` — are regenerated by hvigor and gitignored. Never edit them by hand.
- Third-party native libraries come from `@react-native-oh-tpl/*` npm packages. Their ArkTS side ships as a `.har` inside the npm package and must be declared in `harmony/oh-package.json5` **and** `harmony/entry/oh-package.json5` (ETS imports resolve at entry level; CMake links at project level). Metro redirects the original package names via each tpl package's `harmony.alias`.
- tpl releases older than the platform lack the `createWrappedCustomRNComponentBuilderByComponentNameMap` method; they are registered through adapter subclasses in `harmony/entry/src/main/ets/PackageProvider.ets`. When a package ships a current build, drop its adapter.
- The public npm metadata for `@react-native-safe-area-context` is unfetchable from this network; the dependency is aliased to the oh-tpl fork instead. Do not "fix" this back to the original package name.

## Build and Run

- Build/run goes through `scripts/harmony-run.sh` (ohpm install → hvigor assembleHap → hdc install → reverse port forward → launch). It expects DevEco Studio at `/Applications/DevEco-Studio.app` (override with `DEVECO_HOME`) and supplies `DEVECO_SDK_HOME`/`JAVA_HOME` itself. Default is a debug HAP that loads JS over Metro; `HARMONY_BUILD_MODE=release` (the `harmony:*:release` scripts) embeds a dev plain-JS bundle into `harmony/entry/src/main/resources/rawfile/bundle.harmony.js` (gitignored, like all rawfile bundles) so the app starts standalone and picks up live Metro when one is running.
- Metro runs on port **8082** by default so it can coexist with an iOS Metro on 8081; the wrapper maps the device's hardcoded `localhost:8081` to it with `hdc rport`.
- Env variants work like the iOS app's: `.env.staging`/`.env.production` via dotenv-cli, but the variables are `MULTICA_API_URL`/`MULTICA_WEB_URL` (no `EXPO_PUBLIC_` prefix — they are inlined at bundle time by `babel-plugin-transform-inline-environment-variables`, so changing them requires a Metro restart).
- `harmony/entry/src/main/ets/pages/Index.ets` hardcodes the appKey `"MulticaHarmony"`; it must match the `AppRegistry.registerComponent` name in `index.js`.

## Boundaries

- Same sharing rule as `apps/mobile`: `import type` from `@multica/core/types` plus pure utilities and platform-independent schemas at runtime. No web/desktop stores, hooks, or router imports.
- Data-layer files are ported from `apps/mobile` with platform substitutions behind small seams. Keep those seams when porting more screens; do not reintroduce `expo-*` imports:
  - `lib/device-storage.ts` — durable via the `MulticaSecureStorage` TurboModule (Asset Store Kit), in-memory fallback when the native side is absent.
  - `lib/netinfo-shim.ts` — always-online; wiring the netinfo tpl module back needs a verified simulator cycle.
  - `lib/safe-area.tsx` — `SafeAreaProvider`/`useSafeAreaInsets`/`SafeAreaView` over the app-owned `MulticaSafeArea` TurboModule (system avoid areas in physical px, converted with PixelRatio, refreshed on foreground). The tpl safe-area module resolves all-zero insets in common window states; its JS **component** layer was never usable (no CPP glue for third-party components — see "Native modules" below), so never import `react-native-safe-area-context` or `react-native-svg` from app code.
- Screens use explicit `StyleSheet` styles over `lib/theme.ts` tokens (ported from the iOS app; keep values in sync). NativeWind className styling is not part of this app.
- Navigation is `src/navigation/`: a hand-rolled stack (`StackNavigator` + `navRef` pattern), bottom tabs, and `BottomSheet` (standing in for the iOS formSheet/modal routes) — pure RN Animated. `react-navigation`/screens/gesture-handler remain unported; extending the hand-rolled navigator is the default, not a drive-by port.
- `Pressable` MUST come from `@/components/ui/pressable` (not `react-native`) wherever a function-form `style`/`children` is used: RNOH's Pressable silently drops function-form style callbacks — the component renders with no background and no pressed feedback (observed on the 0.82.30 matrix; the login Send-code button was the visible casualty). The wrapper tracks pressed state manually and resolves callbacks itself; static-style usages may keep the platform Pressable, but importing the wrapper everywhere is the convention. Buttons render through `components/ui/button.tsx`, which already uses static style arrays.
- Icons render as font text: `<Icon name size color/>` (`components/ui/icon.tsx`) against the bundled `Ionicons.ttf` registered under the `Ionicons` family in `Index.ets` (`fontResourceByFontFamily`). Names are Ionicons 7 names; add new ones to the list in `scripts/generate-icons.mjs` and rerun it. Do not use `react-native-svg`.

## Native modules (ArkTS TurboModules) — the two-sided registration contract

App-owned ArkTS turbo modules live in `harmony/entry/src/main/ets/multica/` (SecureStorage via Asset Store Kit, Clipboard via pasteboard, Haptics via vibrator). A module only works when BOTH sides are registered; missing either side crashes the app at first JS access with a fatal "Couldn't find Turbo Module" error:

1. **ArkTS side**: the module class extends `AnyThreadTurboModule` and is returned from `MulticaPackage.ets`'s `getAnyThreadTurboModuleFactoryByNameMap` (the RNOH 0.82 contract — the old `createTurboModulesFactory` override alone is NOT consulted for JS access).
2. **CPP side**: a matching `ArkTSTurboModule` subclass with `methodMap_` entries (name + argc) returned by the delegate in `harmony/entry/src/main/cpp/PackageProvider.cpp`. Use `ARK_ASYNC_METHOD_METADATA` for Promise-returning methods (the plain variant's sync caller drops the Promise — `.then is not a function` at runtime) and `ARK_METHOD_METADATA` only for sync returns like `getConstants`.

JS access goes through `TurboModuleRegistry.get` in `lib/native-modules.ts`; every consumer must degrade gracefully when the getter returns null (old HAP + new JS).

## Embedded bundles — the known-fatal combinations

Verified by bisection on the simulator; all three launch to a white screen
with `"MulticaHarmony" has not been registered` or hooks crashes:

1. **Hermes bytecode (`--js-engine hermes`)** — executes but AppRegistry
   registration never lands in the runtime.
2. **Minified bundles (`--dev false`)** — same failure, plain JS.
3. **`inlineRequires: false`** — same failure even for a 20-line minimal
   entry; the option is pinned `true` in metro.config.js for this reason.
4. Separately, **release ArkTS (`-p buildMode=release`)** races
   runApplication ahead of rawfile registration — the script therefore
   always builds hvigor-debug and only embeds the JS bundle.

Also keep `react` singletons in metro.config.js: pnpm resolves 19.2.x peers
for @multica/core's dependencies alongside the app's 19.1.0, and a bundle
with two Reacts dies with ReactCurrentDispatcher errors.

## Verification

From the repository root:

```bash
pnpm --filter @multica/mobile-harmony typecheck
pnpm --filter @multica/mobile-harmony test
```

No ESLint pipeline yet — the RNOH matrix pins Babel/Metro versions that the
shared RN lint configs assume are current. Adding one is roadmap work; until
then CI runs typecheck + tests only.

- CI runs typecheck/test in Node only (`.github/workflows/harmony-verify.yml`); no HAP is built there. Native rendering must be verified on the DevEco simulator.
- For UI changes, exercise the affected flow in the simulator. Known input quirk: `hdc shell uitest uiInput click` reaches RN but `Pressable` taps have not responded to injected events in testing — automate text with `inputText` and verify taps by hand.
- Report which checks ran and which native checks were unavailable. Do not claim simulator verification from typecheck/unit tests alone.
